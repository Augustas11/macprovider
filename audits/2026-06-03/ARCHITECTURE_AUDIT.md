# Architecture Audit

**Repository:** `macprovider-poc` — P2P AI-inference marketplace settling real USDC
**Date:** 2026-06-03
**Components in scope:** Swift provider binary (`phase3-binary`, untrusted contributor Macs), Go coordinator (`phase4-coordinator`, trusted money authority), Go gateway (`phase5-gateway`, internet edge), and the system-level trust boundaries / money flow between them.

**Scope & methodology.** Each component was reviewed independently by a multi-agent pass focused on the architecture lens (trust boundaries, money integrity, resilience/HA, scalability, concurrency, and service contracts), after which every candidate finding was subjected to an adversarial verification pass that read the cited source, reproduced the claim at `file:line`, removed false positives, and either confirmed or downgraded the severity with supporting evidence. This report synthesizes only the verified, evidence-backed findings; the severity shown for each is the verifier's `adjustedSeverity`. Near-duplicate findings that recur across components (notably the coordinator-as-SPOF theme and the operator-key coupling) have been merged with cross-references.

## Executive summary

The system's money *correctness* in the steady state is reasonably well-defended — the ledger and request log are durable, settlement is idempotent, and most account-attribution headers are bearer-gated — but its money *integrity* against the untrusted provider and its *availability* posture are not. The single most serious defect is structural and unmitigated: provider-self-reported token counts are the sole billing input, with no server-side cross-count, so a modified provider binary can mint payout from trivially cheap requests and have the fraud reconcile cleanly (CRITICAL). The output-byte cap that operators might believe bounds this abuse caps bytes-to-buyer but not billed tokens, giving false assurance (HIGH). The second dominant theme is single-points-of-failure with no horizontal path: the coordinator holds all pool/session/relay state in memory and the gateway pins itself to a local SQLite file plus boot-loaded control state, so any coordinator restart is a marketplace-wide inference outage and the gateway's advertised multi-coordinator failover does not actually exist in code. On the provider leg, liveness depends on a 30s app heartbeat with no WS ping, TCP keepalive, or sleep-prevention assertion, reproducing a known production disconnect class on the money-moving path. Several config surfaces (failover weights, `auto_update_enabled`, `warmup_enabled`) advertise capabilities the code never implements, which is an integrity-of-expectations risk for operators. **Fix first:** make billing consume an independent, server-observed completion-token measure and clamp the provider's reported count to it — every other defense is moot while the untrusted party controls the payout input.

## Findings

### [CRITICAL] Provider self-reported token usage drives real-USDC payout with no independent verification

- **Component:** System / Trust Boundaries / Money Flow (also affects Coordinator billing)
- **File(s):** `phase4-coordinator/internal/billing/formula.go:86-174` (ComputeCredits); `phase4-coordinator/internal/billing/hotpath.go:119-139`; `phase4-coordinator/internal/buyer/server.go:1400-1404,1539,2766-2778`; `phase4-coordinator/internal/billing/recovery.go:75-93,182-249,345-407`
- **Category:** money-math / trust boundary
- **What/Description:** The provider Mac is explicitly untrusted, yet its self-declared `prompt_tokens`/`completion_tokens` — read verbatim from the untrusted `inference_response_end.usage` frame via `tokenPointersFromUsageObject` — are the sole billing input. They flow into `ComputeCredits` (default `usage_source = provider_reported`) and become `provider_credits → payout`. The coordinator never tokenizes the prompt or counts streamed output to cross-check, and reconcile re-reads the same provider-sourced counts, so inflated values reconcile cleanly.
- **Impact:** A malicious or modified provider reports inflated `completion_tokens` on cheap requests and is paid maximum per-request credit, draining operator USDC. Reconciliation, settlement, and the delta metric all pass, making the theft invisible to integrity tooling.
- **Evidence:** `formula.go:95-97` defaults `usage_source` to `UsageProviderReported`; `formula.go:124-133` sets `completion = *completionTokens` directly from the provider value; the only sanitization is `invalidBillableTokenCount` (`formula.go:176-178`), rejecting only `<0`/`>10,000,000` plus `checkedMul` overflow guards. `tokenPointersFromUsageObject` (`server.go:2766-2778`) `json.Unmarshal`s the counts from the provider's raw usage object with no cross-check; `messages.go:175-182` confirms `InferenceResponseEnd.Usage` is `json.RawMessage` from the provider frame. `recovery.go:75-93` re-SELECTs `rl.prompt_tokens/completion_tokens` (provider-sourced) and feeds them back into `ComputeCredits` (`recovery.go:200`); `reconcileExistingCreditTx` (`recovery.go:379-393`) only checks rate/multiplier/share arithmetic, never re-deriving counts. The byte-estimated path (`recovery.go:368`) only activates when `CompletionTokens==nil`, so a non-null inflated count always wins.
- **Recommendation:** Treat provider token reports as untrusted input. (1) Independently count completion tokens server-side — the coordinator already buffers full non-streaming output and proxies every stream chunk — and bill on `min(provider_reported, server_observed)` or a byte-derived estimate. (2) Enforce a per-token byte-floor sanity check (`OutputBytesPerTokenCeiling` exists in config but is unused for billing). (3) In reconcile, recompute completion tokens from a stored output-size measure rather than re-trusting the provider count.

### [HIGH] Pillar-D output byte-cap bounds bytes-to-buyer but not billed completion_tokens

- **Component:** System / Trust Boundaries / Money Flow (companion to the CRITICAL finding above)
- **File(s):** `phase4-coordinator/internal/tier2/pillar_d.go:252-309` (enforceOutputCap); `phase4-coordinator/internal/buyer/server.go:1390-1404,1534-1555`
- **Category:** money-math
- **What/Description:** The behavioral-safety guard `enforceOutputCap` truncates `choices[].message/delta/text.content` to `OutputSizeCapBytes` and rewrites the buyer-facing JSON, but billing is taken from `end.Usage` (the provider's usage object), which the guard never touches. So even with the cap fully enforced, a provider can return 5 bytes of content and report `completion_tokens: 10000000` and be billed for 10M tokens.
- **Impact:** Operators who enable `behavioral_safety` + `output_size_cap_bytes` believing it bounds untrusted-provider abuse still have unbounded billing inflation. The defense gives false assurance.
- **Evidence:** `enforceOutputCap` (`pillar_d.go:252-277`) and `capChoiceContent` (`pillar_d.go:279-309`) only mutate the `content`/`text` string fields and track `g.outputBytes` (`pillar_d.go:289,297,306`); they never read or modify any `usage` object. `CheckNonStreamingBody` (`pillar_d.go:127-165`) returns only the capped body bytes. In `buyer/server.go:1390-1399` the capped body is written to the buyer, then `:1400` calls `tokenPointersFromUsageObject(end.Usage)` on the untouched provider usage frame (streaming mirrors this at `:1539`). `g.outputBytes` is never used to clamp `completion_tokens`; `estimatedCompletionTokensFromBytes` only runs on error/disconnect paths.
- **Recommendation:** Make billing consume the guard's measured emitted-output size: derive a billable completion-token ceiling from `g.outputBytes` and clamp `provider_reported` `completion_tokens` to it. At minimum, when the cap truncates, force `usage_source = byte_estimated` for that request. (Resolved together with the CRITICAL finding.)

### [HIGH] Coordinator restart is a single point of failure: all pool, session, and in-flight relay state is in-memory only

- **Component:** Coordinator (system-level SPOF theme — see also the HIGH gateway-failover finding and the MEDIUM single-coordinator-ledger finding below)
- **File(s):** `phase4-coordinator/internal/pool/provider.go:114-145` (Registry maps); `phase4-coordinator/internal/ws/server.go:42-58` (sync.Map sessions/pending/warmups/timers); `phase4-coordinator/cmd/coordinator/main.go:135-178`
- **Category:** architecture / resilience
- **What/Description:** Every routing-critical structure is process memory with no rehydration: `pool.Registry.providers/sessions/breakerFaults/recoveryHolds` and `ws.Server.sessions/pending/warmups/timers`. SIGTERM drains and closes HTTP servers but persists none of it. After restart the pool is empty; providers must re-establish WS, re-auth, and (if `WarmupGateEnabled`) pass a warm-up gate before `StateReady`, during which buyers get `no_provider_available`/503. Only auth tokens, request_log, billing ledger, and admission counters are durable.
- **Impact:** A coordinator crash/restart/redeploy takes the entire marketplace offline for inference for the reconnect+warmup window; buyers paying real USDC see a cliff of 503s.
- **Evidence:** Registry holds the routing maps as plain Go maps guarded by `sync.RWMutex` (`provider.go:114-124`); `NewRegistry` (`provider.go:131-145`) initializes empty maps with zero load-from-storage. `ws.Server` timers/pending/warmups/sessions are `sync.Map` (`server.go:50-55`). A repo-wide grep for `Rehydrate`/`LoadProviders`/`restoreProviders` returned nothing; the only Registry read method is `Snapshot()` (`provider.go:559`), which strips `conn` and copies — there is no inverse load path. `main.go` shutdown (`158-169`) calls `stopBackground()`, `wsServer.DrainAll()`, then `Shutdown` — `DrainAll` (`server.go:1042`) closes connections but writes no state. `WarmupGateEnabled` sets `initialState = pool.StateDegraded` (not Ready) at `server.go:508-511`. Commit `c1cfc97` ("fix(gateway): add ResponseHeaderTimeout to fast-fail buyers during coordinator restart") confirms restart is a live operational event ("buyers to hang silently for up to 15s during coordinator restart + provider warmup … returning 503 to buyers within 10s"). Stays high (not critical) only because money state is durable — this is an availability cliff, not a money-loss event.
- **Recommendation:** Treat the coordinator as a stateful singleton and minimize restart blast radius: graceful redeploys with a reconnect grace window, a lightweight provider-session hint to skip warmup for fast reconnects, and `Retry-After` on the gateway 503. Long term, the in-memory pool is the SPOF that must be made HA before scaling provider count.

### [HIGH] Multi-coordinator failover config is declared and validated but never used; coordinator is a hard SPOF

- **Component:** Gateway (system-level SPOF theme)
- **File(s):** `phase5-gateway/internal/router/server.go:1736-1743`; `phase5-gateway/internal/router/config.go:46-51,266-279`
- **Category:** architecture / resilience
- **What/Description:** Config defines a full `Coordinators[]` list with `Name/BaseURL/Weight/Enabled` and `Validate()` enforces ≥1 target and `weight>0` per target, implying weighted routing/failover. But the only runtime consumer, `coordinatorBuyerURL()`, iterates the slice and returns the *first* enabled target, then stops. `Weight` is never read; there is no health probe, no rotation, no fallback to the next target on error. Every buyer-facing call targets that single URL; status/sticky/routing-metadata calls hardwire `cfg.Coordinator.OperatorURL/BuyerURL` and ignore the list entirely.
- **Impact:** The coordinator is an unmitigated SPOF for all inference and money flow. The config surface advertises HA/failover that does not exist, so an operator who lists two coordinators believes they have redundancy; a primary outage returns `503 coordinator_unavailable` for 100% of paid traffic.
- **Evidence:** `coordinatorBuyerURL()` (`server.go:1736-1743`) is a plain `for _, target := range s.cfg.Coordinators { if target.Enabled { return target.BaseURL } } return s.cfg.Coordinator.BuyerURL`. A repo-wide grep for `Weight` outside tests matches only `config.go` (field `:49`, default `:146`, validation `:276`) — never read by router code. The only call sites are `handleModels` (`server.go:417`) and `handleChatCompletions` (`server.go:1341`); there is no retry wrapper on `s.client.Do` for coordinator calls. `statusFromPoolz` (`:1709`), routing metadata (`:1181`), sticky purge (`:516`) all hardwire `cfg.Coordinator.OperatorURL`. `Validate()` (`config.go:266-279`) enforces `Weight>0`, advertising a capability the code lacks.
- **Recommendation:** Either (a) implement real failover in `coordinatorBuyerURL()` — iterate enabled targets weighted by `Weight`, track per-target health from the existing poolz probe, retry the next target on connection error/5xx with an empty pool; or (b) if single-coordinator is intentional for this phase, delete the `Coordinators[]`/`Weight` surface and the validation that implies failover, leaving only `Coordinator.BuyerURL`, so config does not promise capability the code lacks.

### [HIGH] Coordinator liveness relies on a 30s app heartbeat with no WS ping/pong, no TCP keepalive, and no sleep-prevention assertion

- **Component:** Provider Binary
- **File(s):** `phase3-binary/Sources/macprovider-cli/CoordinatorClient.swift:380,399-408,46`
- **Category:** architecture / resilience
- **What/Description:** The only liveness signal to the trusted coordinator is the application-level `heartbeat` frame (`startHeartbeat`, `:399-408`), at a coordinator-dictated interval defaulting to 30s when absent (`:380`). The WebSocket is created with `URLSession.shared` defaults (`:46`) — no `sendPing`/pong, no `URLSessionConfiguration` ping interval, no `SO_KEEPALIVE`, and no `IOPMAssertion`/`caffeinate`/`beginActivity` no-sleep assertion anywhere. When a contributor Mac idles into sleep, the heartbeat Task is suspended with the process; the coordinator's liveness timer (documented historical 35s kill) tears the session down. This reproduces the provider-disconnect class in project memory; the noted "optional no-sleep assertion" was never added.
- **Impact:** Idle providers silently drop out and stop earning USDC; buyers see capacity flap. The 30s heartbeat is uncomfortably close to the coordinator's kill threshold even on a healthy machine — a single GC/MLX stall near the boundary can trip an unnecessary disconnect.
- **Evidence:** `CoordinatorClient.swift:380` reads `let interval = max(Self.intValue(payload["heartbeat_interval_s"]) ?? 30, 1)` — 30s default confirmed. `:399-408` `startHeartbeat` is a plain `Task` that `Task.sleep`s then `sendHeartbeat()` — a sleep-suspended process stops the loop. `:46` creates the socket via `URLSession.shared.webSocketTask(with:)` with no configuration. Repo-wide grep across `Sources/` returned 0 hits for `IOPMAssertion`/`caffeinate`/`beginActivity`/`idleSystemSleep`/`kIOPM`, 0 for `sendPing`/`pingInterval`/`pong`, and 0 for `SO_KEEPALIVE`/`keepAlive`/`tcpKeepalive` (the only keepalive refs are `keepaliveDebug` logging, `:668`). The launchd plist template has no sleep-prevention key.
- **Recommendation:** Add an `IOPMAssertion(kIOPMAssertionTypePreventUserIdleSystemSleep)` or `NSProcessInfo.beginActivity(.idleSystemSleepDisabled)` for the lifetime of the serve process. Independently, send a sub-interval WS ping (e.g. `heartbeat_interval/2`) or enable TCP keepalive so transport-level liveness does not depend solely on the app heartbeat, and keep the heartbeat interval comfortably below the kill threshold.

### [MEDIUM] One SQLite money DB opened by two separate *sql.DB pools with no connection cap; PRAGMAs not pool-wide

- **Component:** Coordinator
- **File(s):** `phase4-coordinator/cmd/coordinator/main.go:46-67`; `phase4-coordinator/internal/requestlog/store.go:50-63`; `phase4-coordinator/internal/auth/tokens.go:46-71`
- **Category:** concurrency
- **What/Description:** `cfg.Storage.DBPath` is opened twice as independent connection pools (`auth.OpenStore`, `requestlog.OpenStore`); billing and admission reuse `reqLogStore.DB()`. None call `SetMaxOpenConns(1)`/`SetMaxIdleConns`. `busy_timeout=5000` is issued as a single `ExecContext`, which under `database/sql` binds only to the connection that ran it; pool connections created later do **not** inherit it (`journal_mode=WAL` is a persistent file attribute and survives).
- **Impact:** Under concurrent load two writers can collide; connections lacking the inherited `busy_timeout` return `SQLITE_BUSY` immediately instead of waiting, so the billing hot-path insert fails and falls back to `WriteRequestLogWithIdentity`, dropping the provider credit until nightly reconcile re-derives it (the trigger for the MEDIUM billing-degradation finding below).
- **Evidence:** Two independent `sql.Open` calls on the same path: `auth/tokens.go:46`, `requestlog/store.go:50`. Grep confirms `SetMaxOpenConns`/`SetMaxIdleConns` appear nowhere in production code. Verified against driver source (`modernc.org/sqlite v1.33.0`): `newConn` (`sqlite.go:818-862`) applies pragmas only from DSN `_pragma=` params via `applyQueryParams` (`:881-893`); the DSN here is a bare path, and the driver sets no default `busy_timeout`, so later pool connections have `busy_timeout=0`. `WriteHotPath` uses `BEGIN IMMEDIATE` (`hotpath.go:37`) and `buyer/server.go:887-896` has no retry. Downgraded from high by three real mitigations: the driver opens `SQLITE_OPEN_FULLMUTEX` (`sqlite.go:843`) and WAL is enforced at startup (`billing/store.go:37-41`), so readers never block writers; `database/sql` defaults `MaxIdleConns=2` so the pragma-carrying connection is reused for serial writes; and all three money writers share one pool that SQLite serializes anyway, while the separate auth pool is overwhelmingly read traffic. Fails closed (under-credit recovered by reconcile, never double-credit).
- **Recommendation:** Open the money DB once and share one `*sql.DB`; set `SetMaxOpenConns(1)` for the writer DB **or** apply `busy_timeout`/`journal_mode` via the driver DSN (`_pragma=busy_timeout(5000)`) / a connection hook so every pooled connection inherits them. Alarm the hot-path-fallback rate.

### [MEDIUM] Admission state persisted as a full JSON blob to SQLite synchronously under a global mutex on every reserved request

- **Component:** Coordinator
- **File(s):** `phase4-coordinator/internal/ws/admission.go:133-152,209-221`; `phase4-coordinator/internal/ws/admission_store.go:61-75`
- **Category:** scalability
- **What/Description:** `TryReserveRequest` holds `a.mu` and calls `persistLocked` inside the critical section. `persistLocked` marshals the *entire* admission state — all admissions, ProvisionalRecords, rejected, and per-provider RequestWindows — to JSON and upserts the single-row `admission_state` table on every reservation, refund, admit, and promote, synchronously, to the shared money DB while the mutex is held.
- **Impact:** Every provisional inference request serializes on one mutex AND one O(total-provisional-history) JSON write. As fleet and volume grow, lock-hold and write time grow, throttling all admission/quota decisions and adding write contention to the same DB the billing hot-path uses (compounding the prior MEDIUM finding).
- **Evidence:** `TryReserveRequest` acquires `a.mu` (`admission.go:137-138`) and unconditionally calls `a.persistLocked()` (`:150`) before returning. `persistLocked` (`:209-221`) deep-clones admissions + all records + all rejected + all requestWindows and calls `SaveAdmissionState` synchronously; `SQLiteAdmissionStore.SaveAdmissionState` (`admission_store.go:61-75`) `json.Marshal`s the whole state and upserts the constant key `provisional_admission`, rewriting the blob every call. The pattern repeats in `RefundRequest` (`:167`), `Admit` (`:113`), `Promote` (`:179`), `Reject` (`:187`), all under `a.mu`. The store is `reqLogStore.DB()` (`main.go:58`), the same pool as billing. `keepAfter` prunes windows to the last hour (`admission.go:140`) so the blob is bounded but is still O(active-fleet × requests/hour) rewritten on every reservation while the global mutex is held.
- **Recommendation:** Move persistence off the critical section: snapshot under the lock, release, then write; or debounce/batch via a dirty flag flushed by a background ticker. Store per-provider request windows in a normalized table with incremental updates rather than rewriting the whole blob.

### [MEDIUM] Billing hot-path failure silently degrades to request-log-only, deferring provider credit to the reconcile job

- **Component:** Coordinator
- **File(s):** `phase4-coordinator/internal/buyer/server.go:887-897`; `phase4-coordinator/internal/billing/hotpath.go:31-143`; `phase4-coordinator/internal/billing/recovery.go:282-310`
- **Category:** money-integrity
- **What/Description:** If `WriteHotPath` fails (e.g. `SQLITE_BUSY` per the two-pools finding, or any tx error), the code logs a warning and falls back to `WriteRequestLogWithIdentity`, which writes the request_log row + identity snapshot but **not** `ledger_request_credits`/`operator_credits`. Provider credit then exists only implicitly in request_log until `StartNightlyReconcile`/`StartStartupScan` re-derives it via `RecoverLedger`. Real-money credit creation is best-effort on the hot path; the system can run ~24h under-credited, recovered only if the request_log row, identity snapshot, and config snapshot all survive and resolve unambiguously — ambiguous/identity-missing rows are quarantined.
- **Impact:** Under sustained DB contention provider credits are not created in real time; they depend on reconcile succeeding and rows not being quarantined. A failed reconcile run records `status='failed'` but does not retry until the next cycle; quarantined rows leave providers unpaid until manual intervention. The integrity model is eventually-consistent, not transactional, for the provider's share.
- **Evidence:** `buyer/server.go:887-896`: `WriteHotPath` error → Warn → `WriteRequestLogWithIdentity` fallback with no retry/backoff. `WriteRequestLogWithIdentity` (`hotpath.go:145-172`) inserts only the request_log row + identity snapshot — never `insertRequestCreditTx`/`insertOperatorCreditTx`. `StartNightlyReconcile` (`recovery.go:288-310`) fires at next midnight UTC and discards the `RecoverLedger` error with `_ =` (`:306`) — no retry until the following midnight (~24h). Quarantine paths confirmed: `missing_provider_identity`/`ambiguous_attempt_n` (`recovery.go:142-150`), `missing_config_snapshot` (`:152-171`), `ambiguous_attempt_n` for `attemptN>1` (`:201-219,233-239`) — none credited. `StartupScan` (`:282-285`) bounds its window to `StartupReconcileWindowHours`, so old rows are not re-scanned.
- **Recommendation:** Alarm on the hot-path-fallback rate and on reconciliation runs with `status='failed'` or non-zero orphan/quarantine counts. Retry `WriteHotPath` with backoff before falling back; have reconcile retry failed runs rather than waiting a full cycle. Fixing the two-pools finding removes the most common trigger.

### [MEDIUM] Single shared operator key spans two trust boundaries (gateway→coordinator client auth and operator→gateway admin auth)

- **Component:** Gateway
- **File(s):** `phase5-gateway/internal/router/server.go:1932-1945,522,1185,1358,1713`; `config.go:56`
- **Category:** architecture / authz
- **What/Description:** `cfg.Coordinator.OperatorKey` is overloaded for two unrelated trust relationships. As a *client* credential it is sent outbound on gateway→coordinator requests (poolz `:1713`, routing metadata `:1185`, sticky purge `:522`, sticky-affinity forwarding `:1358`). As a *server* credential it is the exact secret an operator must present to invoke the gateway's privileged endpoints — `operatorAuthorized()` (`:1932-1938`) and `shouldPersistInternalHeaderAudit()` (`:1942`) guard `/admin/kill-switch`, `/admin/capacity-signal`, `/admin/feedback-summary`, and the explorer with `Authorization == "Bearer "+OperatorKey`.
- **Impact:** Compromise/leak of the single key grants the ability to pause the entire public API, manipulate capacity tiering, and read buyer/session explorer data. One secret is the union of two trust domains that should be isolated, and it cannot be rotated on one side without breaking the other.
- **Evidence:** All four outbound sites send `s.cfg.Coordinator.OperatorKey` as a Bearer credential (`:522,:1185,:1358,:1713`); `operatorAuthorized()` (`:1933`) and `shouldPersistInternalHeaderAudit()` (`:1942`) both compare `Authorization == "Bearer "+s.cfg.Coordinator.OperatorKey`. Downgraded from high because realistic blast radius is narrower: all four outbound uses target the coordinator on loopback only (BaseURL/OperatorURL default `127.0.0.1:8443/8444`, `config.go:149`; same-host systemd `macprovider-gateway.service:4,15-16`), so the key is not sent over an untrusted network; and the admin endpoints are 404'd at nginx before reaching the app (`nginx-api.streamvc.live.conf:106-109`) with `publicPaused()` exempting `/admin/`. The coupling/rotation problem is genuine but "anyone holding the outbound credential gets admin" overstates external exploitability behind the loopback boundary.
- **Recommendation:** Split the credential: keep `Coordinator.OperatorKey` strictly as the outbound client token, and introduce a separate `Admin.OperatorKey` (distinct secret, distinct env var) for `operatorAuthorized()`/`shouldPersistInternalHeaderAudit()`. This isolates blast radius and allows independent rotation. (Pairs with the LOW non-constant-time-compare finding below.)

### [MEDIUM] SQLite with MaxOpenConns=1 plus per-process in-memory mutable control state pins the gateway to a single non-replicable instance

- **Component:** Gateway (system-level SPOF theme)
- **File(s):** `phase5-gateway/internal/storage/sqlite/store.go:37-39`; `phase5-gateway/internal/router/server.go:117-132,668-695,1947-2000`
- **Category:** architecture / scalability
- **What/Description:** Persistence is SQLite opened with `SetMaxOpenConns(1)`/`SetMaxIdleConns(1)` and `busy_timeout=5000`, so all writes (`ReserveQuota`/`Settle`/`Refund`/`AcquireConcurrency` run `BEGIN IMMEDIATE` on the single connection) globally serialize through one handle. On top of that, `KillSwitch` is cached in process memory and loaded once at boot (`loadRuntimeKillSwitch`, `server.go:117`; read via `publicPaused`/`demoPaused` under `s.mu`), and flips are written to both memory and DB. Because the DB is a local file and the kill-switch lives in per-process memory, two gateway instances behind a load balancer would diverge on kill-switch state and contend on a file-locked DB.
- **Impact:** No horizontal scale path and no hot-standby: the single gateway is a SPOF for buyer auth, quota accounting, and the kill switch. Write-heavy bursts serialize on one connection (throughput ceiling); a `busy_timeout` breach surfaces as `500 quota_reservation_failed`. A failover instance would silently diverge on kill-switch state (one could keep serving paused traffic).
- **Evidence:** `store.go:37-39` sets `SetMaxOpenConns(1)`/`SetMaxIdleConns(1)`, `busy_timeout=5000`, WAL, `synchronous=NORMAL`. `beginImmediate` (`:848-858`) issues `BEGIN IMMEDIATE` on `s.db.Conn(ctx)`; settle/refund/acquire all call it. `loadRuntimeKillSwitch` is invoked once in the constructor (`server.go:117`), copying DB state into `s.cfg.KillSwitch` (`:130-131`); `publicPaused`/`demoPaused` (`:1947-1962`) read that in-memory copy under `s.mu`. `setAllPublicPaused` (`:1981-2000`) writes the flip to memory (`:1984`) and DB (`SetKillSwitch :1989`), so a second instance's boot-loaded copy diverges. Capacity tier is correctly read live, not cached (`GetCapacityTier` per-request at `:289,492,721,743,1971`). Single-host loopback deployment confirmed (`macprovider-gateway.service:8-16`, nginx → `127.0.0.1:9443`, `:60`). Medium because it is a forward-looking scale/HA constraint partly inherent to the documented single-host Pearl VPS phase.
- **Recommendation:** Document and enforce single-instance as an explicit constraint for this phase. For the scale path, migrate the money ledger to a networked store (Postgres) so replicas can share state, and move `KillSwitch`/capacity tier to a short-TTL re-read (or pub/sub invalidation) instead of boot-only load. At minimum add a startup lock file to prevent a second instance opening the same DB.

### [MEDIUM] Single coordinator is a SPOF for billing authority, WS relay, and the SQLite ledger with no HA path

- **Component:** System / Trust Boundaries / Money Flow (consolidates the coordinator-SPOF theme; see also the HIGH in-memory-state and HIGH gateway-failover findings)
- **File(s):** `phase4-coordinator/cmd/coordinator/main.go:85-142`; `config.go:293-294`; `phase4-coordinator/internal/billing/hotpath.go:37,151`; `phase4-coordinator/internal/requestlog/store.go:56-60`
- **Category:** resilience
- **What/Description:** All money-critical state and relay run in one process against one embedded SQLite file. The hot-path billing write uses `BEGIN IMMEDIATE` single-writer transactions, settlement/reconcile are in-process goroutines, and the WS relay holds all provider sessions in process memory. ### [INFO] Tier-2 AEAD nonce safety depends on a per-session counter that silently wraps and is reset on every reconnect

- **Component:** Provider Binary
- **File(s):** `phase3-binary/Sources/macprovider-cli/Tier2ProviderSession.swift:29-30,112-123,133-151,341-349`
- **Category:** architecture / cryptographic-hygiene
- **What/Description:** AES-GCM nonces are built as a 4-byte session base + 8-byte big-endian per-direction counter, with `c2pCounter`/`p2cCounter` incrementing per frame. Two latent notes: (1) the counters are plain `UInt64` with no overflow guard — at 2^64 frames they would wrap (astronomically unlikely, but an unenforced invariant); (2) a fresh `Tier2ProviderSession` (fresh ECDH keys, fresh derived AEAD keys, counters reset to 0) is created on every reconnect, so nonce-reuse safety relies entirely on the per-reconnect key being unique. That holds today because each `Tier2AuthAttempt` generates a new Curve25519 keypair — but the property is implicit and undocumented at the call site, fragile against a future refactor that reuses a session across reconnects.
- **Impact:** Today the design is safe (new keys per reconnect ⇒ counter reset is fine). The risk is latent: any change that caches/reuses a Tier-2 session or its keys across reconnects while resetting counters would cause catastrophic AES-GCM nonce reuse.
- **Evidence:** The finding self-certifies "Today the design is safe," so this is a maintainability note, not a present vulnerability. Each connect builds a fresh `Tier2AuthAttempt()` (`CoordinatorClient.swift:156`) whose init generates a new `Curve25519.KeyAgreement.PrivateKey()` (`Tier2ProviderSession.swift:9-13`); `makeTier2Session` (`CoordinatorClient.swift:162`) derives keys from `sharedSecret.hkdfData(...)` over a transcript including both ephemeral public keys (`Tier2ProviderSession.swift:74-95,306-314`), so c2p/p2c keys differ per reconnect even though counters reset to 0 — no `(key, nonce)` pair ever repeats. `nonce()` (`:341-349`) is a correct `4-byte-base || 8-byte-BE-counter` construction. There is also an existing defensive layer: `openEnvelope` (`:275-289`) enforces `seqValue == expectedSeq`, recomputes/compares the nonce, and binds `seq` into the AAD, so a counter desync is detected and rejected. No code today reuses a session across reconnects.
- **Recommendation:** Add an explicit assertion/comment that the AEAD key MUST be unique per session and counters MUST start at 0 only with a fresh key, and consider a counter ceiling that forces session renegotiation well before 2^64. This pins the invariant so it survives refactors.

## Cross-cutting themes

1. **The untrusted-provider trust boundary is not enforced on the money input.** The system correctly labels contributor Macs as untrusted everywhere except the one place it matters most — the billing input. Provider-self-reported token counts drive payout (CRITICAL), the output-byte cap does not bound those counts (HIGH), and the binary cannot self-attest model integrity (LOW model_hash). These three are facets of one root cause: a value the untrusted party fully controls is consumed as authoritative for real USDC with no server-side derivation or clamp.

2. **Single points of failure with advertised-but-absent HA.** The coordinator (in-memory pool/relay state, single SQLite ledger) and the gateway (MaxOpenConns=1, boot-loaded kill switch) are each non-replicable singletons, yet the gateway config advertises multi-coordinator failover that does not exist in code. This spans HIGH (in-memory state, unused failover config), MEDIUM (single-coordinator ledger, gateway single-instance), and is the dominant availability risk for paid traffic. Restart is a confirmed live operational event (`c1cfc97`).

3. **Config and contract surfaces that over-promise.** Multiple knobs are parsed and validated but never consumed: `Coordinators[].Weight` failover (HIGH), `auto_update_enabled`/`warmup_enabled` (LOW). Combined with the implicit, unversioned gateway↔coordinator status/header contract (LOW), operators and future maintainers cannot trust that the configuration surface or the inter-service interface mean what they appear to mean. Documentation/expectation integrity is itself a risk in a money system.

4. **SQLite single-writer concurrency and silent money-write degradation.** Both Go services serialize money writes on one SQLite connection, and both have a failure mode that silently degrades the money record rather than failing loudly: the coordinator falls back from `WriteHotPath` to request-log-only (MEDIUM) and the gateway discards settle errors leaving reservations to be reaped at zero (LOW). Compounded by the un-inherited `busy_timeout` (MEDIUM) and the synchronous full-blob admission persist under a global mutex (MEDIUM). The common thread: money-path durability is eventually-consistent and best-effort, with no alarming on the degradation rate.

5. **Loopback bind used as the primary (not defense-in-depth) authorization boundary.** The coordinator buyer endpoint (LOW provider/session pinning), the operator/admin bearer (overloaded credential MEDIUM, non-constant-time compare LOW), and the provider's local HTTP server (LOW) all lean on `127.0.0.1` binding instead of application-level auth. Each is safe only as long as the loopback/host boundary holds; any misconfiguration, SSRF, or co-located malicious process collapses the control.

6. **Observability gaps that hide failure from operators.** Orphaned providers report `status: ready` while disconnected (LOW), hot-path billing fallbacks and discarded settle errors are silent, and stale binaries persist invisibly. The recurring fix is alarming/metrics on the degraded paths so silent failures become visible.

## Prioritized remediation roadmap

1. **Close the provider-token payout vector (money integrity — do this first).** Make billing consume an independent, server-observed completion-token measure (count proxied stream chunks / buffered non-streaming output), bill on `min(provider_reported, server_observed)`, enforce the existing `OutputBytesPerTokenCeiling`/byte-floor sanity check, recompute counts in reconcile from stored output size, and clamp `completion_tokens` to the Pillar-D guard's `g.outputBytes` (forcing `usage_source = byte_estimated` on truncation).
   *Resolves:* "Provider self-reported token usage drives real-USDC payout" (CRITICAL); "Pillar-D output byte-cap bounds bytes-to-buyer but not billed completion_tokens" (HIGH); partially "Inference path does not re-verify model_hash" (LOW) via output-derived billing.

2. **Eliminate the coordinator restart outage cliff and resolve the failover/HA contradiction.** Make the gateway's coordinator routing real (weighted, health-aware, with next-target failover) or delete the misleading `Coordinators[]`/`Weight` surface; add a reconnect grace window + fast-skip-warmup hint + `Retry-After` on 503; and put the ledger on durable, backed-up/replicated storage (e.g. Litestream) with a defined RTO/RPO.
   *Resolves:* "Multi-coordinator failover config is declared … never used" (HIGH); "Coordinator restart is a single point of failure" (HIGH); "Single coordinator is a SPOF for billing authority, WS relay, and the SQLite ledger" (MEDIUM).

3. **Fix the provider liveness/disconnect class and harden self-update.** Add an `IOPMAssertion`/`beginActivity` no-sleep assertion for the serve lifetime, add a sub-interval WS ping or TCP keepalive, and keep the heartbeat comfortably below the kill threshold; run self-update from a detached helper with a post-replace `/v1/status` health gate and rollback to the staged previous binary on `bootstrap` failure.
   *Resolves:* "Coordinator liveness relies on a 30s app heartbeat" (HIGH); "Self-update boots out and replaces the live launchd job … no rollback" (MEDIUM).

4. **Harden the SQLite money path and its silent-degradation modes.** Share one capped writer pool (or set DSN pragmas so every connection inherits `busy_timeout`), retry `WriteHotPath` with backoff before falling back, move admission persistence off the critical section (snapshot-then-write / debounced background flush with normalized request-window storage), use a bounded detached context for settle/refund, and add alarming on the hot-path-fallback rate, discarded settle errors, and `status='failed'`/non-zero-quarantine reconcile runs (with retry of failed runs).
   *Resolves:* "One SQLite money DB opened by two separate pools" (MEDIUM); "Admission state persisted as a full JSON blob … under a global mutex" (MEDIUM); "Billing hot-path failure silently degrades to request-log-only" (MEDIUM); "Settlement and refund DB writes detach from the request context" (LOW).

5. **Isolate and constant-time the operator credential; document single-instance gateway.** Split `Coordinator.OperatorKey` into a distinct outbound client token and a separate `Admin.OperatorKey`, replace both admin `==` checks with `subtle.ConstantTimeCompare`/`hmac.Equal`, and document/enforce single-gateway-instance (startup lock file; plan Postgres + TTL-reloaded kill switch for the scale path).
   *Resolves:* "Single shared operator key spans two trust boundaries" (MEDIUM); "Operator/admin bearer token compared with non-constant-time string equality" (LOW); "SQLite with MaxOpenConns=1 plus per-process in-memory mutable control state" (MEDIUM).

6. **Tighten the remaining trust-boundary and consistency gaps.** Bearer-gate the entire coordinator buyer handler and ignore `X-MacProvider-Provider/Session` without the internal bearer; make the provisional pool-cap check authoritative inside the admission lock; centralize the provisional reserve/refund decision off the final `wsForwardResult`; and authenticate/queue or gate-document the provider's loopback HTTP endpoint.
   *Resolves:* "Coordinator buyer endpoint has no buyer authentication" (LOW); "TOCTOU race in provisional admission" (LOW); "Provisional request-quota reservations leak" (LOW); "Local HTTP server binds 127.0.0.1 with no auth" (LOW).

7. **Close observability, config-contract, and identity hygiene gaps.** Reflect prolonged coordinator loss in local provider health (and jitter/no-reset the post-drain backoff); wire or remove `auto_update_enabled`/`warmup_enabled`; introduce a versioned gateway↔coordinator contract (version header + documented status/header/error-code matrix + contract test); stop trusting the OAuth email as verified; and pin the Tier-2 AEAD key-uniqueness invariant with an assertion/comment and a counter ceiling.
   *Resolves:* "Reconnect/drain loop has no max-attempt ceiling or surfaced unhealthy state" (LOW); "auto_update_enabled and warmup_enabled config keys parsed but never consumed" (LOW); "Service-to-service contract … implicit and unversioned" (LOW); "GitHub OAuth account … no email verification" (LOW); "Tier-2 AEAD nonce safety depends on a per-session counter" (INFO).
