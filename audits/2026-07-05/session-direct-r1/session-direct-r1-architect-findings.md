# Session direct-push R1 - ARCHITECT lane findings

## Verdict

FAIL

The architect lane found 0 CRITICAL and 0 HIGH findings, but ARCH-6 is a real MEDIUM lifecycle/design issue. The six direct-push commits are directionally coherent for the bridge, actor bypass, state compatibility, and config persistence, but the autotune recommendation process tree can leave an orphaned runtime child when the parent path is terminated outside normal Swift unwinding.

## Orphan-child on SIGTERM verification (ARCH-6)

- Real orphan scenario? YES - App onboarding runs `AutotuneRecommendationRunner.run(cliURL:)` before starting the agent (`phase3-binary/app/Sources/Malibu/Onboarding/LaunchProviderController.swift:109`, `phase3-binary/app/Sources/Malibu/Onboarding/LaunchProviderController.swift:196`). That runner launches `macprovider-cli autotune --recommend --json` as a `Foundation.Process` and, on its own timeout, only calls `process.terminate()` on that immediate CLI child (`phase3-binary/app/Sources/Malibu/Onboarding/AutotuneRecommendationRunner.swift:86`, `phase3-binary/app/Sources/Malibu/Onboarding/AutotuneRecommendationRunner.swift:101`, `phase3-binary/app/Sources/Malibu/Onboarding/AutotuneRecommendationRunner.swift:127`, `phase3-binary/app/Sources/Malibu/Onboarding/AutotuneRecommendationRunner.swift:133`). The CLI `--recommend` branch returns before the non-recommend deadline/signal-source setup (`phase3-binary/Sources/macprovider-cli/AutotuneCommand.swift:131`, `phase3-binary/Sources/macprovider-cli/AutotuneCommand.swift:157`, `phase3-binary/Sources/macprovider-cli/AutotuneRuntimeSupport.swift:43`). The recommend benchmarker then creates a `CandidateProviderRunner` (`phase3-binary/Sources/macprovider-cli/AutotuneCommand.swift:701`, `phase3-binary/Sources/macprovider-cli/AutotuneRecommend.swift:1768`), which launches a nested provider `Process` running `serve --no-join` (`phase3-binary/Sources/macprovider-cli/CandidateProviderRunner.swift:102`, `phase3-binary/Sources/macprovider-cli/CandidateProviderRunner.swift:289`). Its cleanup is a normal `stop()`/`defer` path, not a parent-death or process-group guarantee (`phase3-binary/Sources/macprovider-cli/Stage1Iterator.swift:444`, `phase3-binary/Sources/macprovider-cli/CandidateProviderRunner.swift:217`). If the App is force-quit/crashes, or if only the immediate autotune CLI receives SIGTERM without forwarding to its spawned candidate process, the nested `serve --no-join` child can survive.
- Blast radius: a live orphaned model runtime, not merely a Unix zombie. It can keep model/GPU memory resident, hold the autotune probe port, confuse the next onboarding attempt, and leave an operator-facing "Malibu quit but provider still running" state. It is local-machine blast radius and the child uses `--no-join`, so this is not coordinator membership takeover by itself.
- Recommendation: FIX_NOW - this should be fixed before convergence because it is a concrete medium lifecycle defect. Launch the autotune subtree in an explicit process group/session and terminate the group on App cancellation, App shutdown, runner timeout, and CLI SIGTERM. On macOS that likely means replacing plain `Foundation.Process` for at least this subtree with `posix_spawn` plus `POSIX_SPAWN_SETPGROUP`, or a small wrapper that creates a process group before `exec`. Also install recommend-path signal handling so `--recommend` can stop or group-kill its candidate runner before exiting.

## Findings

### ARCH-M-1 (MEDIUM) Autotune recommendation can orphan its nested provider process

- File: `phase3-binary/app/Sources/Malibu/Onboarding/AutotuneRecommendationRunner.swift:101`
- Design concern: The App owns the onboarding lifecycle, but the process tree it starts is not modeled as a lifecycle tree. The App tracks only the immediate `macprovider-cli autotune --recommend --json` process, while the CLI can spawn a nested `serve --no-join` provider process without process-group ownership or recommend-path signal forwarding. Parent termination is therefore not equivalent to subtree termination.
- Evidence: App launch and timeout termination are immediate-child only (`phase3-binary/app/Sources/Malibu/Onboarding/AutotuneRecommendationRunner.swift:127`, `phase3-binary/app/Sources/Malibu/Onboarding/AutotuneRecommendationRunner.swift:133`). The CLI skips the general autotune signal/deadline setup when `recommend` is true (`phase3-binary/Sources/macprovider-cli/AutotuneCommand.swift:131`, `phase3-binary/Sources/macprovider-cli/AutotuneCommand.swift:157`). The recommend benchmarker creates a candidate runner (`phase3-binary/Sources/macprovider-cli/AutotuneRecommend.swift:1768`), and the runner launches a child process for `serve --no-join` (`phase3-binary/Sources/macprovider-cli/CandidateProviderRunner.swift:102`, `phase3-binary/Sources/macprovider-cli/CandidateProviderRunner.swift:289`). Candidate cleanup depends on normal control flow (`phase3-binary/Sources/macprovider-cli/Stage1Iterator.swift:444`, `phase3-binary/Sources/macprovider-cli/CandidateProviderRunner.swift:217`).
- Recommendation: Treat the autotune recommendation invocation as a managed process subtree. Use a process group/session for the CLI and its candidate provider children; kill the group on App cancellation/termination and runner timeout; add recommend-path SIGTERM handling; add a regression test that terminates the parent mid-benchmark and asserts no candidate `serve --no-join` process remains.

### ARCH-L-1 (LOW) State vocabulary compatibility is correct but grep-hostile

- File: `phase3-binary/app/Sources/Malibu/MalibuAgent.swift:230`
- Design concern: The wire/coordinator vocabulary says `ready`, while App-facing state says `serving`. The v1.8.9 compatibility check accepts both strings, which fixes the symptom, but the semantic mapping is embedded as a raw string predicate instead of a named boundary translation.
- Evidence: CLI `SwapState` emits `.ready` (`phase3-binary/Sources/MacProviderCore/RuntimeStateMachine.swift:3`), control-socket status frames serialize that raw value (`phase3-binary/Sources/macprovider-cli/ControlSocket.swift:122`), and SPEC-001 defines runtime state values including `ready`, `loading`, `draining`, and `failed` (`specs/SPEC-001-phase3-binary.md:1994`). The App snapshot vocabulary uses `.serving` (`phase3-binary/app/Sources/Malibu/AgentSnapshot.swift:13`) and now accepts `ready || serving` at the consumer (`phase3-binary/app/Sources/Malibu/MalibuAgent.swift:230`). SPEC-026 still says to wait for a first `.serving` control-socket frame (`specs/SPEC-026-browserless-provider-onboarding.md:1619`), which is not the canonical wire term.
- Recommendation: Keep the CLI/coordinator wire term `ready`; add an explicit frame-boundary mapper such as `ControlSocketRuntimeState.ready -> AgentSnapshot.State.serving`; update SPEC-026 to say the wire frame is `ready` and the App UX state is `serving`.

### ARCH-L-2 (LOW) Timeout hierarchy is understandable but not actually centralized

- File: `phase3-binary/app/Sources/Malibu/Onboarding/MalibuOnboardingTimeouts.swift:3`
- Design concern: The new App timeout file claims every Launch Provider to live-provider timeout belongs there, but the practical onboarding budget spans App, CLI bridge, CLI autotune, and coordinator auth. Those values are split across Swift App constants, Swift CLI defaults, and coordinator YAML/Go configuration, so future changes can accidentally violate the intended sequence.
- Evidence: App control-socket and first-serving waits live in `MalibuOnboardingTimeouts` (`phase3-binary/app/Sources/Malibu/Onboarding/MalibuOnboardingTimeouts.swift:49`, `phase3-binary/app/Sources/Malibu/Onboarding/MalibuOnboardingTimeouts.swift:70`). Autotune recommendation has its own 7260-second budget (`phase3-binary/app/Sources/Malibu/Onboarding/AutotuneRecommendationRunner.swift:61`). CLI identity-signature bridge timeout defaults to 3 seconds (`phase3-binary/Sources/macprovider-cli/CoordinatorClient.swift:278`). Coordinator auth handshake timeout defaults to 10 seconds (`phase4-coordinator/coordinator.yaml.example:82`). The 600-second first-serving timeout does not need to cover the 7260-second autotune budget because autotune runs before `finishLaunch` starts the agent and begins waiting for serving (`phase3-binary/app/Sources/Malibu/Onboarding/LaunchProviderController.swift:196`, `phase3-binary/app/Sources/Malibu/Onboarding/LaunchProviderController.swift:126`).
- Recommendation: Add a SPEC-026 timeout-budget table or a small cross-component timeout contract comment that orders these phases: App connect, App autotune recommendation, CLI identity signature, coordinator handshake, first serving frame. Do not imply one Swift file contains cross-component coordinator or CLI defaults unless it actually does.

### ARCH-L-3 (LOW) SPEC-026 under-specifies the implemented identity-signature bridge contract

- File: `specs/SPEC-026-browserless-provider-onboarding.md:1163`
- Design concern: The implementation satisfies the handshake directionally, but the spec now lags the real contract around bridge ownership, reconnect behavior, and field types. That makes the bridge look like an ad hoc shortcut even though the code has a coherent reason: App owns the identity key, CLI owns the coordinator WebSocket.
- Evidence: The bridge contract is explicit in code comments and request structure (`phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:3`, `phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:35`). Reconnect behavior is bounded because a new subscriber gets the pending request immediately and stale streams are removed on termination (`phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:94`, `phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:129`, `phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:134`). SPEC-026's sample control-socket request shows `"binary_version": 2`, while the implementation carries the coordinator auth `binary_version` string (`specs/SPEC-026-browserless-provider-onboarding.md:1163`, `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:156`, `phase4-coordinator/internal/auth/identity_signature.go:58`).
- Recommendation: Publish a SPEC-026 follow-up that codifies the bridge as the intended local App-signing proxy, states reconnect semantics, defines subscriber cleanup ownership, fixes `binary_version` to string, and cross-links the `ready`/`serving` translation and timeout hierarchy.

### ARCH-I-1 (INFO) Bridge, actor bypass, and config persistence are acceptable as direct-push architecture

- File: `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:584`
- Design concern: No blocking C/H/M architecture issue found in ARCH-1, ARCH-2, or ARCH-5.
- Evidence: `IdentitySignatureBridge` has bounded pending-request behavior and subscriber cleanup through `onTermination` (`phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:77`, `phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:108`, `phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:134`). If the App reconnects mid-auth, the new subscription receives the pending request (`phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:129`), and the request times out rather than hanging indefinitely (`phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:94`). The actor bypass is intentionally narrow: the server comment warns that `receive(timeout:)` blocks the `ControlSocketConnection` actor, and the pusher must use raw fd writes instead of `connection.send` (`phase3-binary/Sources/macprovider-cli/ControlSocket.swift:584`, `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:618`, `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:643`, `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:909`). Other server sends happen after a frame is received in the main loop, not as competing sibling writers while `receive` is blocked (`phase3-binary/Sources/macprovider-cli/ControlSocket.swift:665`). App-side config writes preserve existing ownership-sensitive fields and reject configs not marked as App-owned (`phase3-binary/app/Sources/Malibu/ProviderConfig.swift:203`, `phase3-binary/app/Sources/Malibu/ProviderConfig.swift:213`, `phase3-binary/app/Sources/Malibu/ProviderConfig.swift:229`).
- Recommendation: Keep the current bridge and targeted actor bypass for v1.8.9. If another asynchronous server-side control-socket writer is added, revisit the design and prefer moving receive off the actor, mirroring the App-side detached read loop (`phase3-binary/app/Sources/Malibu/ControlSocketClient.swift:1`, `phase3-binary/app/Sources/Malibu/ControlSocketClient.swift:105`), before adding more raw-fd exceptions.
