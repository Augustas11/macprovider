# Session direct-push R1 — SECURITY lane findings

## Verdict
FAIL

## Findings

### SEC-M-1 (MEDIUM) App persists an unvalidated coordinator WebSocket origin from `/register`
- File: phase3-binary/app/Sources/Malibu/System/RegisterClient.swift:102
- Threat model: A network attacker able to tamper with the HTTPS `/v1/providers/register` response (for example via a locally trusted enterprise/compromised CA or hostile local TLS interception), or a compromised register endpoint, can return `coordinator_ws_url` pointing at an attacker-controlled `ws://` or `wss://` origin. The App persists that URL, then the CLI sends its `Authorization: Bearer <provider_token>` header to that origin on every coordinator WebSocket connect. Blast radius is provider bearer-token disclosure and session steering until the config/token is repaired or revoked.
- Evidence: SPEC-026's response shape expects `"coordinator_ws_url": "wss://coordinator.malibu.tech/v2/provider"` (`specs/SPEC-026-browserless-provider-onboarding.md:1048`). The App hardcodes the register base URL to `https://coordinator.malibu.tech` (`phase3-binary/app/Sources/Malibu/Onboarding/OnboardingWindow.swift:33`), but `RegisterResponse` decodes `coordinator_ws_url` as a bare `URL` with no scheme/host/path validation (`phase3-binary/app/Sources/Malibu/System/RegisterClient.swift:102`). Onboarding passes that response URL straight into persistence (`phase3-binary/app/Sources/Malibu/Onboarding/LaunchProviderController.swift:257`, `phase3-binary/app/Sources/Malibu/Onboarding/LaunchProviderController.swift:386`). `ProviderConfig.saveProviderIdentity` writes any `coordinatorWSURL.absoluteString` to `config.yaml` (`phase3-binary/app/Sources/Malibu/System/ProviderConfig.swift:230`). The CLI later opens `URLRequest(url: coordinatorURL)` and attaches the provider token as an Authorization bearer header (`phase3-binary/Sources/macprovider-cli/CoordinatorClient.swift:845`, `phase3-binary/Sources/macprovider-cli/CoordinatorClient.swift:852`). I checked newline YAML injection separately: `URL.absoluteString` percent-encodes literal CR/LF, so this finding is origin/scheme steering, not scalar injection.
- Recommendation: Reject any register response whose coordinator URL is not the expected production WebSocket origin. At minimum require `scheme == "wss"`, `host == "coordinator.malibu.tech"`, expected path such as `/v2/provider`, no userinfo, and default/expected port. Prefer deriving the WebSocket URL locally from the pinned/hardcoded coordinator base or verifying a signed/pinned response before persisting. Reject `ws://`, `http(s)://`, non-production hosts, and unexpected ports.

### SEC-L-1 (LOW) Direct control-socket writes can corrupt pushed identity frames and fail open to local DoS
- File: phase3-binary/Sources/macprovider-cli/ControlSocket.swift:590
- Threat model: A same-effective-UID local process can connect to the user-only control socket, issue requests that make the CLI write normal response frames, and race the identity-signature pusher's raw `writeFrameDirect` on the same stream fd. This does not expose the App identity private key and does not bypass coordinator auth, but it can corrupt or drop `identity_signature_request` frames, making App-track auth fail until retry.
- Evidence: The control socket is correctly restricted to the user (`chmod(parent.path, S_IRWXU)` at `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:444`, socket `0600` at `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:469`) and `accept()` enforces same EUID with `getpeereid` (`phase3-binary/Sources/macprovider-cli/ControlSocket.swift:558`, `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:842`), so this is not a cross-user LPE. The risk is intra-user protocol integrity: identity requests bypass the `ControlSocketConnection` actor (`phase3-binary/Sources/macprovider-cli/ControlSocket.swift:645`) while normal responses still use `connection.send` (`phase3-binary/Sources/macprovider-cli/ControlSocket.swift:672`, `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:696`, `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:802`). The direct-write comment relies on `<PIPE_BUF` atomicity (`phase3-binary/Sources/macprovider-cli/ControlSocket.swift:584`), but this is a Unix domain `SOCK_STREAM`, not a pipe, and the actor-side protocol allows frames up to 64 KiB (`phase3-binary/Sources/macprovider-cli/ControlSocket.swift:895`). Malibu's reader silently ignores malformed JSON lines and continues (`phase3-binary/app/Sources/Malibu/Agent/ControlSocketClient.swift:134`), so corruption can turn into a quiet missing-signature timeout. Coordinator-side enforcement still closes `4003 identity_signature_required` on missing/invalid signatures (`phase4-coordinator/internal/ws/server.go:913`), limiting impact to local DoS.
- Recommendation: Put all writes for a control-socket fd behind a single writer queue/lock that is not blocked by reads, or replace the actor-blocking read with a detached reader plus serialized writes. Treat malformed server-to-App frames as connection-fatal and surface/log identity-signature pusher write failures and timeouts.

### SEC-L-2 (LOW) Identity-signature timeout is not surfaced before sending an unsigned proof
- File: phase3-binary/Sources/macprovider-cli/CoordinatorClient.swift:1219
- Threat model: A same-user local process or a wedged Malibu.app control connection can prevent the bridge response for three seconds. The CLI then sends the proof-stage frame without `identity_signature`, causing coordinator rejection. This is not a Tier-2 to Tier-1 downgrade with the current coordinator wiring, but it is a quiet local availability attack and poor incident signal during onboarding.
- Evidence: `IdentitySignatureBridge.requestSignature` returns `nil` on timeout/no subscriber and explicitly tells callers to proceed without the signature (`phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:91`). `CoordinatorClient.authProofMessage` simply omits signature fields unless the response is accepted with both values (`phase3-binary/Sources/macprovider-cli/CoordinatorClient.swift:1219`, `phase3-binary/Sources/macprovider-cli/CoordinatorClient.swift:1223`). The coordinator production path wires `WithIdentitySignatureStore` when App-track register is enabled (`phase4-coordinator/cmd/coordinator/main.go:373`, `phase4-coordinator/cmd/coordinator/main.go:382`), and with that store configured missing/invalid signatures reject and close `4003` (`phase4-coordinator/internal/ws/server.go:913`, `phase4-coordinator/internal/ws/server.go:915`). SPEC-026 also requires that behavior (`specs/SPEC-026-browserless-provider-onboarding.md:1212`, `specs/SPEC-026-browserless-provider-onboarding.md:2323`).
- Recommendation: Log bridge timeout/no-subscriber at error level with no secret material, set an App-visible onboarding/auth error, and consider failing locally instead of intentionally sending an unsigned proof for `p_` App-track provider IDs. Keep CLI-track exemption behavior explicit and server-authoritative.

### SEC-I-1 (INFO) Replay binding, coordinator enforcement, and Ed25519 nonce surface checked clean
- File: phase4-coordinator/internal/ws/server.go:817
- Threat model: Captured proof-stage signatures should not replay against a different session or initial frame.
- Evidence: The coordinator creates a fresh server-side `auth_attempt_id` (`phase4-coordinator/internal/ws/server.go:817`), retains the initial frame's canonical transcript hash and ECDH/version fields (`phase4-coordinator/internal/ws/server.go:829`), verifies proof `auth_attempt_id`/provider/expiry before acceptance (`phase4-coordinator/internal/ws/server.go:899`), and releases retained attempts on success or failure (`phase4-coordinator/internal/ws/server.go:855`, `phase4-coordinator/internal/ws/server.go:998`). Signature verification uses retained `binary_version`, retained `provider_ecdh_public_key`, and the retained initial transcript hash (`phase4-coordinator/internal/ws/identity_signature.go:50`, `phase4-coordinator/internal/ws/identity_signature.go:58`). The App signs with CryptoKit `Curve25519.Signing.PrivateKey`, i.e. Ed25519 deterministic signatures, so ECDSA-style nonce reuse is not in play (`phase3-binary/app/Sources/Malibu/System/ProviderIdentity.swift:60`, `phase3-binary/app/Sources/Malibu/System/ProviderIdentity.swift:88`).
- Recommendation: No change for replay/nonce handling from this audit.

### SEC-I-2 (INFO) Debug identity-signature prints are absent from the audited release paths
- File: phase3-binary/Sources/macprovider-cli/IdentitySignatureBridge.swift:1
- Threat model: Release logs should not expose identity signatures, transcript hashes, ECDH public keys paired with auth attempts, or bearer material.
- Evidence: Grep found no `[idsig]` markers in `IdentitySignatureBridge.swift` or `ControlSocket.swift`. Remaining `FileHandle.standardError` writes in the control-socket path are generic errors such as stale socket/decode/close messages (`phase3-binary/Sources/macprovider-cli/ControlSocket.swift:448`, `phase3-binary/Sources/macprovider-cli/ControlSocket.swift:730`) and do not dump identity-signature payloads. The App log tail also redacts lines containing `identity_signature`, bearer tokens, authorization headers, private keys, and token hashes before UI display (`phase3-binary/app/Sources/Malibu/System/LogTailReader.swift:23`).
- Recommendation: No change for the stripped debug prints. Keep future identity-signature diagnostics structured and redacted.
