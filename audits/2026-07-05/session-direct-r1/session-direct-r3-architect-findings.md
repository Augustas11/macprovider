# Session direct-push R3 — ARCHITECT lane findings

## Verdict
PASS

R3 closes the R2 architect MEDIUM. The shutdown model is now coherent for the intended App-timeout/App-quit path: `runAutotuneRecommend()` becomes a process-group leader before any candidate subprocess is spawned, installs recommend-path signal sources with cascade enabled, and passes the interrupt flag into the benchmarker (`phase3-binary/Sources/macprovider-cli/AutotuneCommand.swift:701-754`). Both SIGINT and SIGTERM handlers share one `AutotuneCascadeGate` per `AutotuneSignalSources` instance, and `trip()` is guarded by `NSLock`, so exactly one handler invocation can call `Darwin.killpg(0, SIGTERM)` (`phase3-binary/Sources/macprovider-cli/AutotuneRuntimeSupport.swift:27-89`). The self-signal generated by that `killpg(0, SIGTERM)` can still re-fire the SIGTERM dispatch source, but the second invocation sees `trip() == false`, only re-sets the already-set interrupt flag, and does not cascade again.

The gate is the right surgical abstraction for this fix. A general `OneShotLatch` would be premature: the repo has other "gate" types, but no demonstrated shared one-shot-latch concept, and this latch's only current reason to exist is signal-cascade idempotence. Keeping it named `AutotuneCascadeGate` documents that lifecycle contract directly. The current `let cascadeGate` visibility is acceptable for this package/test shape, though a private stored gate plus an `AutotuneSignalSources.hasCascadedForTest()` wrapper would be marginally cleaner if the surface grows. The important architectural contract is that the gate is per source instance, not static/shared; a future shared-static refactor would couple separate recommend-path lifetimes in a long-lived CLI process. The CLI currently exits after `--recommend`, so that is not a present defect, but the per-instance wording in the code comment should be preserved.

The alternatives are weaker than the gate. Canceling only the SIGTERM dispatch source before `killpg` would leave awkward SIGINT/SIGTERM asymmetry and still needs careful ordering. POSIX has no "process group except self" signal primitive, so excluding self would require more invasive child PID tracking. Temporarily blocking SIGTERM with `pthread_sigmask` adds signal-mask complexity without improving teardown semantics over a simple one-shot guard.

## ARCH-R3.1 verification (orphan scenario closure after cascade gate)
- Case A (normal App quit): CLOSED — App timeout/error cleanup calls `process.terminate()`, which sends SIGTERM to the CLI (`phase3-binary/app/Sources/Malibu/Onboarding/AutotuneRecommendationRunner.swift:132-144`, `:184-201`). The CLI's SIGTERM handler sets the interrupt flag and wins the per-instance gate, then calls `killpg(0, SIGTERM)` once. That group signal reaches the candidate `serve --no-join` descendants because `setpgid(0, 0)` ran before candidate spawn. It also reaches the CLI itself, but the re-fired SIGTERM handler loses the already-tripped gate and performs no second cascade. The benchmarker observes the interrupt flag between candidates and stops spawning fresh runners (`phase3-binary/Sources/macprovider-cli/AutotuneRecommend.swift:1741-1759`), then `runAutotuneRecommend()` exits 130 after subtree cleanup. This leaves one intended cascade syscall, no runaway feedback loop, and no missed grandchild teardown in the designed process group.
- Case B (CLI hang): CLOSED — if the CLI does not exit during the App grace window, App escalation still sends `killpg(cliPid, SIGKILL)` plus direct `kill(cliPid, SIGKILL)` (`phase3-binary/app/Sources/Malibu/Onboarding/AutotuneRecommendationRunner.swift:192-209`). The group-kill path relies on the recommend CLI becoming process-group leader before child spawn (`phase3-binary/Sources/macprovider-cli/AutotuneCommand.swift:701-710`). The direct `kill(cliPid, SIGKILL)` covers the narrow pre-`setpgid` race before grandchildren can exist. Residual test coverage weakness remains LOW, not convergence-blocking.
- Case C (App SIGKILL): CLOSED_DEFERRED — if the App itself is SIGKILLed, neither App cleanup nor the CLI's App-triggered signal path is guaranteed to run. That parent-death-monitor problem remains outside this R3 surgical cascade fix and was already deferred as narrower than the timeout/error orphan path.
