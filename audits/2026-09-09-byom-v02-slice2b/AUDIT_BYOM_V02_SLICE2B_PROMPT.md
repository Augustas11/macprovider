## What the change does
1. Coordinator (`internal/buyer/catalog_artifacts_feed.go`, `autotune_feeds.go`, `server.go`, `internal/config/config.go`): optional `autotune.catalog_artifacts_path` / `_sig_path` pair. Loaded with the three base feeds at boot and SIGHUP reload (`LoadAutotuneFeeds`); when present it must (a) have all three base feeds, (b) equal the candidate feed's version / generated_at / policy_version, (c) be signed by the SAME `key_id` as the candidate feed, (d) carry `candidate_catalog_sha256` equal to the served candidate bytes, (e) pass the closed §3.7.4 identity matrix + global hash uniqueness + `primary_artifact_id` rules, (f) pass §3.7.5 primary-artifact consistency against the candidate rows. Routes `/v1/catalog-artifacts` and `.sig` serve the literal bytes with the same handler as the other feeds; 404 when unconfigured. `/v1/autotune-release` adds a `catalog_artifacts` entry ONLY when bound.
2. nginx (`dist/nginx-coordinator.malibu.tech.conf`): two exact allow-through blocks before `location /v1/ { return 404; }`, same allowlisted directive shape as `/v1/rate-card`; `check_nginx_catalog_routes_test.sh` + Go ordering test assert them.
3. Live release gate (`scripts/verify-live-coordinator-release-gate.py`): reads artifact-feed binding from `pearl-release.json` `catalog.files`; bound → digest + signature + signer equality + release binding checks against the served candidate feed; unbound → the two routes must NOT be served (explicit 404 probe). Fixture suite extended.
4. `catalog-release.py status` drops the two landed surfaces and prints the activation-deploy operator step; runbooks updated. The checked-in `dist/coordinator.yaml` deliberately does NOT name the pair (a configured path with a missing file fails startup closed) — the keys are added by the deploy that installs the first artifact-bound release; `coordinator.yaml.example` documents this.
