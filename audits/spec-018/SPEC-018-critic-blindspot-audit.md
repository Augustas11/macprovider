## Findings

### H-1 — AC-23 verifies the wrong direction of forward compatibility

- **Codex blind-spot category:** CRITIC-3 (Resolved-but-not-really) + CRITIC-1 (Cross-section consistency at distance)
- **SPEC location:** AC-23 (line 362) vs §10c invariant (lines 388-400)
- **The claim:** §10c is the "additive-only forward compatibility guarantee" — its operative protection is that "a client that successfully parses a v0.1.2 non-streaming tool-call response MUST continue parsing the equivalent v0.2+ response without code changes." AC-23 is stated as "Verified as a release gate for any SPEC-018 vN.M version that follows v0.1.2."
- **The refutation:** AC-23 says: `"A v0.2-or-later regression test replays v0.1.2 non-streaming tool-call response fixtures and verifies that a v0.1.2-targeted client parser (e.g. OpenAI Python SDK 1.x at the version locked when v0.1.2 ships) successfully parses each response."` This replays **v0.1.2 fixtures** with a **v0.1.2 parser**. That test cannot fail — the fixtures came from v0.1.2 and the parser is from v0.1.2. The risk §10c protects against (a NEW v0.2 emission shape that breaks an OLD v0.1.2 parser) is not exercised by this AC at all. To verify §10c, the regression must capture **v0.2 (or later) responses** and parse them with the **v0.1.2 parser**. As-written, AC-23 is a tautology and a future v0.2 author could pass the AC while shipping a wire-shape break.
- **Severity rationale:** HIGH because §10c is one of the four "lock features" v0.1.2 added (PD Q-1 absorption), AC-23 is its sole verification handle, and the AC does not actually verify the invariant. Lock-blocking under "if the AC doesn't gate the property, the property is unenforced." Codex PD lane signed off because the invariant prose is sound; codex code lane signed off because the AC is mechanically expressible — neither lane caught that the AC fails to test what the invariant claims.
- **Recommended fix:** Reword AC-23 to: `"A v0.2-or-later regression test captures non-streaming tool-call response fixtures from the candidate vN.M release (with any new fields, deltas, or finish reasons enabled) and verifies that a v0.1.2-targeted client parser (e.g. OpenAI Python SDK 1.x at the version locked when v0.1.2 ships) successfully parses each response without raising on unknown fields. Verified as a release gate for any SPEC-018 vN.M version that follows v0.1.2."`

### H-2 — §1 framework list overclaims OpenAI-wire compatibility (Claude Code, Cursor)

- **Codex blind-spot category:** CRITIC-5 (Honest scope assessment)
- **SPEC location:** §1 line 17, §1.1 line 46, §11 Q1 line 404, §10a #1 narrative line 368
- **The claim:** §1 names `"Cline, Cursor, Aider, OpenCode, Continue, Zed, Claude Code, or any other OpenAI-shape agent framework"` as targets for the v0.2 deliverable. §11 Q1 lists the §1-named frameworks as the candidate compatibility matrix and includes Cursor and Claude Code in option (b).
- **The refutation:** **Claude Code is not an OpenAI-shape agent framework.** Claude Code speaks the Anthropic Messages API natively (`/v1/messages` with Anthropic's `content` blocks and `tool_use` shape, not `chat/completions` with `tool_calls[]`). It is the namesake CLI for Anthropic's API; calling it OpenAI-shape is factually wrong. Cursor's IDE chat is also primarily proxied through its own backend service that does not expose a plain OpenAI-wire toggle to the end user — Cursor compatibility via the Cursor `Models` configuration is a narrower surface than the §1 sentence implies. A buyer reading "Claude Code … or any other OpenAI-shape agent framework" reasonably concludes "I can point Claude Code at macprovider," and that conclusion is wrong even at v0.2's deliverable. **A CTO reading §1 → §10a → §11 Q1 concludes the network targets a 12-framework matrix; the reality is a 5-framework matrix (the AC-16b candidates: Cline, Aider, OpenCode, Continue, Vercel AI SDK) plus possibly LangChain/LlamaIndex/Pydantic-AI/n8n in OpenAI-mode.** PD lane signed off on "certificate" narrowing but did not re-check the framework enumeration for OpenAI-wire honesty.
- **Severity rationale:** HIGH because: (a) it directly contradicts the "honest scope" rewrite that produced v0.1.1 (the entire reason for the Ring-1 → certificate re-scope was to stop overclaiming); (b) Claude Code naming is load-bearing — it appears three times in the SPEC; (c) misleads buyer evaluation in exactly the way Q6/PD C-1 closure intended to prevent.
- **Recommended fix:** Remove "Claude Code" from §1 line 17, §1.1 line 46, §10a #1 line 368, and §11 Q1 line 404. Remove "Cursor" from the same lines OR footnote it explicitly as "(via Cursor's OpenAI-Compatible Custom Models configuration only)". Replace the §1 enumeration with "OpenAI-wire-native frameworks such as Cline, Aider, OpenCode, Continue, Vercel AI SDK, LangChain (`ChatOpenAI`), LlamaIndex (`OpenAI` LLM), Pydantic-AI (`OpenAIModel`), n8n (OpenAI node) … not Claude Code or Cursor IDE chat, which speak Anthropic-shape or proprietary wires." Update §11 Q1 to match.

### H-3 — §3.6 mixed-sentinel rule is a buyer-prompt DoS vector against legitimate Qwen tool calls

- **Codex blind-spot category:** CRITIC-2 (Adversarial refutation of normative claims) + CRITIC-4 (AC edge cases)
- **SPEC location:** §3.6 lines 161-163, AC-22 line 360, §1 IMPL delta #2 line 35
- **The claim:** `"When model output contains sentinels from multiple families simultaneously — specifically, BOTH a Qwen family sentinel (<tool_call> opening or </tool_call> closing) AND a Llama family sentinel (<|python_tag|> or <|eom_id|>) appear in the same response — the parser MUST treat the output as malformed and fall back to plain assistant content."` The IMPL delta clarifies: `"the v0.1.2 IMPL prompt will add a pre-detection pass that scans for sentinels from both families and triggers the mixed-sentinel fallback before either family parser runs."`
- **The refutation:** "Contains" is undefined; the IMPL delta says **pre-detection pass scans for sentinels from both families**, which is necessarily a raw-byte/substring scan (the parsers haven't run yet — there is no AST). A buyer requesting a legitimate Qwen tool call where any of these strings appears anywhere in the model output as **data** (not as Llama framing) triggers a forced fallback:
  - User prompt: "Write a function `compare_tokenizers` that takes a string and returns whether it looks like a Llama `<|python_tag|>` block or a Qwen `<tool_call>` block. Use the `code_search` tool to look up the tokenizer source."
  - Legitimate model response (Qwen): `<tool_call>{"name":"code_search","arguments":{"query":"detect <|python_tag|> framing"}}</tool_call>`
  - Pre-detection scan sees `<tool_call>` (Qwen) AND `<|python_tag|>` (Llama, as a substring inside `arguments.query`) → fallback to plain content → buyer's coding-agent flow breaks.
  This is reachable by **any buyer prompt content** that asks the Qwen model to discuss Llama tokenizer framing — a normal use case for code-assist workloads. Worse, it is **trivially weaponizable**: any buyer who wants to deny-of-service their own provider can include `<|python_tag|>` in a prompt to suppress tool calling. And the security argument for the rule (closing "cross-family bypass surface identified in Security m-1") does NOT apply when modelID already enforces family selection: a Qwen-modelID provider will use the Qwen parser regardless of `<|python_tag|>` presence — the Llama parser never runs. The mixed-sentinel rule's defense-in-depth claim is therefore weaker than its false-positive cost.
- **Severity rationale:** HIGH because: (a) the false-positive scenario is common (code-assist over Qwen-Coder discussing any aspect of model internals/tokenizers); (b) the IMPL delta is committed for the v0.1.2 patch; (c) AC-22 will assert this exact behavior, locking the regression. Code lane and security lane both treated `<|python_tag|>` and `<tool_call>` as opaque sentinels and did not consider that these strings are legitimate data inside argument values.
- **Recommended fix:** Either (a) narrow §3.6 to "sentinels at top-level model output positions outside the matched-family parser's body" — i.e., apply the mixed-sentinel check ONLY to text outside the recognized Qwen `<tool_call>…</tool_call>` extents, OR (b) drop the mixed-sentinel pre-detection entirely given that §3.2 modelID-match-required already pins the family, and rely on §3.2 + family-priority for cross-family safety. Update AC-22 fixtures to include the false-positive case (`<tool_call>{"name":"f","arguments":{"discussion":"<|python_tag|>"}}</tool_call>` against a Qwen-modelID request) and assert the tool call **succeeds**, not fails.

### M-1 — Unbounded JSON nesting in §8.4 / §3.4 / AC-21 commit-worthy validation

- **Codex blind-spot category:** CRITIC-4 (AC cardinality / edge cases) + CRITIC-2 (compositional claim)
- **SPEC location:** §3.4 lines 140-149 (duplicate validator), §8.4 lines 290-298 (commit-worthy validator), AC-21 line 358
- **The claim:** §3.4 requires the validator to detect "duplicate keys in a nested JSON arguments or parameters object" and "duplicate keys in a JSON string supplied as arguments." §8.4/AC-21 require coordinator decode of `function.arguments` to confirm "decoded value is a JSON object."
- **The refutation:** Both validators decode arbitrarily nested JSON with no normative depth, byte, or memory bound. An adversarial provider can emit `function.arguments` containing 100k-deep nested objects: `{"a":{"a":{"a":… × 100000}}}`. The coordinator's commit-signal validator decodes this on the request-handling goroutine. Go's `encoding/json` accepts arbitrary depth by default (no `DisallowDepth` analog) and uses recursion — for sufficiently deep input, the goroutine stack grows or the host runs out of memory. The duplicate-key validator in `ToolCallParser.swift:266-448` (Swift) has analogous risk. §5 explicitly notes `"SPEC-018 v0.1 imposes no max_tool_calls limit and no per-call function.arguments byte cap"` and §10a #7 commits the byte cap to v0.2 — but neither the byte cap nor a depth cap is specified for the **validator's own input**. The byte cap §10a #7 protects the parser; the commit-worthy validator at the coordinator is a separate code path that fires before any cap can apply.
- **Severity rationale:** MEDIUM. Reachable by any legitimate provider (or hostile relay attacker that controls a provider socket); commit-signal path is a money-path under SPEC-016. Not CRITICAL because mitigated by goroutine isolation and Go's eventual OOM-kill being a recoverable outage, and because §10a #7's v0.2 byte cap will partially close. But the v0.1.2 commit-signal validator landing as part of the IMPL prompt should not be unbounded.
- **Recommended fix:** Add to §8.4: `"The commit-worthy validator MUST reject any function.arguments JSON whose nesting depth exceeds 32 or whose byte length exceeds 256 KiB. Rejection follows the same not-commit-worthy semantics as malformed shape."` Add a parallel sentence to §3.4 about the parser-side duplicate validator. Update AC-21 to include a deep-nesting fixture in the rejection set.

### M-2 — §10a #2 "operator override" is an unscoped trust-transfer carve-out

- **Codex blind-spot category:** CRITIC-3 (Resolved-but-not-really) + CRITIC-2 (bad-actor reading)
- **SPEC location:** §10a #2 line 371 ("Buyer-facing impact" paragraph, final clause)
- **The claim:** `"v0.2 MUST require unknown-or-unregistered model_hash to fail closed for tool-call synthesis (NOT fall back to modelID substring matching), unless an explicit operator override is logged and buyer-visible."`
- **The refutation:** "Operator override" — by **the provider operator**, who is the party the fail-closed rule is supposed to protect against (a provider advertising a tool-call-capable family while running a different model). Allowing the provider operator a self-override turns the security guarantee into an honor system. "Logged" — where? Coordinator logs? Provider local file? "Buyer-visible" — visible HOW? In what response field? Does the buyer have to opt-in to seeing it, or is it pushed to every request? Can a buyer policy-engine refuse to execute tool calls when the override flag is set, or does the override pre-empt buyer awareness? Codex Security m-1 r2 absorbed the fail-closed requirement but stopped there; the carve-out itself was not pressure-tested. A bad-faith v0.2 implementer can satisfy this clause by logging `"override=true"` to a local syslog and adding `"model_hash_override": true` to the response JSON — technically compliant, practically the loophole the fail-closed rule is supposed to close.
- **Severity rationale:** MEDIUM. This is a v0.2 commitment, not a v0.1.2 behavior — so it doesn't ship at lock. But it's a normative commitment v0.1.2 makes that ties v0.2's hands AROUND a security guarantee, in a way that an unsophisticated v0.2 author can satisfy while leaking the protection. Lock-blocking under CRITIC-3 because the resolution is a relabel: "fail-closed except when operator decides not to" is not fail-closed.
- **Recommended fix:** Replace the override clause with: `"unless the provider has obtained explicit buyer consent recorded as a request-level header (e.g. X-MacProvider-Allow-Unregistered-Hash: <model_hash>) and the response includes a mandatory model_hash_unregistered: true field at choices[0].message scope. Operator-only overrides without buyer consent are non-compliant."` Defer the precise header / field name to the v0.2 SPEC but pin the buyer-consent invariant now.

### M-3 — §6 coordinator request-side pass-through MUST is unverifiable in v0.1.2

- **Codex blind-spot category:** CRITIC-1 (Cross-section consistency: §6 vs §9)
- **SPEC location:** §6 lines 240-246 vs AC-14 line 340, AC-11/AC-12 lines 334-336
- **The claim:** §6 line 244: `"The coordinator MUST treat request-side tool_calls and tool_call_id values as pass-through fields after validation. This ratifies SPEC-002's value-typed pass-through rule for tool_calls."` AC-14 line 340: provider rejects assistant-history `tool_calls[]` with HTTP 400 `unsupported_tool_messages`.
- **The refutation:** No v0.1.2 AC verifies the §6 coordinator request-side pass-through MUST. AC-11 verifies relay preserves **response-side** `tool_calls[]`. AC-12 verifies gateway preserves **response-side** `tool_calls[]`. AC-14 confirms the provider rejects the request before any pass-through fidelity could be observed end-to-end. Because the provider is the only entity that can confirm whether the coordinator preserved the field, and the provider rejects with 400 before consuming the body, the coordinator's pass-through fidelity is observable only at the WS frame level — not at the §9 acceptance-criterion level. §6 thus declares a normative behavior with no v0.1.2 verification handle. If a coordinator regression silently dropped `tool_calls[]` from request-side messages, no SPEC-018 v0.1.2 AC would detect it; the only signal would be the provider's "unsupported_tool_messages" error firing for the wrong reason.
- **Severity rationale:** MEDIUM. Architect lane checked §6 vs SPEC-002 cross-reference (consistent) and security lane checked §6 vs §8 pass-through invariants (consistent). Neither lane traced §6 ↔ §9 to discover the AC gap. Not a behavior bug in v0.1.2, but a SPEC-quality bug — the SPEC asserts a MUST that the SPEC's own ACs cannot validate.
- **Recommended fix:** Add `AC-24. Coordinator request-side tool_calls[] and tool_call_id pass-through fidelity is verified at the WebSocket frame layer by a unit test inspecting the outbound InferenceRequest frame for byte-equivalence with the buyer-supplied tool_calls[]/tool_call_id field bytes (after request validation per SPEC-001 / SPEC-002). The test does not require the provider to accept the request — it asserts that what the coordinator forwarded matches what the buyer sent.`

### M-4 — §10b ID rescope vs §10c "shape" invariant: call_ prefix not protected

- **Codex blind-spot category:** CRITIC-6 (Future-version commitment) + CRITIC-1 (§2 ↔ §10c)
- **SPEC location:** §2.1 lines 73-77, §10b line 386, §10c lines 388-400
- **The claim:** §2.1 `"For each parsed tool call, the provider MUST mint an ID of the form: call_<uuid-hex-lowercase-without-hyphens>"`. §10b reserves: `"Promotion of id minting from a per-response opaque UUID to a (provider_id, request_id, choice_index)-scoped identifier (Security M-2 v0.3+ candidate)."` §10c `"MUST preserve the v0.1.2 non-streaming response shape defined in §2 (role, content, tool_calls[] schema with id, type, function.name, function.arguments; finish_reason = 'tool_calls')"`.
- **The refutation:** §10c protects "shape." It is ambiguous whether "shape" means the structural JSON schema (field names + types) only, or also the format of the values (the `call_` prefix specifically). If v0.3+ promotes `id` to `(provider_id, request_id, choice_index)`-scoped per §10b, the resulting ID will look like `prov_X-req_Y-0` or similar — NOT `call_<32-hex>`. Multiple OpenAI-shape SDK validators (and downstream tooling that parses tool_call IDs for telemetry/correlation) have soft expectations that tool_call IDs start with `call_`. A v0.3 author reading §10c could reasonably conclude that as long as `id` is still a string field, the additive invariant holds. But that interpretation breaks any buyer that asserts `id.startswith("call_")` — an entirely reasonable client check given §2.1's MUST format.
- **Severity rationale:** MEDIUM. This is a forward-compatibility tension that v0.1.2 introduced (§10c is new) while leaving §10b open. The two commitments cannot both stand without disambiguation: either §10c forbids the §10b promotion, or §10c must explicitly carve out value-format changes. Codex did not flag because §10c verbosity was about "fields" not "value formats," and §10b is a §10b future-enhancement (not v0.2-gating), so neither lane treated them as in scope together.
- **Recommended fix:** Add to §10c: `"The id value format defined in §2.1 (call_<uuid-hex-lowercase-without-hyphens>) is part of the protected shape. Future ID rescope (§10b) MUST either preserve the call_ prefix as a leading substring, or land via a major SPEC-018 version bump that explicitly retires §10c for the id field with operator notice."`

### M-5 — §2.3 sorted-keys scope unspecified for nested objects (AC-17 receipts tension)

- **Codex blind-spot category:** CRITIC-1 (Cross-section consistency: §2 ↔ AC-17 / SPEC-015 v0.3)
- **SPEC location:** §2.3 line 100, AC-17 line 350
- **The claim:** §2.3 `"JSON object arguments decoded from a structured object MUST be serialized with sorted keys, no insignificant whitespace, and without escaping /."` AC-17 binds SPEC-015 v0.3 canonical output object to include canonicalized `tool_calls[]`.
- **The refutation:** "Sorted keys" — at what depth? §2.3 does not specify whether sort is top-level-only or recursive. SPEC-015 v0.3 canonical output binding (per AC-17) is strictly canonical, which by JCS convention is recursive sort. If the provider sorts only top-level keys and emits nested objects in iteration order, the SPEC-015 receipt's canonical-output binding will hash a different byte sequence than the wire bytes — producing a binding mismatch that surfaces as "receipt does not verify" for any tool call with nested-object arguments.
- **Severity rationale:** MEDIUM. SPEC-015 v0.3 is a money-path settlement contract. A subtle receipt-bind mismatch on nested tool-call arguments would surface as billing failures for legitimate workloads.
- **Recommended fix:** Update §2.3 line 100 to: `"JSON object arguments decoded from a structured object MUST be serialized with keys sorted recursively at every depth, no insignificant whitespace, and without escaping /."`

### m-1 through m-4 (deferrable polish)

- **m-1 — AC-7 raw-delimiter prohibition is over-broad.** Read strictly, AC-7 prohibits the literal byte substrings `<tool_call>` etc. appearing **anywhere** in the streamed response, including inside `function.arguments` string values that legitimately discuss those tokens. Reword: "no raw … delimiters at framing positions — i.e., outside the JSON-escaped contents of function.arguments string values."
- **m-2 — §3.2 silent on omitted/empty modelID.** Add: "A request with a missing, empty, or whitespace-only modelID MUST be treated as no §3.1 family match for §3.2 purposes; the response falls back to plain assistant content per §3.5."
- **m-3 — §3.7 family-row addition can silently change parser selection.** Add: "New rows MUST be appended at the end of §3.1, and new-row predicates MUST be disjoint from existing predicates."
- **m-4 — §10c "MUST NOT change the assistant-response shape after a successful turn" silently changes the AC-14 error path.** Reword: "...but MUST NOT change the schema of the assistant tool-call response shape (§2) produced when a multi-turn request succeeds. v0.2 promotion of AC-14's 400 error path to a success path is permitted under additive-only."

## Codex-coverage critique

Codex's four lanes did exactly what their per-lane prompts asked. Architect lane found the table-priority + Qwen-row issues and absorbed §7 voice; code lane caught citation drift cleanly; security lane drove the prompt-injection re-scope and commit-on-bogus-delta tightening; PD lane drove the Ring-1 → certificate re-scope. The convergence trajectory (r1: 2 CRITICAL → r2: 0/0/5 MEDIUM → r3: 0/0/0/1 MINOR) is real — codex four-lane is a strong gate for adjacent-section consistency, lane-specific normative tightening, and citation precision.

What codex missed clusters around three blind spots that this pass surfaced. **First, distant-section invariants.** §10c was a new section v0.1.2 added, and its sole AC (AC-23) tests the wrong direction of forward compatibility (H-1). §10c also creates a §2 ↔ §10b tension around the `call_` ID prefix (M-4) that no lane was scoped to detect because §2 was treated as "ratified as-built" and §10b as "future." **Second, scope-honesty re-checking after re-scope.** PD lane drove the §1 narrowing for "certificate," but no lane re-walked the framework enumeration to check that the named targets are actually OpenAI-wire (H-2). **Third, treating sentinel strings as opaque framing rather than as substrings of legitimate data values** (H-3 mixed-sentinel false-positive). Codex security and code lanes both reasoned about `<|python_tag|>` as Llama framing, never as a string that might appear inside a Qwen tool call's argument value.
