## Fresh findings

### H-1: WS-tunneled non-streaming SPEC-019 errors lose `FaultBreakerQualifying` before billing

The r1 absorption extended the shared `spec001EndStatus` allow-list to include the SPEC-019 codes (`phase4-coordinator/internal/buyer/server.go:4933`). That is correct for direct HTTP, but one allow-list consumer is the WS-tunneled non-streaming terminal path. When a provider sends an `inference_response_end` with `status:"malformed_json_response"` or `status:"json_schema_validation_failed"`, `forwardWS` writes the structured error and returns a `requestLogAttempt` with only `ErrorCode: spec001EndStatus(end.Status)` (`server.go:2125`, `:2130`, `:2131`). `classifyWSResult` treats `wsForwardFailed` as non-retryable (`phase4-coordinator/internal/buyer/transport_result.go:85`, `:108`), and `forwardWSNonStreamSequence.handleNonRetryableTerminal` logs that attempt as-is (`server.go:1670`, `:1674`).

That path never sets `requestLogAttempt.FaultFlag = billing.FaultBreakerQualifying`. The logging closure passes `attempt.FaultFlag` into `rec.recordRow` (`server.go:1413`, `:1422`), `recordRow` defaults an empty flag to `billing.FaultNone` before constructing `HotPathInput` (`phase4-coordinator/internal/buyer/billing_recorder.go:181`, `:197`), and `WriteHotPath` then calls `ComputeCredits` with that non-breaker flag (`phase4-coordinator/internal/billing/hotpath.go:119`, `:124`). With no usage tokens on this terminal WS error, billing will likely end as zero-credit `null_usage_error`, but it is not the required `breaker_qualifying` settlement row and does not satisfy the SPEC-019 fault-breaker classification contract.

Security impact: a WS-tunneled provider can return the same post-inference structured-output failure that the HTTP path correctly records as breaker-qualified, but the coordinator records it as a non-breaker/null-usage billing outcome. This weakens the money-path fault signal and leaves direct HTTP and WS-tunneled providers with divergent settlement semantics for identical SPEC-019 errors.

Required fix: when `end.Status` is a SPEC-019 provider detail code in WS non-streaming, set `FaultFlag: billing.FaultBreakerQualifying` on the returned `requestLogAttempt`. Add a WS-tunneled coordinator test mirroring `TestStructuredOutputProviderDetailErrorsPassThroughWithoutRetry` that asserts buyer-visible code/body/retryable preservation, one request-log row, `fault_flag = breaker_qualifying`, and zero provider credits for both codes.
