## Fresh findings

### Finding 1: §7 gzip body-byte preservation contradicts the gateway's existing JSON quota-parse path — request fails before pass-through can run

- **Severity:** HIGH
- **Location:** SPEC-019 §7 lines 717-725 (Inbound content-encoding preservation block) and AC-28a lines 354-359; gateway code `phase5-gateway/internal/router/chat_proxy.go:102-117`.
- **Issue:** §7 line 717-721 says: "the gateway MUST forward the inbound request body bytes to the coordinator without decompressing any `Content-Encoding` (`gzip`, `deflate`, `br`)." AC-28a asserts: "a buyer-sent compressed request body (`Content-Encoding: gzip` with a 14 KiB `json_schema.schema`) is forwarded to the coordinator without gateway-side decompression." But the current gateway implementation at `chat_proxy.go:111` calls `parseChatRequest(body)`, which runs `json.Unmarshal(body, &req)` at `chat_proxy.go:999`. Go's `net/http` does NOT auto-decompress request bodies — `r.Body` returns raw transport bytes. So `body` is gzipped bytes, `json.Unmarshal` fails with "Malformed JSON", and the gateway returns HTTP 400 `invalid_request` BEFORE the body ever reaches the coordinator. The gateway-parses-for-quota path is incompatible with the no-decompression mandate. SPEC-006 has no `Content-Encoding` policy (confirmed: `grep -ni content-encoding specs/SPEC-006-buyer-api.md` returns nothing), so this is the first SPEC to surface the issue. The SPEC has three internally-consistent options, but currently picks none:
  - (a) Gateway DOES decompress on inbound (Go stdlib gzip on `r.Body`) and re-emits decompressed bytes to coordinator. Provider+coordinator+gateway all see decompressed bytes. Byte invariant holds at decompressed layer. SPEC-019 §7 today PROHIBITS this.
  - (b) Gateway forwards compressed body bytes unchanged. Quota-parse must be moved AFTER decompression at coordinator, OR gateway must skip quota for gzipped buyer requests. SPEC §7 says "may parse enough to enforce existing quota" — incompatible with (b).
  - (c) Gateway rejects compressed buyer bodies with HTTP 415 (current de-facto behavior, but as "Malformed JSON" 400 not 415). Then AC-28a is moot.
- **Recommendation:** Pick one. Most realistic for v0.1.0 is (a): "Gateway decompresses inbound `Content-Encoding: gzip|deflate|br` request bodies before quota-parse, then forwards the decompressed bytes to the coordinator. Provider, coordinator, and gateway compute schema-byte caps and JCS-canonicalize over the IDENTICAL decompressed byte sequence." This matches what the byte-cap invariant actually needs (a single normative byte layer) without breaking the existing quota path. Rewrite §7 line 717-725 to reflect this and adjust AC-28a to assert "coordinator-side decompressed schema bytes equal gateway-side decompressed schema bytes equal provider-parser decompressed schema bytes." Alternative — if SPEC-019 v0.1.0 wants to stay narrow — simply forbid `Content-Encoding` on `/v1/chat/completions` requests with `response_format:json_schema` in v0.1.0 (HTTP 415 `unsupported_request_encoding`) and defer compressed-body support to v0.2.

### Finding 2: §5 empty-content actionable message names `max_tokens` as a remediation — almost always wrong cause

- **Severity:** MEDIUM
- **Location:** SPEC-019 §5 lines 577-584 (Empty-content subcase override).
- **Issue:** The verbatim error message reads: "Model emitted zero tokens for the requested schema; modify the prompt, increase `max_tokens`, or relax the schema before retrying". Zero tokens emitted is almost never caused by `max_tokens` being too small. `max_tokens=0` is the only literal cause via that knob, and explicit `max_tokens=0` would be either rejected upstream or generate exactly zero tokens by construction. The realistic causes are: (1) model decoder produces an immediate stop token (eg EOS as first emission, which the stop-token filter (`ModelRuntime.swift:811-828`) then strips to empty), (2) sampling produces only stop-token-filtered content for the entire generated window, (3) chat-template format mismatch where the model emits assistant-turn-end immediately. None of these is fixed by raising `max_tokens` — at zero tokens, you never approached the `max_tokens` ceiling. Misleading buyer remediation is product-design quality but, given `retryable:false` is the override that prevents auto-retry, the SPEC-prescribed remediation IS the buyer-facing actionable. Saying "increase `max_tokens`" sends buyers to fix the wrong knob and may degrade SDK ergonomics signal.
- **Recommendation:** Change §5 line 580-582 to: "Model emitted zero tokens for the requested schema; modify the prompt, lower `temperature`, set a non-zero `seed`, or relax the schema before retrying — automatic same-request retry will not succeed." Drop the `max_tokens` reference. The other three knobs (prompt, temperature/seed, schema complexity) are the actual signal-bearing buyer-side fixes for empty output.

### Finding 3: §6 depth-counting example doesn't cover the array-of-array-of-object case — implementers will diverge on items-vs-properties symmetry

- **Severity:** MEDIUM
- **Location:** SPEC-019 §6 lines 663-672 (Depth counting algorithm).
- **Issue:** The algorithm states "each nested `properties[*]` subtree, `items` subtree, `additionalProperties` subtree... increments the count by 1." The worked example is properties-only: `{"type":"object","properties":{"a":{"type":"object","properties":{"b":{"type":"string"}}}}}` = depth 3. For an array-nested schema like `{"type":"array","items":{"type":"array","items":{"type":"object","properties":{"a":{"type":"string"}}}}}` — applying the algorithm literally yields depth 4 (root array=1, items array=2, items object=3, properties.a string=4). A second competent implementer who counts only nesting through `properties` (treating `items` as part of the array node, not its own depth level) yields depth 2. The SPEC's worded rule unambiguously gives 4, but the absence of an `items` example invites the "items is part of the parent array, not a separate level" misreading. AC-12 says "a schema nested exactly 32 levels deep succeeds; 33 levels returns 400" — but the fixture construction is unspecified. Two parity-tested implementations could each "pass" AC-12 against their own depth definition while disagreeing on real adversarial schemas. The SPEC-019 v0.1.0 schema subset disallows `oneOf`/`anyOf`/`$ref`/`$defs`, so the only depth-increasing constructs are `properties`, `items`, and `additionalProperties`. Picking one of these as the only-mentioned-in-example creates exactly the parity drift AC-27 is supposed to prevent.
- **Recommendation:** Add a second worked example under the §6 algorithm: "`{"type":"array","items":{"type":"object","properties":{"a":{"type":"string"}}}}` is depth 3 (root array → items object → properties.a string)." Also add a parity fixture under AC-12 or AC-27: "Mixed array+object depth fixture: `{type:array, items:{type:array, items:{type:object, properties:{a:{type:string}}}}}` MUST count as depth 4 at both provider and coordinator." Without these, the algorithm is technically computable but the IMPL-test surface is under-specified.

### Finding 4: AC-30/AC-31 paired Person fixture quietly relies on Pydantic emitting no `$defs` — true for flat models, false for nested-class models, but SPEC doesn't say so

- **Severity:** minor
- **Location:** SPEC-019 AC-30 lines 369-380, AC-31 lines 382-391, §3 line 432 (rejected keywords list).
- **Issue:** AC-30 fixture is `class Person(BaseModel): name: str; age: int` — a flat Pydantic model. Pydantic's `model_json_schema()` emits `$defs` for any nested class reference. Vercel's Zod schema for the same logical contract inlines nested schemas; no `$defs` emitted. The AC-30/AC-31 byte-equality check uses an allow-list for `title` and `description` differences. But §3 line 432 rejects `$defs` outright (`json_schema_unsupported_keyword`). So the moment a buyer Pydantic-derives a schema that includes a nested class (eg `class Address(BaseModel)...; class Person(BaseModel): name: str; address: Address`), the request fails with HTTP 400 BEFORE inference. This is a real Pydantic ergonomic limitation in v0.1.0, and AC-30 silently sidesteps it by picking a flat fixture. Vercel/Zod has no equivalent limitation. SDK parity holds for flat models, breaks for nested-class models. The SPEC doesn't say this constraint exists.
- **Recommendation:** Add a sentence to §1 under "Buyer-visible contract" or to §10 deferred items: "v0.1.0 supports flat Pydantic models only. Nested `BaseModel` references emit `$defs`, which v0.1.0 rejects per §3. Buyers MUST inline nested types or upgrade to v0.3 (`$defs` deferred per §10) for nested-class schemas." Alternatively add an AC noting the explicit failure mode for a nested Pydantic fixture so buyers receive a clear failure rather than silent confusion.

This is real: a buyer sending `Content-Encoding: gzip` today hits `json.Unmarshal` on raw gzipped bytes at `chat_proxy.go:111`, fails as "Malformed JSON" 400, and the body never reaches the coordinator — so AC-28a's premise ("forwarded to the coordinator without gateway-side decompression") cannot be implemented unless the gateway either (a) decompresses on inbound (SPEC currently forbids), (b) skips quota-parse for gzipped requests (SPEC silent), or (c) rejects gzipped requests outright (SPEC silent). The blast radius is: any buyer who turns on transport-level gzip on their HTTP client (default in some HTTP clients) silently fails before SPEC-019 logic runs. This is a HIGH because the SPEC is unimplementable as written and the contradiction will surface immediately in IMPL.

Documenting the constraint as a known v0.1.0 limitation closes it; deferring `$defs` support is already in §10.
