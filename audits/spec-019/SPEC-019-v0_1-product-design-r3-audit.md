## Fresh findings

### Finding 1: AC-31 cannot pass with the pinned Zod `Person` fixture
- Severity: HIGH
- Location: SPEC §2 AC-31 (`specs/SPEC-019-structured-output.md:382-390`), SPEC §3 rejected keywords (`specs/SPEC-019-structured-output.md:429-436`)
- Issue: AC-31 requires Vercel's Zod fixture `z.object({ name: z.string(), age: z.number().int() })` to JCS-match AC-30's Pydantic schema modulo only `title` / `description`. A pinned local capture with `@ai-sdk/openai-compatible@2.0.38` and `ai` showed the Vercel outbound schema includes `"$schema":"http://json-schema.org/draft-07/schema#"` and, for `z.number().int()`, `minimum` / `maximum` bounds on `age`. §3 rejects `$schema`, `minimum`, and `maximum` as unknown / unsupported keywords. The simple Pydantic `Person` path with `openai==2.44.0` does not emit `$defs`, but a nested Pydantic model does emit `$defs` and `$ref`, which §3 also rejects and §10 defers. So the current paired-fixture text prevents a false green in intent, but creates a different false red: the required Vercel fixture is not macprovider-valid and cannot byte-match the Pydantic fixture under the stated allow-list.
- Recommendation: Make AC-31 commit the actual captured Vercel outbound body and choose one product posture. Either define a canonical SDK-normalization step that strips or rejects `$schema` and uses a supported Zod shape before macprovider submission, or widen §3 to allow the emitted metadata / numeric bounds and implement those validator semantics. If v0.1.0 keeps the narrow subset, change the AC-31 fixture away from `z.number().int()` and explicitly state how `$schema` is handled; keep `$defs` / `$ref` out of the v0.1 fixture or document them as v0.3-only.

### Finding 2: Empty-content `retryable:false` overgeneralizes deterministic failure to stochastic retry
- Severity: MEDIUM
- Location: SPEC §5 empty-content override (`specs/SPEC-019-structured-output.md:577-584`), SPEC §5 retry rule (`specs/SPEC-019-structured-output.md:600`), SPEC §11 SDK ergonomics hook (`specs/SPEC-019-structured-output.md:862-864`)
- Issue: The r2 fix correctly stops deterministic empty-output loops, but the new blanket empty-content override says automatic same-request retry will not succeed. That is too absolute for non-deterministic generation: with `temperature > 0` and no fixed seed, the same logical buyer request can emit empty content on one attempt and valid JSON on another. Because buyers key retry policy off `error.retryable`, `retryable:false` can cause SDKs to abandon a recoverable structured-output request instead of trying a controlled retry with a different seed / temperature policy. The current actionable message mentions prompt, `max_tokens`, and schema, but omits seed / temperature and does not distinguish "identical deterministic retry" from "buyer-chosen modified retry".
- Recommendation: Keep `retryable:false` for provider-side automatic identical retries, but change §5 wording to say it means "do not blindly replay the identical request"; buyers MAY issue a deliberate modified request, including seed / temperature / sampling changes, after their own policy check. Update the example message accordingly, and add a §11 audit hook for whether v0.2 needs a richer retry hint than one boolean.
