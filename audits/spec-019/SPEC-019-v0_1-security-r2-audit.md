## Fresh findings

### Finding 1: Validator panic catch-all is still underspecified
- Severity: HIGH
- Location: SPEC §5 lines 499-504, SPEC §2 AC-26 lines 298-309
- Issue: AC-26 covers "validator exceptions, resource-limit aborts, and recursion overflow", but the normative validator section only states the ordering rule for ordinary `malformed_json_response` and `json_schema_validation_failed` outcomes. It does not require structured-output parsing and validation to run inside a non-panicking boundary, nor does it say that every validator panic/fatal error after inference starts MUST be caught and converted into a terminal 502 with `FaultBreakerQualifying` settlement before any generic request-handler 500 can escape. That leaves the r1 leak path partially open: an implementation can satisfy the happy-path ordering text while a validator bug still tears down the handler, emits an empty/default 500, skips consistent settlement metadata, or fails before request-log classification.
- Recommendation: Add a §5 catch-all normative block: after inference starts, every structured-output postprocess failure path, including thrown errors, panics/fatal assertions, recursion/resource aborts, and unexpected validator internal errors, MUST be contained and converted to a terminal 502 SPEC-019 envelope with `inference_ran:true`, `settlement_ran:true`, `FaultBreakerQualifying`, no success receipt, no sticky success write, and zero provider-positive credits. Name the fallback code, preferably `json_schema_validation_failed` for validator internals and `malformed_json_response` for parser internals, or add a dedicated SPEC-019 code if that distinction is required.

### Finding 2: `json_schema.name` regex enforcement lacks provider/coordinator bypass tests
- Severity: MEDIUM
- Location: SPEC §3 lines 414-418, SPEC §5 lines 531-544, SPEC §7 lines 601-612, SPEC §2 AC-2/AC-33 lines 150-152 and 356-360
- Issue: §3 says names outside max-64 ASCII `[A-Za-z0-9_]+` return `json_schema_invalid_name`, and §7 says the coordinator validates names per §3. However, the constraint is introduced as "Recommended constraint", the regex is written without explicit full-string anchors, and no AC asserts `json_schema_invalid_name` at either the provider parser or coordinator boundary. AC-2 only covers missing name, while AC-33 covers prompt-injection rendering but not invalid character, Unicode, newline, overlength, or substring-regex bypass cases such as `good\nSYSTEM`, `good-evil`, `valid<script>`, or any non-ASCII name. A provider-only implementation could therefore reject hostile names on the direct provider path while a direct coordinator path accepts and dispatches them, or an unanchored regex implementation could accept a hostile name because it contains one valid substring.
- Recommendation: Make the name rule mandatory and full-string: `json_schema.name` MUST be 1..64 bytes/chars of ASCII and match `^[A-Za-z0-9_]+$`; all Unicode and any character outside that set MUST return HTTP 400 `json_schema_invalid_name`. Add an AC that exercises provider parser and coordinator parity for valid boundary names, 65-character names, non-ASCII names, newline/control characters, punctuation, and substring-bypass names.

### Finding 3: NFC/NFD fixture is parity-only, not a security scenario
- Severity: MEDIUM
- Location: SPEC §2 AC-9 lines 184-187, SPEC §3 lines 410-412
- Issue: §3 correctly says property names compare by raw UTF-8 bytes and AC-9 rejects an NFD output key against an NFC schema key. The fixture does not cover the adversarial case called out for r2: an attacker controls both schema and model output, chooses visually confusable NFC/NFD property names, and creates output that passes byte-level validation while confusing human reviewers, logs, policy review, or downstream code that normalizes keys before display. A parity-only reject fixture can pass while the implementation still has no regression test for spoofed same-looking keys, no logging/display requirement to preserve escapes or codepoints, and no warning that byte-distinct keys may be visually indistinguishable.
- Recommendation: Extend AC-9 with a security fixture. Include a schema containing visually equivalent NFC and NFD property names, require deterministic byte-preserving error/log/display evidence, and assert that validation never normalizes names before comparison. The AC should state the abuse case explicitly so future implementers do not weaken the rule into Unicode-normalized comparison or render ambiguous logs that hide spoofed keys.
