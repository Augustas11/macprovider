# Decision Log (public excerpt)

The project keeps a dated decision log: each entry records a ruling, why it
was made, and the follow-ups it requires. The full log (formerly
`beta/DECISION_CRITERIA.md`) holds production operations detail and lives in
the private engineering archive. Code comments, specs, config examples, and
`ops/exceptions/production-exceptions.json` cite it as "DECISION_CRITERIA
Entry N" or "docs/decision-log.md Entry N".

This excerpt keeps the entries that public code and tests read verbatim.

| 2026-06-22 | **Entry 80 — Open Q3 ruling: target tier-2 posture for the 2-person beta remains "defer Part C entirely"; the five enforcement flags stay at their `false` defaults until the team has a buyer-side reason to flip any individual one.** The five flags are `Tier2Config.RequireHashVerified`, `.RequireEncryptedLeg`, `.RequireAttestation`, `.BehavioralSafetyEnabled`, `.EncodingValidationEnabled` in `phase4-coordinator/internal/config/config.go:142-159`; all default to Go zero-value `false`. The audit's M1-6 Part C task was to add `g(coord, "<flag>")` lines to `phase4-coordinator/dist/check-deploy-config.sh` so the deploy gate refuses to start the coordinator if production drops a flag that was supposed to stay on. The operator-instructed answer recorded in `audits/2026-06-10/MILESTONE_1_HANDOFF.md:55-65` during the M1 autopilot was "Defer Part C entirely" — i.e. don't assert any of the five yet. That decision was not previously captured in DECISION_CRITERIA; this entry is the dated record. **What the flags actually do (so the next reader can revisit without re-deriving):** `RequireHashVerified` rejects routing to any provider whose reported `model_hash` is absent or doesn't match the signed catalog at `Tier2Config.CatalogPath` — turning this on prevents weight-substitution attacks but breaks any model that isn't in the catalog yet (the catalog signing script is in `scripts/sign-catalog.go`); `RequireEncryptedLeg` mandates AEAD on the coordinator→provider segment with a periodic rekey (`EncryptedLegRekeyAfterRequests` / `EncryptedLegRekeyAfterSeconds`) — pure defence-in-depth, no buyer-visible behaviour change; `RequireAttestation` demands a valid Apple App Attest receipt from the provider at admission with a freshness bound (`AttestationMaxAgeS`) — gates by hardware/OS integrity, blocks any non-attestable provider (mock attestation is gated separately by `AllowMockAttestation`); `BehavioralSafetyEnabled` enforces `OutputSizeCapBytes` / `OutputBytesPerTokenCeiling` / `ResponseTimeAnomalyFactor` thresholds on every response — catches a misbehaving provider streaming garbage at the wire instead of post-hoc; `EncodingValidationEnabled` checks UTF-8 + JSON-object well-formedness on streaming chunks — catches malformed SSE before it reaches the buyer. | **The 2-person beta cannot afford the friction of a flag that fail-closes on a legitimate scenario the team hasn't yet exercised end-to-end.** The five flags each have a buyer-visible failure mode (catalog misses, attestation outages on macOS minor upgrades, false-positive size caps when a long-form completion is genuinely large, encoding rejections on a model that emits trailing whitespace) and the cost of debugging a "why is my request 503-ing" against the right one of five is meaningfully higher than the marginal security improvement from any individual flag in a 2-provider closed beta. The deferral does NOT mean tier-2 is off — `Tier2Config.ObserveEnabled` and the catalog hash check still run in observation mode; the `model_hash_verified` event logs that hit Pearl journald during air5's connect cycles (`reason:"hash_match"`) are proof the observation half is live. **Flipping any flag is a config change on Pearl `coordinator.yaml`, not a code change** — so this deferral has zero engineering cost to reverse later. The MORE actionable closure for M1-6 Part C is to ship the deploy-gate lines for whichever flag the team WILL turn on next, so deploy assertion drift is impossible by construction. | **Operator follow-ups, in order:** (1) **Revisit trigger — when any of three things change:** (a) the provider pool stops being "2-3 Macs the team can text" (next-tier providers start joining whose hardware/OS hygiene we cannot personally vouch for — `BehavioralSafetyEnabled` + `EncodingValidationEnabled` become high-leverage); (b) the catalog signing pipeline is ergonomic enough that adding a new MLX model takes <10 minutes operator time (`RequireHashVerified` becomes feasible); (c) a buyer with a real privacy posture lands and asks for attested-only routing (`RequireAttestation` becomes a sales-required flag for that customer). Any of those is a reason to revisit; before then the deferral stands. (2) **When ANY flag is turned on,** ship M1-6 Part C in the same PR — add the corresponding `g(coord, "<flag>")` line(s) to `phase4-coordinator/dist/check-deploy-config.sh` so the deploy gate enforces that production keeps the flag on. The flags + the gate ship together or the gate becomes a paper rule. (3) **Q3 is hereby logged as resolved** in DECISION_CRITERIA terms — the deferral is the ruling, this entry is the record. `audits/2026-06-10/REMAINING_WORK.md` "operator-pending item 2" can be updated to reference Entry 80 in lieu of the freestanding deferral note. |
