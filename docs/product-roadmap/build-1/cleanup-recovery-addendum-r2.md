## Closed contract

SPEC-044 protocol 2 adds a top-level `recoveries` array, emitted even when empty. Protocol 1 omits this key and retains its exact closed shape. Updated app decoding permits absent recoveries as an empty list for existing protocol-2 peers, but rejects any recoveries key on protocol 1. Unknown keys remain rejected.

Each recovery entry has exactly `target_model_id` (nonempty canonical served target from the validated journal), `model_key` (historical signed key used solely to validate the cleanup transcript), and `action` (existing closed Action descriptor with kind cleanup_staging, available true, explicit confirmation, UUID, bounded1800-second deadline, null estimated bytes, null unavailable reason). Duplicate transaction UUIDs or duplicate target_model_id entries invalidate the recovery list. This introduces no admission source/state value, model Row field, or trusted identity. Operation selectors required by the separately reviewed transaction-control contract must also be carried by the action; its final exact revision must pass independently before combined implementation.

The CLI reads validated private journal records under its existing lock, independently of current feeds, supported-model configuration, discovery and memory fit. Only records requiring owned staging cleanup are eligible. Select one per exact case-sensitive canonical target: oldest createdAt, then UUID lexical order as deterministic tie-break. Subsequent refresh exposes the next outstanding cleanup for that target. Validate record/event identity and target, bounded regular private file, owner/recovery safety and all cleanup invariants. Corrupt or unsafe records do not become executable recovery actions; preserve their bytes. No raw path, feed, recommendation, key material or estimated model size is published.

## Projection and UX

Recovery entries are separate from model rows. Never manufacture, merge, overwrite, re-key, reclassify or duplicate a current catalog/discovery row based on historical metadata. The same target may have its ordinary model row and one recovery entry, but recovery UI identity is prefixed transaction UUID and occupies a separate Staging cleanup section. Existing model grouping, current model identity, readiness, economics and admission remain derived from their existing sources. Historical model_key is never used to infer current model or enable offer/adoption/prepare/evaluate.

Remove available cleanup descriptors from ordinary protocol-2 rows after moving them to this section; their existing cleanup_staging field remains present and unavailable. This prevents cleanup from replacing a current model category or hiding an independently available model action. Protocol1 behavior is unchanged.

App confirmation names target and CLI-owned staging, says published/active artifacts are preserved, and claims no current feed authority. Entry dispatch is a dedicated typed cleanup action using exact target/UUID and the independently gated operation selector; it never reuses row.id as authority. Require compatible authenticated CLI capability/executable evidence, explicit confirmation and no other pending mutation. The same transaction stream validation, cancellation, recovery, and terminal-plus-new-projection gate applies. Feed unavailable/stale or target disappearance does not disable cleanup. A disappeared recovery after successful cleanup is acceptable only with the matching terminal event and newer validated projection. Failure preserves pending recovery; corrupt projection makes no success claim.
