# Build 1 command composition testability addendum r1

Status: proposed for independent approval before production edits. Addresses CODE-M2 and B1-T11; owner-only tests remain separate evidence. This addendum does not relax feed trust, recommendation eligibility, admission, billing, or physical qualification.

## Shared command execution

Introduce an internal typed `ModelCommandExecutionContext` with a production default. Each participating `AsyncParsableCommand.run()` delegates to `run(context: .production)`. The overload contains the existing command body, including validation, config resolution, error/exit mapping and JSON serialization. Both production and fixture therefore execute the same parsed command implementation. No process-global mutable context, environment flag, CLI flag, test-only authority switch in the shipping executable, or replacement command implementation is permitted.

The context carries only these default-preserving boundary dependencies:

| Boundary | Production default | Fixture supply |
| --- | --- | --- |
| Static input loader factory | `AutotuneStaticInputs()` with the committed keyring, URLSession fetch and real signature verifier | Real `AutotuneStaticInputs` with disposable fixture public keys and fixture bytes delivered through its existing fetch boundary; real Ed25519 verification, freshness and row binding remain active |
| Transaction runner configuration | Existing `ModelCatalogTransactionRunner(config:configPath:store:)`, unchanged defaults | Configure only the approved owner-testability-r2 dependencies, existing downloader HTTP transport and input loader; real store, publisher, verifier, engine and result writer |
| Discovery environment creation | Existing `BYOMDiscoveryEnvironment.production` arguments and scanner behavior | Same production environment with explicit config, namespace and cache paths under the fixture root; loopback scans disabled for discovery through existing options or existing environment scanner boundary |
| Credential and receipt identity stores | Existing `ProviderCredentialStoreFactory` methods | Existing file-backed store implementations at explicit test-owned paths, with disposable credentials; no Keychain access |
| Admission transport | Existing `BYOMModelAdmissionClient(coordinatorURL:)` | Same client pointed to the local coordinator URL; no injected admission success, signature acceptance or status rows |
| Adoption hardware sampling | Existing `MachineFingerprinter().sample()` | Fixed hardware fixture matching the producer hardware dependency, clearly identified as deterministic fixture data |
| Adoption journal root | Existing `RecommendationAdoptionJournalStore.defaultRoot` | Explicit directory below the fixture root |

Use narrow concrete factories/values where practical; do not inject whole command results, arbitrary command handlers, recommendation outputs, authority validators, artifact verifiers, admission records, transaction terminal records, or settlement results. A runner configuration closure may configure approved dependencies but must not replace `run`. Adoption continues to load the original file bytes, validate signed authority and artifact bytes, and use the existing control socket transaction protocol. Existing explicit control socket/switch-state/config options remain the path boundary; no synthetic adoption-success callback is added. Discovery keeps durable publication scanning and canonical namespace identity logic. Status/result/cancel execute their real read paths and need no behavioral substitution.

Affected command bodies are prepare, recommend-prepared, discover, offer, admission status/retry, and adopt-recommendation. Transaction status/result/cancel remain parsed real commands in the fixture. If evaluation is needed for offer evidence, its parsed command uses the same input/discovery context and real evaluator; it may not fabricate an evaluation digest. Shared private helpers accept the context explicitly. Existing direct `.run()` callers remain source-compatible and production-bound.

## Default-wiring proof

Tests assert that context construction defaults to the existing committed trusted keyring and real signature verification, default network fetch, real runner/engine/prober, existing credential factories and adoption root/hardware sampler. Also execute representative `.run()` delegation with a default context against safe invalid arguments and compare validation/error outcomes with the explicit default overload. No test invokes default secret/keychain/network paths to prove a wiring identity: verify factory construction or explicit immutable default values, and rely on existing adapter tests for behavior. Existing command grammar and production adapter tests remain required. An internal override must be an explicit argument reachable only by test code, not by parsing an option or reading process environment.

## Separate-process fixture

Add test-target-only subprocess entry coverage. The XCTest child entry receives a root and command argument list through a fixture-owned request file. It parses with the real top-level `MacProviderCLI.parseAsRoot` (use the actual root type name if different), selects the typed parsed command and invokes its shared `run(context:)`. The parent launches the test executable's dedicated child test in a sanitized environment; the request file is a harness input, not a shipping CLI/environment seam. Production source does not know this file exists. Separate invocations have no shared in-memory namespace, inputs, owner or recommendation state.

Before spawning, create a 0700 temporary root and assert every mutable config/cache/transaction/HMAC/admission/identity/journal/socket/log/output/request path is beneath it after resolving parents/symlinks. HOME alone is not isolation. The subprocess environment is an allowlist (PATH, temporary HOME/TMPDIR and required platform test-runner values); it excludes inherited provider/coordinator credentials, Hugging Face credentials, cloud tokens and operator configuration. Children have bounded deadlines and process-group cleanup. Fixture private signing/auth keys remain temporary 0600 files, never printed or committed. Loopback service URLs and dynamically allocated fixture ports are explicit.

The journey starts with no Hugging Face snapshot, provider session, admission event, recommendation, transaction or durable publication. Disposable account/provider authentication is acquired through the existing local service protocol when joining the service portion; seed no trust state. Signed feed fixtures provide authoritative metadata, not a prepared artifact or eligible result.

1. Parse and run prepare against deterministic metadata/file HTTP transport. Verify exact downloaded bytes, canonical digest, committed durable artifact and terminal transaction output.
2. Exit that process. Start a fresh child and parse/run discover. Assert exactly one ready row with the same stable candidate ID and durable path; transaction status and result use real persisted read paths. No download after preparation is allowed (transport records/fails unexpected fetches).
3. Parse/run recommend-prepared in a fresh child using real `AutotuneRecommendEngine`, `AutotuneRecommendationBenchmarker`, `Stage1Prober`, and `CandidateProviderRunner`. The compiled fixture executable owns its loopback listener and emits delayed SSE chunks. Measured throughput/latency must differ from catalog thresholds; terminal eligibility must be produced by the real engine. Record starts, requests, termination and port closure.
4. Parse/run transaction result in another child. Compare result bytes and recorded digest with the owner's committed document, including selected artifact/catalog/rate/hardware authority. Supply this exact original result file to parsed adopt-recommendation. Use the real existing control socket protocol against a test-owned control fixture; assert incumbent config switch and journal/readback behavior. Label control fixture adoption separately from an installed MLX provider.
5. Parse/run discover and any required evaluation, then signed offer/status/retry using file-backed disposable provider identity and actual client serialization/signing. Prefer composition into the existing local coordinator/WS fixture harness: authenticate, connect, submit pending offer before probe, retry/read back, permit the actual fixture WS probe, then verify promotion. A retry already admitted may legitimately read back admitted; a pending retry assertion needs a deliberately held real probe, not a fabricated status.
6. If the same command-created offer can be connected to the existing real-service buyer/receipt/ledger journey without another runtime seam, carry it through and assert exact settlement. Otherwise report that join as an explicit unclosed B1-T11 gap; the hand-built Go offer journey alone does not close command composition.

The compiled provider, signed static feeds, hardware sampler and control endpoint are deterministic fixtures. They do not establish MLX execution, an independently calibrated Tier2 reference, production-key trust, or B1-T10 physical qualification. No prewritten eligible recommendation, production trust bypass, operator state access, or manufactured authority label is acceptable. Any additional dependency boundary or production behavior change reopens approval before implementation.
