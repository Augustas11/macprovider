# Immutable retirement binding r1 — bounded plan and tests

Status: proposed; no runtime change until independent zero-C/H/M approval. This corrects an uncovered enforcement gap in approved retention r4 and preserves approved retention-lock-budget-r2. No new generation, trust tier, pricing authority, history scan, artifact deletion or pointer-repair exception is introduced.

## Concrete gap

`indexCompletedEvaluation` derives the recommendation context hash from the current original record, including its artifact-feed digest and signer key ID. Existing pointer validation rejects substitution when reading the original context pointer. However, after those fields change, maintenance can derive a different context filename, see no pointer there, publish a new pointer and retire the changed original. The older pointer remains untouched and rejects adoption, but the immutable-substitution requirement also requires retirement to fail closed. Current tests assert original-context projection rejection and unchanged original pointer bytes; they do not establish retirement rejection for every immutable field.

A direct, immutable binding by transaction UUID is required to detect that relocation without enumerating historical context pointers. A binding minted from an already-successful unbound record merely because its newly computed context is empty would repeat the bug. The ordering below deliberately prohibits that fallback.

## One new immutable sidecar

Add exactly one private, bounded sidecar at the original journal namespace: `<uuid>.success-binding`. Schema `model_catalog_evaluation_success_binding.v1`, canonical closed JSON, maximum 16 KiB. It contains canonical transaction UUID, actual evaluation operation-generation UUID, the existing complete context digest, the existing immutable success-commitment digest, original result SHA-256, exact prospective original successful terminal event, and SHA-256 of the exact preterminal primary bytes from which that terminal transition was authorized. The stored event uses the existing event schema and carries the exact successful outcome, sequence, generation, timestamp and warning. It contains no filesystem paths or new wire fields. Validate safe file ownership/modes/ACLs, no-follow placement, regular single-link identity and byte bounds through the receipt storage layer.

The context and success digests use precisely the existing r4 closed commitment definitions. Do not expand or narrow those definitions in this change. The successful terminal event includes the original warning even when subsequent cleanup resolves staging. Cleanup changes only its allowed bookkeeping/own stream and never rewrites this sidecar. The binding is created exclusively and fsynced once. No generic overwrite, regeneration, deletion or quarantine permits a different binding for the same UUID.

## Binding precedes original terminal success

The evaluation owner retains its UUID owner lock. Once result bytes and their original record digest are durably committed under existing rules, prepare the prospective final successful record and this binding outside the journal lock. Use the actual terminal event which that record will persist, including truthful cleanup warning. Validate the original result, exact selector, complete context and immutable commitment. The input is a nonterminal preterminal record plus the actual successful result commitment; a bare `.result` or provider assertion is insufficient.

In one short journal-locked mutation bundle, validate the current active generated receipt, result placement/digest receipt, required binding absence, and owner lifetime fence. First write the pre-encoded binding exclusively, fsync the file and journal directory. Only then persist the exact pre-encoded original successful terminal record and fsync it. Preserve the approved metadata→fence→write checks. After releasing the global lock, index the result using this binding before emitting ordinary successful completion. Bulk parsing/hashing stays outside the lock.

An existing binding is never replaced in this bundle. If it already exists, take the explicit pending-binding recovery path below, using its recorded exact event rather than manufacturing another terminal timestamp or warning. A different binding or unexpected primary/result bytes fails closed and retains active membership. This avoids the ambiguity of success-record-first publication: every newly generated successful original must have a durable UUID binding before success becomes visible on disk.

All writers of a generated nonterminal evaluation must account for a present binding before appending a progress/cancel/failure event or starting a new owner. Its presence means a successful terminal transition is committed as pending local truth and must be reconciled first under the exact-selector/owner rules. The normal bundle holds the journal continuously, so a live heartbeat/cancel cannot interleave between binding and terminal publication. This guard matters after a crash; do not let a subsequent status/cancel append invalidate the sole authorized preterminal record before recovery has inspected it. Presence alone never authorizes success: full binding/result/preterminal validation below is mandatory. Corrupt binding blocks mutation and remains counted.

## Crash and reconciliation rules

- Before binding publication: existing result-commit/owner-loss rules apply. A current nonterminal evaluation with supported committed result evidence may reconcile a successful terminal transition by creating the binding before success using the same owner helper. No successful historical event has yet been replaced.
- After binding publication but before successful primary publication: active membership remains. Under a nonblocking UUID owner, capture binding, primary and result outside the journal lock. Require the original exact selector, actual committed result digest, the binding's exact preterminal primary SHA-256 and its stored next terminal event sequence/generation. Build the prospective successful record by appending that exact stored event, then recompute the existing success/context digests and require equality to the binding. Under short generation/metadata CAS plus lifetime fence, persist that exact successful primary. Never regenerate its timestamp, sequence or warning. If primary/result/binding changed, leave the entry protected and return unavailable/needs attention.
- After original terminal publication but before context pointer: validate the existing binding against the exact original successful commitment and result, then publish the existing context pointer outside-lock/CAS workflow. Do not replace terminal truth or binding. Active membership makes this recoverable on the next bounded projection, independent of queued reuse.
- After pointer publication but before retirement: pointer and UUID binding must agree; normal idempotent indexing/retirement may proceed.
- After retirement: original, result, binding, events and pointer remain immutable at their direct paths. Read-only archived lookup validates all of them without recreating active membership or owner files.

A failed write/fsync is not success. Once the binding is durably published, errors after that point cannot be converted into a different failed/cancelled terminal record. Leave the pending binding and existing committed result for exact reconciliation; the owner watchdog may exit and release OS locks while retaining that evidence. Existing restoration guards remain responsible for incumbent restoration; neither binding nor owner exit claims restoration completed.

## Indexing, pointer cross-check and retirement

Every generated successful evaluation index/retirement operation reads `<uuid>.success-binding` directly. Validate UUID, actual generation, original successful terminal event, context digest, success digest and result digest against the current fully validated record/result. Then validate the existing context pointer, if present, using its ordinary previous-pointer rules plus that previous UUID's immutable binding. No prior-target owner lock is acquired; its pinned read-only observations are rechecked at final pointer CAS. The current owner stays held.

A missing or mismatched binding cannot be treated as a new context. It cannot publish a relocated pointer or remove active membership. In particular, changing signer/artifact digest, target/catalog identity, candidate/hash/revision, timestamps, operation generation, committed/result digest or the original terminal event breaks the UUID binding even when it produces a previously absent context filename. Corrupt/missing/unsafe binding always protects generated successful evidence. Legitimate cleanup still yields exactly the same commitment and succeeds with unchanged binding/pointer bytes.

Retirement snapshots and final metadata CAS include the binding alongside primary/result/current-cleanup/seal evidence. Allocation's required-absence set includes `.success-binding`; an orphan binding prevents empty-intent deletion or UUID reuse. Untouched queued reuse/expiry rejects a present binding. Direct generic historical reads retain their existing read-only contract; generation-scoped adoption additionally requires the binding. No file is removed to free capacity.

## Existing-format compatibility and bounded capacity

Supported generation-less legacy records keep the explicitly approved historical-format retirement rule: validate their original result/terminal evidence, preserve every byte, and retire without inventing a selector, binding, generated commitment or action. The required 1,024-legacy-history migration test remains unchanged. Unresolved or unsupported legacy evidence stays active.

For a generation-bearing successful record created by the earlier unbound Build 1 implementation, permit exactly one narrow upgrade: read the directly computed existing context pointer and require that it already references this exact UUID and has the exact validated success/result/context digests. That existing immutable commitment can seed the identical exclusive UUID binding. Capture/recheck pointer, primary and result observations under short CAS and retain all bytes. A mismatched pointer is never overwritten. This upgrade cannot mint a binding from a missing pointer, a different UUID's pointer, a newly computed empty context or a result alone.

A superseded or context-substituted unbound generated success lacking its own exact context pointer is indistinguishable from unbound corruption without a history scan or previously absent authority. It therefore stays protected and receives an explicit `transaction_binding_unavailable` local diagnostic; no history scan or guessed binding is authorized. The generation-bearing transaction store is introduced by this unreleased Build 1 slice, so this limitation concerns pre-binding development/acceptance journals rather than an asserted shipped-format migration. Do not claim arbitrary unbound generated journals can all retire. If an operator's 1,024 protected entries hit capacity, allocation remains honestly unavailable until a separately authorized evidence recovery is designed; this change neither deletes evidence nor claims healthy legacy retirement solved that unsupported case.

Newly created healthy generated work has binding-before-success ordering, so completed history can retire indefinitely up to actual disk capacity. The active cap still counts every unresolved/corrupt/unbound-protected entry. This does not restore the rejected lifetime cap on healthy supported operation. Exact pointer-based upgrade is read-through for at most the active UUID/direct prior pointer already being processed, never a sweep of archived UUIDs or context directories.

## Required tests and ownership

1. Expand the immutable substitution matrix to run maintenance after each individual alteration of UUID, actual generation, original timestamps, target/key/revision/artifact hash, candidate/feed digest, signer, committed bit, result SHA-256 and original successful event. Assert original binding/pointer/result bytes remain unchanged, no relocated pointer appears, active membership remains, and original-authority adoption fails. Include signer/feed changes that intentionally hash to a nonexistent context path.
2. Successful evaluation with unresolved cleanup → binding → pointer → supported cleanup → restart → adoption and retirement. Binding, immutable commitment, original event and result stay byte-identical. Repeat cleanup crash boundaries and fresh queued successor regression.
3. Actual subprocess exits before binding, after binding fsync, after successful primary fsync, after pointer fsync and before/after retirement CAS. Recovery must append only the stored exact terminal event when pending, preserve its warning/sequence/timestamp, and never manufacture success from a binding without matching preterminal/result evidence. Race status/cancel/heartbeat against the live bundle and pending-binding recovery.
4. Binding corruption, absence after original success, hardlink/symlink/foreign mode, inode replacement, oversized/duplicate/unknown JSON, mismatched original/result, and same-size in-place changes all fail closed. A missing binding may not be regenerated through indexing or retirement. No artifact bytes or historical files are deleted. Owner heartbeat remains available while bulk binding/result validation blocks outside the global lock; lifetime fencing covers both writes in the short bundle.
5. Exact old pointer→UUID-binding upgrade succeeds without changing primary/result/pointer. Old pointer for a different UUID, missing pointer, changed context, or mismatched commitment refuses upgrade and retains membership with the stated diagnostic. Generation-less supported 1,024-record history still retires without creating bindings/generations/actions; new healthy generated histories beyond 1,024 retain all direct bindings and remain allocatable.
6. Allocation-intent and queued-expiry matrices include orphan binding presence: empty-intent recovery never creates an owner or discards the binding. Archived pointer lookup uses the retained UUID binding read-only, with no active membership or owner recreation and no history enumeration.

Retention owner owns binding schema/storage, index/retirement/archived validation and scoped tests. CLI owner owns binding-before-terminal and exact pending-terminal recovery, writer guards, lifetime fence/terminal acknowledgment and emission order. Both use one shared binding helper and the existing pure result/commitment validation cores; no duplicated authority checks. Root owns combined code/security/architecture review and full test/physical evidence. This proposal is a material persistence addition and requires its own independent gate before any source implementation.
