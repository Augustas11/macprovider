# Immutable retirement binding r3 — plan and tests

Status: proposed; no binding/origin implementation until independent zero-C/H/M approval. This supersedes r2, preserves its resolutions of BIND-ARCH-M1/M2/M3, and addresses BIND2-ARCH-M1/M2. It preserves retention r4, lock-budget r2, actual operation generations, the 1,024 unresolved cap, immutable history, and the existing trust/paid-authority boundary. New persistence described here is an explicit proposal, not an already implemented feature.

## Correction and scope

A context pointer alone cannot prevent retirement after a substituted signer/feed digest selects a new context filename. Bind the original success directly by UUID before terminal publication. The contract also freezes the exact terminal cleanup delta, removes the old-pointer upgrade entirely, and records UUID origin independently of the mutable primary. Origin classification must survive retirement. Neither a missing binding nor removing generation/schema from a primary makes it legacy.

No pre-binding successful generated record is automatically upgraded, even with its own matching pointer. Neither that pointer nor the final primary retains exact historical preterminal bytes. Such records remain protected with `transaction_binding_unavailable`; no preterminal hash is guessed and no historical provenance variant enters pending replay. This explicitly limits compatibility with earlier, unreleased Build 1 development journals. Supported generation-less legacy retirement and indefinitely repeatable healthy new allocations up to disk capacity remain required.

## Closed immutable records and cross-links

All new records use canonical sorted-key JSON, reject duplicate/unknown keys, contain no paths, and use the existing descriptor-relative private/single-link/no-follow/ACL and receipt rules. The three per-UUID records below have a maximum size of 16 KiB each. The separately specified bounded migration source/progress controls have their own explicit limits. Files are exclusive, fsynced, retained forever, and never repaired by replacement or deletion. Exact matching already-published bytes support idempotence; mismatching bytes protect the UUID.

1. `<uuid>.origin`, schema `model_catalog_transaction_origin.v1`, has an exhaustive provenance discriminator:
   - `allocated`: canonical UUID, original actual operation generation, kind, createdAt, target, modelKey, revision, artifact SHA, candidate/feed digests, signerKeyID, and SHA-256 of exact initial queued primary bytes. All fields come from the pre-encoded allocation, not subsequent reconstruction of authority.
   - `legacy_snapshot`: canonical UUID and SHA-256 of the exact supported generation-less original primary at migration. This is a read-only legacy baseline, never a generation, selector, generated success commitment or permission to run/repair it. Only the already-approved fully validated resolved generation-less format qualifies. Its original bytes cannot subsequently change and remain eligible under this baseline.
   - `protected_snapshot`: canonical UUID and exact observed primary SHA when available, recording preexisting generated, unsupported, unresolved or ambiguous evidence. This variant never becomes allocated/legacy automatically and never grants mutation/adoption/retirement authority. A corrupt body can be recorded by exact bounded-byte digest without declaring it valid; unsafe or unreadable evidence stays protected without a fabricated digest.
2. `<uuid>.success-binding`, schema `model_catalog_evaluation_success_binding.v2`: canonical UUID, actual evaluation generation, exact origin SHA, existing r4 context digest, existing r4 immutable success-commitment digest, result SHA, exact preterminal primary SHA, exact prospective successful terminal event, a closed `terminalDelta` containing only `cleanupRequired: Bool`, and SHA-256 of the canonically encoded complete prospective terminal primary. It has no historical-upgrade variant.
3. `<uuid>.retired`, schema `model_catalog_transaction_retirement.v1`: canonical UUID, exact origin SHA and one of the five closed outcome variants defined below. It records the exact validated retirement decision, contains no timestamp-based authority, survives active-index removal, and is neither an action nor permission to mutate an archived original. There is no undefined generic terminal-commitment value.

The active index gains a versioned origin reference for each UUID: exact origin SHA and provenance, plus an optional expected success-binding SHA once that immutable file has been committed. Allocation-phase entries can carry the prospective origin SHA before its file exists. New context pointers additionally cross-link origin and binding SHA under an explicit new closed pointer schema; old pointers remain historical evidence and cannot seed a binding. The r4 success commitment itself is unchanged, including exclusion of mutable cleanup bookkeeping.

## Write-ahead migration decisions and progress (BIND2-ARCH-M1)

Migration never derives provenance from creation time, a guessed release epoch, directory order or a rewritten primary. It examines only the bounded existing active-index membership. Previously archived files are never enumerated. With no old index, retain the approved one-time root inventory limit of 8,192 names and at most 1,024 candidate UUIDs. Persist the actual canonical sorted UUID/phase list, not just an inventory digest, before any origin is published.

A private `.binding-migration` control directory contains two closed JSON files. Its source snapshot is immutable; its progress file is replaced atomically with fsync under exact metadata/generation CAS. The progress file is authoritative decision state, not the non-authoritative maintenance cursor.

- `source.json` (maximum 256 KiB): schema, migration identity UUID (not an operation generation), source kind `active_index_v2` or `initial_inventory`, exact source-index SHA/generation where present, initial inventory digest where applicable, and the complete unique ordered list of canonical UUIDs with original phases. A frozen set cannot gain, lose, reorder or rephase entries during migration. Root binding remains supplied by the existing store context/descriptor, not stored path authority.
- `progress.json` (maximum 1 MiB): schema, source-file SHA, migration identity, monotonically increasing progress generation, phase `classifying`, `finalizing` or `complete`, exact next position in that source list, compact acknowledged entries, and at most one pending decision. Acknowledged entries contain UUID, original phase, frozen provenance, exact origin SHA, and the source-primary SHA when that decision had readable bytes. The pending decision contains the complete canonical proposed origin bytes (bounded by 16 KiB), their SHA, frozen provenance, exact source-primary SHA or explicit unreadable/unsafe classification, and required sidecar presence/absence plus byte digests supporting the decision. It also records source-list position and UUID. An unsafe/unreadable source can only authorize a protected entry; it cannot authorize legacy retirement. The total file stays below 1 MiB for 1,024 entries. `finalizing`/`complete` additionally contain the exact canonical intended initial new-index SHA, generation and source/migration link. Mutually incompatible state fields, duplicate IDs, gaps and out-of-range positions are invalid.

Create and fsync source plus initial empty-prefix/classifying progress in `.binding-migration.init` under the existing nonblocking bootstrap lock, then fsync and atomically rename that whole prepared directory into place after unchanged old-index/root metadata CAS. No per-UUID origin may be written before this publication. All supported callers require completed migration before ordinary allocation/projection/mutation/retirement; an init or prepared directory causes bounded migration/retry, never continued old-format writes. A surviving init directory can only be published after validation of its exact frozen source and empty decision state; it cannot be discarded and silently rebaseline an already published decision. Any ambiguous init/prepared combination fails closed. No old binary may concurrently mutate this upgraded journal.

For each source UUID, use these exhaustive states and durability boundaries:

1. **Unclassified:** position equals the next source-list entry and no pending decision exists. Acquire its UUID owner nonblocking for existing-primary classification, capture primary/sidecar evidence outside the global lock and validate existing format rules. Pre-encode the exact origin and pending decision outside the lock. Under short source/progress generation and file-metadata CAS, fsync the progress file containing that decision BEFORE writing the origin. Classification has now happened exactly once. A crash before this decision write leaves genuinely unclassified work; a crash after it can never return to unclassified work.
2. **Authorized, not acknowledged:** the pending decision exists durably. Validate its exact expected bytes/source link. If origin is absent, publish only those already-stored origin bytes exclusively after revalidating the decision's source evidence and final metadata. If origin exists, require exact pending origin SHA/bytes; a mismatch protects the UUID. Replay may recreate an absent origin only in this explicit pending state from the frozen decision, never by rereading the primary to choose another classification. Changed source evidence blocks rather than reclassifies. Crash after origin fsync but before acknowledgment repeats this exact matching path.
3. **Acknowledged:** after origin file and directory fsync, atomically fsync progress which moves that entry into the acknowledged prefix, removes pending and advances next position. Acknowledgment pins provenance and origin digest. Missing/corrupt acknowledged origin is protected and is never republished by migration. No body of an acknowledged primary is reread to advance the migration prefix or change classification. Later ordinary eligibility validates its exact origin/source baseline and rejects changed evidence.

The UUID owner is retained through the current decision/origin/acknowledgment sequence, subject to the eight-second work budget; after an interruption, resumption acquires the same owner nonblocking. A busy source owner leaves position unchanged and reports retry. Each invocation starts at the authoritative next position, processes at most 1,024 UUIDs, yields per 16 and persists every completed advance. Budget exhaustion cannot repeatedly spend time reclassifying the completed prefix. A process may reread/decode the bounded progress control, but not all completed primary bodies. A pending decision with corrupt/missing source evidence stays pending/protected and does not permit skipping the UUID into another provenance.

Once every source entry is acknowledged, derive the proposed initial new index entirely from the frozen source phases plus exact acknowledged origin/provenance references. Check equal counts, exact ordered membership, no duplicates/omissions, matching original phases and every expected origin reference. These references represent individually fsynced publications acknowledged above; completion does not infer them from current primary bodies. Pre-encode and hash the whole proposed index outside the global lock, then fsync a `finalizing` progress state pinning its exact SHA/generation/source/migration link. No new classification is permitted from this state. Publish/fsync exactly that index under short source/progress CAS, then fsync `complete` progress. Prepared+new-index recovery requires byte SHA equality to the pinned initial index AND full membership/reference/source linkage, not just a compatible schema. It cannot bless a omitted/reclassified entry. Finalization never recreates a missing acknowledged origin: eligibility for that UUID will remain unavailable with its active slot retained. An optional presence check may report that condition sooner but may not repair it or rewrite the planned set.

Missing/corrupt progress after `.binding-migration` publication is a hard migration-unavailable state, not permission to restart baselining. Source mismatch likewise fails closed. Complete+old-format index rejects downgrade. Normal new-index mutations begin only after complete, preserve source/migration lineage, and increment the existing index generation; the pinned initial-index SHA is a completion proof, not a requirement that every later index remain byte-identical. Retain source/progress evidence after completion. Initialized operations never scan archived UUIDs or replay migration to repair missing origin files.

For legacy eligibility, validate the entire supported resolved generation-less original format and required terminal/result/seal evidence. Reject conflicting generated evidence in events, cleanup streams, binding, origin or retirement sidecars. Only that explicitly supported format gets `legacy_snapshot`; every generation-bearing record, even queued or with a valid old pointer, is `protected_snapshot`. Inconsistent/ambiguous missing-generation evidence is protected. The exact baseline preserves validated preexisting legacy bytes; it cannot authenticate a perfectly forged historical state before any retained authority existed and makes no such forensic claim. After the write-ahead decision, changed primary bytes can never establish new legacy provenance. Supported legacy originals are read-only, so legitimate cleanup requiring primary rewrite must have completed before legacy qualification; unresolved legacy remains protected under the inherited contract.

Existing archived UUIDs lacking origin/retirement proof retain only their earlier generic read-only historical diagnostics. Direct lookup cannot start migration for them or mint binding, generation-scoped adoption, cleanup/start authority or retirement certification. This preserves archived no-scan behavior without guessing a release boundary.

## Allocation and origin crash ordering

Pre-encode the exact queued primary, allocated origin, allocating index and active index outside the journal lock. The allocating entry pins the prospective origin SHA. Under one continuous short journal lock and owner-lifetime fence, publish: allocating intent → queued primary → exclusive origin → active index. Each arrow follows file and directory fsync. All new sidecars join the UUID's required-absence set. Allocation recovery creates no owner inode and never removes evidence to make absence true.

- Intent only: primary/origin/binding/retirement/result/seal/cleanup/staging/owner all absent permits removal of the same unexposed intent after exact index/absence CAS.
- Primary but no origin: only exact untouched queued primary, no other sidecar/owner, and an origin deterministically derived from those exact bytes whose hash equals the intent's already-persisted expected origin SHA permits publishing that exact origin and activating. The index precommit supplies the missing authority; arbitrary queued bytes cannot seed origin.
- Origin present before active: require exact intent-pinned origin, exact initial primary SHA/tuple, and other required absences before activation.
- Any conflicting or unsafe evidence protects the allocating slot. Missing required origin in an active entry is corruption, never allocation recovery or migration.

Queued reuse and expiration validate allocated origin and binding/retirement absence before acting. A removed generation or changed target cannot reach the legacy path. Every generated mutation validates the original allocated authority plus current exact selector/receipt; cleanup's fresh operation generation does not rewrite the original origin.

## Exact pending terminal publication and replay (M1)

The evaluation owner remains held. After supported result commitment and actual cleanup attempt, capture exact nonterminal primary bytes and result observations. Outside the global lock, construct the prospective primary by applying exactly two changes: assign the frozen terminalDelta.cleanupRequired and append the stored successful terminal event through the existing append semantics (state is derived from the last event; do not add a state or updatedAt primary field). No other field changes are permitted. Canonically encode it and record its SHA. The event contains its actual generation, sequence, timestamp, warning and outcome. The primary retains its original committed result fields.

In a short bundle, validate the active allocated origin/index receipt, exact result/preterminal observations, binding absence and lifetime fence; then publish/fsync exclusive binding, publish/fsync the active index's expected binding SHA, and publish/fsync the exact pre-encoded successful primary. Recheck budget/fence immediately before each mutation. This changes the earlier terminal-first ordering explicitly. Once binding publication succeeds, no subsequent error may produce a different failed/cancelled terminal. Keep pending truth and let exact recovery finish; restoration success is never inferred from binding or owner exit.

Every writer checks direct origin and binding before heartbeat/cancel/failure/progress append or owner restart. A present pending binding must reconcile first, not be overwritten by new status bookkeeping. Live publication holds the global lock throughout; after crash, owner-scoped recovery validates binding/result/preterminal outside the lock. If index binding reference is absent solely because crash occurred between binding and that reference, require the exact still-nonterminal preterminal SHA, allocated-origin cross-link, committed result, and deterministic prospective primary SHA before pinning the already-existing binding. A successful primary with no expected binding reference is impossible under the supported order and is protected; a missing binding with an expected reference is never regenerated.

Recovery reconstructs the exact whole prospective primary using the stored event AND terminal delta and requires its canonical SHA to equal the binding. It then uses short exact selector/index/metadata CAS and lifetime fence to persist those same bytes. It never recomputes staging outcome, timestamp or warning. False→true cleanup failure and true→false cleanup resolution must recover the same normal terminal bytes. Once the original successful primary is durable, later authorized cleanup may change its existing mutable bookkeeping; ongoing validation uses the unchanged r4 success commitment, not the prospective full-primary SHA. That SHA authorizes only the pending terminal reconstruction.

## Indexing, retirement and archive eligibility

Dispatch origin/binding/retirement evidence before considering current primary state, generation or pointer context. Active index provenance/digests are authoritative expectations. A stored binding or expected binding cannot be bypassed by changing success to failed/cancelled or removing generation/schema. Validate direct UUID origin/binding and all immutable fields before deriving a context filename, publishing a pointer, expiring or removing membership. A mismatch protects the UUID even when a new context filename would be empty.

After terminal fsync, index outside the global lock while retaining the current owner. Current/previous pointer validation captures direct origins, bindings, records/results and existing retirement certificate for an archived prior target. Previous targets remain read-only: no previous-owner creation/acquisition and no active-membership reconstruction. Final pointer CAS rechecks pinned metadata and lifetime fence; corrupt old pointers are never generically overwritten. A healthy old pointer that cannot meet the new binding contract reports explicit unavailable, not fabricated upgrade.

Retirement first fully validates and pre-encodes its immutable certificate outside the lock. Under short owner/index/metadata CAS, publish/fsync certificate only after required successful pointer publication, then remove membership. Crash after certificate but before removal leaves the entry active; only exact matching certificate plus unchanged validated evidence permits finishing removal. Existing mismatched certificates protect membership. A certificate is not permission to change terminal truth or delete any file.

After membership removal, direct UUID eligibility is determined by retained origin + retirement certificate, and successful generated evaluation also requires binding + result + exact immutable commitment. No active entry is created or needed. The certificate pins the origin and binding after their index expectations disappear. Deleting origin/binding/certificate or downgrading primary/origin classification makes archived generated eligibility unavailable; no lookup regenerates a missing file. Generic historical reads are explicitly weaker read-only diagnostics and never promote to action or binding authority. They must not label incomplete/corrupt archived evidence as generation-scoped eligible. New allocated generated work cannot enter legacy dispatch merely because its primary was rewritten. Legacy certificates retain exact primary bytes and never yield generated actions.

## Closed retirement outcome snapshots (BIND2-ARCH-M2)

The certificate is canonical closed JSON with schema, transactionID, originSHA256 and exactly one outcome discriminator below. Every generated variant checks allocated-origin authority against the current original before recording anything. These are historical retirement proofs; none substitutes for current artifact verification, current qualified-feed authority or adoption validation. All original events, timestamps, cancellation/attempt bookkeeping and sidecars remain untouched.

For non-adoption outcomes, use the exact primary bytes at retirement, not a newly invented generic immutable commitment. Freeze only after the original is supported terminal, cleanupRequired is false, owned staging is absent, and the current cleanup stream is absent or supported terminal. These conditions are checked outside-lock plus final metadata/absence CAS under the original owner. Once certificate publication succeeds, ALL primary/current-cleanup mutations for this UUID are forbidden, including while it is still active awaiting membership removal. All writer/reservation/reconciliation paths inspect a present retirement certificate before mutation. No later cleanup reservation is authorized for a certified resolved original. Unexpected staging reappearance or changed evidence protects the entry; certification does not authorize deletion.

Define the closed `retirementSnapshot` value as: exact primarySHA256; result evidence `absent` or `present {sha256}`; seal evidence `absent` or `present {sha256}`; current-cleanup evidence `absent` or `present {sha256, operationGeneration, terminalState}` for generated streams. A present cleanup stream must validate the same transaction UUID, original target/model/artifact authority, kind cleanup_staging and exact actual cleanup generation under existing stream rules. Its terminalState is one of succeeded/failed/cancelled/timed_out; original cleanupRequired false and actual staging absence remain mandatory regardless of that terminal label. The exact stream SHA freezes all its events, flags and timestamps. Legacy cleanup uses a separate `legacy_present {sha256, terminalState}` arm only where the existing supported legacy validator permits absent generation; it never fabricates one. Prior retained cleanup-generation sidecars are not enumerated or rewritten; their continued direct historical reads retain existing validation. The snapshot concerns the exact current stream used in the retirement decision.

`absent` requires both the primary's corresponding digest field to be nil and the sidecar to be absent. `present` requires the exact primary digest and sidecar SHA to agree AND the existing pure result/seal validator to pass. Presence is never inferred from a nonnil digest without bytes. Unknown/orphan/mismatched sidecars block retirement; they are not silently omitted from a snapshot.

- **`evaluation_success`:** actual evaluation generation, exact binding SHA, context digest, existing r4 success-commitment SHA and result SHA, plus the resolved current-cleanup evidence arm. Require evaluate_model, committed true, valid required result, allocated origin and expected binding reference, original successful event and unchanged r4 commitment; seal evidence must be absent for this kind. Required pointer publication precedes this certificate. Use the r4 commitment, not whole-primary SHA, as the successful immutable authority so legitimate pre-certificate cleanup does not invalidate binding/pointer. After certification, ordinary active/archived read validation still requires resolved cleanup/staging and rejects any attempted further mutation. No certificate bypasses missing binding or stale current adoption authority.
- **`prepare_success_snapshot`:** actual original generation and retirementSnapshot. Require prepare_model with original succeeded terminal, startedAt present, committed true, result absent, and valid required preparation seal present. The snapshot binds ALL original fields/events through exact primarySHA, including committed/publication evidence. A failed or intent-only prepare cannot enter this arm. This proves historical preparation evidence only, never that current artifact bytes remain available or ready.
- **`prepare_non_success_snapshot`:** actual original generation, terminalState exactly failed/cancelled/timed_out, and retirementSnapshot. Require prepare_model and matching original last event. Result must be absent. Seal is absent when committed is false and its digest nil; a committed preparation requires its valid seal present under the existing validator. Thus a supported post-commit failure retains its historical seal without claiming succeeded. An uncommitted orphan seal/digest is protected, not certified as successful publication. A queued reservation expired through the approved timed_out event may have startedAt nil; the exact primary snapshot preserves that fact.
- **`evaluation_non_success_snapshot`:** actual original generation, terminalState exactly failed/cancelled/timed_out, and retirementSnapshot. Require evaluate_model and matching original last event. Seal must be absent. Result is absent with committed false and digest nil, or present with committed true and exact pure-validator success. This arm does not promote a valid retained result into successful evaluation or adoption. A present/expected success-binding is inspected first and requires exact success recovery/validation; it cannot be bypassed into this arm by a rewritten terminal state. Unsupported committed-without-result and orphan result combinations remain protected.
- **`legacy_terminal_snapshot`:** terminalState exactly succeeded/failed/cancelled/timed_out, original kind prepare_model/evaluate_model, and retirementSnapshot using only legacy-compatible cleanup evidence. Require `legacy_snapshot` origin and exact unchanged primary SHA equal to that baseline, absent operation generation, and existing supported legacy terminal/result/seal validation. Evaluation success still requires its supported retained result. No generated success commitment, selector, pointer or action is created. Do not impose a new generated-seal requirement on previously supported legacy prepare success; optional/required evidence follows the existing explicit legacy validator, and every present supported sidecar is pinned in the snapshot.

No top-level original cleanup_staging transaction is allocated or retired by these variants; cleanup is the existing side stream on its original UUID. Unknown kinds/outcomes are protected. Each snapshot arm's primary SHA binds its complete exact event history, createdAt/startedAt, generation, kind, target/key/revision/hash/candidate/feed/signer, committed/result/seal digests, cancelRequested, cleanupRequired and attemptStartSequence without omitting mutable fields by accident. Snapshot capture occurs after their last authorized mutation, avoiding a conflict with earlier legitimate cleanup.

Before certificate→membership removal and during direct archived validation, reload/validate the same closed variant and evidence, verify exact primary/snapshot digests (or r4 success commitment for evaluation_success), origin and sidecar expectations, and reject every changed/missing required proof. No primary or sidecar is rewritten to make a certificate match. No owner or active entry is created for archived diagnostics. A certificate with active membership can only complete its exact validated removal; it cannot grant new mutation. Immutable certificate loss after retirement makes eligibility unavailable. Generic read-only diagnostic bytes remain distinguishable from validated certified outcomes.

## Capacity, file safety and failure policy

Count every unresolved, corrupt, migrating and protected UUID against the same 1,024 active limit. Healthy new histories retire repeatedly without history enumeration or lifetime count. A full protected pre-binding development journal honestly remains unavailable; no deletion, quarantine-as-recovery or guessed migration frees slots. Every origin/binding/certificate observation joins receipt metadata CAS, allocation absence checks and bounded recognized filename rules. Reject hardlinks, symlinks, unsafe ACLs/modes/owners, duplicate/unknown JSON, oversized bytes and changed placement/content. Never chmod, overwrite or erase evidence to repair eligibility.

Retain the lock-budget r2 rules across all new seams: eight-second bounded work, current-UUID owner only, bulk reads/hash/encode outside the global lock, constant metadata/mutation bundles, exact index generation CAS, independent owner heartbeat/exit fence, and sanitized unavailable outcomes. New control-file durability steps must be included in actual process-death/fence tests. Healthy filesystem timing is tested; stalled kernel calls still rely on the existing independent command/owner lifecycle behavior.
