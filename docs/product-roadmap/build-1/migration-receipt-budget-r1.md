# Migration receipt and budget correction r1

Author proposal only. Runtime implementation is blocked until independent review reports zero Critical, High and Medium findings. This refines the approved immutable-retirement-binding-r3 and retention-lock-budget-r2 implementation without changing their schemas, authority, crash ordering, 1,024 unresolved limit, immutable archive, or eight-second operation budget.

## Observed failure and call graph

Root-coordinated Swift29 (`/tmp/build1-joint-swift29.log`) completed the retention selection with 27 methods, two failures, in 275.492 seconds. The mixed history test passed in 76.142 seconds. The supported legacy 1,024-record test failed in 164.981 seconds: after three deliberately exhausted migration budgets and sixteen additional bounded passes, its assertion still observed 1,024 active records. Its subsequent allocation and direct per-UUID history reads did not produce another error. This is evidence of insufficient finite progress in that fixture, not proof that migration lost evidence. The full owner selection was still running when this proposal was written; Swift29 is not acceptance.

`ModelCatalogTransactionMigration.swift:247–257` currently rereads and closed-decodes the complete source, progress and active index for every decision and acknowledgment, then validates the entire source/prefix again. The bootstrap lock is already retained throughout the bounded call. The work grows quadratically with the prefix despite the per-call deadline. `requireBindingMigrationCompleteLocked` at lines 155–164 rereads/decodes up to 1 MiB of progress plus 256 KiB of source, hashes source and validates all entries under the global journal lock. `snapshotIndex` (`ModelCatalogTransactionRetention.swift:203`) calls this for each retirement/index observation; `retireOne` obtains multiple snapshots. This violates the approved placement rule allowing only bounded active-index/format decoding and metadata mutations under that lock. The final `load(id:target:)` (`ModelCatalogTransactions.swift:211`) reads only the selected primary; it does not reread migration origins.

The other Swift29 retention failure is a separate one-call full-capacity fixture expectation. Approved lock-budget r2 test 5 explicitly permits repeated bounded passes and cursor wrap; its finite retry correction is not a reason to raise the runtime budget.

## Correction 1: completed migration receipt

Introduce an operation-local, read-only completion receipt containing the existing pinned source/progress file evidence and their validated decoded lineage: exact source SHA, migration UUID, complete phase and intended initial index generation. Capture bounded bytes, hash, closed-decode and validate source/progress entirely outside the global journal lock. Missing, malformed, oversized, unknown/duplicate-key, incomplete, substituted or inconsistent evidence fails closed; no default completion or migration downgrade is inferred.

Inside the global lock, read the existing bounded active index, revalidate the captured source/progress descriptors and placement metadata plus bound journal identity, and compare the index's exact schema/migration UUID/source SHA and allowed generation against the receipt. No source/progress body read, hash or prefix validation occurs there. If either pinned file changes, reject the receipt; do not silently recapture different authority during a mutation.

`snapshotIndex` accepts an optional already-captured completion receipt. A standalone call captures its own receipt outside the lock. One bounded maintenance pass captures one receipt and threads it through its repeated snapshots and retirement calls; each locked use rechecks metadata and lineage. The receipt cannot outlive the operation or be stored in a global/process cache. It retains descriptors, so deletion/replacement/in-place changes remain detectable. There is no additional disk certificate or schema. Initialization's already-complete and resumed-complete paths use the same read-only receipt discipline. The ordinary bootstrap/classification path still requires the existing bootstrap lock.

## Correction 2: retain validated migration state within one call

After acquiring the existing nonblocking bootstrap lock, capture and fully validate the exact source, initial progress and index once outside the global lock. Retain their decoded values and pinned evidence for this bounded call. The source and initial index remain immutable until the existing final publication; every mutation rechecks their descriptor/placement metadata. Every restart or new call performs the full durable source/progress validation again, including exact ordered prefix, pending observations, source binding and intended complete index.

Within the call, mutate only the already-validated in-memory progress using the existing closed transitions: unclassified to durable pending decision; exact pending observations to exclusive origin publication and acknowledgment; complete prefix to finalizing intent; exact intended index then complete progress. Retain the scoped UUID owner across decision/origin/acknowledgment. Never reclassify an existing pending decision or acknowledged prefix. No replacement of missing acknowledged origins, fabricated generation or adoption binding is permitted.

Before each publication, encode the next progress outside the global lock. Inside the lock, revalidate the previous progress, source, index, affected origin and classified per-UUID evidence metadata, then check the operation budget immediately before the existing constant write bundle. After our successful progress publication, capture that new progress file outside the lock and require its exact bytes equal the preencoded bytes before replacing the receipt. Reuse the already-generated decoded value only after that equality check. A changed/missing file or any publication/capture failure ends the call; it does not authorize another write using guessed disk state. The next ordinary call resumes from the durable ledger. No generic automatic retry follows a partially completed bundle.

The finalizing/index/complete sequence and every crash hook remain unchanged. The final index is still byte-bound by the previously fsynced finalizing intent, and the old index or exact intended new index are the only valid recovery observations. After final index publication the function returns following complete progress fsync; it does not reuse the old index receipt for another operation. Budget expiry releases custody on unwind and preserves all partial durable truth.

This removes repeated full-prefix decoding/validation within a call; it does not eliminate the WAL rewrite, durable fsync, exact byte hashing or final metadata checks. It does not claim arbitrary filesystem latency can be bounded by cooperative cancellation; the already-approved owner watchdog/fence remains independently responsible for live owner process limits.
