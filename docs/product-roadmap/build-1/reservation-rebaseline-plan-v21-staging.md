# Build 1 preparation v21 staging-cleanup contract correction

Status: proposed; **implementation gate reopened**. This addendum changes only the staging-cleanup private record and its target derivation. It composes with the approved [v20 plan](reservation-rebaseline-plan-v20.md) (SHA-256 `8045eccb1660e98a8213bbcf41b5a0b26f72970324a7f92bcf3afca152addf57`) and [v20 test specification](reservation-rebaseline-test-spec-v20.md) (SHA-256 `f218249c00586c829a8364971ea3fa2382c789e2f7c78b019c60741a96794c0f`). The v20 gate does not approve the staging cleanup codec at #1491 head `b310e06e`; the storage round-1 review exposed this contradiction.

## Problem and authority boundary

A provider's interrupted preparation attempt owns `work/staging/<preparation-transaction>/<preparation-attempt>/`. A later `cleanup_staging` action has its own cleanup transaction and attempt. The v20 private `model_catalog_cleanup_record.v1` contains only the latter two identifiers yet tries to derive the former's target. Reusing cleanup IDs for the source would target the wrong tree. SPEC-044 requires an attempt-owned recorded target, exact saved root and same-parent reversible tombstone, not a scan or an inferred current action. This is a private, unshipped contract; origin/main has no production preparation writer for it.

## Normative proposed correction

1. `model_catalog_cleanup_record.v2` replaces the draft v1 record for both cleanup kinds. All v1 fields and existing receipt, tuple, immutable event key, root, phase, totals, and digest checks remain required. The decoder rejects v1 at the private cleanup target; no automatic v1 migration or deletion is permitted.
2. For `target_kind: "staging"`, add exactly `source_transaction_id` and `source_attempt_id`, each a canonical lowercase UUIDv4, both present and non-null. These identify the interrupted preparation attempt. `transaction_id` and `attempt_id` remain the distinct cleanup operation's identifiers. Equality between a source ID and a cleanup ID is allowed by coincidence but never used as derivation authority. For `target_kind: "published"`, both source fields are absent; explicit nulls are rejected. The branch-specific key sets are closed.
3. The staging final relative path is exactly `work/staging/<source_transaction_id>/<source_attempt_id>/`. The staging tombstone relative path is exactly `work/staging/<source_transaction_id>/.tombstone-<cleanup-transaction_id>/`. These stored `final_leaf`/`tombstone_leaf` strings are canonical root-relative paths despite their historical field names. Both resolved leaves are immediate children of the same descriptor-verified `work/staging/<source_transaction_id>` parent. Their exact path bytes, saved root locator and identity, source pair, cleanup pair, tuple, event key, receipt, and expected totals are validated before any rename, restoration, unlink, or recovery side effect. Cross-parent paths and aliases fail closed.
4. Published v2 remains exactly `objects/<tuple_sha256>/` and `objects/.tombstone-<cleanup-transaction_id>/`, with no source pair. Published and staging records cannot be interpreted as one another. The artifact identity digest remains a separate receipt-derived binding, never the published directory name.
5. The CLI writer records the source pair from the validated interrupted attempt before showing a cleanup action; the direct dispatch revalidates the immutable projected action and source pair under the v20 locks. Worker and restart recovery take the saved root locator from that record, verify `root.identity` on the opened descriptor, and target only the recorded relative paths. A new current config, current active attempt, or other root cannot retarget cleanup. The continuous `cancel.lock` and reversible intent/tombstoned/removed rules in SPEC-044 and v20 remain unchanged.
6. Update the applicable SPEC-044 private cleanup contract before editing the v2 codec. If that SPEC already freezes an incompatible schema or field spelling, resolve it in the SPEC first and rerun this gate. The governed SPEC declaration and consumer tests must reflect the private schema change.

## Delivery, compatibility, and rollback

After this addendum and its companion test specification pass independent adversarial review with zero Critical/High/Medium findings, revise the #1491 codec and focused tests, then the dependent storage reader/writer and worker. Do not advertise v2 CLI preparation until read/run/cancel are executable. A malformed or draft v1 durable cleanup record blocks cleanup but preserves every incumbent, published, staging, and legacy tree; diagnose out of band rather than migrate or delete it automatically. A rollback to code without v2 support must likewise fail closed on v2 records and leave files intact. No network admission, pricing, payout, release, or production activation is authorized by this correction.

Acceptance requires a real staging target whose source IDs differ from cleanup IDs, exact path and same-parent tombstone proof, crash/restart recovery from the saved root, cancellation before/after durable tombstoned phase, and the negative matrix in the [v21 test addendum](reservation-rebaseline-test-spec-v21-staging.md). Physical power-loss and actual settled requests remain later qualification gates. Observability uses bounded typed cleanup failure/phase states without leaking paths or credentials to the public UI.
