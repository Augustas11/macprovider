The source pair/root/tuple/event/projection values must match the already durable source preparation reservation and active attempt; the source record's exact serialized bytes have a SHA-256 recorded below. A crash before this complete barrier cannot have produced staged artifact bytes. The source record itself counts as logical staging metadata when measuring exact cleanup totals.

A staging cleanup action is available only for one incomplete, non-live, unprotected, exact pair whose source record hash, saved root, tuple, event key, and path all validate. For `cleanup_staging`, the closed private `model_catalog_reservation.v4` adds exactly `source_transaction_id`, `source_attempt_id`, and `source_record_sha256`, all bound into `projection_binding_sha256`; those keys are absent for every other kind. The public action/event schemas remain unchanged. Direct dispatch validates the immutable reservation and index entry under the existing lock protocol, opens **that entry's saved root**, and checks the source file at the phase-directed location below. Worker and recovery never use current config, current active attempt, or a scan to choose a root or source. A and B can each remain cleanup-eligible after config changes to C only while their own indexed source, saved root locator/identity, the source reservation/active identity proved at registration (without requiring their later retention), projected reservation, deletion phase, and opened descriptors agree exactly; any differing root in that chain is forbidden. Published cleanup remains barred from a different-root target. Terminal/history compaction may never remove a source registry entry or file; precommit cancellation restores/preserves both.

Source-file lookup follows the **durable cleanup phase and exact recorded leaves**. With `intent`, final present/tombstone absent means open and hash `final_leaf/source.json`; final absent/tombstone present after a crash means open and hash `tombstone_leaf/source.json` before the exact-marker restoration or resume; both present or both absent fails closed. With `tombstoned`, final must be absent and the exact tombstone must exist; open and hash `tombstone_leaf/source.json` before removing remaining contents. Remove that source file last. A crash after its last-file unlink may leave an empty tombstone with no source file: accept that **only** under durable `tombstoned`, exact saved root/record/hash, final absence, descriptor-proven empty tombstone, and no remaining deletion work, then remove the empty tombstone and durably advance to `removed` in one owned recovery pass before success; a crash after tombstone unlink but before durable `removed` leaves both leaves absent under `tombstoned` and must fail closed for diagnosis, even if prior work was legitimate. A missing source beside any remaining content fails closed. With `removed`, both exact leaves and the source file are absent; validate only the durable deletion record's saved root, source pair/hash, tuple/event key, paths, expected totals, and target absence. No phase reopens the old final path by habit or treats a missing source as proof of completion. This phase lookup precedes every mutation and repeats after crash; no counterpart object is deleted because of a current projection.

After durable `removed` and full-synced exact target absence, **while the deletion record still exists**, retire only its exact index entry with a full-synced/readback-validated registry generation, then durably clear the deletion record and commit terminal state. A crash between those barriers leaves `removed` as authority: recovery verifies the record's saved root, exact paths and absence, recorded source hash/tuple/event key, and that this exact index entry is either still present for retirement or already absent, then resumes clear without scanning or touching another tree. A missing entry during `intent` or `tombstoned` fails closed; failed retirement keeps `removed` for retry and never emits success. Successful preparation may retire an entry only after verified publication and proof the corresponding staging tree is absent; interrupted staging retains it until explicit cleanup or operator diagnosis.

## Count admission and publication without a speculative receipt

At pre-network dispatch under the common `operation.lock`/cleanup serialization, bound the verified inventory to 256 with one extra entry only for overflow detection and apply the already required logical budget/free-space/verified signed artifact gates. At count 256, use an existing object **only if** its separately opened, verified prior receipt and signed tuple/root/artifact bindings establish the exact previously published artifact identity and valid leaf; return that object idempotently without network/staging. Same displayed name, tuple SHA alone, or predicted receipt digest is insufficient. If no such exact proof exists, refuse before any network or staging side effect. At count <=255, a prospective **distinct** publication reserves one count slot in durable active state while holding the common operation lock; this reserves capacity, not an unknown artifact leaf/digest. An existing verified identity is idempotent and takes no new slot. At publication, recheck feed/guidance/root/cancel/physical space/logical budget and inventory under the retained locks, construct and durably verify the final receipt from completed verified bytes, compute `receipt_sha256`, then compute SPEC's `artifact_identity_digest`, choose only `objects/<artifact_identity_digest>`, and exclusively rename the exact unpublished tree. If the final digest resolves to a previously verified identical object, prove byte-for-byte receipt and tuple equivalence and use the existing object without overwrite; any discrepancy fails closed. A new object may become only the 256th; an externally consumed slot, malformed inventory, conflicting final leaf, or 257th observation fails before rename. Preserve the v20 bottom-up file/parent full-sync, publish-ready, exclusive rename, destination-parent full-sync, terminal and crash-recovery barriers. A physical post-crash published object is accepted only by verifying its receipt and SPEC digest against the opened leaf; no tuple-named fallback or automatic repair.
