## Authority and explicit overrides

Landed SPEC-044 v0.2.8 defines `artifact_identity_digest` as a domain-separated, length-prefixed SHA-256 over display model ID, model revision, artifact ID, release ID, root identity digest, and **publication receipt SHA-256**, and mandates that this digest is the managed published-object leaf (R002). It also mandates an exact attempt-owned staging cleanup target, bounded object-count admission before network/staging, and reversible same-parent cleanup with durable readback-validated `tombstoned` as sole cleanup commit evidence. These already govern this correction. The private record/index spelling proposed here is an implementation contract; if operator review finds any normative conflict or requires private spelling to be normative, amend and govern SPEC-044 **before** changing the codec, rerun this plan gate, and do not invent authority in code. No SPEC or production-network change is authorized by this document.

This v22 text supersedes v20's `objects/<tuple-sha256>` layout, its publication/count/idempotence statements to the extent they imply an artifact-identity digest exists before a receipt, its five-kind private-state inventory and corresponding temp cap, and any v20 deletion example that derives a published leaf from `tuple_sha256`. It supersedes v21's published `objects/<tuple_sha256>` path and its assertion that **all** receipt/artifact-digest checks apply to staging. Both v20 and v21's attempt-owned staging parent, cancellation, root/ACL, atomic envelope, byte budget, and fail-closed principles remain. `tuple_sha256` is a separate recomputed private tuple/reservation binding; it is never the published leaf or a substitute for the SPEC digest. The current unshipped storage draft at `phase3-binary/Sources/macprovider-cli/ModelPreparationContracts.swift` has `model_catalog_cleanup_record.v1`, a required receipt on both target kinds, staging leaves derived from cleanup `attempt_id`, and a stdout acknowledgement type that cannot serve as a durable cancel marker; these are implementation defects, not precedent. No existing production writer is presumed from this draft.

## Distinct closed cleanup records and exact paths

The proposed private `model_catalog_cleanup_record.v2` has one shared closed portion: `schema`, `target_kind`, `phase`, cleanup `transaction_id`, cleanup `attempt_id`, `event_model_key`, complete saved `root` locator/identity, `tuple`, recomputed `tuple_sha256`, root-relative `final_leaf` and `tombstone_leaf`, and checked exact logical `expected_bytes` and `expected_files`. Its two closed variants have **different required keys**; missing, extra, explicit null for an absent-branch key, or cross-kind reinterpretation is invalid. Both retain the existing bounded private envelope, generation/readback, descriptor, ACL, single-root, record-cap, and phase rules. `final_leaf` and `tombstone_leaf` retain their historical field names but hold canonical root-relative paths, not arbitrary filesystem paths.

| `target_kind` | Additional required fields | Exact relative final and tombstone paths |
|---|---|---|
| `staging` | `source_transaction_id`, `source_attempt_id`, `source_record_sha256`; **no** `receipt`, `receipt_sha256`, or `artifact_identity_digest` keys | `work/staging/<source_transaction_id>/<source_attempt_id>` and `work/staging/<source_transaction_id>/.tombstone-<cleanup-transaction_id>` |
| `published` | complete verified `receipt`, recomputed `receipt_sha256`, recomputed `artifact_identity_digest`; **no** source pair or source-record digest keys | `objects/<artifact_identity_digest>` and `objects/.tombstone-<cleanup-transaction_id>` |

All IDs are canonical lowercase UUIDv4. The cleanup pair identifies the cleanup operation; the source pair identifies the earlier interrupted preparation. Neither pair is derived from the other, even when bytes coincide. Resolve both leaves as immediate children of the **same opened, identity-validated parent descriptor**, using exact component bytes and no symlinks, hard links, ACLs, mount crossings, aliases, or traversal. The tombstone name is reserved exclusively and cannot collide with any live intent; retries use the same record/leaf and cannot create a second tombstone. A published receipt must bind the saved tuple, immutable historical event key and root; independently recompute receipt SHA and SPEC's artifact identity digest from exact validated bytes, compare to recorded digest and opened published leaf, and validate immutable inventory/action/keep-set bindings before a destructive operation. An incomplete staging attempt has no publication receipt and cannot be made to pass published validation by fabricated/null receipt fields. Its action's public v2 `artifact_identity_digest` stays null.

## Durable staging source provenance and discovery

Before the first **transfer or staged artifact payload byte**, the preparation worker under `operation.lock` atomically creates the owner-only attempt parent and a closed `model_catalog_staging_source.v1` file at exactly `work/staging/<source_transaction_id>/<source_attempt_id>/source.json`. The descriptor-relative file is created unpublished with empty ACL before its first sensitive byte; it is fully synced, parent-full-synced, reopened and readback-validated before work. Its closed fields are `schema`, `source_transaction_id`, `source_attempt_id`, saved complete `root`, complete immutable `tuple`, recomputed `tuple_sha256`, immutable `event_model_key`, `projection_binding_sha256`, and exact root-relative `staging_leaf`. It carries no receipt, publication digest, URL, credential, feed body, or claim of current download/admission authority. The source pair/root/tuple/event/projection values must match the already durable source preparation reservation and active attempt; the source record's exact serialized bytes have a SHA-256 recorded below. A crash before this complete barrier cannot have produced staged artifact bytes. The source record itself counts as logical staging metadata when measuring exact cleanup totals.

Add one private, bounded `staging-sources.json` registry at the authority-state root, with a closed `model_catalog_staging_sources.v1` payload containing exactly `schema` and sorted unique `entries`—**no registry-wide root**. Each entry has exactly `source_transaction_id`, `source_attempt_id`, the complete saved `root` locator/identity object, and `source_record_sha256`, and points only to that pair's exact relative file under **that entry's** root. The entry root must equal the source record's, original source reservation/active record's, projected cleanup reservation's, and deletion record's saved root; identical pairs with different roots are a conflict, not a deduplication opportunity. Thus A and B roots may coexist without current-config substitution. Maximum 256 entries and a 262144-byte inner payload; both entry count and byte cap are independent limits. Reject a prospective entry that would exceed either cap before network or staged payload bytes, even with fewer than 256 entries or long escaped root paths; read at most 257 entries to detect count overflow and fail closed without truncation or a cleanup action. The common envelope remains capped at 360000 bytes, so an encoded candidate that would exceed that cap also refuses before side effects. Publish its generation-checked, full-synced, readback-validated envelope after the source file and before the first transfer/staged payload byte. Never invent an entry by scanning `work/staging`, a current config, current active attempt, or a compacted terminal history. Crash between the source-file barrier and registry barrier is pre-payload: recover only through the still-durable exact active attempt, finish the indexed publication if valid, or preserve the empty source attempt for out-of-band diagnosis. Missing, inconsistent, full, overfull, or malformed registry blocks new staging before network and all affected cleanup projections; unrelated serving remains intact.

The replaceable private-state map now has **seven** exact `(record_kind, target_leaf, inner-payload cap)` pairs: (`reservations`, `reservations.json`, 262144); (`active`, `active.json`, 65536); (`cancel`, `cancel.json`, 4096); (`published_inventory`, `published-inventory.json`, 262144); (`deletion`, `deletion.json`, 32768); (`staging_sources`, `staging-sources.json`, 262144); and (`failed_dispatch_pending`, `failed-dispatch-pending.json`, 16384). Every target uses the v20 closed `model_catalog_private_state_envelope.v1` and 360000-byte outer cap, exact kind/target agreement, generation/readback, and byte-identical unique-temp rename protocol. The new pending target is required by SPEC-044's independently durable failed-dispatch pending publication and copy-before-unlink; it cannot be represented solely by a reservations snapshot. `state-tmp` recovery recognizes at most four temps per kind and **28 total**, with exact filename/UUID/kind/target agreement; a 29th recognized entry or fifth of one kind is not decoded/promoted. Unknown kinds, extras, checksum-valid semantic mismatches, and wrong target/payload shape fail closed. The source file is an immutable per-attempt descriptor-validated record outside these seven replaceable targets. `root.identity` remains its separate raw bootstrap protocol.

Recovery opens `state-tmp` by descriptor under `operation.lock` and streams at most **29 names plus one EOF/non-EOF probe per invocation**, retaining only bounded names/descriptors; it never materializes or lexically sorts an unbounded directory. In observed stream order, at most 28 total/four per kind can enter normal complete-envelope decoding. **No temp is promoted unless EOF is proven, every observed sibling is safe, the directory descriptor remains stable, and all within-cap validation succeeds.** If the probe finds a 30th sibling, this invocation performs no promotion and makes no claim about unseen entries; it can only reconcile validation of the bounded prefix and remove an exact recognized excess temp as below, then retry from a fresh scan. After bounded reconciliation, every observed excess exact `state-tmp/<target-leaf>.<canonical-lowercase-UUIDv4>.tmp` is an **uncommitted** temp, not a durable target; whether empty or complete, it may be unlinked without decoding/promotion only after descriptor-bound owner, mode, type, link count, device, inode, empty ACL, parent, and exact filename/kind/UUID revalidation immediately before unlink. The rule and outcome for each observed entry are deterministic; no global lexical-minimum claim is possible under bounded streaming. This may discard an interrupted but never committed complete excess write; it never unlinks a durable target or a temp within processing caps. A seen unknown name, unsafe node, descriptor drift, or ambiguous target/kind stops fail-closed without deleting that node. A 29th recognized temp cannot conceal a hostile 30th: no promotion occurs on the non-EOF pass, and later passes remain unavailable until all remaining siblings are examined and EOF proven. Repeated bounded recovery calls may drain ordinary recognized excess; a hostile flood remains bounded in memory, descriptors, and entries examined per invocation and may require operator diagnosis. No excess is silently decoded, promoted, or treated as authoritative.

`reservations.json` has a closed inner `model_catalog_reservations_history.v1` snapshot with exactly `schema`, `projected_reservations`, and `terminal_history`. `projected_reservations` is an array of at most 64 distinct closed `model_catalog_reservation.v4` records, sorted by transaction ID. Each v4 record requires literal `schema: "model_catalog_reservation.v4"` and otherwise retains exactly v3's `transaction_id`, `transaction_kind`, `event_model_key`, complete saved `root`, `tuple`, recomputed `tuple_sha256`, `projection_binding_sha256`, and RFC3339 `created_at`; only `cleanup_staging` additionally requires the source pair and source-record SHA named below, while every other kind forbids them. The v3 decoder rejects the v4 literal or added keys; the v4 decoder rejects a v3 literal even when all common fields match, and rejects v3-tagged records with source keys. Neither version is silently upgraded. `terminal_history` is written and retained in oldest-to-newest insertion order as an array of at most 256 distinct entries, each either the **unchanged exact** SPEC-044 `model_catalog_failed_dispatch.v1` record or a closed `model_catalog_terminal_history.v1` record with exactly `schema`, `transaction_id`, `attempt_id`, `transaction_kind`, `event_model_key`, complete saved `root`, `tuple_sha256`, `projection_binding_sha256`, final positive `event_sequence`, `terminal_state`, nullable `error_code`, RFC3339 `completed_at`, and `live_attempt: false`. The ordinary terminal state is exactly `succeeded`, `cancelled`, `failed`, or `timed_out`; `error_code` is required for `failed`/`timed_out` and null otherwise. Every history entry is bounded to 16384 canonical UTF-8 bytes; the whole snapshot is bounded to 262144 inner bytes. Decoder validation cannot infer historical insertion order from an unsigned array alone; writer/recovery preserve append and oldest-first eviction order under the ordered locks, while a checksum-valid permutation is not claimed to be intrinsically detectable. Duplicate transaction/attempt identity is legal only as byte-identical pending/history crash overlap, never twice inside a snapshot or with divergent root, kind, tuple, event key, or outcome. Projected reservation capacity, history count, history bytes, and outer envelope size are checked before publication; no truncation is allowed.

`failed-dispatch-pending.json` contains **only** the exact closed `model_catalog_failed_dispatch.v1` record fixed by SPEC-044: `schema`, `transaction_id`, fresh `attempt_id`, `transaction_kind`, `event_model_key`, complete saved `root`, `tuple_sha256`, `projection_binding_sha256`, `event_sequence: 1`, `terminal_state: failed`, allowed semantic `error_code`, and `live_attempt: false`. It has no array/wrapper or stdout event, and is at most 16384 inner bytes. At most one is pending. Pending plus terminal history share one global 256-record and 262144-byte aggregate cap; count and sum the canonical UTF-8 bytes of distinct terminal records once, including a byte-identical crash duplicate in pending and history only once. Before a new pending publication, under SPEC-044's failure→cancel locks, build and durably readback-validate the replacement history snapshot, compacting any prior pending and evicting oldest entries from the front until both global caps hold; then independently publish/readback the new pending. Later compaction first durably publishes/readback-validates a snapshot containing pending, then unlinks pending and fully syncs/readbacks its parent. A crash duplicate deduplicates by exact identity and bytes. Every intermediate snapshot must fit its own 262144-byte cap, and a projected-reservation byte burden that prevents the required terminal preservation blocks the new projection/dispatch before side effects rather than dropping terminal evidence. No old pending is unlinked before its copy is durable; no interval loses a previously durable terminal from both places.

Before publishing a changed projection with up to 64 selected reservations, the projection writer holds `operation.lock` then `failure.lock` then `cancel.lock` from the final candidate read through replacement snapshot full-sync/readback. It counts the separately durable pending record once and protects it, the current active attempt and its terminal correlation if any, and the **eight newest** terminal-history entries (or all if fewer than eight). It evicts only older eligible entries from the front, one by one, until the candidate `model_catalog_reservations_history.v1` snapshot satisfies its 262144-byte inner cap, 360000-byte outer cap, 64-reservation ceiling, and shared 256-record/262144-terminal-byte cap; it validates each full candidate before rename and never truncates one record. Eviction and replacement occur in the same serialized history snapshot, preserving writer insertion order and pending copy-before-unlink. If even maximal eligible eviction cannot fit, it publishes no new actionable reservation/projection generation, returns the existing fail-closed unavailable result, and leaves pending, active, recent terminal evidence, and incumbent files intact. A later smaller projection can recover without operator mutation. There is no generic promise that 64 worst-case-sized actions fit beside protected records.

`cancel.json` is **only** a closed `model_catalog_cancel_marker.v1` inner record with exactly `schema`, `transaction_id`, `attempt_id`, `transaction_kind`, `event_model_key`, complete saved `root`, `tuple_sha256`, `projection_binding_sha256`, and RFC3339 `recorded_at`. It is the one current attempt-bound marker or the leaf is absent; it has no `outcome`, `observed_at`, or acknowledgement fields. The direct cancel process validates active, history, pending, projected and marker state under one bounded failure→cancel lock pair, publishes/readback-validates only the exact current marker or removes only a proven older marker under SPEC-044's precedence, then releases locks before emitting the **separate public stdout** `model_catalog_transaction_cancel_ack.v1` acknowledgement. The acknowledgement is never persisted as a marker, terminal claim, or transaction event. An unrecognized or malformed marker/ack substitution fails closed; an exact previously durable marker yields `already_recorded`; failed dispatch durable in pending/history yields `terminal` without marker creation. No new public status/control-frame or event schema is introduced.

To make that 4096-byte **private marker** cap constructive, the marker writer uses one deterministic canonical UTF-8 JSON encoder and a fixed 20-byte UTC second-precision RFC3339 `recorded_at` (`YYYY-MM-DDTHH:MM:SSZ`). Before advertising an available action, projection serializes the complete prospective marker with its actual escaped `root` object, actual escaped `event_model_key`, exact transaction kind/tuple/projection binding, and canonical 36-byte UUIDv4 placeholders for the future attempt; UUIDv4 value changes cannot change encoded length. It checks inner <=4096 and outer <=360000 including worst-case bounded envelope overhead: fixed-width envelope writer UUID, maximum representable generation decimal width, canonical base64 expansion, and fixed keys. A too-large candidate makes the action unavailable **at projection**; no root or event key is truncated. Direct dispatch repeats the same calculation with the fresh actual attempt and fixed-width timestamp before `active.json` or any live work; root/action drift follows SPEC-044's serialized `stale_transaction` precedence, otherwise a size failure follows `action_unavailable` in its existing failed-dispatch path, with no live state, network, or staging. The actual marker is re-encoded and capped before publication; matching immutable fields and fixed widths make the projection/dispatch bound sufficient for every admitted action, while any unexpected mismatch is typed unavailable before live state. The separate public `model_catalog_transaction_cancel_ack.v1` remains capped at exactly 4096 bytes, uses only its five approved fields, and is never charged to the private marker.

Only the validated registry's at-most-256 exact pairs may be inspected at projection, with bounded per-pair record and tree walks. A staging cleanup action is available only for one incomplete, non-live, unprotected, exact pair whose source record hash, saved root, tuple, event key, and path all validate. For `cleanup_staging`, the closed private `model_catalog_reservation.v4` adds exactly `source_transaction_id`, `source_attempt_id`, and `source_record_sha256`, all bound into `projection_binding_sha256`; those keys are absent for every other kind. The public action/event schemas remain unchanged. Direct dispatch validates the immutable reservation and index entry under the existing lock protocol, opens **that entry's saved root**, and checks the source file at the phase-directed location below. Worker and recovery never use current config, current active attempt, or a scan to choose a root or source. Terminal/history compaction may never remove a source registry entry or file; precommit cancellation restores/preserves both.

Source-file lookup follows the **durable cleanup phase and exact recorded leaves**. With `intent`, final present/tombstone absent means open and hash `final_leaf/source.json`; final absent/tombstone present after a crash means open and hash `tombstone_leaf/source.json` before the exact-marker restoration or resume; both present or both absent fails closed. With `tombstoned`, final must be absent and the exact tombstone must exist; open and hash `tombstone_leaf/source.json` before removing remaining contents. Remove that source file last. A crash after its last-file unlink may leave an empty tombstone with no source file: accept that **only** under durable `tombstoned`, exact saved root/record/hash, final absence, descriptor-proven empty tombstone, and no remaining deletion work, then remove the empty tombstone and advance to `removed`; a missing source beside any remaining content fails closed. With `removed`, both exact leaves and the source file are absent; validate only the durable deletion record's saved root, source pair/hash, tuple/event key, paths, expected totals, and target absence. No phase reopens the old final path by habit or treats a missing source as proof of completion. This phase lookup precedes every mutation and repeats after crash; no counterpart object is deleted because of a current projection.

After durable `removed` and full-synced exact target absence, **while the deletion record still exists**, retire only its exact index entry with a full-synced/readback-validated registry generation, then durably clear the deletion record and commit terminal state. A crash between those barriers leaves `removed` as authority: recovery verifies the record's saved root, exact paths and absence, recorded source hash/tuple/event key, and that this exact index entry is either still present for retirement or already absent, then resumes clear without scanning or touching another tree. A missing entry during `intent` or `tombstoned` fails closed; failed retirement keeps `removed` for retry and never emits success. Successful preparation may retire an entry only after verified publication and proof the corresponding staging tree is absent; interrupted staging retains it until explicit cleanup or operator diagnosis.

## Count admission and publication without a speculative receipt

At pre-network dispatch under the common `operation.lock`/cleanup serialization, bound the verified inventory to 256 with one extra entry only for overflow detection and apply the already required logical budget/free-space/verified signed artifact gates. At count 256, use an existing object **only if** its separately opened, verified prior receipt and signed tuple/root/artifact bindings establish the exact previously published artifact identity and valid leaf; return that object idempotently without network/staging. Same displayed name, tuple SHA alone, or predicted receipt digest is insufficient. If no such exact proof exists, refuse before any network or staging side effect. At count <=255, a prospective **distinct** publication reserves one count slot in durable active state while holding the common operation lock; this reserves capacity, not an unknown artifact leaf/digest. An existing verified identity is idempotent and takes no new slot. At publication, recheck feed/guidance/root/cancel/physical space/logical budget and inventory under the retained locks, construct and durably verify the final receipt from completed verified bytes, compute `receipt_sha256`, then compute SPEC's `artifact_identity_digest`, choose only `objects/<artifact_identity_digest>`, and exclusively rename the exact unpublished tree. If the final digest resolves to a previously verified identical object, prove byte-for-byte receipt and tuple equivalence and use the existing object without overwrite; any discrepancy fails closed. A new object may become only the 256th; an externally consumed slot, malformed inventory, conflicting final leaf, or 257th observation fails before rename. Preserve the v20 bottom-up file/parent full-sync, publish-ready, exclusive rename, destination-parent full-sync, terminal and crash-recovery barriers. A physical post-crash published object is accepted only by verifying its receipt and SPEC digest against the opened leaf; no tuple-named fallback or automatic repair.
