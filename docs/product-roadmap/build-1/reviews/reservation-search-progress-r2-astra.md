## Prior findings: independently assessed

**RSP-ARCH-M1: closed at plan level.** R2 removes the pre-primary prospective-start intent. A durable pending metadata receipt can only describe an already-published primary and cannot mutate it. Live start retains its owner through primary/exclusion/index publication, cannot acknowledge progress or launch work after a failed bundle, and uses prepublication-only retry. Controls consult metadata intent before `startedAt`, distinguish live-owner busy from ownerless recovery, and complete only exact frozen metadata before ordinary interrupted-owner reconciliation. The explicit queued-cancel owner rule prevents a cancellation transform racing an unfinished starter. Tests cover actual status/cancel/reserve/run after primary and metadata crash points. These rules address the old queued-looking orphan-start gap without inventing execution or success.

**RSP-ARCH-M2: closed at the previously reported protocol level, with a new allocation-boundary finding below.** R2 selects frozen membership, per-entry publication intents, classify-before-write and exact finalizing installation. A busy/pending UUID cannot require another owner's heartbeat to finish that UUID's work. Changes before intent can recapture; referenced intent bytes cannot rebaseline. Completion freezes an exact install snapshot while preserving current binding and exclusion refs, and missing acknowledged metadata stays protected. The live-owner tests and shared-writer inventory meaningfully address the prior unspecified global busy policy and mutable pending decisions. Actual implementation must still prove all direct writer participation and latency.

**RSP-ARCH-M3: closed at plan level.** R2 moves the fence to an existing mandatory closed format, publishes it before classification, specifies post-format/pre-v4 recovery, and requires final old-writer format validation. It limits compatibility claims to actual qualified binaries and blocks release where an incompatible writer can run; it does not silently permit such a writer. The current index receipt validates pinned format evidence at final mutation (`ModelCatalogTransactionEvidence.swift`, `ModelTransactionIndexReceipt.validateLocked`), so byte-identical format replacement as well as schema change can invalidate a previously captured receipt. Actual prior-binary manifests and all representative final mutation checks remain unexecuted qualification requirements, not established proof.

## RSP2-ARCH-M1 — Quiescent migration cut does not handle allocating intents safely

**Severity: Medium.**

**Evidence:** R2 requires acquiring all active UUID owners before installing the format fence and freezes the existing membership during classification. It does not first resolve or explicitly reject `phase == allocating` entries, nor distinguish their owner rules. Current `initializeRetention` finishes format/binding initialization but does not itself recover allocations; `reserveOperation` separately calls `recoverAllocations`. That recovery iterates allocating entries and explicitly requires `absent(id, includeOwner: true)` without acquiring an owner. `ownerLock` calls `ModelCatalogFileLock`, which opens the stable owner file with `O_CREAT` (`ModelCatalogTransactions.swift:139–145,203–209`); releasing the lock does not remove that file. Approved `retention-lock-budget-r2.md`, verification 8, expressly requires absent-intent recovery to leave the owner file absent.

**Consequence:** A valid pre-v4 crash after allocating-index publication can leave an allocating entry with no primary/origin. If the new cut attempts to lock that UUID, it creates contradictory owner evidence and prevents the existing recovery from freeing the slot, even when the cut aborts. If “active UUID” means only active-phase entries, the alternative problem remains unspecified: frozen membership can include an allocating entry without the origin/generation required by the source/class graph, while migration forbids the membership changes needed to recover it. Neither interpretation establishes safe progress for the already-supported allocation-crash states.

**Required correction:** Add an explicit pre-cut allocating-intent phase. Use the existing absence-specific recovery rules without creating owner files; after recovery, require and CAS a source consisting only of fully active members. Any unresolved/unsafe allocating intent must cause a defined pre-fence retry/protected outcome without poisoning its owner evidence. Recheck the phase-complete membership at the final cut so a concurrent allocator cannot introduce an unseen allocating entry. Alternatively specify a complete migration representation for allocating entries, but do not freeze them and defer their recovery to a membership-changing operation that migration forbids.

**Required tests:** Crash a real pre-v4 allocator at intent, primary, origin and active boundaries, then invoke migration activation. Cover empty intent, primary-only recoverable intent, contradictory sidecars/owner and a concurrently paused allocator. Assert no new owner inode for absent-intent recovery or failed cut, exact original bytes, at most one surviving allocated UUID, no fence over an unrepresentable entry, and subsequent bounded recovery. Qualify the simultaneous-owner cut at 1,024 active entries with actual descriptor/resource usage and the original deadline; do not assume acquiring that many descriptors is free.

## RSP2-ARCH-M2 — Post-migration fresh allocation has no defined v4 publication/recovery protocol

**Severity: Medium.**

**Evidence:** R2 says it replaces R1's executable protocol and changes the field names/receipt graph. It requires a class reference for every completed entry, but only specifies class publication for existing source members and departures. Its new-allocation paragraph removes the 65,536-byte limit without defining allocation order. The writer inventory names allocation recovery; the tests do not explicitly cover the new v4 allocating/class/active bundle. Current `reserveOperation` still creates an allocating entry with origin hash, writes primary and origin, then publishes active membership. Current recovery reconstructs the expected origin from the exact initial queued primary, but knows no class reference or v4 receipt. Completed migration's install snapshot binds the initial membership, whereas normal subsequent allocations necessarily add members outside that frozen source.

**Consequence:** Implementing the existing allocator unchanged either exposes an active v4 entry without mandatory class authority or makes every new allocation invalid after migration. Improvising class creation later risks treating an incomplete search root as complete or rebaselining an orphan allocation from changed bytes. The design also needs to distinguish immutable migration completion evidence from current dynamic membership, otherwise the first legitimate allocation/retirement can invalidate the completion proof or tempt a weaker check. This is the normal repeated-use path, not merely an unusual recovery case.

**Required correction:** Specify a complete v4 fresh-allocation state machine under the existing index CAS. A bounded viable shape is: fully encode initial primary/origin/class and hashes outside the lock; persist an allocating intent with exact expected origin/class refs; exclusively publish the exact files; publish active membership only when all required class authority is durable; return the reservation only afterward. Define every crash observation, including absent primary/origin/class, matching and conflicting orphan files, and when exact bytes may be completed without fabricating a new origin/class. Keep the distinct absence-recovery owner rules. Define how later completed-index generations preserve immutable source/install lineage while legally adding/removing current members, and ensure concurrent allocations invalidate an earlier search absence proof through the final index CAS. Do not carry over R1's field names or byte bound implicitly.

**Required tests:** Real child death and thrown errors at each v4 allocating intent/primary/origin/class/active boundary; concurrent reserve/reserve and allocation versus retirement; restart after migration followed by repeated new allocations and retirement, including source-membership-empty journals. Assert no returned active reservation without its validated class, no duplicate allocation while a matching candidate is unresolved, no owner creation for empty intent recovery, exact completion of matching intents, rejection of altered files, and continued validation of historical install evidence after legitimate membership changes.

## Scope and acceptance remain unchanged

The separately approved index-receipt measurement is the first prerequisite. Passing the healthy eight-call/64-second capacity fixture does not prove the maximum-shape structural requirement; the all-primary search still appears in the current source. Report the measurements and either demonstrate all required bounded-progress outcomes through the smaller correction or return to an independently approved structural solution. Do not implement v4 solely because a proposal exists, and do not close maximum-shape acceptance from the small-record fixture.

R2's explicit cooperative profile and per-record feasibility limit are honest: completed classification must persist across calls without rescanning those large primary bodies, while a record that cannot fit any single budget receives no false progress claim. The original eight-second call budget, owner fence/watchdog, exact cancellation truth, legacy/protected behavior and immutable history remain required. All metadata/index size bounds require actual maximum-field derivation; complete metadata-graph reads and finalizing installation still need measured latency. No full Build 1 or S2 gate is implied by this review.
