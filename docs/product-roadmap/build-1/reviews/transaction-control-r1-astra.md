## M1 — The ten-second UI wait does not bound the control helper's lifetime or resources

**Severity: Medium.**

**Evidence.** Section B says to keep the existing ten-second control wait and defines termination/reaping only for a never-resumed helper that fails identity verification. Current `ModelManagement.swift:runCatalogRead` completes its continuation at the deadline but does not cancel or reap the separate `runner.run` task. `MalibuModelCLI.run` then continues `process.waitUntilExit()` and unbounded stdout/stderr/partial-line buffering. A caller can return from timeout and attempt another control while the first helper remains alive. The new suspended-launch seam does not itself change that resumed-helper lifecycle. CLI `ModelCatalogTransactionStore.reconcile` can perform owner-loss cleanup and full artifact hashing, so a control is not guaranteed to finish promptly merely because its name is `status`.

**Consequence.** A wedged or long-running helper survives the promised bound. Repeated status/cancel attempts can accumulate helpers, pipe buffers and blocked work, making cancellation/recovery progressively less usable while the incumbent is absent. Scoped callbacks prevent some incorrect UI updates but do not reclaim resources or fence a helper that still holds a journal lock. The proposal therefore does not yet supply the bounded helper requested by its own scope.

**Required correction.** Specify the resumed-helper lifecycle independently of the owner transaction: finite concurrency, output/line byte limits, timeout behavior, descriptor cleanup and eventual reaping, including app exit/restart. If timeout termination is chosen, target only the exact spawned control child and never the owner/incumbent/probe process or their groups; establish that interruption of the helper's journal work is recoverable, and report uncertain status rather than synthesizing cancellation. Alternatively define a bounded single-helper ownership/recovery scheme that cannot accumulate processes and has a finite cleanup path. Do not reuse the general process runner's mutable current-process cancellation slot for multiple helper operations. Add tests for a helper that ignores ordinary completion, output/partial-line flooding, repeated timed-out controls, concurrent status/cancel, and app exit, asserting bounded resources and zero owner/runner signals.

## M2 — The helper command cannot enforce the promised transaction-kind binding before mutation

**Severity: Medium.**

**Evidence.** Section B persists and verifies UUID/target/model-key/kind, but each allowed CLI command carries only UUID and `--model TARGET`. The addendum excludes CLI wire/contract changes. Current `ModelCatalogTransactionStore.reconcile(id:target:cancel:original:)` selects the cleanup stream whenever `<UUID>.cleanup` exists (unless its internal `original` flag is true), then performs recovery or cancellation against that selected record. `modelCatalogTransactionRead` supplies neither an expected kind nor an original-stream selector for status/cancel. The app's transcript binding runs after helper output and therefore after any CLI journal mutation. The same UUID is deliberately reused for `cleanup_staging`.

**Failure sequence and consequence.** The app retains authorization for prepare/evaluate transaction A. The original operation completes, and another authorized CLI/app instance starts its cleanup under the same UUID. A delayed cancellation from the original app passes its persisted prepare/evaluate checks, but the helper selects `<A>.cleanup` and cancels that newer cleanup. Rejecting the returned cleanup transcript cannot undo the wrong operation's cancellation. The original action should instead receive its terminal/too-late result. This breaks the addendum's exact UUID-plus-kind scoping, especially TC-07's cleanup reuse case.

**Required correction.** Give the CLI an immutable expected operation selector and enforce it under the journal lock before any owner-loss reconciliation, cleanup or cancellation write. This may be a narrowly specified expected kind/stream and generation option, or another equally strong existing contract that can be demonstrated in code. App-only output validation or a separate preflight status read cannot close the race. If this requires a CLI command-contract/spec change, revise the stated scope and obtain approval of that exact revised contract rather than implementing around the limitation. Preserve original-result retrieval and legitimate cleanup controls. Add an interleaving test: capture original A authorization, create cleanup A, issue delayed original status/cancel, and prove cleanup receives no mutation and the original terminal/too-late state is handled correctly; also prove a cleanup-authorized control reaches only cleanup, including cleanup retry generations.

## Assessment of the remainder

The underlying architecture findings are confirmed. Draining launchd removes the peer/PID evidence required by the current general runner, so a separate runner instance alone cannot repair cancellation or cold restart. The proposed fixed-path configured-provider resolver, strict signing requirement, pinned code identity, pre-dispatch persisted authorization, private pending file, config identity/digest, no arbitrary saved launch path, and typed command boundary are appropriate. Captured capabilities are tied to unchanged code rather than treated as current health/admission evidence. Legacy/unreadable records conservatively block new operations. Legitimate upgrades/config edits remain explicitly recoverable limitations, not reasons to silently refresh the authorization.

The proposed suspended-launch identity check directly addresses executable replacement between static validation and helper execution; its real macOS test and deployment-target compatibility must be demonstrated before that seam is accepted. Deterministic trust seams and unsigned DEBUG tests cannot establish the production signing positive. Keep the fixed config revalidation and no-follow/private-chain/ACL checks through the tested launch boundary.

The admission predicate split addresses architecture-r1 M2 at plan level: terminal states retain status readback; confirmed fresh offers and pending-only retries use distinct state sets; CLI/coordinator identity, journal, sanction and CAS authority remain decisive; admission-only failure cannot permanently disable readback. The AR tests preserve that distinction and avoid automatic reoffer, withdrawal or paid claims.

No new Critical/High/Medium finding was identified in those remaining requirements during this pass. This is not implementation acceptance.
