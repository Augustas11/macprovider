## M1 — The proposed supervisor still has an unclosed suspended-orphan failure

**Severity: Medium.**

**Evidence.** Addendum lines 150–156 suspend the CLI before validation; lines 184–193 explicitly leave supervisor death during suspension unresolved. The CLI self-deadline cannot start until it runs. The GUI's promise to reclaim the child “where available” supplies neither an independently retained child handle nor recovery when the GUI is also absent. The process is the supervisor's child, not the GUI's directly spawned child. TC-10 asks implementation to prove or block on this case rather than naming a mechanism that closes it. The supervisor alone owns the global control lock (lines 142–145).

**Consequence.** Kill the supervisor after suspended spawn and before resume, then restart the app. The stopped child cannot run its self-deadline, the supervisor cannot reclaim it, and release of the supervisor-owned lock can admit another helper. A remaining suspended process and repeated orphan accumulation contradict bounded controls and restart recovery. Moving the unresolved design question into implementation is incompatible with this zero-Medium plan gate.

**Required correction.** Remove the suspended-orphan state or provide a concrete independently surviving ownership/reclamation mechanism, including control-lock ownership until the actual child exits. Do not solve this by another unbounded chain of watchdog processes, guessing saved PIDs, or treating a helper kill as transaction cancellation. Replace TC-10's “prove or block” alternative with an executable design and definite pass criteria.

**Minimal correction supported by the current trust boundary.** Suspension is not inherently required by the existing signed, owner-private execution boundary. `ModelManagement.swift:1329–1404` checks an owner-private configured/live-peer executable and strict signing/CDHash, then the ordinary runner launches by path. `InstalledProviderMonitor.swift:401–435` requires the current UID, a regular executable, safe permissions/ACLs and private directory chains; it does not make files immutable to that same UID. The pending authorization and config likewise live in that user's private files. This code does not establish protection from a malicious process already running as the operator UID.

A smaller revised design can capture an app-owned, private executable snapshot of the authorized CLI and launch it normally, eliminating the deliberately stopped interval. The revision must make these details explicit:

- Copy from a safely opened configured executable into a fixed app-controlled private transaction location, never a persisted arbitrary launch path. Validate the completed copy's full strict signature, identifier/team and pinned CDHash before publication or execution; compare against the live-peer pin captured at authorization. Bound storage and use atomic private publication. Never refresh the snapshot to an updated binary silently.
- Keep the configured-source identity/change checks required by the recovery policy. A replacement after the final source check must execute only the already verified pinned snapshot, or fail; it must never execute replacement bytes. Revise TC-06 to test that invariant. Unsafe snapshot paths, changed snapshot bytes, wrong signatures, and invalid pins still fail closed. Explicitly state that the owner UID is trusted, as it already is for pending metadata and config; a private copy is not an anti-malware boundary against that UID. If hostile same-UID mutation is actually required, this alternative is insufficient and a different authority design needs review.
- Reuse the existing bounded process-lifecycle approach in `ProviderCredentialHandoffRunner.swift:1008–1156` instead of introducing a new signing/embedding target solely to own suspension. Adapt its bounded output, termination and completion handling to the stricter addendum limits; do not copy its implementation blindly as acceptance proof. Start the short CLI control's independent deadline and parent-lifetime/pipe guard before config or journal work. `CandidateParentLifetimeGuard.swift:4–23` already demonstrates child-local kernel parent checks and noncooperative `_exit`, without signaling a saved PID. This guard belongs only to the short control, never the long-running owner.
- Define a safe launch handoff for the one-control lock so that it remains owned by the control after GUI failure, with no release/spawn gap. An inherited lock descriptor retained by the CLI is one candidate; verify its actual macOS behavior and descriptor lifetime. A replacement app must not admit another control until the prior child has exited/released that ownership. Preserve all byte bounds, coalesced cancellation priority, atomic-journal interruption recovery, and uncertain-result semantics.
- Prove the actual signed CLI's status/cancel/result commands work from the private snapshot, including any executable-relative resource dependencies. Test GUI failure before and immediately after normal spawn, early child initialization failure, blocked journal work, output flooding, and cold restart. A snapshot and early guard are a concrete simpler direction, not a claim that existing code already supplies these guarantees or that scheduling/OS failures have been tested.

Keeping a single supervisor is also possible if normal verified-snapshot launch removes suspension and the child independently retains its lock/deadline/lifetime guarantees. The correction does not require adding a supervisor to the supervisor. Either choice must be captured in a new exact proposal before implementation.

## M2 — Pre-resume config checks do not bind the config actually consumed by the CLI

**Severity: Medium.**

**Evidence.** Sections A/B pin a fixed config identity and digest and recheck it before dispatch/resume (lines 72–74, 97–102, 119–123 and 152). Section D passes only `--config CONFIG` plus transaction selectors; it carries no expected config identity/digest or equivalent bound read contract. Current `ModelCatalogTransactions.swift:666–669` independently calls `ConfigLoader.load` after the process begins, then constructs `ModelCatalogTransactionStore.forConfig(resolved)`. That store's `forConfig` at lines 136–137 selects the transaction root from the resolved artifact configuration. Generation checks then occur inside whichever root was selected.

**Failure sequence and consequence.** The parent validates config A; a normal atomic config edit replaces it with config B after the final check but before the helper reads it. The helper resolves B and accesses its journal despite authorization being pinned to A. A copied/migrated store can contain the same UUID/kind/generation, so those selectors do not by themselves prove the original config/root. Even absent such a matching record, the promised fail-closed config boundary has already been bypassed before root selection. Suspending and checking before resume only moves this window; it does not eliminate it. This does not require an adversarial same-UID threat model: legitimate concurrent configuration replacement is sufficient.

**Required correction.** Bind the expected config identity and SHA-256 into the typed control invocation and have the CLI verify the bounded, safely read config object it actually decodes and uses, before deriving or accessing a journal/root. A check followed by a second `ConfigLoader.load` is insufficient. Use the same verified bytes/file identity for the decode and resolved configuration, preserving existing config interpretation and safe-path checks. No credential bytes need appear in argv, persisted metadata, output, or logs. The binding may use typed private IPC or a narrow explicit control contract; name the choice and owner in the revision. Apply the same consumed-config rule where new owner dispatch relies on this frozen pin.

Add a failpoint after the final parent check and before the CLI config read: atomically replace the config with another valid private config/root, including a copied journal with matching selectors. Assert failure before either journal is secured, recovered, hashed, cleaned, cancelled or otherwise mutated. Also test replacement after the CLI has obtained its verified input: it must never decode the replacement through a second read or change the selected root mid-operation.

## Dispositions and remaining assessment

Prior r1 M2 (UUID/kind stream selection) is **closed at plan level** by Section D's immutable generation, expected-kind selection under the same journal lock before side effects, original-terminal retrieval, cleanup-attempt isolation and TC-11/12. It is not sufficient to validate the returned event after mutation, and r2 correctly says so. Preserve that correction in the next revision.

Prior r1 M1 (unbounded helper lifetime/resources) is **substantially addressed but not closed**: fixed byte/line caps, global concurrency, cancellation priority, independent deadlines, exact-child reclamation and atomic-interruption tests are appropriate. The remaining supervisor-death case is M1 above, not a reason to discard those requirements.

The admission predicate split remains appropriate: authoritative readback is available after terminal failures, explicit reoffer and retry have separate conservative state sets, and the CLI/coordinator retain journal, sanction, key, freshness and generation authority. No offline control exception authorizes offering, adoption, readiness or settlement. Safe pending persistence, pinless legacy recovery, exact transcript/result validation, and retaining pending state until fresh terminal reconciliation remain necessary.

This rejection is bounded to the two open findings. It does not require broad process-framework replacement or stronger operator-UID isolation than the existing trust model. It does require a concrete crash-recovery design and binding of the actual consumed config. Production signing/snapshot execution evidence, complete app tests, cumulative code/security/architecture gates and separately qualified physical preparation-to-settlement acceptance remain outstanding implementation/verification obligations.
