## Product result

For the one Gate-C-approved qualification, a provider can see a sanitized, narrowly scoped observation state and trace a real request through immutable request-start capture, receipt persistence, billing projection, and app/portal presentation. An isolated qualification-only shadow decision is operator/test evidence and is structurally absent from provider APIs, balances, reward activity, and clients. Provider-visible `earning` requires a production-ledger accrual plus a separately authorized production reward capability. Because Build 3 cannot enable that capability, its earning projection remains explicitly unavailable while historical ledger balance and withdrawal eligibility remain independently truthful.

Missing, stale, revoked, mismatched, unreadable, incomplete, or uncovered evidence produces a conservative state. It never becomes confirmed idleness, current earning, broad provider integrity, or physical-computation proof by inference.

## User journeys

### Provider becomes observable

1. The provider serves the exact Gate-C-qualified key through an authenticated session with a unique session-instance UUID and model-generation tuple.
2. The shared MLX resource arbiter issues a bounded, overt, non-billable lease through the negotiated carrier only after all other MLX owners are quiescent.
3. Swift executes the exact profile without changing buyer output and returns only bounded governed data to the coordinator evidence ingress.
4. Coordinator validates session, generation, qualification, nonce, replay key, limits, references, calibration, and policy before a durable event.
5. Sanitized status shows state, key digest, evidence time, expiry, freshness, limitation, and recovery action without raw prompts, vectors, thresholds, secrets, or buyer data.

### First job is traceable

1. WS authority mints a single-boot route token for the exact live session/model tuple.
2. The money writer stores the token, route, and request observation capture atomically. A WS reservation and a durable dispatch-attempt event must both succeed before network send.
3. Receipt, verdict, finality, and exclusion changes append complete immutable billing snapshots.
4. Mirror verifies event lineage and consumes event payloads without reconstructing old facts.
5. An operator-only qualification sink may record the request’s shadow decision. The sink cannot enter provider status, balances, reward activity, emission, withdrawal, or payment.
6. App and portal show matching request stage, observation state, existing production-ledger balance/withdrawal facts, `earning unavailable` while reward capability is disabled, payment unavailability, and independent freshness.

### Evidence degrades

Reference, calibration, policy, artifact, runtime, profile, hardware class, session, or operator revocation advances the durable revision. New requests cannot capture the prior positive state. Historical captures remain immutable; prospective holds require separate governed ledger events. UI reports the closed reason and recovery action.

## Normative contracts required before implementation

### Qualification collector implementation and equivalence

The inspected `1.8.123` CLI is historical baseline evidence and cannot collect governed values. After this plan passes, Gate H0 jointly reviews `compute_hook_design.v1` and `compute_acquisition_authority.v1`; only then may Collector Slice H0 implement the two named Swift targets and tests. The collector target is absent from Malibu.app, `macprovider-cli`, installer, release archive, updater, provider runtime scripts, and production command registration. It writes one bounded encrypted result to a custodian-selected destination and has no coordinator URL, provider credential, settlement client, reward client, or production feature flag.

The shared measurement module exposes exactly one value-bearing operation, `withAuthorizedPostSamplerValues`; the raw tensor/value-storage handle remains private to that operation. Collector CLI, future provider runtime, tests and adapters can request metadata separately, but cannot obtain or copy values through another public/internal symbol. Gate-H0 source and link-map rules inventory every MLX tensor read/index/reduce/hash/transfer/copy/serialization call in both targets and fail if a value-bearing call is reachable without this operation. Immediately before invoking the closure that first touches value storage, the operation must obtain and verify all of the following:

- a Gate-A0 `compute_acquisition_approval.v1` signed by the independently governed approval key and binding the exact collector manifest, profile, calibration protocol, reference-successor policy, authority incarnation/sequence root, approval decision digest, not-before time and expiry;
- a custodian-signed `compute_acquisition_job.v1` binding the approval digest, unique nonce, monotonically reserved sequence, acquisition mode (`calibration|reference|release_qualification|production_observation`), physical-unit identity, blinded partition, exact collector/profile, any release-candidate and qualification digest required by that mode, result-destination encryption key, issue/expiry times and permitted acquisition count of one; and
- an online `compute_acquisition_consumption_grant.v1` returned only after the independent sequence authority atomically changes that exact `(authority_incarnation, sequence, nonce)` from `reserved` to `executing`, binds the current collector execution nonce and physical-unit attestation, and confirms that neither approval nor job is expired or revoked.

The approval/sequence authority is independently hosted and durably replicated from qualification machines. Its private keys, current sequence head and mutation API are absent from collector and production binaries. It allocates a sequence only after the Gate-A0 approval record and capsule are durable; sequences never repeat across authority incarnations. Job issuance is mode gated: calibration/reference requires the exact Gate-A0 capsule, release qualification also requires an independently admitted release-candidate manifest with byte-identical measurement module, and production observation additionally requires the Gate-C qualification digest and separately authorized rollout state. A collector or runtime must be online at the value-access boundary. Offline collection, cached grants and grace periods are prohibited. Missing authority, partition, network or destination availability returns a typed pre-value blocker. A crash after consumption burns the sequence; recovery may close it `failed|completed` from the encrypted result receipt but never reset it to `reserved`, and a retry requires a new job/sequence. Revocation is checked during atomic consumption. The encrypted result binds the approval, job, grant, execution nonce, collector manifest, profile, sequence and content digest. The authority records only bounded metadata and result receipt, never raw values or labels.

Gate H0 closes approval-key custody/quorum, public-key rotation, authority replication, anti-rollback incarnation transition, reserve/consume/fail/complete state transitions, outage behavior, job expiry, revocation and disaster recovery. A recovered authority may resume only from a quorum-verified checkpoint plus append log whose sequence head is at least the externally witnessed head; otherwise all value access remains blocked and a new incarnation requires a signed transition that permanently retires the prior sequence namespace. Instrumented tests place an access sentinel at the first tensor value operation. Missing, pre-approval, wrong-manifest/profile/protocol/policy, replayed, expired, revoked, rolled-back, wrong-unit/partition/destination, cached or already consumed authority must fail before that sentinel in both the CLI collector and future production runtime integration.

Gate H1 inspects source independently, runs structural real-MLX parity without exposing governed values, recomputes all manifest digests, verifies signing, and requires zero Critical/High/Medium code, security, and architecture findings. The `ComputeObservationMeasurement` build product is a separately emitted immutable object/archive. Collection, the later provider probe, and Gate-C qualification must use byte-identical module object bytes under the same dependency lock, compiler/SDK ABI, processor-order manifest, and serialization fixtures. The release build records the embedded module section digest and proves it equals Gate H1. Source-level similarity, API compatibility, or a new compiler build is insufficient. Any measurement-semantic, dependency, compiler, object-byte, encoding, or processor-order change creates a new collector manifest, profile, Gate H1, Gate A0, and complete reference/calibration campaign.

### Precommitted calibration protocol

`compute_calibration_protocol.v1` is committed and independently approved before the collector reads or copies any real governed numeric value from normal inference. It freezes:

- one exact hardware predicate over allowlisted `hw.model`, chip family/name, physical memory, GPU core count, OS build range, Metal feature-set/runtime and MLX revisions; equality is fieldwise and one out-of-range field is uncovered;
- 80 physical calibration units, where one decision unit is one independently adjudicated host plus its operator authority, power/network failure domain, and runtime-build/kernel provenance campaign. Positions, prompts, warm repetitions and process launches are correlated measurements inside that unit and never increase the decision count;
- an immutable partition selected before acquisition: 20 threshold-development units and 60 sealed held-out units. Every unit, both counted reference sources, and the provider under test use distinct physical hosts and distinct power/network failure domains. Each partition spans at least four operator authorities and four independently produced runtime-build/kernel provenance groups. No held-out result is opened until the threshold and its digest are frozen from development/reference data;
- for each unit, 8 fixed prompts, 32 fixed positions, `K=32`, 3 cold process launches and 10 warm repetitions, deterministic seed `0`, exact processor order, float32 little-endian probability encoding after device synchronization, and JCS metadata;
- the host-level statistic: a protocol-fixed aggregate of the base-2 Jensen-Shannon divergence over the top-32 probabilities plus a remainder bucket against both admitted references. The exact aggregation, bootstrap strata, safety ceiling and threshold formula are immutable before collection;
- a host-level known-good decision formed only after the complete matrix. The 60 held-out good units must have zero false quarantines; the one-sided 95% exact binomial upper bound is reported and must be at most 5.0%. No position or repetition is a Bernoulli trial;
- a paired, blinded positive-control campaign on all 60 held-out units. The protocol fixes a minimum meaningful divergence of at least `0.010` base-2 Jensen-Shannon at at least 10% of governed positions and a signed transform/runtime-control digest before collection. At least 59 of 60 host-level controls must be detected and the one-sided 95% exact-binomial lower bound must be at least 90%. Controls cover both an end-to-end controlled runtime perturbation and a separately signed hook-boundary transform; structural mismatches are reported separately and do not count toward numeric power;
- blind custody: custodian-assigned good/control labels and raw vectors are withheld from threshold authors/reviewers until the threshold digest is committed. The analysis executable accepts sealed inputs and produces a signed per-unit verdict. Custodians cannot author/approve the protocol, references, threshold, or product state;
- a precommitted reference-successor envelope learned from development/reference data and tested blindly on all 60 held-out units: per-source predecessor movement, A/B mutual divergence, maximum source-time skew, golden-fixture stability, and the minimum meaningful successor drift controls use host-level decisions. The held-out known-good refresh rule must meet the same zero-of-60 false-suspension bound, while both single-source and correlated two-source meaningful-drift controls meet the same 59-of-60 detection and 90% lower-bound requirements;
- tail feasibility at the unit level, fixed exclusions, retries/missing-data treatment, zero early stopping, 30-day calibration and qualification expiry, 24-hour reference event expiry, two-hour observation window, 90-day protocol expiry, rolling capacity qualification, and a failure outcome that blocks rather than changes any parameter.

The counts above are qualification prerequisites, not an assertion that this session has the hardware or operators. Until all 80 independent units, two disjoint references, custody roles, and held-out/power gates exist, calibration and positive observation remain blocked. The result supports observation-only qualification. It cannot support SPEC-036 warn/enforce, verified settlement, production reward eligibility, or economic activation.

### Independent reference admission

The two counted reference sources differ simultaneously in approved operator authority, physical host plus power/network failure domain, and independently produced runtime-build/kernel provenance. They are disjoint from all calibration units and the provider under test. Admission records bind signed identity, attested physical/fault-domain evidence, build/kernel provenance, exact profile/protocol/artifact/catalog/tokenizer equality, production/expiry/revocation times, predecessor digest, and custody digest.

Each source independently passes the same signed golden-distribution fixture at admission and refresh. Each source has an immutable `series_root_digest` and exactly one current `event_digest`; a successor must name its source predecessor and the common prior `reference_epoch_digest`. Forks, gaps, replay, late old events, changed series root, changed antecedent, or successor outside the Gate-A0-approved numeric envelope reject without changing the accepted head. The evaluator stages successors independently but atomically publishes a new `compute_reference_epoch.v1` only when A and B are simultaneously fresh, overlap within the fixed skew bound, preserve all independence axes, pass golden validation, remain within each predecessor-movement bound and the A/B mutual-divergence bound, and name the same prior epoch. One-source advance, excessive skew, or disagreement suspends new positive observations as `reference_refresh_pending|reference_disagreement`; it never mixes epochs.

Gate-C qualification binds both series roots, the Gate-A0 successor-policy digest, the calibration digest, and the then-current reference epoch, and explicitly authorizes only successors admitted by that fixed policy while calibration, qualification, protocol, and source events remain unexpired. An admitted successor advances the observation authority revision and preserves qualification; it does not rewrite a prior observation or request capture. An envelope violation, fork/gap, revocation, changed provenance/profile, calibration expiry, or qualification expiry makes new state nonpositive until a new approved epoch or full requalification as specified by the closed reason. In-flight work keeps its immutable request-start capture; a later reference change cannot upgrade or downgrade it implicitly. Daily refresh is therefore a governed successor transition, not an unreviewed replacement or an automatic Gate-C rerun. Golden validation never replaces an independence dimension, held-out discrimination, refresh-stability test, or calibration. Raw vectors remain controlled evidence and never enter public status.

### Observation authority and restart-safe request-start linearization

Observation tables live in the money SQLite database. Append-only events, current materialization, immutable request captures, revocation tombstones, route-token lifecycle events, and audit metadata bind qualification and evidence digests.

Every coordinator process creates a random 128-bit `coordinator_boot_epoch`, loads one route-MAC `key_epoch`, and starts an in-memory monotonically increasing 64-bit `mint_sequence`. Every routable WS session receives a random 128-bit nonreused `session_instance_id`. The live tuple is `(stable_provider_id, assigned_session_id, session_instance_id, target_generation, release_generation, admission_binding_epoch, canonical_model_key, artifact_digest, catalog_digest, rate_card_digest)`. A token serializes this tuple, boot/key epochs, mint sequence, request ID/attempt, observation predecessor revision/digest, bounded signed UTC issue/expiry times, and random token ID. Its live deadline is derived from the process monotonic clock at mint and is never reconstructed from serialized wall time. Tokens are valid only in the same boot/key epoch; wall-clock movement cannot extend the monotonic deadline. Nil generation or tuple fields are uncovered/ineligible.

The cross-owner protocol is:

1. Under lock order `provider-pool -> session actor -> model admission`, mint and register `minted` with the live monotonic deadline; release WS locks.
2. Under lineage `flock` and the local+witness PREPARE protocol, `BEGIN IMMEDIATE`, validate the same boot/key epoch, signed UTC bounds, and current monotonic deadline, then atomically insert route snapshot, token bytes/digest, observation capture, and durable `capture_committed` event. Release money locks.
3. Reacquire WS locks, compare the full tuple, and CAS `minted -> claim_reserved` with a fresh claim nonce. This reserves authority but cannot send.
4. Release WS locks and append durable `dispatch_attempt_authorized` under the money lineage, binding token, claim nonce, boot/key epochs, and full tuple. Failure journals `dispatch_blocked_orphan` and cannot send.
5. Reacquire WS locks, verify the same live `claim_reserved`, tuple, deadline, boot/key epochs and durable attempt digest, then CAS to `send_lease`. The session actor sends only under that lease. A send failure or lifecycle mismatch appends a terminal failed/orphan event. A result is accepted only for that token/attempt/tuple and an already durable attempt event.

Startup completes lineage recovery before routing. Every `capture_committed` token without `dispatch_attempt_authorized` becomes terminal `restart_orphan_nonrewardable`. Every authorized attempt without a persisted accepted result becomes `dispatch_outcome_unknown_nonrewardable`, releases/refunds the buyer reservation through the existing authoritative money path, and rejects old-epoch late results. Exact accepted receipts already committed remain immutable. MAC-key rotation creates a new key epoch and performs the same orphan reconciliation. No WS lock is held while acquiring lineage or SQLite locks. No durable state is inferred from an in-memory claim after restart.

### Immutable billing projection journal and safe restoration

`billing_projection_event.v1` is a canonical complete snapshot appended in the same SQLite transaction as every inventoried route, capture, dispatch attempt, receipt, verification, finality, exclusion, quarantine, credit, reversal, refund, and void mutation. Mirror consumes payload bytes only; changed replay, chain gap/fork, lower request revision, or changed incarnation fails completeness.

Lineage uses two fault-domain-separated authorities: a local append-only `billing_lineage_prepare.v1` journal outside SQLite/backup bundles and an independently durable witness implementing conditional append by `(incarnation, sequence, predecessor_digest, record_digest)`. Both contain canonical PREPARE/COMMIT/ABORT/SUPERSEDE records and neither contains secrets. A PREPARE contains a canonical mutation manifest: exact table, operation, primary-key digest, before-row digest, after-row digest, required projection-event digest, multiplicity and ordering for every statement in the proposed SQLite transaction. A mutation may enter SQLite only after identical PREPARE bytes are fsynced locally and acknowledged durable by the witness. It is not acknowledged, dispatched, mirrored, or published until identical COMMIT is durable in both. Build 3 production qualification is blocked unless the witness is deployed on an independently failed host/volume with authenticated transport, bounded records, retention at least equal to the source, tested restore access, and an approved RPO of zero for acknowledged lineage.

The activated SQLite store never exposes the raw writer pool or its native-connection authorization setter outside the lineage owner. After both PREPARE acknowledgements, the owner leases one dedicated native SQLite connection, begins `IMMEDIATE`, and installs an unexported connection-local single-use authorization bound to the native connection identity, SQLite transaction identity, incarnation, sequence, predecessor, canonical event digest and exact mutation manifest. Durable BEFORE triggers on every governed table call `macprovider_lineage_authorize(table, operation, key_digest, before_digest, after_digest)`; a registered protocol-2 connection without the exact transaction authorization fails just like an old or unregistered connection. Each accepted trigger consumes one expected manifest occurrence. The required projection-event insert is itself governed. Before COMMIT, the owner calls `macprovider_lineage_finalize(event_digest)`, which succeeds only when the exact ordered manifest is exhausted and the immutable projection row matches; a driver commit hook rolls back any transaction that is unfinalized, has extra/missing/reordered statements, or presents a reused authorization. COMMIT atomically consumes the authorization. ROLLBACK, failed statement, connection return, cancellation or process death clears the connection context without changing the durable PREPARE; normal lineage recovery resolves it. SQL text, `set_config`, a protocol-number function, migration helpers and public Go methods cannot create or copy the authorization. Any direct `Exec`, alternate connection, newly opened handle or changed table/body/key/multiplicity therefore fails before a governed row commits.

Recovery runs offline with money writes, routing, projection, and status unavailable. It compares local journal, witness, SQLite, Postgres applied head, buyer reservation/credit records, and acknowledgement audit:

| State | Required resolution |
| --- | --- |
| Exact PREPARE plus exact SQLite event, no COMMIT on one/both lineage copies | Verify predecessor/event bytes and no conflicting descendant; append/repair the identical COMMIT on both, then resume from that committed head. |
| Exact PREPARE on both, SQLite event absent, no COMMIT/mirror apply/acknowledgement/dispatch | Two authorized operators sign a `supersede_abort` record binding all inspected heads and evidence. Conservatively void the attempt and release/refund its reservation; never reapply the proposed mutation. |
| PREPARE present but any DB/mirror/ack/dispatch evidence is incomplete or contradictory | Remain unavailable. Restore missing authority from the intact copy or committed target evidence; no operator vote may guess the outcome. |
| Local journal lost/corrupt, witness intact | Rebuild a byte-identical local copy through the witness committed head, verify every digest and SQLite/mirror equality, then dual-control reopen. |
| Witness lost/corrupt, local intact | Provision a replacement independent witness, replicate/verify the complete lineage and heads, then dual-control reopen. |
| Both lineage authorities lost without a target carrying a fully verified committed head | Permanent qualification blocker. No new incarnation may claim continuity. |

A new incarnation is permitted only under dual control after every prior PREPARE is committed or superseded, every outstanding request/reservation/credit is restored exactly or terminally voided/refunded, and local/witness/SQLite/Postgres heads agree. Its genesis binds the prior incarnation/head, recovery-bundle digest, operator approvals, terminalization manifest, and global idempotency namespace. Sequence numbers never repeat across the `(incarnation, sequence)` key, and external references remain globally unique, so mirror or reward application cannot duplicate. Compensating events reference prior event IDs; history is never rewritten. Failure to prove any precondition keeps service unavailable.

### Gate-B0 executable feasibility slice and sustainable lineage

The Gate-B0 lane has no dependency on Gate H0, H1, A0, references, calibration hosts or governed numeric evidence. Its documentation/schema package commits closed canonical schemas and field bounds; the exhaustive symbol/SQL mutation inventory; exact SQLite/WAL/APFS, coordinator and witness topology; deterministic seeded synthetic workload and fault schedule; the protocol-module interface, including native-connection authorization and commit-hook feasibility; benchmark formulas; and the segment/checkpoint/archive state machine. Gate B0D reviews those exact digests plus the bounded write scope for Feasibility Tooling Slice B0I. No executable benchmark claim exists at B0D. Its schema forbids collector/profile/reference/calibration/probability/threshold fields and its build graph cannot import Swift measurement or evidence packages.

After B0D passes, Slice B0I may implement only `phase4-coordinator/internal/billinglineage/`, its `feasibility` adapters, `cmd/lineage-feasibility`, tests and fixtures. The core package implements the exact canonical encoding, predecessor checks, local/witness PREPARE/COMMIT sequence, transaction-scoped SQLite authorization/finalization, segment sealing and checkpoint verification later reused unchanged by production. Feasibility adapters operate only on generated synthetic money mutations and isolated disposable paths. The command requires an explicit `qualification` build tag plus a compile-time marker absent from production builds. Import-graph, binary-symbol, command-registry, container, package, installer, workflow and deploy-manifest tests prove coordinator/provider/Malibu/release artifacts cannot contain, invoke, enable or route to it. Gate B0E performs independent full-slice code/security/architecture review, verifies those exclusions, and freezes the source, dependency, compiler and executable digests. Production must reuse the exact core package commit and contract; a change reopens B0D/B0E and invalidates measurements. Gate-B0 output is feasibility evidence only: without the numeric lane and Gate B it cannot authorize Product Slices 1–7, qualification, status publication, settlement or economics.

Only after B0E may the frozen command execute the exact `local PREPARE fsync -> witness PREPARE durable ack -> SQLite transaction/WAL fsync -> local COMMIT fsync -> witness COMMIT durable ack` protocol at 10k/1M/10M events and concurrency 1/8/32. It must sustain at least 100 complete mutations/s for 10 minutes; added p50/p95/p99 route-start latency at most 5/15/30 ms and p99 no more than 15% over the bound baseline; p99 lineage-lock wait at most 20 ms and hard 50 ms deadline; 1,024-entry bounded queue; 64 KiB hard event limit and p99 at most 16 KiB; and the bootstrap/recovery/storage/RSS/reserve/continuation gates in the paired test spec.

Lineage is indefinitely append-only at the logical level and bounded in the hot tier. Local and witness authorities write identical numbered segments, each capped at the lesser of 1 GiB or 7 UTC days. A `segment_seal.v1` is the final record and binds incarnation, first/last sequence, record count, predecessor segment seal, byte length and ordered record-chain root. Every 30 days or 4 sealed segments, whichever comes first, both authorities append an identical `lineage_checkpoint.v1` binding all prior segment seals through the current head, SQLite and Postgres applied heads, the canonical individually bounded recovery record and digest for every nonterminal request/reservation/credit obligation, global idempotency namespace, archive catalog generation, and previous checkpoint digest. Gate B0D fixes both a maximum obligation count and checkpoint byte size; admission stops before either limit and resumes only after authoritative terminalization reduces the next checkpoint below both bounds. Checkpoints summarize for startup but never rewrite events or authorize a missing segment.

A sealed segment may leave hot storage only after byte-identical copies and metadata are durably stored and read-back verified in two archive authorities independently failed from each other and from both active local/witness authorities, the local and witness catalogs conditionally append the same archive-location/content digests, no nonterminal obligation depends on payload not carried in the checkpoint, the configured minimum full-event retention has elapsed, and dual control signs the move. This is replica relocation, not logical deletion: at least two verified retrievable copies of every segment remain, chain order and external IDs remain unchanged, and restore validates from genesis or a previously fully validated checkpoint plus every later segment. If either archive copy, catalog, checkpoint, or obligation proof disagrees, eviction and new money work stop. Archive replacement repeats copy/read-back/catalog-CAS before retiring an old volume; an archive cannot be its own witness failure domain.

Positive qualification lasts at most 30 days and renewal requires a fresh measured growth percentile, archive restore sample, checkpoint replay, volume-health result, and proof that every hot and archive authority retains at least `max(10 GiB, 180 days at the measured p99 daily growth)` free usable capacity after current obligations. Alerts fire at 365/270/210 days projected exhaustion; the 210-day boundary suspends qualification renewal and the 180-day boundary blocks new money work before PREPARE. Benchmarks cover five years of synthetic segment/checkpoint continuation, two archive migrations, crash at every seal/checkpoint/catalog/move boundary, near-capacity recovery, and rollback to an old segment/catalog/checkpoint. Capacity, retention, or protocol changes reopen B0D/B0E/B; emergency deletion or head reset never restores qualification.

### Shared MLX resource arbiter

The in-process arbiter owns only MLX/Metal work submitted inside the serving provider process: buyer inference, compute observation, losslessness probes, `IdlePrewarmer.runInternalWarmup`, control-socket model load/swap/adoption/finalize, unload/shutdown, and explicitly classified in-process maintenance. `ProviderPreWarmer` is not an arbiter client: it calls `CandidateProviderRunner.start` and therefore belongs with decode bench, SPEC-028 canary/benchmark and isolated autotune under a mutually exclusive cross-process lifecycle coordinator. New MLX call sites and every process-launch site fail a static owner-registry test until classified.

Every supported serving entrypoint acquires the same lifecycle `flock` before constructing `ModelRuntime`, loading MLX/Metal, opening a routable session or spawning a candidate. Malibu.app and an explicit supervisor mode own the lease in the parent from before child birth through start, readiness, serving, drain and termination. Foreground `macprovider-cli serve`, including launchd when configured to invoke that command directly, is a self-supervised owner: it opens the lease itself, writes an atomic owner record binding boot-session UUID, random lease nonce, its PID/process-start identity, process-group ID, mode/profile and state, and retains the FD until admission is disabled, in-process work is drained/cancelled, device synchronization succeeds, `ModelRuntime` is destroyed and the record is cleared. A second direct serve, app-versus-direct serve, or any prewarm/decode/SPEC-028/autotune launcher fails before MLX initialization or `spawn`.

Supervisor-owned lock FDs are close-on-exec and never delegated to children; the child receives only a bounded nonce-bound control channel and a parent-liveness pipe. Closing that pipe or loss of authenticated heartbeats makes the child synchronously stop admission, cancel/quiesce MLX, and exit. Direct serve handles TERM/INT by the same drain/synchronize/destroy sequence and does not unlock early. Live in-place re-exec and lease handoff are unsupported; app, launchd and CLI upgrades must drain, exit, release, then start a new owner. A serving incumbent blocks a candidate before `spawn`; transition requires the incumbent to drain, synchronize, destroy its runtime, exit and release, after which one contender acquires and revalidates. The supervisor uses a new process group, bounded TERM/KILL escalation, `waitpid`, and verified PID-start identity.

After an owner crash the kernel releases `flock`, but the stale record remains. A contender holding the newly acquired lock validates boot/PID-start/process-group identity, rejects a live or ambiguous/PID-reused owner, and kills/reaps only a verified orphan child group. For a dead self-owner it verifies absence of every registry-classified MLX process and completes a bounded Metal/device-quiescence barrier before clearing the record; inability to prove quiescence fails closed. The registry gives one explicit launcher mode to Malibu.app, launchd-supervisor, launchd-direct and interactive-direct paths, so wrappers cannot double-acquire or silently bypass ownership. No child becomes routable from readiness alone.

In-process lease states are `queued -> dispatching -> running_load -> running_prefill -> running_sampler -> serializing -> cancelling -> quiescing -> quiesced -> terminal`. Buyer inference has absolute admission priority inside the serving process. Model load/swap/adoption takes an exclusive transition lease, blocks probes and idle prewarm, drains/cancels lower-priority work, synchronizes the device, changes generation, and only then exposes the new runtime. A two-second quiescence miss drains the provider from routing until device synchronization proves quiescence. Lease generation fences late callbacks and old-runtime results.

### Canonical reward inputs, seven-scope dispositions, and shadow boundary

Before Gate B, SPEC-021 and SPEC-014 must commit machine-readable `provider_reward_status_inputs.v2`, `provider_reward_status.v2`, and generated vectors. The reward owner, not status handlers or clients, produces an effective projection byte-for-byte equivalent to the canonical SQL predicate. The input preserves every simultaneous disposition at these seven closed scopes: `ledger_row`, `useful_work_source`, `provider`, `wallet`, `cohort`, `duplicate_class`, and `epoch`.

Each projected ledger row carries bounded amount, source/accrual ID, scope memberships, and a canonically sorted disposition array `(scope, scope_key_digest, kind=hold|exclude|burn|retire, lifecycle=active|released|terminal, effective_event_id, effective_at, release_at?)`. Active holds are nonwithdrawable until an authoritative release; active/terminal exclude, burn, or retire facts are nonwithdrawable and cannot be overridden by another scope. Released facts remain activity only. The projection also carries provider-day and wallet-day cap states, withheld amounts, `cap_replay_pending`, ledger source head/completeness/freshness, and exact aggregates for withdrawable, held, capped, excluded, burned, and retired amounts. Unknown scope, multiplicity/order violation, disagreement with SQL, or pending cap replay makes withdrawal unavailable; it can never map to `withdrawable`.

Postgres owns a monotonic `reward_source_revision` for its ledger rows, all seven disposition facts and lifecycles, provider/wallet/cohort/duplicate/epoch membership, provider-day and wallet-day cap counters, withheld amounts, `cap_replay_pending`, production-accrual links, reward activity, billing-mirror completeness/head, and the applied payout-wallet source head. Every inventoried Postgres writer calls a `SECURITY DEFINER` database mutation entry point inside its existing transaction. Direct DML privileges on governed tables and the revision sequence are revoked from runtime roles. The entry point allocates one monotonic revision, binds it to the current transaction ID plus an unforgeable server-side token unavailable to callers, writes every affected fact/activity row with that revision, and inserts the revision record with `source_transaction_at=transaction_timestamp()` as the final statement before the atomic transaction commit. Triggers validate that transaction/token/revision tuple and reject direct INSERT/UPDATE/DELETE, including legacy writer paths; a caller cannot authorize itself with `set_config`. Sequence gaps are allowed; revision reuse or a fact visible without its committed revision is not.

Payout-wallet authority remains in the separate SPEC-016 SQLite database, so Build 3 does not claim a single atomic revision across both databases. It receives a separate `payout_wallet_lineage.v1` stream with its own incarnation/sequence/head, local append-only journal and independent witness. Every add, replace, revoke, disable or remove mutation first durably PREPAREs the canonical `payout_wallet_event.v1` on both authorities, then uses the same connection-and-transaction-scoped authorization to atomically mutate `provider_payout_addresses`, append the immutable event and advance the database-local `(wallet_source_incarnation, wallet_source_sequence, wallet_source_head_digest, source_committed_at)`, then durably COMMITs both lineage authorities before acknowledging the wallet operation. Durable triggers prohibit lifecycle mutation without its exact event/head advance. An SQLite-committed event missing either lineage COMMIT is recovery-pending and cannot be mirrored or reported current.

The polling mirror reads a stable SQLite event range and independently verifies that local and witness COMMIT heads equal the SQLite head. It consumes only a contiguous, dual-committed range and in one Postgres reward-revision transaction applies the versioned wallet facts/activity plus the exact applied wallet head and gap/fork/recovery state. Events are idempotent by incarnation/sequence/digest; changed replay, gap, fork, source restore, lower head or authority disagreement makes the wallet domain unavailable and cannot delete last-known facts. Poll time is never represented as source commit time. Payout execution may keep its independently fresh operational source, but it is a separate payment domain and cannot be joined into reward or withdrawal truth by a handler.

The reward endpoint implements a truthful joined-version protocol. It first opens one Postgres `REPEATABLE READ READ ONLY` transaction, reads the greatest visible reward revision `R`, its transaction snapshot time, the applied wallet head `H`, billing head/completeness and all versioned reward facts plus first activity page. While that transaction remains open, it asks the wallet-source owner for a read-only authoritative snapshot containing only the SQLite head/source commit time and matching local+witness COMMIT heads; raw payout rows are never returned. It returns a composite `reward_view_version=(R,H)` only when all three wallet heads equal `H`, the source incarnation matches, neither side reports a gap/fork/restore/recovery, and the wallet source time satisfies the closed freshness bound. If the wallet source advances after the Postgres snapshot, the heads differ and wallet/withdrawal facts fail `wallet_projection_pending`; if it advances after the authoritative head read, the returned view is linearizable immediately before that later mutation. If any wallet authority is unavailable or stale, last-known wallet facts may be displayed with their old source time, but wallet-bound and withdrawal eligibility are unavailable; balances, compute and independently reported payment/USDC states retain their own truth. No endpoint reads payout-address rows directly or combines current SQLite wallet contents with Postgres balances.

`generated_at` is allocated only after both snapshots and validation succeed and is distinct from Postgres `source_transaction_at`, wallet `source_committed_at` and payment/USDC times. Activity is append-only with `created_revision` and optional wallet source sequence; state changes append new facts rather than erasing prior activity. A cursor MAC-binds provider, `R`, `H`, stable `(effective_at,event_id)` boundary, filter, page size and a 24-hour expiry; immutable/versioned source rows needed by a cursor are retained for at least 48 hours. Later pages use revision-as-of predicates for both heads and return the same composite version after verifying that retained wallet history still contains `H`; unavailable as-of data fails `snapshot_expired` and never silently opens a new snapshot. A separately requested refresh creates a new joined view. Static inventory covers every Postgres writer and every payout-wallet lifecycle writer. No status handler or client constructs its own join.

Earning input additionally requires `projection_environment=production`, `reward_capability=enabled`, and an authoritative production-ledger accrual ID for the displayed recent request. Build 3 fixes `reward_capability=disabled`; therefore provider-visible earning is `unavailable/reward_capability_disabled` even when an operator shadow decision passes. `eligible_idle` is also unavailable while capability is disabled. Shadow records use a separate qualification schema, database/sink and dependency graph; provider APIs cannot query it, reward activity excludes it, and Swift/portal schemas have no shadow identifier or state. Balances and withdrawal eligibility continue to reflect only canonical production ledger facts. Payment remains `unavailable/malibu_payment_execution_unavailable`.

The exact precedence and all output enums are committed in the schema package. Tests enumerate all seven scopes, simultaneous facts, release/terminal transitions, cap replay, amount aggregation, unknowns, production capability/accrual requirements, and cross-client vectors. One blocked canonical row is sufficient to prevent its amount from entering withdrawable aggregation.

## Data changes, compatibility, rollback, and observability

All migrations are additive until the one-way lineage activation. Before activation, rollback remains ordinary while new consumers stay disabled. Activation occurs in an offline maintenance state with routing and all money writers stopped: first the external supervisor installs and verifies a protocol-2 signing/digest allowlist and withholds the dedicated money-directory identity/handle from every other executable; then the sole approved writer locks and reconciles local/witness/SQLite heads; then identical `lineage_activation.v1` PREPARE records become durable locally and at the witness; then one SQLite transaction sets `lineage_min_writer_protocol=2` and installs the durable BEFORE triggers plus authorization/finalization metadata required by the transaction-scoped contract; finally identical activation COMMIT records become durable in both authorities before the service can start. Any failure remains offline. The new writer enables its private native-connection authorization setter only after supervisor identity and local/witness/SQLite activation heads agree. A restored pre-activation SQLite file is rejected because the supervisor and external witness retain the activated epoch; a restored post-activation file retains triggers that reject an unregistered connection or a registered connection without the exact PREPARE-derived authorization. Direct SQL, overlooked same-process helpers and every supported previous binary fail before their first governed mutation.

Binary rollback after activation is prohibited. Operational recovery uses a forward recovery build that preserves protocol-2 writers, triggers, segment/checkpoint/archive handling and reward revision writers while disabling probes, consumers and v2 UI. It cannot lower the activation epoch or minimum writer protocol. Qualification includes signed startup rejection tests for each supported previous release, the pre-activation-file restore case, every direct legacy mutation entry point, and forward recovery. V1 clients receive conservative legacy fields for 90 days after separately authorized v2 rollout or through the next provider-app stable release, whichever is later. New clients fail only the affected projection closed. Shadow artifacts remain outside provider dependencies. Recovery never deletes logical history, rewrites captures, resumes an uncertain cursor, or restores misleading language.

Metrics cover probe/arbiter leases, queue/cancel/quiescence, model transitions, evaluation reason, CAS/revocation, token boot/key epoch and orphan reconciliation, lineage local/witness heads, recovery states, SQLite/lock/ack latency, bootstrap, seven-scope reward reasons, cap replay, freshness, pagination and redaction. Labels exclude raw prompts, vectors, tokens, secrets, buyer identity, scope keys and unbounded provider strings. Ambiguity, chain disagreement, stale observations, reference disagreement and unknown contracts fail closed and alert.
