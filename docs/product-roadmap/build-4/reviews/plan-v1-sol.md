## Findings

### HIGH H1 — The proposed observation-failure terminal outcome contradicts the normative settlement contracts

**Evidence.** `docs/product-roadmap/build-4/implementation-plan-v1.md:223-231` defines the four settlement outcomes, then allows missing, expired, revoked, or mismatched observation evidence to finish as either `quarantined` or `zero_settled`. SPEC-022 defines `quarantined` as the trust-failure outcome and `zero_settled` only as a verified non-creditable terminal outcome (`specs/SPEC-022-verified-model-settlement.md:347-358`); its normative rules repeat that receipt trust failures cannot be `zero_settled` (`specs/SPEC-022-verified-model-settlement.md:594-600`). SPEC-036 is even more specific: compute-integrity drift must not use `zero_settled` (`specs/SPEC-036-compute-integrity-receipt.md:482-489`), and unknown, pending, expired, stale, unreadable, or uncovered evidence must remain non-payable and become `quarantined` at the bounded deadline (`specs/SPEC-036-compute-integrity-receipt.md:560-575`). Test T39 says only “pending/quarantined,” while T47 and T54 do not assert the closed Build 3 reason-to-outcome mapping (`docs/product-roadmap/build-4/test-spec-v1.md:206-208,238-240,266-268`).

**Consequence.** An implementation following the plan could record an observation trust failure as a verified-zero economic terminal, erasing the distinction between failed trust and a verified non-creditable outcome. That corrupts settlement/audit meaning and can make later reconciliation, dispute handling, reward exclusion, and buyer/provider accounting follow the wrong branch.

**Required correction.** Remove `zero_settled` from every observation-evidence failure path. State that an optional bounded `pending` interval ends in `quarantined` with the exact accepted SPEC-036 closed reason and precedence; reserve `zero_settled` for fully verified non-creditable terminal outcomes. Make T39, T42-T47, and T54 assert the exact terminal outcome, reason, buyer debit, provider credit, reward, payout-readiness, and first-terminal finality for each missing/stale/revoked/mismatched observation case.

### HIGH H2 — The private authority chain does not pin the provider receipt key accepted at request start

**Evidence.** `PrivatePoolRouteAuthorityV1` contains a receipt contract and observation profile but no provider receipt-key identity, key source, public-key digest, validity interval, or receipt-key generation (`docs/product-roadmap/build-4/implementation-plan-v1.md:124-138`). The reservation, AAD/wallet transcript, and authenticated dispatch context repeat the omission (`docs/product-roadmap/build-4/implementation-plan-v1.md:151-159,165-182,199-203`). The successor receipt carries its own signature key id, and the verifier is told to require an accepted key “at request start,” but the plan defines no immutable input from which to prove that temporal acceptance (`docs/product-roadmap/build-4/implementation-plan-v1.md:207-219,223-229`). This regresses an existing settlement invariant: `billing.RouteSnapshot` stores `ProviderReceiptKeyID` and `ProviderReceiptKeySource` (`phase4-coordinator/internal/billing/route_snapshot.go:38-47,102-112`), and `verifySettlementReceiptSPEC022` requires the receipt key id to match both the supplied public key and the route snapshot (`phase4-coordinator/internal/billing/settlement_verifier.go:165-181`). SPEC-022 requires the route-time snapshot and settlement receipt to bind the provider receipt-key identity (`specs/SPEC-022-verified-model-settlement.md:309-329,331-345`). T23 rotates only the relay identity/key-record material, T25 rotates provider session/release/admission state, and T31 mutates generic digests; none rotates or revokes the distinct SPEC-015 receipt key around request start (`docs/product-roadmap/build-4/test-spec-v1.md:138-148,172-174`). SPEC-041 explicitly says relay identity, request-encryption keys, and SPEC-015 receipt keys are distinct (`specs/SPEC-041-relay-blind-request-encryption.md:84-93`).

**Consequence.** A verifier cannot prove that the signing key in a successor receipt was the independently accepted receipt key for that request attempt. It could accidentally verify against a later, rotated, revoked, provider-selected, or compromised key, or implementations could invent incompatible hidden lookup rules. Since this key authorizes positive provider settlement, the omission breaks the cryptographic money-path root of trust.

**Required correction.** Add the exact accepted receipt-key identity and provenance to the immutable request-start route snapshot and `PrivatePoolRouteAuthorityV1`: at minimum key id, source/authority, public-key digest (or an unambiguous key-record digest), key generation, and validity/revocation snapshot required by the owning SPEC. Bind those fields through reservation response, AAD, wallet semantic signature, durable consume/dispatch state, authenticated provider dispatch context, receipt signing preimage, and settlement lookup. Add cross-language vectors and deterministic rotation/revocation/substitution tests at every lifecycle cut, including after dispatch to prove immutable request-start verification and before dispatch to prove rejection.

### HIGH H3 — “Immediately before WebSocket commit” has no atomic authorization/dispatch linearization contract

**Evidence.** The plan requires coherent rechecks at reservation, consume, quota hold, dispatch arm, and immediately before provider WebSocket commit, and requires a revocation after arm but before commit to prevent dispatch (`docs/product-roadmap/build-4/implementation-plan-v1.md:184-197,315-323`). It does not define what “commit” means, which component owns the final fence, how pool/auth/session/key/observation generations are synchronized with the first provider-visible byte, or how gateway quota, coordinator SQLite, the in-memory pool registry, and WebSocket session state compose. On the inspected base, the gateway consumes before its quota hold (`phase5-gateway/internal/router/relay_blind_success.go:175-213`), the coordinator commits the relay-blind row to `dispatched` in `relayblind.Store.armDispatch` (`phase4-coordinator/internal/relayblind/store.go:515-565`), and the buyer handler marks dispatch and builds the WS context before invoking the relay (`phase4-coordinator/internal/buyer/relay_blind.go:401-424`). The first provider network write happens later in `dispatchInference` at `session.sendProbe` (`phase4-coordinator/internal/ws/relay.go:1350-1390`). Existing Trusted Pool plaintext routing closes one pool-generation race with an atomic locked `BeginPoolDeliveryAtGeneration` decision (`phase4-coordinator/internal/trustpool/registry.go:495-514`), but the plan does not state how that fence is extended to all private-request authorities and the WS send. Test T21-T27 requests 100+ concurrent attempts but specifies no deterministic barrier at the final validation/write boundary (`docs/product-roadmap/build-4/test-spec-v1.md:126-156`).

**Consequence.** Authorization, membership, key, policy, or observation state can change after a successful recheck and before the ciphertext reaches the provider. The system may then dispatch work the plan promises has been prevented, while durable state and quota already describe a committed dispatch. Probabilistic race repetition cannot prove that this time-of-check/time-of-use window is closed.

**Required correction.** Define one exact dispatch linearization point and the authority that owns it. Specify the fence/lease token, generation fields, lock or compare-and-swap ordering, first-byte semantics, failure state, gateway quota compensation, coordinator/provider recovery, and interaction with immediate SPEC-042 revocation. The final generation check and delivery registration must be atomic with respect to the revocation mechanism; if the WS write cannot be in the same critical section, define an authenticated dispatch lease whose validity/revocation semantics close the gap. Add deterministic barrier-driven tests that pause immediately before the first provider-visible write, perform each revocation/change, then release the barrier and assert zero bytes, zero inference entry, burned material, correct quota state, and durable terminal state. Keep stress/race runs as additional evidence.

### MEDIUM M1 — The plan names an observation snapshot digest without defining its authoritative producer and delivery path

**Evidence.** The successor receipt must bind a request-start observation snapshot digest (`docs/product-roadmap/build-4/implementation-plan-v1.md:207-219`), but `PrivatePoolRouteAuthorityV1`, the AAD, and authenticated outer dispatch carry only the required observation profile id/version/generation (`docs/product-roadmap/build-4/implementation-plan-v1.md:124-138,165-180,199-203`). No step says which coordinator boundary captures the accepted Build 3 state, where it is persisted before dispatch, or how the provider receives an authenticated digest to sign without being trusted to choose or fabricate it. SPEC-036 requires the coordinator to persist the complete request-start state beside the route-time snapshot and to settle from that immutable state (`specs/SPEC-036-compute-integrity-receipt.md:720-724,801-810`). T31 mutates an “observation digest,” and T42 checks matching dimensions, but neither proves the digest originated from the authoritative coordinator capture rather than provider input or a settlement-time lookup (`docs/product-roadmap/build-4/test-spec-v1.md:172-174,218-228`).

**Consequence.** The receipt producer may be unable to sign the promised field, may sign a provider-selected claim, or may receive a digest that is not the same immutable state used by settlement. Recomputing at settlement would violate request-start immutability; trusting the provider would collapse the independent observation gate into provider attestation.

**Required correction.** After Build 3 is accepted, define the coordinator-owned atomic request-start capture, its complete canonical schema/domain, its link to the route snapshot and attempt, and its immutable persistence/freshness rules. Carry the authoritative digest to the provider in authenticated dispatch metadata and require the provider to echo/sign it; settlement must compare it to the persisted capture, not current observation state. Add origin-substitution, omitted capture, late capture, provider-chosen digest, stale generation, restart, and settlement-time state-change tests.

### MEDIUM M2 — Store migration and binary rollback behavior is not specified or tested

**Evidence.** Phase B says migrations are additive, idempotent, and “downgrade-readable where possible” (`docs/product-roadmap/build-4/implementation-plan-v1.md:260-264`). Rollback instructions disable new reservations and preserve dispatched rows but do not state whether old gateway/coordinator/provider/verifier binaries may open each migrated store, how schema-version rejection works, when a pre-deploy snapshot is safe, or how post-snapshot quota/settlement/journal effects are drained and reconciled (`docs/product-roadmap/build-4/implementation-plan-v1.md:286-294`). T27 exercises restarts/failover reconstruction, not old-binary startup against migrated databases or provider journal formats (`docs/product-roadmap/build-4/test-spec-v1.md:154-156`). The repository already has a concrete money/auth-path precedent: SPEC-040 explicitly allows fail-closed old-binary startup, permits snapshot restore only before post-snapshot traffic, otherwise requires drain plus preservation/reconciliation, and names required rollback evidence (`specs/SPEC-040-wallet-native-buyer-sessions.md:303-311`).

**Consequence.** A rollback can strand unknown private rows, make an old binary reinterpret or ignore successor state, reopen work, lose quota/settlement effects, or fail after traffic with no safe recovery procedure. “Where possible” is not a testable compatibility promise.

**Required correction.** Add a per-component/per-store migration and rollback matrix for gateway database, coordinator relay-blind and settlement stores, request logs, verifier inputs, and provider journals. For every old/new binary and old/new store pairing, define startup result, read/write behavior, disabled-mode behavior, snapshot/drain constraints, in-flight row handling, and reconciliation owner. Add fresh-upgrade, idempotent rerun, disable-after-use, fail-closed downgrade, zero-traffic snapshot restore, post-traffic drain/reconcile, and roll-forward-after-failed-rollback tests.

### MEDIUM M3 — Protected physical-Mac evidence has no closed artifact or validator contract

**Evidence.** Phase G and T64 require signed journey capture and enumerate report fields (`docs/product-roadmap/build-4/implementation-plan-v1.md:282-284`; `docs/product-roadmap/build-4/test-spec-v1.md:304-328`). T63 only says signed-journey semantic validation and expiration pass; it does not define the artifact schema, signature authority, canonical bytes, hashes of raw test outputs, expiry, replay protection, commit ancestry, dirty-tree policy, or validation tool (`docs/product-roadmap/build-4/test-spec-v1.md:304-306`). T64 records a repository commit and high-level outcomes but does not bind the signature to coordinator receipt/settlement rows, gateway quota rows, provider journal claims, MLX runtime output, or the exact commands that generated those records (`docs/product-roadmap/build-4/test-spec-v1.md:310-328`). The plan itself says a protected signing environment is only a prerequisite “if conformance promotion is later attempted” (`docs/product-roadmap/build-4/implementation-plan-v1.md:327-335`), while T64 classifies protected evidence as required for implementation acceptance.

**Consequence.** A hand-authored summary with a valid detached signature could satisfy the written acceptance language without proving that one execution produced the MLX result, receipt, persisted settlement, quota finality, and buyer-visible state. Reviewers also cannot determine whether evidence is fresh, belongs to the reviewed commit, or was captured from a dirty/instrumented tree.

**Required correction.** Define a Build 4 protected-journey schema and semantic validator before qualification: canonical format, trusted signer and custody, commit/ancestry/dirty-state rules, capture time and expiry, exact command transcript, immutable IDs/digests joining request attempt, route authority, envelope, WS dispatch, provider claim/runtime, receipt, observation capture, settlement row, quota row, and buyer response, plus hashes of sanitized raw outputs. State whether protected signed evidence is mandatory for local hardware qualification and separately for conformance promotion. Make T63-T65 reject missing joins, mismatched hashes, reused evidence, untrusted signers, expired evidence, dirty-tree ambiguity, and fixture/selftest substitution.

### MEDIUM M4 — Mixed-version capability tests do not prove the claimed five-component fail-before-quota rule

**Evidence.** The plan says gateway, coordinator, provider runtime, verifier, and buyer client independently advertise compatible versions, and any old component fails before quota (`docs/product-roadmap/build-4/implementation-plan-v1.md:110-120,239-250,286-294`). The test spec checks unknown receipt versions, one selected provider capability, and broad legacy regressions (`docs/product-roadmap/build-4/test-spec-v1.md:76-82,114-124,274-306`), but it has no Cartesian rollout matrix over old/new client, gateway, coordinator, provider, verifier, and migrated/unmigrated stores. It also does not specify capability authenticity, freshness, cache invalidation after downgrade/reconnect, or which pre-quota hop proves verifier support.

**Consequence.** A partial rollout or stale capability cache can admit a request that a downstream component cannot process, after quota/consume or after encryption. The unsupported path can become an uncertain committed request rather than the promised pre-quota typed failure, and an old verifier can leave money rows pending indefinitely.

**Required correction.** Define the version-negotiation source and signed/authenticated freshness semantics for each component. Add a bounded but complete compatibility matrix covering every single-old-component case, supported version intersection, downgrade/reconnect/cache expiry, unknown future versions, migrated/unmigrated stores, verifier unavailability, and rollback/roll-forward. For each unsupported combination, assert no reservation consumption, no quota hold, no provider bytes, no inference, no settlement/reward mutation, and the exact buyer recovery action.

### MEDIUM M5 — Retention and pruning rules are missing for the expanded replay and settlement evidence graph

**Evidence.** Phase B adds private authority fields to relay-blind reservations, route snapshots, settlement receipts, request logs, gateway replay metadata, and provider journals, but the plan gives no cross-store retention deadlines or deletion ordering (`docs/product-roadmap/build-4/implementation-plan-v1.md:260-264`). Rollback preserves in-flight state, yet neither the plan nor T27/T39-T55 tests pruning near pending deadlines, settlement finality, replay windows, reconciliation, disputes, or provider-journal recovery (`docs/product-roadmap/build-4/implementation-plan-v1.md:286-294`; `docs/product-roadmap/build-4/test-spec-v1.md:154-156,204-272`). Current SPEC-041 requires key revocations to survive signed expiry plus replay retention and provider journal entries to survive replay retention plus active execution (`specs/SPEC-041-relay-blind-request-encryption.md:91-93,168-170`); SPEC-022 requires retrieval contracts to define retention (`specs/SPEC-022-verified-model-settlement.md:568-579`).

**Consequence.** One store can prune the authority, key, observation, receipt, or journal record needed by another store before pending settlement or recovery completes, producing an avoidable quarantine or losing proof of replay. Unbounded retention also conflicts with the plan's privacy and bounded-metadata claims.

**Required correction.** Add a field/store retention matrix with a shared attempt identifier, minimum replay/pending/reconciliation/dispute windows, maximum privacy bounds, tombstone requirements, and dependency-aware purge order. No authority/evidence record may be removed while any linked request is active, pending, uncertain, appealable, or not durably reconciled. Add clock-boundary, restart, partial-purge, delayed receipt/evidence, dispute retrieval, and configuration-cycling tests that prove both recoverability and bounded deletion.

### LOW L1 — Timing-oracle acceptance is not measurable

Neither test defines the bound, sample size, warm-up, network/runtime isolation, statistical decision rule, false-positive budget, or whether a constant minimum-work/floor strategy is required.

**Consequence.** Implementations and reviewers can interpret any observed distributions as acceptable, so the tests do not prove the non-enumeration claim and are likely to be flaky in CI.

**Required correction.** Define the observable fields and concrete timing policy. Prefer a deterministic common-work/floor invariant where feasible; otherwise specify environment, sample size, quantile/difference threshold, statistical test, retry policy, and separate local-versus-network qualification criteria.
