# Incident: v1.8.102 did not land on a stranded HOME-ACL provider

**When:** 2026-08-19 release → 2026-08-20 live failure (MrBeison)  
**Witness:** Pearl `mp-1962fb3ccb9fa0d227767c3a77b54fbe` (`MrBeison MacBook Pro`)  
**Status at write:** Malibu.app shows 1.8.102; launchd CLI still **1.8.93**, ready, routing eligible, ~3 jobs/min. Repair click requested ~00:53Z; heartbeat still 1.8.93 at 00:54Z.

## What 102 was supposed to do

PR [#1082](https://github.com/Augustas11/macprovider/pull/1082) / commit `54233e51`:

The incumbent watchdog rejected write-style ACLs on `$HOME` while walking to the autoupdate root (`acl_write_rejected:$HOME`). That loop ran **before** the new watchdog/CLI could be installed, so in-app update could not apply the fix.

102 did three things:

1. New watchdog: exact-path HOME ACL exception (`allow_home_acl_write` only when path == `~`). Descendants stay strict.
2. Malibu: if watchdog logs still contain `autoupdate recovery_error=acl_write_rejected:` on `$HOME`, show **Repair provider software**.
3. Repair: bundled `install.sh` with `MACPROVIDER_REPAIR_EXISTING_INSTALL=1`, no referral, keep identity and models.

Explicitly **rejected** in that commit: log-triggered automatic repair; broadening ACL tolerance beyond `$HOME`.

Explicitly **not tested**: notarized packaging and **updater-path release verification**. House runbook `docs/runbooks/provider-cli-release-verification.md` still requires updater acceptance from the previous stable CLI. That gate was deferred, then the coordinator advertised 1.8.102 anyway (`c201129b`).

## Why in-app update failed (expected)

The ACL fix lives in the **new** watchdog. The Mac was still running the **old** watchdog. Old watchdog still rejects `$HOME`, still loops, still never installs 102. Advertising 1.8.102 made clients *try* the updater into a known-stuck path.

## Why the GitHub DMG also failed to land

`Malibu-v1.8.102.dmg` (34 downloads by 2026-08-20) is a GUI replacement, not a provider update.

Architecture (release notes, same tag): the launchd CLI owns the atomic transaction; Malibu.app is one member of that transaction. Dragging the `.app` to Applications replaces `/Applications/Malibu.app` only. It does **not** replace `~/macprovider/macprovider-cli` or `~/.local/share/macprovider-watchdog/`.

So after a “direct download”:

| Piece | After DMG drag | Needed for 102 to have landed |
|---|---|---|
| Malibu.app | 1.8.102 | 1.8.102 |
| launchd CLI | still 1.8.93 | 1.8.102 |
| watchdog | still old (HOME ACL reject) | new (HOME ACL exception) |

Pearl evidence: MrBeison’s GUI was 1.8.102; `provider_last_known.binary_version` stayed `1.8.93`.

102 then did what it was coded to do: read the old watchdog log, put **Repair provider software** on the dashboard, and wait for a click. That click *is* the landing. The DMG is not.

Release notes made this worse: “First run drives install.sh onboarding.” For an admitted provider, first run of a sideloaded app is an upgrade, not onboarding. Combined with `die 20` mapped to “A referral code is required to join right now,” Repair/onboarding looks like eviction. `invalidCLI` (“The installed provider could not be verified”) is Malibu failing to attach to the still-old CLI, not Pearl revoking the token.

## Catch-22 if Repair cannot prove the incumbent

Repair skips referral only if `repair_safe_incumbent_present` succeeds. That check still fail-closes on ACLs on **descendant** dirs and on evidence files (`no_acl`). The watchdog exception is `$HOME` only. If the same write ACL sits on `~/Library` or the identity files, Repair exits 20 and the UI says “enter an invite.” The mitigation cannot install itself.

102 also refused to auto-run Repair from those logs. A non-proficient provider who already downloaded the DMG still has to find and press a second button. If that button is shown next to “referral required,” they stop.

## What did not happen

- Pearl did not drop him. Token, payout bind, and routing stayed up. 24h leaderboard rank 1 at the time of the screenshots.
- This is his third provider_id (`mp-bcacdf97…` Jul 30 revoked Aug 5 → `mp-9182c337…` 7-minute bootstrap → `mp-1962fb3c…` Aug 6). A referral “fix” would have been a fourth identity.

## Learnings

1. **Landing = new CLI + new watchdog via the transactional installer.** A notarized Malibu.app on GitHub is not a landing. Do not hand a DMG as the workaround for a stuck updater unless the next launch auto-runs Repair for this exact ACL finding.
2. **Do not advertise a release whose updater path is the bug being fixed** until a stranded journey is proven: previous-stable CLI + `$HOME` write ACL + DMG sideload + one Repair click, no terminal, no invite copy.
3. **Never map existing-provider repair failure (exit 20) to “enter an invite.”** That copy is what turned a local ACL stall into a trust incident.

## Follow-up (not this fire)

- Revisit “no automatic repair” for this one log signature: incumbent present + `acl_write_rejected:$HOME` should run `repairExistingInstall` without a second click.
- Repair evidence must tolerate the same `$HOME` ACL the new watchdog allows; keep descendant checks.
- Split installer exit 20: missing invite (new join) vs missing repair evidence (keep identity, different copy).
- GitHub release body: dragging Malibu.app is not an update; Repair is.
- Do not mint a referral for MrBeison. Watch Pearl for `binary_version` 1.8.102 on `mp-1962fb3c…`.
