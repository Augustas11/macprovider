## Launch counts per MoE layer

Counted from graph inspection: `mx.export_to_dot` of the identical op
sequence on mlx 0.31.2, view-only primitives excluded (Reshape, ExpandDims,
Squeeze, Slice, Broadcast). Hidden copies inside `GatherQMM` and `GatherAxis`
for the non-contiguous top-k slice are not counted, so stock is a lower bound.

| T | stock | fused |
|---:|---:|---:|
| 1, 2, 4 | 24 | 3 |
| ≥ 8 (sorted gather path) | 30 | 3 (stock is used above T = 4) |

The 24 stock launches are:

- 5 `QuantizedMatmul`: router, shared gate/up/down, shared-expert gate.
- 1 `Softmax`, 1 `ArgPartition`, 1 `GatherAxis` (takeAlong), 2 `Sum`, 1 `Divide`.
- 3 `GatherQMM` and their 3 `Arange` lhs-index launches.
- 3 compiled elementwise kernels: routed silu·up, shared silu, the weighted
  multiply.
- 1 `Sigmoid`, 2 `Multiply`, 1 `Add`.

Per forward that is 960 → 120 MoE launches.

## Kernel design (v2, the measured default)

1. **Router.**
   - The 8-bit 257-row GEMV (256 router rows + the shared-expert gate row) is
     spread over 33 threadgroups of 8 simdgroups. Each threadgroup computes its
     rows for every token, so the weights stream once.
   - Each threadgroup bumps a per-block device counter. The last one, after
     `atomic_thread_fence(mem_device, seq_cst, device)`, runs the rest, one
     simdgroup per token: softmax over the bf16 logits, top-8 by
     `(bf16 prob bits | expert id)` keys, which reproduces the stock last-k
     stable-sort tie rule, then bf16 renormalization and sigmoid(shared gate).
     It resets the counter.
   - Outputs: ids `[T, 8]` and weights `[T, 9]`.
   - v1 used one threadgroup per token, so a single core read the whole 526 KB
     router. That cost about as much as the 6 stock launches.
2. **Gate/up.**
   - The grid is `(I/16 row tiles) × (T·8 + 1 slots)`.
   - A slot threadgroup continues only if its pair is the first occurrence of
     its expert (inline de-duplication, no bucket launch). The last slot is the
     shared expert.
   - Lanes cover 16 consecutive k per step, so up to `gateUpTokens = 2` tokens
     routed to the expert share each weight load and dequant.
   - The epilogue is `bf16(silu(bf16 g)) · bf16 u`, rounded as in the stock
     compiled kernel. Output h is `[T·8 + T, 512]` bf16.
3. **Down + combine + shared.**
   - The grid is `(H/8 row tiles) × (token blocks of 1)`.
   - Each threadgroup builds its token's expert mask in threadgroup memory and
     walks the experts in ascending id. For each it computes
     `bf16(dot) → bf16(·w) → +=`. It then adds `bf16(sigmoid gate · shared)`.

Determinism: every output row is one fixed-order dot plus an
ascending-expert-id sum. A token's output therefore does not depend on its
co-batched tokens.

Constraint: the router counter assumes one in-flight call per block. The lab
`layer` check originally evaluated several independent calls of the same block
concurrently and read garbage. Production decode and verify are serial per
block. A core primitive would own its scratch instead.

## MTP verify ratio and decode effect

- `[1,2]/[1,1]` forward total goes from 1.19 (stock) to 1.29 (fused). GPU only,
  it goes from 1.22 to 1.35. The verify step itself gets cheaper: fused
  `[1,2]` (11.19 ms) costs about what stock `[1,1]` does (11.00 ms).
- Ordinary decode gains more than verify does, so native MTP's relative edge
  shrinks:
  - At 1 slot, native/ordinary goes from 1.29x to 1.15x.
  - At 2 slots, it goes from 1.16x to 1.03x.
- Absolute throughput still rises. At 1 slot, stock native MTP gives 104
  tok/s, fused ordinary 100 and fused native MTP 114. At 2 slots, 143 / 141 /
  146.
- The fused ordinary path alone captures most of what MTP gave at 1-2 slots.

## Verdict and integration path

**Go for T ≤ 4 (decode B ≤ 4, verify B ≤ 2).** The decode and MTP numbers
above are the case. Correctness is better than stock against fp32, routing is
bit-identical in selection, and the path is batch invariant.

**Not yet for T ≥ 8.** The fused gate/up only matches `gather_qmv` bandwidth,
so stock stays there. 8-slot serving is unchanged.

Next:

1. Gate/up bandwidth. Use 16-byte weight loads with x staged in threadgroup
   memory, so more tokens share each dequant without register spill. The
   target is above 450 GB/s, which would extend the win to T = 8-16.
2. Production integration. Move the three kernels into an mlx core primitive
   (`fast::qwen_moe_small_t`) in an mlx-swift fork:
   - fixed pipelines;
   - scratch owned per call, which removes the shared-counter constraint;
   - no `metalKernel` source copy per call.
   Then gate it in `Qwen35SparseMoeBlock` by T and quantization, with a SPEC
   note, because it changes logits at near-ties (same drift class as stock
   batched paths).
3. Re-run the MTP admission matrix with the fused path. Native MTP's margin
   over ordinary shrinks at 1-2 slots, so `max_native_active_rows` policy
   should be re-derived on the fused baseline.

## v3 (production safety, gate/up, threshold): 2026-10-02

Fork `perf/a3b-fused-moe`: `df4dea7` (v3 kernels and test), `d9df6aa`

### Safety: no cross-call device state

- The router now runs as two dispatches: logits (33 threadgroups, 257 rows,
  unchanged math) then top-k (one simdgroup per token). The v2 device counter,
  `atomic_thread_fence` and last-threadgroup tail are gone. Every scratch
  buffer (`flog`, `inds`, `wts`, `h`) is a fresh output of the call, so calls
  can overlap on one stream or across streams.
- The split costs nothing measurable: router + glue is 31 µs at T = 1 for
  both v2 (counter) and v3 (split).
- Block weight resolution and the lab call counter are now behind locks.
- Fork test `Qwen35FusedMoETests` uses a synthetic A3B-layout block (256
  experts, top-8, 8-bit router, 4-bit experts).
  - Overlapping calls are built without an eval between them: the same block
    on two inputs, plus a second block, on one stream and on two streams. They
    must be bit-equal to serial evaluation at T = 1/2/4/8/16.
  - Fused rows must be batch invariant and within 2% of stock.
  - The test passes on v3. On the v2 counter router (`2714f70`) it fails, with
    2047 to 2048 of 2048 elements differing per call.
- Lab `concurrency` mode runs the same check on the real model: the first 4
  layers, 8 calls, 8 rounds, one and two streams, T = 1/2/3/4/7/8/16. Every
  run gave 0 mismatched elements (windows 4 to 7).

### Gate/up bandwidth

Swept on the real model, all 40 layers (windows 4 and 5):

- **v3a, per-lane full group:** one 64-wide group per lane per row, the tile
  held in registers, one token per pass. It was slower than v2 at every T,
  and worse at larger T (T = 8: 194 µs against v2's 161).
- **Expert-major down plus combine:** bit-identical to the v2 down, but slower
  at every T (T = 8: 96 µs against 81; T = 16: 195 against 164). It was
  removed.
- **v3 final:** 16-byte coalesced loads, where each instruction covers 512
  contiguous bytes of a row, plus a register-resident tile, TT tokens per
  pass, and the shared expert split into ceil(T/TT) columns dispatched first.
  The best configuration is 1 row × 4 simdgroups × 2 tokens with no
  threadgroup staging. Larger row or token tiles lost, consistent with
  register pressure, and TT = 8 collapsed: at T = 8, gate/up took 630 to 776 µs
  for R1 and R2. Threadgroup staging of x was neutral to slightly negative at
  TT ≤ 2.
