3-hour local soak result (2026-05-27 07:13–10:13 UTC)

Operator-side smoke soak on M1 (8GB), Llama 3.2 3B 4-bit, 1 request per 120s for 3 hours.

Result: PASS

  • 89 requests fired, 89 HTTP 200 (100%)
  • Latency p50 = 781 ms, p95 = 964 ms (stable across 3 hours)
  • Zero crashes; binary tmux session alive throughout
  • Tunneled cleanly through cron's existing infrastructure

Caveat: RSS-based AC-3 5% growth check is the wrong metric for MLX workloads

The soak script's auto-summary reports AC-3 5% memory growth ceiling: FAIL because RSS went from 108 MB at startup to 5.5 MB at end (-95%). This is NOT a real failure — it's a measurement bug:

  • MLX uses memory-mapped model weights (file-backed pages).
  • ps -o rss does not count file-backed mmap memory.
  • macOS pages out idle mmap regions during low-traffic periods, so resident set shrinks during the 120s gaps between requests.

The real AC-3 signal — does the binary crash or leak over 3 hours — is unambiguously PASS (89/89, latency stable, no crashes).

SPEC-001 v1.2 amendment candidate: AC-3 memory metric should use footprint or vm_stat-based compressed-pages tracking instead of RSS, OR drop the 5% growth threshold for mmap-heavy workloads and rely on crash count alone.

One latency outlier worth investigating

Single 9306 ms latency reading vs p50=781 ms (10× median). Likely a Metal command-buffer warm-up after a longer idle gap, OR a GC pause, OR macOS waking GPU from sleep. Not blocking but worth a targeted probe during M4 parity — does the same pattern show up on M4 hardware?

Implication for AC-3 24h soak

3h local PASS is a strong proxy for 24h. The genuine 24h validation will come naturally when phase3-binary deploys to M4 partner — that swap IS the 24h soak under real traffic.

Step 1 blocker diagnosis (2026-05-28)

Codex correctly scaffolded the Swift package per SPEC-001 § 11 Step 1. The Package.swift is well-formed for swift-tools-version 5.9. The blocker is NOT in the Package.swift — it is in the operator's macOS Swift toolchain install.

Root cause

The CommandLineTools install at /Library/Developer/CommandLineTools is internally inconsistent. Investigation:

  • libPackageDescription.dylib — built Dec 7, 2024 (Swift 6.0.3)
  • Public swiftinterface — Dec 6, 2024 (matches dylib)
  • Private swiftinterface — Feb 15, 2024 (stale, Swift 5.10 era)

The stale private swiftinterface advertises a deprecated 5.3-era Package.init with parameter swiftLanguageVersions: marked @_disfavoredOverload. The Swift 6.0 dylib only contains the modern init with parameter swiftLanguageModes:. When the compiler resolves Package(...), it picks the stale-interface init's symbol; the linker can't find it in the dylib → unresolved symbol error.

Tried and failed:

  • Bumping swift-tools-version 5.9 → 6.0
  • Passing pkgConfig: nil, providers: nil explicitly to force overload disambiguation
  • Clearing ~/Library/Caches/org.swift.swiftpm, ~/Library/org.swift.swiftpm, .build/, Xcode DerivedData

None of these help because the issue is in the toolchain's stored swiftinterface files, not in any cache.

Resolution path (operator action)

Recommended: reinstall CommandLineTools. Takes ~5-10 min.

sudo rm -rf /Library/Developer/CommandLineTools
sudo xcode-select --install
# GUI installer pops up; click Install; wait ~600 MB download

Alternatives:

  • Install Xcode.app from Mac App Store (~7 GB, slower, also fixes)
  • Install Swift toolchain from swift.org (no sudo, alternative path)

After CLT reinstall:

cd /Users/augstar/macprovider-poc/phase3-binary
swift --version    # should show Swift 6.0.x
rm -rf .build
swift package describe

If that succeeds, run swift build to verify Step 1 deliverable.

Why this isn't a Codex bug

The Package.swift is correct per SPEC-001's pinned versions and per Apple's Package Manager documentation for swift-tools-version 5.9. The toolchain is the broken party. Codex correctly stopped at the blocker rather than committing unverifiable code.

Resolved 2026-05-28: operator reinstalled CommandLineTools, upgrading Swift from 6.0.3 to 6.3.2. SwiftPM is now coherent; swift build succeeds and the scaffold binary runs.

Design decisions

Choices made where the spec was ambiguous.

2026-05-27

Canonical step sequence: The operator wrapper prompt contains a condensed 9-step build sequence that differs from SPEC-001 § 11's 11-step implementation hand-off. The operator explicitly directed this build to follow specs/BUILD_PHASE3_BINARY_PROMPT.md, so checkpoint commits now follow the wrapper prompt's step numbers.

2026-05-28

Step 2 config defaults: SPEC-001 defines a default port, log level, log format, drain timeout, warm-up behavior, and request body size limit, but does not define a built-in model. The resolved config therefore leaves model unset until provided by CLI, env, or YAML. The Step 3 /v1/models endpoint returns HTTP 503 when no model is configured.

2026-05-28

Testable config core: I introduced a small MacProviderCore library target for config loading, with the executable target depending on it. This keeps the CLI entry point thin and lets future tests exercise config and request handling without shelling out to the binary.

2026-05-28

Step 4 design: The current implementation loads the configured MLX model at startup, validates non-streaming chat requests before inference, and returns OpenAI-shaped responses with usage populated from MLX token counts. User-provided stop sequences are applied to the final text along with model special-token stripping.

2026-05-28

Canonical MLX build path: For this binary, the canonical macOS build command is xcodebuild -scheme macprovider-cli -configuration Debug -destination platform=macOS,arch=arm64 build. swift build can compile Swift code but does not produce the MLX Metal shader resource bundle needed for a working inference binary.

2026-05-28

Local HuggingFace cache fallback: When --model is a HuggingFace id and a matching standard cache snapshot exists under ~/.cache/huggingface/hub/models--org--name/refs/main, the runtime loads that snapshot directory while preserving the public model id for request validation and API responses. This keeps local verification deterministic and avoids an unnecessary Hub download path when the model is already cached.

2026-05-27

Step 5 streaming design: Streaming uses the pinned MLX cumulative-token callback instead of waiting for the final GenerateResult. Each callback decodes the current token prefix, emits only the newly safe delta, and keeps any suffix that could still become a configured stop sequence or model special token. The final GenerateResult still supplies authoritative prompt and completion token counts for the synthesized usage chunk.

2026-05-27

Step 6 context pre-flight: Stage 2 pre-flight uses context.processor.prepare(input:) to tokenize the full chat prompt with the loaded model tokenizer, then rejects before generation if prompt tokens exceed the runtime's safe context capacity. Capacity defaults follow the FR-9 RAM tiers using ProcessInfo.physicalMemory, and the existing max_context_override config/env setting can pin a deterministic lower cap for tests or operator policy.

2026-05-27

Step 7 coordinator client: The provider uses Foundation URLSessionWebSocketTask for the outbound coordinator connection instead of adding a WebSocket dependency. If --coordinator / coordinator_url is unset, the provider remains a standalone OpenAI-compatible HTTP server. The Step 7 client implements the SPEC-001 provider-side protocol messages only; coordinator internals remain deferred to SPEC-002.

2026-05-27

Step 7 capacity placeholder: Heartbeat and hello messages include all FR-17 capacity fields, but throughput_tps_estimate remained 0.0 until Step 8 added the startup self-test measurement.

2026-05-27

Step 8 capacity source of truth: Capacity and health fields now come from a shared ProviderStatus actor. It computes FR-9 RAM-tier defaults from sysctl hw.memsize, applies config overrides, records request totals/in-flight/error counters, and feeds both coordinator heartbeats and GET /v1/health. Startup runs a short MLX generation self-test when a model is loaded and publishes the measured throughput_tps_estimate in hello, heartbeat, and health capacity data.

2026-05-27

Step 9 acceptance scripts: Acceptance entry points now live under phase3-binary/scripts/ and build through xcodebuild. They locate the Xcode product binary and run it with DYLD_FRAMEWORK_PATH=Build/Products/Debug/PackageFrameworks:Build/Products/Debug so MLX can find package frameworks and the compiled Metal shader bundle. The scripts keep the Phase 2 harness clean by writing temporary JSON harness config and a small yaml.safe_load shim under /private/tmp instead of modifying beta/.
