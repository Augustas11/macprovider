Step 8 preflight and capacity routing (2026-05-27)

2026-05-27

Implemented: context-heavy buyer requests now use the SPEC-002 bytes/4 token estimate and send C->P preflight messages before forwarding when the estimate exceeds routing.preflight_threshold_tokens. Provider preflight_ack responses are correlated by request_id and provider ID, with timeout/rejection causing the router to skip that provider for the current request.

Capacity routing: default, session-pinned, and provider-pinned routing all enforce the FR-R5 context-length filter. If another ready provider can fit the request, the router selects it; if every ready provider for the model is too small, the buyer receives 413 with context_exceeds_capacity. Pinned providers do not fall back after a preflight rejection.

Preflight reasons: preflight_ack validation accepts the six SPEC-001 rejection reasons: context_exceeds_capacity, queue_full, draining, model_not_loaded, unhealthy, and tier_mismatch.

Failure recovery: routed provider HTTP 502/504 responses mark the provider degraded and start the configured recovery preflight loop with recovery-probe- request IDs. Accepted recovery preflight marks the same session ready; repeated failures mark it unavailable. Literal HTTP 530 marks the provider unavailable immediately with http_530_observed in the log.

Verification: GOCACHE=/private/tmp/macprovider-go-build-cache go test ./... passes with tests for rejected-candidate fallback, pinned preflight rejection without fallback, context route-or-413 behavior, recovery preflight IDs, HTTP 530 state handling, WebSocket preflight round trip, and all six rejection reasons. Step 6 non-streaming chat routing (2026-05-27)

2026-05-27

The buyer server validates JSON and OpenAI-compatible request shape before model lookup, selects an eligible provider, forwards the request body to the provider HTTP endpoint, relays the provider JSON response, and adds X-MacProvider-Provider plus X-MacProvider-Route.

Step 4 provider state machine (2026-05-27)

2026-05-27

Implemented: state_update parsing, validation for the five SPEC-002 states (ready, busy, degraded, draining, unavailable), metrics snapshot slot updates, and Provider.RoutingEligible() for the Step 5+ router filter (ready + slots_free > 0).

Wake handling: heartbeat gaps greater than pool.wake_gap_threshold_s send {"type":"warm_up"}, mark the provider degraded even if the heartbeat says ready, and start the SPEC fallback timer that returns it to ready after 60 seconds if no state_update: ready arrives.

Disconnect handling: WebSocket read failure marks the current session unavailable, then removes it after pool.disconnect_grace_period_s. Reconnects are protected by session ID matching, so an old disconnected goroutine cannot remove a newer session with the same stable provider_id.
