SPEC-002 v1.0.2 post-joint-audit patches (2026-05-27)

Applied after joint SPEC-001 + SPEC-002 audit at JOINT-SPEC-001-002-audit.md identified 0 CRITICAL, 6 MAJOR, 2 MINOR, 1 QUESTION. All addressed in-place; no SPEC-001 amendment required.

MAJOR cross-spec findings resolved

  • M-J1 (preflight.purpose extra field): Removed "purpose": "health_recovery" from recovery preflight. Recovery probes now use only the recovery-probe- prefix on request_id as the coordinator-side discriminator. Wire-strict subset of SPEC-001 § 6.5.
  • M-J2 (C→P nak direction): Coordinator never sends nak to providers — that direction isn't in SPEC-001 § 6.5. All coordinator-initiated rejections (invalid hello, unknown provider_id, tier mismatch, version mismatch, invalid token, pool full) now use standard WebSocket application close codes 4001–4005 + 4429 with descriptive reason text. New table "Provider rejection via WebSocket close codes" in FR-P13.
  • M-J3 (header table contradiction): § 7.2 custom-header table now correctly shows X-MacProvider-Provider = stable provider_id and adds X-MacProvider-Session = session assigned_id. Routing pseudocode updated to check Session first (more specific), then Provider. Cross-references FR-R3 precedence.
  • M-J4 + Q-J1 (HTTP 530 open question): Promoted to normative FR-P11 row. Literal HTTP 530 on a routed buyer request → unavailable, log state_update.reason = "http_530_observed", trigger WebSocket liveness probe with 5s ack timeout. OQ-1 deleted from § 12; § 12 now has zero open questions.
  • M-J5 (static endpoint YAML schema): § 13 config schema replaced with full YAML example including providers: [{provider_id, endpoint_url, display_name?}] block plus 5 startup validation rules (non-empty list, unique IDs, HTTPS URLs, ID regex, operator_key set).
  • M-J6 (routing.retry_on_502 stale config): Renamed to pool.degraded_probe_after_502 in the YAML schema. The config controls the degraded recovery probe behavior, which is real; the previous name implied buyer-visible retry which v1 FR-B7 forbids. Explanatory note in § 13 documents the rename.

MINOR findings resolved

  • m-J1 (header namespace incomplete): § 7.2 now has TWO header tables (request + response) with all four headers enumerated and direction-tagged.
  • m-J2 (AC-8b degraded routing conflict): AC-8b step 6 rewritten to assert NO routing while degraded (matches FR-R4's state=ready filter). Removed the "ONLY if no other ready provider" last-resort clause that contradicted the main routing rule.
  • AC-10 alignment: Step 5 added with explicit two-phase observable behavior (draining → close → remove), matches § 7.4 blacklist semantics. Step 6 covers 404 for unknown provider.

Patch verification (joint audit Part 1) — items revisited

  • M3 (NOT ADDRESSED in v1.0.1) → now ADDRESSED: § 7.2 header table reflects FR-R3's stable-provider_id semantics.
  • M8 (NOT ADDRESSED in v1.0.1) → now ADDRESSED: recovery preflight is SPEC-001-§6.5-strict subset (no extra fields).
  • M9 (NOT ADDRESSED in v1.0.1) → now ADDRESSED: AC-10 step 5/6 align with § 7.4 two-phase removal.
  • Q1 (NOT RESOLVED in v1.0.1) → now RESOLVED: HTTP 530 is normative in FR-P11; OQ-1 deleted.

Knowingly deferred

  • None. All joint-audit findings either addressed or rolled into explicit normative requirements.

SPEC-002 v1.0.1 post-audit patches (2026-05-27)

Applied after audit at SPEC-002-audit.md identified 3 CRITICAL, 9 MAJOR, 5 MINOR, 1 QUESTION. All CRITICALs and the build-blocking MAJORs patched in place; no full FIX prompt cycle.

Resolved operator decisions (locked into spec)

  • C1 endpoint discovery: static provider_id → endpoint_url config map in coordinator. No SPEC-001 amendment. Documented in § 3 "Request forwarding model" and FR-P3.
  • C2 provider auth: optional in v1 (two-path FR-P12 — no header OR bearer-token). SPEC-001 v1.1.1 binaries connect without modification. Path B preserves future-compat for when SPEC-001 mandates auth.
  • C3 retry: no coordinator-managed retry across providers in v1. Buyer receives clean 502/streaming-error; SPEC-004 / SPEC-006 may add visible retry policies later.
  • Q1 HTTP 530: distinct signal logged as state_update.reason = "http_530_observed"; same pool behavior as WS disconnect but distinguishable in logs.

MAJOR findings addressed

  • M1 (D1 tunnel polling): Explicit rejection documented in § 10 D1 with rationale (rate limits, credential burden, signal lag).
  • M2 (D4 capacity-vs-quality): Same-model tradeoff is in-scope via X-MacProvider-Pref; cross-model-family routing explicitly deferred to SPEC-004.
  • M3 (pin identity): X-MacProvider-Provider takes stable provider_id (the operator-meaningful identity); X-MacProvider-Session added for session-scoped pinning via assigned_id.
  • M4 (FR-O5 / pool persistence): Reframed — auth + request log persisted; pool snapshots are debug-only history; live pool routing state is in-memory only. Scope item in § 2 clarified.
  • M5 (buyer API schema): Full request schema inlined in § 7.2 (was previously a delegate-to-SPEC-001 reference). Spec is now self-contained for build session.
  • M6 (warm-up AC): AC-8b added with concrete assertions (warm_up sent within 5s of resumption heartbeat, degraded state until ready/60s).
  • M7 (revocation semantics): Revocation = future-connection-only. Combined with separate blacklist for immediate disconnect. New revoke-and-kick CLI for the combined case.
  • M8 (recovery preflight shape): Concrete shape defined with request_id="recovery-probe-<uuid>", estimated_tokens=128, purpose="health_recovery". Provider treats as normal preflight; no special-casing required.
  • M9 (blacklist semantics): Two-phase observable behavior — drain command → draining state (up to 60s) → pool removal on close. AC-10 must assert this, not "immediate removal."

MINOR findings addressed

  • m1 (clean-room replication): § 8.2 reframed as "adapted from SPEC-001 § 7.2" with coordinator-specific additions.
  • m2 (dependency pin language): "starting points" weakening removed; pins are required for v1.0.1, bumps require implementation-notes entry with rationale.
  • m3 (AC-6 manual test): Replaced with explicit phase4-coordinator/scripts/test-sigterm-drain.sh requirement.
  • m4 (404 vs 503 model errors): Split clarified in § 7.2 error table — 404 = model unknown to pool history; 503 = known model but no eligible provider right now.
  • m5 (open questions trimmed): § 12 reduced to 1 truly open question (Q1 HTTP 530 handling). Defaults moved to requirements sections.

Knowingly deferred

  • No items knowingly deferred this round — all findings either addressed or recorded as explicit scope-out with rationale.

Verification

Spec version bumped to 1.0.1. Open question count: 1 (down from 5). Re-audit recommended before binary/coordinator build begins together; the C1 architecture choice (static config) is the highest-leverage decision and worth one more cross-model pass.
