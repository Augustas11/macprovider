## Intent

The chaos lane exercises money-path invariants I1–I4 under adversarial
provider-side conditions. Scenario 05 (`05_mid_stream_drop.yaml`) covers
a single provider-process kill mid-stream. Scenario 12 is the delta:
FOUR kicks against a fleet of THREE concurrent streaming buyers, so
reconnect + settlement paths run repeatedly under load. That's where
subtle billing bugs (double-settlement on reconnect, orphaned
settlement rows on the killed attempt, pool re-election races) live.

All chaos is scoped to the LOCAL provider process (via `launchctl
kickstart -k gui/$(id -u)/live.streamvc.macprovider`). Pearl coord+gateway
are the SUT — never fault-injected.

### 1. Scenario YAML correctness against the schema

- Does the YAML parse and pass `Scenario.Validate()` in
  `test/network-harness/internal/scenario/schema.go`? Cross-check every
  set field against the schema struct (buyers, chaos_events, target,
  prompts). Types, tags, required-when-set rules.
- `buyers.pattern: constant` with `requests_per_buyer: 2` — schema
  validation allows this. Confirm no other constraint (e.g. min duration
  vs buyers × requests) is silently broken.
- `duration: 90s`, `request_timeout: 60s`, `silent_hang_threshold: 20s`
  — sanity-check the arithmetic: 3 buyers × 2 streaming requests on
  Qwen3-Coder-30B-A3B (typical 10–30 tok/s, max_tokens=384 ≈ 15–40 s per
  request) must be able to complete within `duration` before the runner
  stops accepting new starts.
- `max_tokens: 384` combined with a single prompt for a coder model —
  is generation reliably long enough to overlap the 5s/25s/45s/65s
  kick timeline?

### 2. Chaos-command correctness

- `launchctl kickstart -k gui/$(id -u)/live.streamvc.macprovider` fires
  from the harness process (running as $USER); `$(id -u)` expands inside
  `/bin/sh -c` (see `internal/chaos/runner.go` fire()). Confirm expansion
  order is safe — no injection surface here since command is committed
  YAML, but flag if the `id -u` expansion could return a different value
  than the launchd label was created under.
- Kick #5 (at 85s) uses `launchctl kickstart` (no `-k`) as
  belt-and-suspenders. Verify this is a no-op when the daemon is already
  running (per launchctl semantics), not a double-restart.
- Timing gaps: kicks at 5/25/45/65s with 20s spacing. Confirm launchd
  KeepAlive typically brings the provider back within 20s so the next
  kick fires against a running process — otherwise later kicks are
  no-ops and don't produce the intended churn. If unclear, this is a
  LOW/MEDIUM discovery for the phase-B triage, not a shipping blocker.
- Chaos runner records `ExitCode`, `Stdout`, `Stderr` per event. Verify
  `launchctl kickstart -k` exits 0 on this path (it should, given the
  label exists and belongs to $USER's GUI domain).

### 3. Invariant applicability
