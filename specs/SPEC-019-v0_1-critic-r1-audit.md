## Findings

### Finding 1: OpenAI strict-mode parity break — `required` must list every key in `properties`
- Severity: CRITICAL
- Location: SPEC-019 §3 (lines 257-281), AC-6 (line 135), AC-8 (lines 144-147), AC-15 (lines 187-190)
- Issue: OpenAI's strict-mode contract (the documented compatibility anchor SPEC-019 cites at line 248) requires that `required` enumerate **every** key in `properties`; optional fields are forbidden in strict mode. SPEC-019 §3 inverts only half the constraint — it requires that "each entry in `required` MUST name a key in `properties`" but is silent on the reverse direction. A buyer who sends `{"type":"object","properties":{"a":{...},"b":{...}},"required":["a"],"additionalProperties":false,"strict":true}` will pass macprovider validation and fail under OpenAI / Vercel SDK fixture parity (AC-15, AC-16) silently — buyer paid for an inference whose output is "valid per macprovider but invalid per OpenAI fixture", which is the exact compat break this slice is supposed to close. This is the kind of parity break product-design H-1 surfaced for Vercel's enforcement path, but at a different layer (schema-shape parity, not enforcement-path parity), so codex did not catch it.
- Recommendation: Add a §3 rule: under `strict:true`, an object schema's `required` array MUST contain every key in `properties`; mismatch returns HTTP 400 `json_schema_strict_requires_all_properties_required`. Add an AC asserting the rule, ideally co-located with AC-6. Update §3 table footnote accordingly.

### Finding 2: Post-hoc validation vs receipt-write ordering is undefined — money-path race
- Severity: HIGH
- Location: SPEC-019 §5 (lines 322-352), §8 (lines 416-433), AC-19 (lines 207-213)
- Issue: SPEC-019 §5 says validation runs "after non-streaming inference completes" and §8 says validation failures are `FaultBreakerQualifying`. But the SPEC nowhere specifies that the success receipt MUST NOT be committed/emitted before the post-hoc validator runs. In current code the receipt prompt hash is computed up-front from `promptSource` and there is an implicit timing, but no normative ordering constraint. If an IMPL pulls receipt commit forward (e.g. for streaming-prep or for write-fanout), a buyer could receive a success receipt for an inference whose output is about to be rejected as `json_schema_validation_failed`, leading to billing/audit-trail inconsistency on the money path. Codex architect/code lanes flagged the SPEC-006 502-normalization issue (C-2) and ModelRuntime call-site sequence (M-2), but not the receipt-vs-validation ordering invariant.
- Recommendation: Add a §5 normative rule: "A success receipt MUST NOT be emitted until validator behavior in §5 has completed and decided success. On `malformed_json_response` or `json_schema_validation_failed`, no success receipt is emitted; the request is settled as `FaultBreakerQualifying` per §8." Add an AC: "order-of-operations regression test — no success receipt is written when post-hoc validation fails."

### Finding 3: Empty model output (0 completion tokens) classification is undefined
- Severity: HIGH
- Location: SPEC-019 §5 (lines 322-352), AC-9 (lines 149-154)
- Issue: If the model produces zero completion tokens — empty `content` after stop-token filtering (`ModelRuntime.swift:477-483`) — and `json_schema` or `json_object` is requested, what error is returned? Empty string is not valid JSON, so the natural classification is `malformed_json_response`. But it's also `finishReason:"length"` or `"stop"` with empty content, which is a different fault class semantically (model decided to emit nothing, not "model emitted garbage"). Buyers retrying on `retryable:true` `malformed_json_response` may retry forever if the model deterministically emits empty content on a given schema, generating fault-breaker rotations and zero credits per attempt but real compute load. Spec is silent. Codex security H-2 covered validator-exception classification but at a different layer (internal exceptions, not empty-content output classification).
- Recommendation: Add to §5: "Empty `content` after stop-token filtering when `json_schema` or `json_object` is requested MUST be classified as `malformed_json_response` with `inference_ran:true`, `settlement_ran:true`, `FaultBreakerQualifying`." Optionally add an AC for the empty-content fixture.

### Finding 4: Schema depth cap is missing — schema-side stack/CPU bomb at validation
- Severity: HIGH
- Location: SPEC-019 §3, §6 (lines 370-390), AC-4 (lines 125-128), AC-25 (lines 240-244)
- Issue: AC-25 caps **output** JSON depth at 32 by reusing the SPEC-018 constant. §3 caps **schema** size by bytes (16 KiB). But SPEC-019 places no cap on **schema** depth. A 14 KiB schema can nest objects to several-hundred-deep, e.g. `{"type":"object","properties":{"a":{"type":"object","properties":{"a":...}}}}`. The pre-inference schema validator that walks the schema to enforce §3 rules will recurse on this hostile input and may exhaust Swift's call stack at validation time, before the byte cap helps. Codex security H-1 flagged "schema depth/node-count caps missing at parse time" but the security framing landed on parse-time CPU cost; this is a **stack-exhaustion** concern that crashes the validator, takes the provider offline as a denial-of-service, and is distinct from the parse-cost framing. Both flavors of the issue are real.
- Recommendation: Add to §6: "Schema depth is capped at 32 nested levels matching output-side AC-25; schemas exceeding this depth return HTTP 400 `json_schema_too_deep` at provider and coordinator before inference." Or fold into security H-1's resolution with explicit numeric values, the same constant as output-side, and an AC.

### Finding 5: Response cap interaction with structured output is unimplementable as worded
- Severity: HIGH
- Location: SPEC-019 §6 (lines 380-388)
- Issue: §6 says: "For structured output, the cap applies to the final assistant content's UTF-8 bytes **after JSON parsing and validation**, not to the outer HTTP response envelope." The natural reading: parse → validate → check byte count → reject if over cap. But by then inference has already produced (and the buyer has already paid for) 2 MiB+ of tokens; the provider has already buffered the output, and `JSONSerialization` will happily decode multi-MiB blobs. The intended posture (per SPEC-018 §10d.7 parity) is fail-closed early. As worded, §6 either (a) contradicts the SPEC-018 posture or (b) forces the IMPL into a hostile state of fully decoding hostile multi-MiB JSON just to reject it. This is the inverse of the intended invariant. Codex architect H-1 raised tool×schema composite render order, distinct from this content-cap order-of-checks question.
- Recommendation: Reword §6 to: "For structured output, the response cap applies to the final assistant content's **raw UTF-8 bytes as emitted by inference**. The cap is checked **before** JSON parsing; exceeding the cap returns HTTP 502 `response_too_large` (or the existing SPEC-018 §10d.7 error code), `inference_ran:true`, `settlement_ran:true`, `FaultBreakerQualifying`. Validation never runs if the cap is exceeded."

### Finding 6: Renderer concurrency / per-request schema cache contamination is unspecified
- Severity: HIGH
- Location: SPEC-019 §4 (lines 282-319), AC-13 (lines 173-177)
- Issue: `ToolPromptRenderer` is referenced as the family-renderer pattern to reuse. SPEC-019 requires injecting the buyer-supplied schema as a JSON-serialized blob into the system position per family. SPEC-019 §4 nowhere specifies that the renderer must be **stateless across requests**. The BUILD prompt §10 explicitly lists "schema warm-cache between requests on the same connection" as deferred-to-v0.2, which signals that a per-connection cache is on the radar. If an IMPL adds even an innocuous per-family cache (or memoization), and the cache key is anything weaker than the full canonical schema bytes, request A's schema may render into request B's prompt across tenants. This is a money-path cross-request contamination risk that the SPEC must forbid in v0.1.0. None of the codex lanes flagged renderer state-management.
- Recommendation: Add to §4: "The structured-output renderer MUST be stateless across requests in v0.1.0. No schema cache (in-process, per-connection, or per-family) is permitted in v0.1.0; schema warm-cache is deferred per §10." Add an AC: "concurrent-request fixture proves two simultaneous requests with different schemas render their own schemas into their own system prompts, with no cross-render."

### Finding 7: Receipt-of-defaulted-strict idempotency cliff
- Severity: MEDIUM
- Location: SPEC-019 §1 (lines 82-86), AC-12 (lines 168-171), `PromptCanonicalizer.swift:5-16`, `ChatCompletionRequest.swift:144` (`responseFormat: JSONValue?`)
- Issue: §1 says `strict` defaults to `true`. The typed `parseResponseFormat` would fill the default. But the receipt canonicalizes `promptSource.responseFormat` — the **raw** `JSONValue?` (`ChatCompletionRequest.swift:144,162`) — which does NOT have the default applied because `promptSource` is built directly from the request dict via `optionalJSONValue(dict["response_format"])`. So a buyer who sends `{"type":"json_schema","json_schema":{"name":"x","schema":{...}}}` (no `strict` key) and a buyer who sends the same with `"strict":true` explicitly will produce **two different prompt hashes** for behaviorally identical requests. This is the inverse of the idempotency contract buyers usually expect. AC-12 only says hash changes when "any byte of schema changes" — it neither asserts nor denies that defaulted fields are folded in. None of the codex lanes flagged the defaulted-field receipt asymmetry; product-design Q-1 covered the strict:false opt-out posture but not this idempotency cliff.
- Recommendation: Add to §9 (forward-compat invariants) or AC-12 commentary: "The receipt prompt hash is computed over the raw request bytes for `response_format`; defaulted-but-absent fields (e.g. omitted `strict` defaulting to `true`) are NOT canonicalized into the hash. Buyers seeking byte-stable receipts MUST send the explicit field." Document the choice — either folding defaults in or excluding them is acceptable, but the SPEC must be normative.

### Finding 8: Schema `const`/`enum` type-conformance error code is unspecified
- Severity: MEDIUM
- Location: SPEC-019 §3 (lines 261-263)
- Issue: §3 says `enum` values MUST conform to `type` and `const` value MUST conform to `type`. A schema like `{"type":"string","const":42}` violates this. Validation MUST reject pre-inference. But the SPEC does not specify the error code. Reasonable candidates: `json_schema_unsupported_keyword` (wrong — the keyword is allowed), `json_schema_invalid_keyword_value` (not defined), or a new code. Two competent implementers will pick differently, breaking coordinator/provider parity (AC-20). Codex architect C-1 caught a SPEC-001 contradiction on `response_format.type`; this is a similar but distinct gap on schema-internal validation.
- Recommendation: Add to §3: "A schema where `const` or any `enum` element does not conform to `type` returns HTTP 400 `json_schema_invalid_const_or_enum_type` with `param` set to the JSON pointer of the offending node." Add to AC-4 or as a new AC.

### Finding 9: Unicode normalization for property names is undefined — strict-mode bypass
- Severity: MEDIUM
- Location: SPEC-019 §3 (line 259), §5 (lines 322-352), AC-8 (lines 144-147)
- Issue: If a buyer schema has `properties: {"café": {...}}` with "café" in NFC form, and the model emits `{"café": "..."}` with "café" in NFD (decomposed), are these the same key? JSON's RFC 8259 §8.3 leaves the answer implementation-defined. SPEC-019 §5 says "validate against the supplied schema subset" but is silent on Unicode comparison rules. This matters because `additionalProperties:false` either accepts or rejects an NFD-form key for an NFC-form `properties` entry depending on the parser. An attacker crafting a schema and a hostile model response can collide or evade `additionalProperties:false` depending on which side normalizes. Codex security M-1 flagged prompt-injection in the name field, but not key-name comparison semantics.
- Recommendation: Add to §3: "Property names are compared by raw UTF-8 byte sequence; no Unicode normalization is applied. Two property names with different byte sequences are distinct keys even if they normalize to the same form." Add an AC: "NFC-vs-NFD property name fixture proves byte-distinct keys are rejected by `additionalProperties:false`."

### Finding 10: Body-byte preservation under inbound content-encoding is undefined
- Severity: MEDIUM
- Location: SPEC-019 AC-17 (lines 195-200), AC-21 (lines 220-224), AC-5 (lines 129-132)
- Issue: AC-5/AC-17 specify the schema cap is over "raw UTF-8 bytes over the schema JSON value as it appears in the request body, including insignificant whitespace inside that value." AC-21 says the gateway forwards the original request bytes byte-preservingly. But the gateway reads the inbound body via `io.LimitReader` and re-creates the upstream request from `body` (`chat_proxy.go:102-117`). If the inbound transport applied content-encoding (gzip, br), `r.Body` will already be the decoded form, and the "byte-equivalent" claim only holds in the decoded plane. For the coordinator's defense-in-depth cap check (AC-20), the coordinator must compute the same byte count as the provider's parser computes from its own re-read of the body. The spec assumes both layers see byte-identical bodies; transport-layer choices can drift this. (Codex product-design H-1 caught Vercel AI SDK enforcement-path drift; AC-21's byte-preservation invariant is the analogous wire-level issue.)
- Recommendation: Clarify AC-21 to: "The gateway MUST forward the chat request body to the coordinator with byte-identical content in the decoded plane (after any inbound content-encoding is stripped). The byte count for the schema cap is computed over the decoded request body." Add a fixture exercising a gzipped inbound request that pushes schema bytes near the 16_384 boundary.

### Finding 11: Schema-vs-message system instruction position composition with SPEC-018
- Severity: MEDIUM
- Location: SPEC-019 §4 (lines 296-307), AC-14 (lines 178-184)
- Issue: §4 says: "If the buyer supplied a system message, the structured-output instruction is appended after it with a deterministic separator. If no system message exists, the renderer creates one." But SPEC-018 also injects a tool-call sentinel system instruction. When both `tools` and `json_schema` are present (AC-14), the renderer must compose two system-side blocks — SPEC-018's tool-call instructions and SPEC-019's schema instructions. The deterministic separator AND the relative ordering between the two blocks is unspecified for the composite case. Codex architect H-1 flagged "tool×schema composite-rendering order undefined" — this is the same family of issue but called out at the separator/system-segment composition level specifically. The IMPL author needs both H-1's ordering answer and a specific separator rule.
- Recommendation: Define the separator and ordering in §4: "When SPEC-018 tool-call instructions are also injected, the SPEC-019 schema instruction MUST appear after the SPEC-018 tool-call instruction within the system position, separated by a literal `\n\n`. The buyer system message comes first, then the SPEC-018 block, then the SPEC-019 block." Cross-reference architect H-1.

### Finding 12: `strict` parser-type asymmetry between provider and coordinator
- Severity: minor
- Location: SPEC-019 §1 (lines 82-86), `ChatCompletionRequest.swift:144` and `server.go:3608-3615`
- Issue: The provider's `optionalBool` will likely reject `strict:1` as wrong-type. The coordinator's defense-in-depth `json.Unmarshal` into a Go struct with `Strict bool` will also reject. But absent an explicit normative rule, an integer-tolerant parser added later (or a permissive proxy in between) could disagree. Low confidence — depends on details of both parsers. Worth tightening for hygiene.
- Recommendation: Tighten §1 to: "`json_schema.strict` MUST be JSON boolean. Any other JSON type (integer, string, null, object, array) returns HTTP 400 `json_schema_strict_invalid_type` at provider and coordinator."

### Finding 13: AC-12 hash-stability for whole-number schema literals depends on parser quirks
- Severity: minor
- Location: SPEC-019 AC-12 (lines 168-171), `JSONValue.swift:25-37`
- Issue: `JSONValue.parse` collapses any finite double whose value is a whole integer in range to `.int(_)` (`JSONValue.swift:33-37`), so `{"const": 1}` and `{"const": 1.0}` hash identically — good. But `{"const": 1e100}` exceeds `Int.max`, stays as `.double`, and may collapse differently than the same number written `1e+100` vs `10000000000000000159028911097599180468360808563945281389781327557747838772170381060813469985856815104`. RFC 8785 JCS specifies float serialization based on ECMAScript `Number.prototype.toString`, which is well-defined, so this is probably fine in practice — but AC-12 should explicitly invoke RFC 8785 semantics so the boundary is on a published standard rather than implementation choice.
- Recommendation: Add to AC-12 commentary: "Hash stability for numeric schema literals follows RFC 8785 §3.2.2.3 ECMAScript number serialization, as already implemented in `RFC8785JCS`."

### Finding 14: Q — should `n != 1` interact with `response_format:json_schema` specially?
- Severity: Q
- Location: SPEC-019 §1, `ChatCompletionRequest.swift:56-58`
- Issue: Provider already rejects `n != 1` with HTTP 400. SPEC-019 nowhere mentions `n`, and a future widening to `n>1` would create undefined behavior for structured output (does each of `n` choices validate independently? what if 3 of 5 pass?). Not actionable for v0.1.0 since `n != 1` is already a 400. But §9 forward-compat could pin this.
- Recommendation: Optional: add to §9: "Structured output is bound to `n=1` in v0.1.0. Any future relaxation of the provider's `n=1` requirement MUST define independent per-choice validation semantics in a new SPEC version."

### Finding 15: Q — error envelope leakage of attacker-controlled `description`/`enum`/`const` strings
- Severity: Q
- Location: SPEC-019 §4 (lines 316-319), §5 (lines 353-368)
- Issue: §4 says `description` etc. are untrusted prompt data, embedded only as JSON string data into the prompt block. But §5's validator error message MAY include the expected type/keyword. If the validator's error message echoes the `description` or `enum`/`const` literal of the offending field (e.g. "field `/x` (description: <attacker-controlled string>) failed type check"), the attacker can inject content into the error envelope returned to a downstream buyer. Out of scope for v0.1.0 if the IMPL stays strict, but worth a Q so the IMPL author resolves it deliberately.
- Recommendation: Optional: add to §5: "Error messages MUST NOT echo any buyer-supplied schema content (descriptions, enum values, const values, property names) into the error message. Only the JSON pointer and the expected `type`/keyword identifier may appear in `error.message` and `error.param`."
