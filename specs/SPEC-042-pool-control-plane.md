## 1. Purpose and scope

MacProvider today is a single global provider network. Buyer route selection starts from a global provider snapshot (`phase4-coordinator/internal/buyer/server.go` selection → `phase4-coordinator/internal/routing/filter.go` eligibility); provider admission, request logs, route snapshots, receipts, settlement, payout, and buyer disclosure are all account/request/provider-centric, with no notion of a pool as a first-class object. `pool_id` appears zero times in `phase4-coordinator/internal` and `phase5-gateway/internal` (verified 2026-08-18). SPEC-042 defines the **pool control plane**: a Trusted Pool as a creator-operated trust boundary over the shared MacProvider infrastructure and settlement, addressed by a mandatory `pool_id` authority field and governed by a signed **pool manifest**.

The product tier defined here is administrative trust, not cryptographic privacy. The single canonical product name is **"Trusted Pool"**; "MacProvider Subnet" and "Controlled Pool" are retired synonyms and MUST NOT be used in buyer-facing copy ("Subnet" additionally imports Bittensor validator/miner-incentive connotations that would mislead the crypto-adjacent audience). The term "Privacy Pool" is reserved for the Layer 3 capability set (SPEC-041 relay-blind request encryption and later unlinkability/anonymous-membership SPECs) and MUST NOT be applied to any capability defined solely by SPEC-042.

**MVP wedge — the intended v0.1 first operator.** The v0.1 target is the **vertically-integrated operator**: an operator that is simultaneously the pool creator *and* the supply (it brings its own Macs) *and* the demand (it resells to its own buyers), using MacProvider only as fail-closed isolation + labeled-settlement rails and capturing its margin at its own application layer. This wedge deliberately requires **no third-party provider supply** (so the negative-incentive problem of asking global providers to accept stricter predicates and a permanent blocklist for no extra pay does not arise at MVP) and **no SPEC-016 revenue-split execution** (the operator monetizes upstream, so the deferred split is irrelevant at MVP). Regulated-vertical *marketing claims* (legal/medical/banking) remain gated to V1/V2, but the *rails* ship at MVP for a design-partner operator. Multi-party pools — third-party providers joining a creator's pool for a share of buyer revenue — are a V1 concern that depends on the SPEC-005/016 split (R006) and on the multi-signer authority machinery (R012); at MVP a single-operator/single-signer cut is sufficient and is the recommended first implementation.

In scope (skeleton → first build slice):

- the pool object and signed pool manifest (stable identity core + versioned policy core + mutable operational fields) as the Layer 2 contract;
- `pool_id` as a mandatory authority field threaded through gateway, coordinator, provider admission/routing, route snapshots, request logs, routing logs, receipts, settlement, payout accounting, and public disclosure;
- pool selection **authorization** (who may name a pool; API-key/wallet-session binding; narrow-only route params);
- pool-scoped provider membership and durable revocation, creator-controlled admission;
- conversion of SE/MDA/Tier-2/provider-leg-encryption/binary-floor/model-catalog controls from global-optional features into **pool-enforceable, fail-closed predicates**, re-evaluated on every provider selection attempt;
- pool-scoped tenant isolation with fail-closed routing and pool-generation fencing (no spill to global or other-pool providers);
- pool-scoped settlement labels cryptographically bound to the route snapshot, creator revenue split, per-pool payout accounting;
- pool-scoped observability with a field-level retention/redaction matrix;
- pool promise surfaces: a buyer-verifiable signed `pool_policy.json` and a coordinator-attested live `pool_status.json`, with defined schema/freshness/staleness semantics;
- pool lifecycle, provider migration, and failover/restart reconstruction;
- forward-declared Layer 3 compatibility fields (bound into SPEC-041 flows) so Layer 3 privacy can be added without re-architecting.

Out of scope (owned elsewhere or by later versions):

- coordinator-blind request content, unlinkable routing, anonymous membership, ZK membership proofs, nullifiers, unlinkable settlement — Layer 3, owned by SPEC-041 and future SPECs;
- regulated-vertical product packaging (legal/medical/banking compliance bundles) — gated behind Layer 2 V1/V2, MUST NOT be claimed at MVP;
- creator billing plans, cross-pool provider-reuse governance, sanctions/appeals workflow — Layer 2 V2;
- multi-coordinator/pool-state distributed consistency — v0.1 assumes a single authoritative coordinator; the design MUST NOT preclude it (SPEC-042-R011);
- hardware-backed confidential compute / "invisible to the provider operator" — a separate roadmap track, cannot be inferred from any SPEC-042 mechanism.

## 2. Authority and dependencies

SPEC-042 owns the authority domain `pool-control-plane`: the pool object, pool manifest schema/signature/versioning, `pool_id` propagation and authorization contract, pool membership and revocation ledger, pool-enforceable trust predicates, pool-scoped routing isolation, pool-scoped settlement/revenue-split binding, pool observability/retention policy, buyer-facing pool promise surfaces, and pool lifecycle.

SPEC-002 owns coordinator admission and routing. SPEC-042 adds a `pool_id` routing namespace and pool-scoped eligibility predicates, but MUST NOT bypass the SPEC-002 request lifecycle, provider assignment, capacity accounting, cancellation, or request-log ownership. Global (poolless) routing MUST continue to behave exactly as today when no `pool_id` is present, and global traffic MUST remain outside pool authorization and MUST NEVER serve as fallback for a request that selected a pool. *(Open-A is a representation-only decision — nullable `pool_id` vs. a reserved sentinel value on the wire/storage — and MUST NOT reopen whether global traffic is semantically a pool.)*

SPEC-003 owns provider onboarding identity. Pool membership and the durable pool revocation blocklist MUST be keyed on the existing authenticated, durable SPEC-003 provider identity; a pool membership credential binds an already-admitted provider identity to a `pool_id`. SPEC-042 MUST NOT introduce a second provider-identity root.

SPEC-005 owns billing arithmetic and settlement formulas. SPEC-042 v0.1 adds only immutable pool *labels* to existing settlement records and MUST NOT redefine SPEC-005 delivered-output settlement, over-report handling, or ledger ownership. Creator revenue-split *execution* crosses SPEC-005 arithmetic and is deferred to a Layer 2 V1 that carries explicit SPEC-005 amendments and AUTHORITY consumer edges (SPEC-042-R006).

SPEC-016 owns payout lifecycle and execution. SPEC-042 v0.1 does not enable payouts and does not alter payout ownership; per-pool payout accounting and creator-split payout are deferred to a Layer 2 V1 that carries explicit SPEC-016 amendments (ledger schema for `creator_account_id`/`creator_payout_subject_hash`, idempotency, payout-ready semantics) and AUTHORITY consumer edges (SPEC-042-R006).

SPEC-006 owns the buyer API error envelope and OpenAI-compatible route shape. SPEC-042 adds a pool-selection mechanism and pool disclosure/error fields, but MUST preserve existing global behavior when no pool is selected, and MUST NOT expose stable provider IDs unless SPEC-006 is amended.

SPEC-008 owns Tier-2 trust evidence (SE key custody/liveness, MDA hardware attestation) and provider-leg encryption. SPEC-042 does NOT redefine any SPEC-008 evidence; it defines the ability for a pool manifest to **require** a minimum SPEC-008 posture as a fail-closed routing predicate, using the exact mapping in SPEC-042-R004. SPEC-042 MUST reuse SPEC-008 verification verdicts as-is and MUST NOT interpret client-set posture fields as satisfying a predicate.

SPEC-010 owns model-catalog identity. A pool manifest model allowlist and any required model-catalog/hash policy MUST reference SPEC-010 canonical model/catalog identity and MUST NOT define a parallel model-identity scheme. Model hash remains provider-reported unless SPEC-010/enforce-mode checks prove otherwise; a pool MUST NOT imply verified model identity beyond what SPEC-010 enforce-mode provides.

SPEC-015 owns inference receipts. SPEC-042 MUST NOT change the v0.4 provider-signed receipt tuple without a SPEC-015 version bump. `pool_id`/manifest binding for settlement is carried as coordinator route-snapshot/settlement-journal context per SPEC-042-R006; injecting `pool_id` into the signed receipt tuple requires a coordinated SPEC-015 version bump. *(Open-B: signed-receipt field vs. route-snapshot/journal context — resolve with SPEC-015 owner before v0.1.)*

SPEC-020 owns provider auto-update / release admission. A pool manifest minimum-binary-version predicate MUST reference SPEC-020/SPEC-001 version authority, not a parallel version notion; wire-advertised provider version remains SPEC-001-owned and is metadata, not proof of the running binary (see SPEC-042-R004).

SPEC-022 owns verified model settlement. A pool manifest MAY require verified-model settlement in enforce mode; a pool that requires enforce MUST NOT admit traffic while that pool's effective settlement mode is observe. SPEC-042 MUST NOT create a parallel settlement ledger.

SPEC-040 owns wallet-native buyer sessions. A wallet session MAY be scoped to a `pool_id`; pool scoping MUST NOT weaken SPEC-040 request signatures, replay checks, expiry, revocation, model allowlist, or spend caps. When a wallet session names a pool, the SPEC-040 semantic signature MUST cover `pool_id` and the manifest core digest (SPEC-042-R002, R009).

SPEC-041 owns relay-blind request encryption (Layer 3 MVP). SPEC-042 forward-declares Layer 3 compatibility fields and, per SPEC-042-R009, requires pool identity + manifest digest to bind into SPEC-041 route reservations, AAD/transcript, and wallet semantic signatures whenever a pool requires relay-blind or non-default privacy behavior. SPEC-042 v0.1 MUST NOT claim any relay-blind or content-confidentiality property.

## 3. Terms

| Term | Meaning |
|---|---|
| Trusted Pool (canonical; a.k.a. "pool") | A creator-operated trust boundary over shared MacProvider infrastructure, addressed by a `pool_id` and governed by a signed pool manifest. Not a cryptographic privacy domain. "Subnet"/"Controlled Pool" are retired synonyms, not buyer-facing names. |
| `pool_id` | Stable, mandatory authority identifier for a pool, derived as `base64url(SHA256(canonical identity core)[0:16])` (SPEC-042-R001). Stable for the pool's lifetime; ordinary policy/trust-predicate changes preserve it. |
| Pool manifest | The signed Layer 2 contract: a stable **identity core** (creator keys + genesis params, fixes `pool_id`), a per-version **policy core** (trust predicates + economics + Layer 3 fields), plus separately-signed mutable operational fields. |
| Manifest core digest | `manifest_core_digest = SHA256(canonical length-prefixed versioned policy core)`; changes per `manifest_version`; equals the pool policy hash exposed in `pool_policy.json`. |
| Identity core | The stable genesis fields (creator/admin signing key id(s) + genesis nonce/params) whose digest yields `pool_id`; excludes `pool_id`, `manifest_version`, and all policy/mutable fields. |
| Pool creator / operator | The identity holding manifest signing authority; creates the pool, sets the manifest, approves/revokes members. |
| Pool member | A SPEC-003 provider identity admitted to a specific `pool_id` and eligible for that pool's traffic. |
| Pool-enforceable predicate | A manifest-declared requirement enforced fail-closed at every route attempt for that pool, independent of the network-global default. |
| Pool generation | A monotonically increasing counter of the pool's routable membership/predicate state, fenced into each route reservation to reject stale reroutes. |
| Tenant isolation | The invariant that a request bearing `pool_id` receives **new dispatch** only from a current member of that pool satisfying its predicates, and fails closed rather than spilling elsewhere. Already-dispatched in-flight requests may complete per the revocation mode / lifecycle rules (SPEC-042-R003/R011), because the serving provider already holds the prompt. |
| `pool_policy.json` | Signed, buyer-verifiable publication of a pool's enforced predicates, allowlist, settlement mode, retention, revenue split, and policy hash. |
| `pool_status.json` | Live, **coordinator-attested** readiness surface derived from the actually-enforced predicates for a pool (not cryptographically buyer-verifiable in the sense `pool_policy.json` is — SPEC-042-R008). |

## 4. Normative requirements

> Each requirement states intent and load-bearing MUST/MUST NOT constraints. Remaining `(Open-*)` items are enumerated in the promotion checklist (SPEC-042-R010) and MUST close before v0.1 implementation. Any signed-record encoding MUST use the deterministic binary length-prefixed framing precedent of SPEC-041-R002 (unsigned 32-bit big-endian length prefixes; sorted, individually length-prefixed list elements; unsigned/signed 64-bit big-endian integers).

### SPEC-042-R001 - Pool object, signed manifest, identity and rollback

Every pool MUST be defined by a signed pool manifest with three clearly partitioned parts: a stable **identity core**, a per-version **policy core**, and separately-signed **mutable operational fields**.

Pool identity MUST be separated from versioned policy so that a policy change does not change the pool's identity.

- The **identity core** fixes the stable pool identity and MUST contain only identity-genesis fields: the pool's stable **root issuer** signing key id and a creator-chosen genesis nonce/parameters. It MUST NOT contain `pool_id`, `manifest_version`, any version-chaining hash, the rotating operational signer set, or any mutable/versioned policy field. `pool_id` MUST equal `base64url(SHA256(canonical length-prefixed identity core)[0:16])` and is therefore stable for the pool's lifetime. `pool_id` MUST NOT appear inside the identity-core digest preimage; it is carried alongside the signed manifest and MUST be rejected on mismatch against the recomputed identity-core digest. `pool_id` is a 128-bit truncation and is a **non-capability identifier** (a naming/grouping key for the membership ledger, blocklist, routing, logs, and settlement): authorization is never granted by presenting a `pool_id`, only by signature verification over the full identity/policy cores, which the coordinator recomputes. Second-preimage resistance is ~2^128; the only realistic truncation risk is an actor who controls two of its own pools colliding their ids (~2^64, limited blast radius), which the coordinator MUST still reject via full-core comparison. Operational admin/creator keys that sign policy cores and mutable fields are NOT in the identity core; they are a versioned signer set authorized by the root issuer (SPEC-042-R012), so rotating them preserves `pool_id`.
- The **versioned policy core** carries the trust contract for one `manifest_version` and MUST contain: the stable `pool_id` (as a reference, not part of its own identity preimage), `manifest_version` (monotonic unsigned integer), `prev_manifest_core_hash` (the versioned policy-core digest of the immediately preceding version, or a defined genesis value), the signer-set version it was signed under (SPEC-042-R012), model allowlist (SPEC-010 canonical ids), minimum provider binary version (SPEC-020/SPEC-001 authority), minimum attestation tier, `require_encrypted_leg`, settlement mode, declared `revenue_split_bps` with its `split_execution_status` (SPEC-042-R006; `declared_not_executed` in v0.1), retention-policy id (SPEC-042-R007), `min_eligible_members` (supply-readiness threshold, SPEC-042-R011), the Layer 3 compatibility fields of SPEC-042-R009, `not_before_unix`, and `expires_at_unix`. The `manifest_core_digest` (the pool policy hash) MUST be `SHA256(canonical length-prefixed versioned policy core)`.

The coordinator MUST reject manifests that are malformed, unsigned, signature-invalid (against the signer set in force per SPEC-042-R012), schema-invalid, `pool_id`-mismatched against the recomputed identity-core digest, non-monotonic in `manifest_version`, or broken in the `prev_manifest_core_hash` chain. A signed policy core whose `manifest_version` is less than or equal to the last accepted version for that stable `pool_id` MUST be rejected as a rollback. Mutable operational fields (e.g. disclosure wording, non-narrowing capacity hints) MUST be separately signed by an authorized operational admin key (SPEC-042-R012) and MUST NOT alter `pool_id` or the `manifest_core_digest`.

Loosening any confidentiality/attestation/settlement predicate is a trust-contract change: it MUST mint a new `manifest_version` under the same stable `pool_id` with `prev_manifest_core_hash` lineage, and MUST NOT silently apply to in-flight route reservations issued under the prior policy core. The coordinator MUST durably retain policy-core history sufficient to reconstruct which policy core was in force for any settled request. Because `pool_id` is derived from the identity core only, ordinary policy and trust-predicate changes preserve `pool_id`; buyer references, logs, settlement grouping, and rollback checks remain stable across versions.

**Active-policy selection.** At most one policy version MAY be the current policy for a `pool_id` at any instant. A policy core is *active* only when `now` is within the half-open interval `[not_before_unix, expires_at_unix)`; adjacent versions MAY share a boundary where `old.expires_at_unix == new.not_before_unix` without overlapping. Because overlapping validity windows are rejected (below), at most one version is active at any instant, and that version is the current policy. Future-dated policy cores MAY be pre-accepted but MUST remain inactive until `not_before_unix`. If no policy core is currently active — a validity gap, or all accepted versions expired — pool admission MUST fail closed with `pool_policy_stale` and MUST NOT route. The coordinator MUST reject a new policy core whose half-open validity window would overlap an already-accepted version for the same `pool_id`.

**Canonical encoding (identity core and versioned policy core).** Both cores use one deterministic, domain-separated, length-prefixed byte grammar (the SPEC-041-R002 framing precedent): unsigned 32-bit big-endian length prefixes on every string and byte field; unsigned 64-bit big-endian integers; a one-byte boolean (`0x01`/`0x00`); and set-like lists (the model allowlist) encoded as a 32-bit count followed by each element length-prefixed in byte-lexicographic ascending order with no duplicates. Each core's preimage begins with a fixed ASCII domain tag — `macprovider/spec042/identity-core/v1` and `macprovider/spec042/policy-core/v1` — so an identity-core digest can never collide with a policy-core digest or any other signed structure. The identity core encodes exactly `root_issuer_key_id` then `genesis_nonce`; `pool_id` = unpadded `base64url(SHA256(identity-core preimage)[0:16])`. The policy core encodes the SPEC-042-R001 field list above in the order listed, with `pool_id` carried as a reference bound into the preimage (so a signed policy core is non-transferable to another pool) and the genesis `prev_manifest_core_hash` fixed at 32 zero bytes; `manifest_core_digest` = `SHA256(policy-core preimage)`. The normative encoding is implemented in `phase4-coordinator/internal/poolmanifest` and frozen by the golden vectors in `phase4-coordinator/internal/poolmanifest/manifest_test.go`; the authority-log entry encoding (SPEC-042-R012) is specified with its implementation slice, not here.

**Signature verification (policy core).** A policy-core signature is a detached Ed25519 signature over a domain-separated signing message `macprovider/spec042/policy-core-sig/v1 ‖ manifest_core_digest`. The signing-domain tag is DISTINCT from the `policy-core/v1` digest-preimage tag so a policy-core signature can never be replayed as an identity-core, authority-log-entry, or mutable-field signature (each later structure gets its own signing tag). Because `manifest_core_digest` already commits to `pool_id`, `manifest_version`, `signer_set_version`, and every predicate, signing the digest binds the whole policy core. Verification (SPEC-042-R012) is M-of-N over the signer set the policy core names: the signer set MUST be structurally valid (`1 ≤ M ≤ N`, distinct key ids, distinct well-formed public keys — distinct public keys are required so one private key cannot satisfy the threshold under two key ids); its `Version` MUST equal the policy core's `signer_set_version`; it MUST be unrevoked with its half-open validity window containing the policy's `not_before_unix` (acceptance validity is anchored to `not_before_unix`, never to `manifest_version`); and the signature list MUST consist only of distinct, authorized, cryptographically valid signatures numbering at least `M` — so `M`-of-`N` means M *distinct authorized keys* signed the same digest, never M signatures from one key nor M valid signatures padded with an unauthorized one. This verification and the `pool_id`-binding recompute-and-compare are implemented in `phase4-coordinator/internal/poolmanifest/signature.go` and frozen by golden signature vectors in `signature_test.go`. The signer set consumed here is produced by the SPEC-042-R012 authority log (a later slice); this slice verifies a policy core against a signer set it is handed and does not itself establish or version signer sets.

### SPEC-042-R002 - `pool_id` authority threading and selection authorization

`pool_id` MUST be threaded as a first-class authority field through gateway admission, coordinator routing, provider admission/eligibility, route snapshots, request logs, routing logs (candidate set + chosen provider), route-snapshot and settlement context (not the v0.4 provider-signed receipt tuple unless SPEC-015 is revised), settlement journal, payout accounting, and public disclosure. Live Layer 2 traffic MUST NOT be enabled until `pool_id` is present and authoritative across all of those paths. Every settled **pool** request MUST record `pool_id`, `manifest_version`, and `manifest_core_digest`; global (poolless) requests carry no pool identity (represented per the Open-A nullable/sentinel decision) and this recording requirement does not apply to them. Absence of a pool selection MUST resolve to today's global behavior unchanged. A request MUST NOT be silently reassigned from one `pool_id` to another, nor from a pool to global, after admission.

Pool selection MUST be authorized before quota reservation or dispatch. The set of pools a caller may name MUST be bound to the buyer credential: for API-key requests, to the API key's authorized-pool scope; for wallet sessions, to the SPEC-040 session scope with the semantic signature covering `pool_id` and the manifest core digest. Selection-source precedence MUST be closed and deterministic (session/credential binding is authoritative; an explicit route parameter or header MAY only **narrow** to a pool the credential is already authorized for and MUST NEVER widen or override it). A request naming a pool the credential is not authorized for MUST be rejected before reservation with the non-disclosing error of SPEC-042-R010 (generic `pool_unavailable`), not a "not authorized for pool X" signal. Conflicting selection sources MUST be rejected as `pool_selection_invalid`.

### SPEC-042-R003 - Pool-scoped membership and durable revocation

A provider MUST be explicitly admitted to a pool by that pool's creator/admin before it is eligible for the pool's traffic. Membership MUST be a pool-scoped credential bound to an authenticated SPEC-003 provider identity and MUST be distinct from network-global provisional/trusted admission; satisfying global admission MUST NOT imply pool membership. A pool member MAY, by default, concurrently serve global (poolless) traffic. Per-request routing prevents a pool request from being served by a non-member and prevents a global buyer from receiving pool response content; it does NOT by itself eliminate shared-provider cross-request side channels (KV/prefix-cache occupancy, capacity, timing) on a co-serving member — cross-request cache sharing is bounded instead by SPEC-008 account-scoped `conv:` key derivation, and a pool sensitive to co-tenant side channels MUST use the dedicated-supply option below. Whether a given pool forbids co-tenancy and offers dedicated supply is a manifest choice that MUST be disclosed in `pool_policy.json` (SPEC-042-R008), because a buyer's mental model of a "dedicated" pool depends on it.

The coordinator MUST maintain a durable, creator-operated pool membership ledger and a **durable per-pool identity blocklist keyed by SPEC-003 provider identity**. Revocation MUST be checked both before membership issuance and on every route attempt (SPEC-042-R005). A revoked provider MUST NOT be re-admitted to that pool by re-satisfying global admission, and MUST NOT receive **new dispatch** for that pool once its revocation is committed (in-flight disposition is governed by SPEC-042-R011 and the revocation mode below). Membership and revocation state MUST survive coordinator restart and MUST be reconstructable per SPEC-042-R011. Because a pool identity blocklist is durable and identity-scoped, it is deliberately stronger than the existing TTL-scoped `AdmissionManager.Reject`, which is not an identity-forever blocklist.

A successful revocation MUST, synchronously and atomically: durably append to the blocklist, increment the pool generation counter (SPEC-042-R005), record a new `pool_state_epoch_hash`, and **invalidate cached eligibility for the pool**. Any eligibility snapshot used for selection MUST be keyed to the `pool_generation` under which it was computed, and the membership set and its generation MUST be captured in a single consistent read (so a revocation committing between reading membership and reading generation cannot stamp a stale membership set with the current generation). A selection attempt MUST recompute or discard any eligibility snapshot whose generation is not the current one, so a committed revocation is reflected at the very next selection attempt (≈0 ms) rather than persisting in a cached snapshot that then feeds a fresh reservation. The `pool_revocation_freshness_max_ms` bound (v0.1 maximum **5000 ms**; an implementation MAY configure tighter, never looser) is a **cache-coherence liveness backstop** for detecting missed invalidations, NOT a licensed window of continued dispatch: any route attempt whose eligibility generation cannot be proven current within the bound MUST fail closed with `pool_policy_stale`. Conformance MUST assert that a route attempt at any time **after** a revocation is committed — including immediately after (T+ε), not only after `pool_revocation_freshness_max_ms` — does not select or dispatch to the revoked provider.

Revocation carries a mode: `revoke_graceful` permits already-dispatched in-flight requests to complete (the provider already holds the prompt); `revoke_immediate` (for compromise/emergency, triggerable via a SPEC-042-R012 signed control message) additionally cuts already-dispatched in-flight dispatch for that provider. Both modes block all new dispatch immediately.

### SPEC-042-R004 - Pool-enforceable trust predicates, fail-closed, with exact SPEC-008 mapping

A pool manifest MUST be able to require, as fail-closed route-time predicates independent of the network-global default: minimum attestation tier, fresh SE liveness/key freshness, `require_encrypted_leg=true`, minimum signed provider binary version, and a model-catalog/hash policy. When a manifest requires a predicate, a request for that pool MUST be rejected (typed error, SPEC-042-R010) rather than routed to a provider not currently satisfying it, and MUST NOT be downgraded.

The attestation-tier predicate is an **ordered lattice** `none < se_custody < hardware_mda`; a "minimum tier" is satisfied by that tier or any stronger tier, and a raw "attested" status MUST NOT by itself satisfy a hardware requirement. Mapping to SPEC-008 evidence (which serializes tiers as `self_signed` and `hardware`):

- `se_custody` is satisfied when SPEC-008 yields `attestation_status = attested` with `attestation_tier` of **`self_signed` or `hardware`** AND SE liveness/key freshness is within bound (a hardware-attested provider therefore also satisfies a `se_custody` minimum);
- `hardware_mda` is satisfied **only** when SPEC-008 yields `attestation_status = attested` AND `attestation_tier = hardware` AND a live MDA proof is fresh and bound to the SE public key.

**`hardware_mda` gating requires a SPEC-008 amendment.** SPEC-008 currently mints the `hardware` tier via the live-MDA **observe** path and does not bless it as gating-grade (its `require_attestation` still admits `self_signed`). Mirroring the discipline SPEC-042 applies to revenue-split (SPEC-005/016, R006), privacy (SPEC-041/040, R009), and receipts (SPEC-015, R002), the `hardware_mda` predicate MUST NOT be enabled as a fail-closed gate until a coordinated SPEC-008 amendment/version bump promotes the live-MDA hardware verdict from observe to gating-grade. Until that amendment lands, a pool that requires `hardware_mda` MUST fail closed by construction (`pool_attestation_unsatisfied`), and this is stated as an intended pre-amendment behavior, not a defect. `se_custody` gating is available now (it maps to signals SPEC-008 already blesses).

The coordinator MUST NOT interpret client-set posture fields (`sipEnabled`, `secureBootEnabled` in the SE blob) as satisfying any predicate unless MDA-backed or runtime-measured.

A minimum-binary-version predicate MUST be satisfied only by coordinator-held SPEC-020 release-admission evidence bound to the provider identity/session — an accepted signed binary hash, release signing identity, and freshness timestamp — never by the wire-advertised provider version alone (which is metadata, not proof of the running binary). Absent sufficient release evidence, the predicate MUST fail closed with `pool_binary_too_old`.

This requirement is load-bearing because the live network default is fail-open: as of 2026-08-18 the production coordinator (`coordinator.malibu.tech`, v1.8.95) runs `require_attestation=false` and `require_encrypted_leg=false` (neither is set in the base config or the Pearl overlay, so both take the code default of false), while `verified_model_settlement_mode=enforce` and `live_mda_enabled=true` (observe-only, non-gating). A Trusted Pool therefore CANNOT inherit its confidentiality/attestation floor from the network; the manifest MUST carry these as pool-level fail-closed predicates that override the network default.

### SPEC-042-R005 - Tenant isolation and per-attempt pool-scoped routing

Coordinator provider selection for a request bearing `pool_id = P` MUST consider only current members of P that satisfy P's manifest predicates, and MUST re-apply both the membership check and the predicate checks on **every** selection attempt — initial selection, failover, sticky/affinity retry, hard/pinned routing, preflight replacement, and mid-request provider loss. The generation fence MUST apply to **every dispatch-authorizing decision**, not only to objects named "route reservations": each reservation-based, pinned/self-route, and slot-queue dispatch path MUST carry and verify the current `pool_generation`/`pool_state_epoch_hash` for P as a mandatory dispatch precondition. If the live pool generation no longer matches the fenced generation at dispatch, the coordinator MUST reject with `pool_state_stale` and require fresh selection rather than reusing a prior candidate. The substrate's dispatch paths are not currently funneled through a single choke-point (the pinned/self-route path bypasses the eligibility filter today), so conformance MUST drive the pinned/self-route path — not only the ordinary reservation path — through a mid-flight revocation and a lifecycle transition. If no eligible member is available at any attempt, the request MUST fail closed and MUST NOT spill to a global provider, a non-member, or a member of a different pool. Pool routing MUST NOT begin from the global provider snapshot without the pool filter applied.

Tenant isolation is the hardest-risk invariant of the Layer 2 MVP: any fallback path that reuses SPEC-002 global selection breaks the product promise even if base routing "works." Fail-closed isolation conformance tests (including every reroute/failover/revocation-race window above) MUST be written before the routing-filter implementation (SPEC-042-R010).

### SPEC-042-R006 - Pool-scoped settlement bound to the route snapshot

**v0.1 is labels-only and MUST NOT change money-path arithmetic or ownership.** SPEC-005 owns billing/settlement formulas and SPEC-016 owns payout lifecycle; SPEC-042 v0.1 adds only immutable pool *labels* to the existing settlement records (the durable `settlement_route_snapshots` and the settlement-receipt ledger — this SPEC uses "settlement journal" as a generic term for those existing objects, not a new ledger). Those entries for pool traffic MUST carry the immutable `pool_id`, `manifest_version`, `manifest_core_digest`, and `route_snapshot_hash` captured at routing time. If any of these mismatch between the routing-time route snapshot and settlement time, the coordinator MUST NOT silently drop the label or reassign the request to global (which SPEC-042-R002 forbids); it MUST settle the underlying usage under existing SPEC-005 rules but mark the pool label `label_disputed` and emit a pool-audit record, and MUST NOT attribute the request to the pool for any pool-scoped accounting. Per-pool usage attribution MUST be by verified (non-disputed) `pool_id`. Payout execution remains governed by the existing guarded payout runner (default-disabled); SPEC-042 does not enable payouts.

**Creator revenue split is DEFERRED to a Layer 2 V1** because it crosses into SPEC-005 billing arithmetic and SPEC-016 payout authority, which SPEC-042 does not own. `revenue_split_bps` MAY be *declared* in the versioned policy core and published (a fixed economic promise buyers/creators can read), but MUST NOT be *executed* as a distribution until a V1 that carries: named SPEC-005 and SPEC-016 amendments, AUTHORITY consumer edges for the billing/payout domains, ledger schema fields (`creator_account_id`, `creator_payout_subject_hash`, split fields), idempotency rules, and money-path review. When the split executes, settlement MUST bind and use the routing-time-captured `creator_account_id`/`creator_payout_subject_hash` from the policy core and MUST reject any payout entry whose recipient subject differs, so a compromised or mutable settlement path cannot redirect creator revenue.

Layer 2 pool settlement is **linkable by design** (account/request/provider/pool are joined) and MUST be disclosed as such; unlinkable/batched settlement is Layer 3 and out of scope here.

### SPEC-042-R007 - Pool-scoped observability and field-level retention matrix

Each pool MUST reference a retention-policy id (bound in the versioned policy core) that resolves to a normative **field-level retention/redaction matrix**. The matrix MUST enumerate, per field, whether it is permitted in the pool tier, its retention window, any minimum aggregation threshold before exposure, and the viewer class allowed to see it — covering at least: request logs, routing logs (candidate set + chosen provider), audit logs, `buyer_ip`, request ids, provider ids, selected headers, prompt hashes, timing, and size buckets. The default `buyer_ip` capture and 90-day request-log retention MUST be overridable to a tighter pool-specific policy. Buyer-safe aggregate pool health MUST avoid identifying individual providers. This is Layer 2 metadata hygiene, not unlinkability, and MUST NOT be described as anonymity.

No retention policy — for any pool tier — MAY permit storing raw credential-bearing headers or fields: `Authorization`, `Cookie`, `Set-Cookie`, API-key, wallet-session bearer, provider-token, and signature-secret values MUST NOT be retained. Where header observability is required, only an allowlisted header **name** with a redacted or classified value digest MAY be stored.

### SPEC-042-R008 - Buyer-verifiable pool promise surfaces

A pool MUST publish a creator-signed `pool_policy.json` and expose a live `pool_status.json`. Both MUST be closed-schema. `pool_policy.json` MUST expose enforced predicates, minimum binary version, attestation tier, model allowlist, retention-policy id, settlement mode, `revenue_split_bps`, and a `policy_hash` equal to the manifest core digest, signed by the pool creator/admin key over a canonical length-prefixed encoding. It MUST also carry two mandatory honesty fields: a `confidentiality_scope` field stating plainly that prompt and response content are visible to the coordinator and the selected provider operator and that the pool provides administrative trust, not content privacy; and, whenever `revenue_split_bps` is present, a `split_execution_status` field (`declared_not_executed` in v0.1) so no reader interprets the declared split as an active distribution. Any buyer-facing exposure of `require_encrypted_leg` MUST label it as transport-leg-only (SPEC-042-R009). `pool_policy.json` MUST also disclose whether pool members may concurrently serve global (poolless) traffic (see SPEC-042-R003); if dedicated supply is offered as a tier, it MUST be named and truthful.

`pool_status.json` is **coordinator-attested**, not cryptographically buyer-verifiable, and MUST be labeled as such (the Layer 2 trust model already trusts the coordinator; it MUST NOT be described as buyer-verifiable in the sense `pool_policy.json` is). It MUST expose a `readiness` enum drawn from a closed set (`ready`, `degraded`, `unavailable`, `stale`, `unknown`) derived from the actually-enforced predicates and current member health, plus the `pool_id`, `manifest_version`, `policy_hash`, and a freshness timestamp. Both surfaces MUST declare cache semantics (`no-store` or a bounded TTL); consumers MUST treat a fetch failure or expired freshness as `stale`/`unknown` and MUST NOT silently downgrade to a generic disclosure. Promotion requires negative tests proving a stale/unknown state is surfaced rather than masked.

### SPEC-042-R009 - Layer 3 compatibility fields, claim control, and privacy binding

The versioned policy core MUST carry forward-declared Layer 3 compatibility fields: `privacy_mode` (default `none` for Layer 2), `relay_blind_capable`, `receipt_contract`, `metadata_visible`, `downgrade_policy`, and `sticky_routing_allowed` (default `false` for trust-sensitive pools, because sticky routing increases provider correlation). For SPEC-042 v0.1, `privacy_mode` MUST be `none`; a non-default `privacy_mode` (relay-blind or later Layer 3 behavior) is **blocked** and MUST NOT be enabled by SPEC-042 alone.

Enabling a non-default `privacy_mode` requires a coordinated SPEC-041 and SPEC-040 amendment (version bump), because SPEC-041 v0.1's closed request/reservation/AAD schema and SPEC-040's wallet semantic signature do not currently reserve pool fields. That amendment MUST reserve and bind `pool_id`, `manifest_version`, `manifest_core_digest`, and the pool generation / `pool_state_epoch_hash` (SPEC-042-R005) into the SPEC-041 route reservation, the SPEC-041 AEAD AAD/transcript, the SPEC-040 wallet semantic signature, the route snapshot, and settlement context. Until that amendment lands, a pool that declares a non-default `privacy_mode` MUST fail closed rather than route, and conversely a v0.1 relay-blind (SPEC-041) request MUST NOT be pool-scoped at all — its closed envelope cannot carry bound pool selection, so any pool intent would be an unbound out-of-band source and MUST be rejected — so no unbound pool→global path exists. This SPEC forward-declares the fields so the amendment is additive, not a re-architecture.

Claim control MUST be enforced in copy: SPEC-042 pools MUST use the single canonical name "Trusted Pool", MUST NOT be called "Privacy Pools", and MUST NOT claim coordinator-blind content, provider blindness, unlinkability, hidden provider identity, "end-to-end encrypted," "confidential compute," or "private from provider." Beyond banning overclaims, claim control MUST **mandate the load-bearing true negative**: every buyer-facing pool surface MUST disclose that prompt and response content are visible to the coordinator and to the selected provider operator, and that a Trusted Pool provides administrative trust, not content privacy (this is structural even under Layer 3 relay-blind, which still does not hide content from the provider operator). Wherever `require_encrypted_leg` is exposed to buyers it MUST be labeled as **transport (coordinator→provider) leg only**, never as content confidentiality. The permitted Layer 2 claim is "creator-run Trusted Pool with an explicit, buyer-verifiable trust policy — enforcing, fail-closed, the attestation/encryption/binary floors the global network leaves optional." Claim control MUST be machine-enforced, not left to copy: the coordinator MUST reject, at manifest / `pool_policy.json` acceptance, any signed `confidentiality_scope` or claim that exceeds the structural Layer 2 truth (content is visible to the coordinator and the selected provider operator), so a validly-signed overclaim cannot be published.

### SPEC-042-R010 - Configuration, rollout, error taxonomy, and evidence gate

Pool control-plane configuration MUST be default-off and MUST NOT change global (poolless) behavior when disabled. Rollout MUST be staged so mixed binaries fail safely: old components MUST ignore or reject unknown pool fields without changing global behavior; `pool_id` ingestion MAY land before pool-scoped routing is enabled, but pool-required traffic MUST fail closed until gateway, coordinator, and provider support are all present; rollback by disabling pool config MUST reject pool-required requests before quota reservation and MUST NOT affect global or SPEC-008 provider-leg-encrypted traffic.

**Positive pool-capability negotiation is required to prevent a pool→global spill under version skew.** Because an old coordinator ignores `pool_id` and routes from the global snapshot, a new gateway MUST NOT rely on the old coordinator to "fail closed" (it cannot understand the concept). The coordinator and provider MUST each advertise a pool-support capability version, and the gateway MUST refuse pool-required dispatch unless the assigned coordinator **and** the selected provider positively advertise pool support at the required version. Absent that positive advertisement, the gateway MUST fail closed with `pool_unavailable`. This handshake is architectural (not a deferred byte-grammar item) and MUST be specified before v0.1.

SPEC-042 defines this minimal SPEC-006-compatible error taxonomy. Predicate-specific and existence-revealing codes MUST be returned only to a caller already authorized for the pool; unauthorized or unknown-pool callers MUST receive the generic `pool_unavailable` so error responses do not reveal private-pool existence, membership health, attestation posture, or capacity timing. To avoid a timing oracle, the credential-scope check (is `pool_id` in the caller's authorized set?) MUST precede and be independent of any pool-registry existence or predicate evaluation, and the response latency for an unauthorized caller MUST NOT depend on whether the named pool exists.

| Code | HTTP | Retryable | Visibility | Meaning |
|---|---:|---|---|---|
| `pool_unavailable` | 503 | no | any caller | Generic: pool disabled, unknown, or caller not authorized for it. Does not distinguish cause. |
| `pool_selection_invalid` | 400 | no | any caller | Syntactically conflicting or ambiguous pool selection sources only. A route param naming a pool outside the credential's authorized scope (including any widening attempt) MUST instead return the generic `pool_unavailable`, so the error does not confirm the named pool exists. |
| `pool_no_eligible_member` | 503 | no | authorized only | No current member satisfies the manifest predicates; fail-closed, no spill. Same reservation MUST NOT be retried. |
| `pool_at_capacity` | 503 | yes | authorized only | Eligible members exist but all are at capacity; fail-closed, no spill. Retry after backpressure. |
| `pool_attestation_unsatisfied` | 503 | no | authorized only | No member meets the required attestation tier / SE freshness. |
| `pool_encrypted_leg_unsatisfied` | 503 | no | authorized only | No member offers the required provider-leg encryption. |
| `pool_binary_too_old` | 503 | no | authorized only | No member meets the minimum signed binary version. |
| `pool_model_not_allowed` | 400 | no | authorized only | Requested model is not in the pool allowlist. |
| `pool_settlement_mode_unsatisfied` | 503 | no | authorized only | Pool requires enforce-mode settlement but effective mode is observe. |
| `pool_state_stale` | 409 | yes | authorized only | Route reservation's fenced pool generation no longer matches; obtain a fresh reservation. |
| `pool_policy_stale` | 503 | yes | authorized only | Pool policy/status freshness is unknown or expired; fail closed. |

Errors MUST use the existing OpenAI-compatible envelope and retry metadata; the explicit `retryable` field takes precedence over generic HTTP-status heuristics.

### SPEC-042-R011 - Pool lifecycle, provider migration, and failover reconstruction

A pool MUST have an explicit lifecycle state machine with a closed state set (`created`, `active`, `paused`, `draining`, `retired`) and recorded effective times for each transition. The behavior of each state MUST be deterministic and testable per this transition table:

| State | New admission | Existing reservations | In-flight dispatch | Failover / reroute | `pool_status` readiness | Settlement/payout | Allowed next states |
|---|---|---|---|---|---|---|---|
| `created` | reject (`pool_unavailable`) | none exist | none | n/a | `unavailable` | n/a | `active`, `retired` |
| `active` | accept if predicates pass | honored | allowed | allowed within pool (SPEC-042-R005) | `ready`/`degraded`/`unavailable` by supply | normal, labeled | `paused`, `draining`, `retired` |
| `paused` | reject (`pool_unavailable`) | dispatched in-flight only; un-dispatched invalidated by fence | allowed (dispatched) | allowed within pool | `unavailable` | continues for in-flight | `active`, `draining`, `retired` |
| `draining` | reject (`pool_unavailable`) | dispatched in-flight only; un-dispatched invalidated by fence | allowed to completion (dispatched) | allowed within pool only | `unavailable` | continues for in-flight | `retired` |
| `retired` | reject (`pool_unavailable`) | none honored | none | none | `unavailable` | terminal after in-flight settle | terminal |

Every lifecycle transition MUST atomically bump `pool_generation` and record a new `pool_state_epoch_hash`, so route reservations fenced under a prior generation (SPEC-042-R005) are invalidated at dispatch and failover without a separate ad hoc state check. "Existing reservations honored" in the table above means **only already-dispatched in-flight requests may complete** (subject to the revocation mode of SPEC-042-R003 — `revoke_immediate` cuts even those for the revoked provider); every un-dispatched reservation minted before the transition MUST be invalidated by the generation fence (consistent with SPEC-042-R005), and this rule is uniform across `paused`, `draining`, and any revocation. The `draining`→`retired` transition MUST be gated on **dispatch/delivery drain**: a pool enters `retired` only after every already-dispatched request has finished delivering output. `retired` rejects all new admission and dispatch, but MUST still permit **asynchronous settlement/receipt finalization** of requests delivered before retirement (SPEC-022 receipts arrive seconds to minutes later); "delivery drain" (the entry gate) and "settlement finalization" (the permitted post-entry activity) are distinct and MUST NOT be conflated. No state MAY fall back to global or other-pool supply for a request that selected the pool.

Migrating an existing global provider into a pool MUST require explicit creator member admission (SPEC-042-R003); a provider MUST NOT be auto-enrolled into a pool by virtue of global network membership. A pool MUST enforce the signed `min_eligible_members` supply-readiness threshold (SPEC-042-R001) below which `pool_status.json` reports non-`ready` and required traffic fails closed with `pool_no_eligible_member` rather than serving from insufficient or again-global supply. For a deterministic count, an **eligible member** is a current, non-revoked pool member that, at the route-time snapshot, passes all manifest predicates (SPEC-042-R004) and has fresh health within the SPEC-042-R003 freshness bound; members that are unhealthy, stale, or predicate-failing MUST NOT be counted. Whether a busy/at-capacity member counts toward `min_eligible_members` MUST be fixed by the manifest's readiness policy (default: capacity-blocked members count toward supply readiness but cannot receive a dispatch until a slot frees); the count MUST be taken from a single consistent snapshot, not summed across attempts. Because a member may be predicate-eligible yet saturated (especially under the co-tenancy default of SPEC-042-R003), `readiness = ready` MUST NOT be read as a promise of immediate free capacity. When every eligible member is at capacity, the request MUST NOT report `pool_no_eligible_member` (the members do satisfy predicates); it MUST either queue under existing SPEC-002 capacity backpressure or fail with the distinct typed error `pool_at_capacity` (SPEC-042-R010), never spill to global.

The coordinator MUST reconstruct pool state — manifests and version history, membership ledger, revocation blocklist, and lifecycle state — from durable storage across restart and failover, because current coordinator pool state is live/in-memory and provider records carry no `pool_id` today. v0.1 assumes a single authoritative coordinator for a given pool; the design MUST NOT preclude a later multi-coordinator consistency model, and MUST NOT assume in-memory-only pool state.

### SPEC-042-R012 - Manifest authority and key lifecycle

The pool's stable **root issuer** key (identity core, SPEC-042-R001) is the trust anchor for `pool_id` and MUST NOT be rotated in place; rotating it is equivalent to minting a new pool identity.

Operational admin/creator keys that sign policy cores and mutable operational fields form a **versioned signer set** authorized by the root issuer through a signed, append-only **authority log** keyed under the stable `pool_id`. Each authority-log entry MUST carry: a monotonic `signer_set_version`, `prev_authority_log_entry_hash` and `authority_log_entry_hash` (hash chain), the authorized signer key ids, a signing threshold `M` of `N` with `1 <= M <= N`, a validity window, and a signature from the root issuer or a prior still-authorized signer set. The coordinator MUST durably persist the highest accepted `signer_set_version` per `pool_id` and MUST reject any entry that is `<=` that value (rollback), breaks the hash chain, uses a revoked signer set, or declares a threshold with `M < 1` or `M > N`.

Each policy core carries the explicit `signer_set_version` under which it was signed (SPEC-042-R001). A policy core MUST be verified against exactly that `signer_set_version`, and that signer set MUST be valid (not revoked, and its validity window containing the policy core's `not_before_unix`) at the policy's acceptance-time epoch — `manifest_version` is a policy ordinal, not a time anchor, so acceptance-time validity MUST be evaluated against `not_before_unix`/signer-set validity windows, never against `manifest_version`. The coordinator MUST reject material signed under a not-yet-active, expired, revoked, or version-mismatched signer set. The acceptance verdict and the epoch at which it was made MUST be durably recorded as final, so restart/failover reconstruction (SPEC-042-R011) replays the recorded verdict rather than re-evaluating validity against the current wall-clock (which could flip an accepted policy to rejected after its signer set later expires).

Operational key rotation, threshold change, and compromised-key revocation MUST be expressed as new signer-set versions and MUST preserve `pool_id` (they do not touch the identity core). Root-issuer compromise or loss has **no in-pool recovery**: it MUST require minting a new pool (new identity core → new `pool_id`) with signed `supersedes` lineage to the retired `pool_id`, and buyers MUST be able to follow that lineage. An authorized signer set (or the root issuer) MUST be able to trigger an emergency `paused`/`draining`/`revoke_immediate` transition (SPEC-042-R011/R003) via a signed control message that the coordinator honors fail-closed. The authority log and current signer set MUST be durable and reconstructable across restart/failover (SPEC-042-R011).

**Operator provenance.** `pool_id` and the signing chain anchor to a bare root-issuer key; by itself that proves key *continuity*, not that the pool named "Acme Legal" is operated by Acme rather than an impostor who generated a key. For a trust product sold on operator reputation this is load-bearing. v0.1 therefore MUST either (a) bind the root issuer key to a verifiable operator identity — a MacProvider-countersigned operator-registry entry and/or a domain/DNS binding — exposed in `pool_policy.json`, or (b) if that binding is deferred, state explicitly on every buyer surface that **pool names are self-asserted and not verified operator identity in v0.1**. A pool name MUST NOT be presented to buyers as a verified operator identity unless option (a) is in force. (For the v0.1 vertically-integrated-operator wedge, where the operator runs its own buyers, option (b) is acceptable; option (a) is a V1 requirement before third-party buyers transact on operator reputation.)
