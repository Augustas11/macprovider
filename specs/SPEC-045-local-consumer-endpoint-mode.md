## 1. Purpose and scope

SPEC-045 defines a local consumer endpoint mode for `macprovider-cli`: a loopback-only OpenAI-compatible `/v1` HTTP server that lets local tools, agents, and SDKs send buyer requests through MacProvider without embedding the upstream buyer credential in each tool.

The user outcome is a low-friction local development surface. A buyer should be able to run a local command, point an OpenAI-compatible client at a loopback base URL, choose an allowed model, enforce a local estimated-exposure cap, inspect status, and stop the process without exposing upstream credentials or bypassing gateway admission.

This spec is required because the feature crosses CLI UX, local HTTP serving, buyer credential custody, gateway compatibility, local exposure accounting, and user-visible exposure controls. SPEC-006 owns the public gateway API; SPEC-045 owns only the local consumer proxy that speaks to that gateway on behalf of a local buyer.

The sections below intentionally separate the product contract, safety invariants, and release evidence so implementers can review the feature shape without inferring scope from hardening details alone.

### Explicit non-goals

SPEC-045 does not create a new public gateway, coordinator endpoint, provider serving path, settlement formula, rate-card source of truth, wallet session authority, provider payout rule, or model catalog authority.

SPEC-045 does not make `macprovider-cli` a general reverse proxy. The local endpoint is only for MacProvider buyer traffic and only for the OpenAI-compatible gateway surfaces allowed by this spec.

SPEC-045 does not authorize public-network listeners, daemon installation, background login items, shared multi-user service mode, credential issuance or rotation, provider-selection hints, raw receipt storage, or buyer-side token accounting as settlement evidence.

SPEC-045 does not require local clients to know the upstream buyer API key. Local clients authenticate to the loopback endpoint with a per-run local bearer token that has no upstream identity and must never be forwarded to the gateway.

SPEC-045's loopback guarantee is limited to the host operating system's network namespace. Container, VM, SSH tunnel, browser, or port-forward exposure of the loopback listener is out of scope for v0.1 and must be handled by the operator or a later authenticated multi-user mode.

SPEC-045 v0.1 is macOS-only and uses plain HTTP on the loopback listener. Linux, Windows, TLS-on-loopback, and Unix-domain socket serving are out of scope until a later SPEC-045 version defines their paths, trust assumptions, and tests.

## 2. Dependencies and authority

SPEC-045 owns `local-consumer-endpoint`: the local CLI command, loopback listener, credential custody rules, local exposure admission, local status contract, and restart behavior for buyer-side endpoint mode.

SPEC-001 remains authoritative for the `macprovider-cli` binary lifecycle, provider-binary packaging conventions, and existing provider-side inference-server behavior. SPEC-045 consumes that CLI authority only to reserve and define the new `consume` subcommand contract for buyer-side local endpoint mode; it does not change SPEC-001's provider wire protocol or provider serving path.

SPEC-006 remains authoritative for the public buyer gateway's OpenAI-compatible request/response surface, upstream authentication, quota enforcement, and error semantics. SPEC-045 may proxy only the SPEC-006-compatible endpoints it implements locally, and it must preserve upstream gateway enforcement rather than replacing it.

SPEC-005 remains authoritative for billing formulas, rate math, settlement, token accounting, and provider payout. SPEC-045 may use trusted catalog/rate metadata only to make conservative local exposure-admission decisions and must not treat local estimates as settlement evidence.

SPEC-010 remains authoritative for model catalog identity. SPEC-045 consumes model identifiers and local allowlist entries but must not create new canonical model ids.

SPEC-015 remains authoritative for receipt privacy and retention. SPEC-045 may surface redacted request ids and local exposure ledger entries, but it must not persist raw prompts, raw completions, bearer tokens, full upstream errors, or raw receipt bodies.

SPEC-018 and SPEC-019 remain authoritative for tool-calling and structured-output request/response semantics. SPEC-045 may require local pass-through for those chat-completions fields, but it must not reinterpret tool calls, validate tool arguments, or redefine structured-output behavior.

SPEC-023 remains authoritative for signed static catalog/rate-card feed trust, keyring resolution, detached sidecar verification, generated-at freshness policy, and fail-closed rate-card acceptance. SPEC-045 consumes that trust contract only to decide local exposure admission; it does not change installer/autotune recommendation policy.

SPEC-024 remains authoritative for prefix-cache billing isolation. SPEC-045 consumes SPEC-024 only to exclude cache-hit discounts from conservative admission unless a trusted gateway quote or later SPEC-045 dependency defines cache-hit token evidence that is safe for local admission.

SPEC-040 is related but not a dependency for v0.1. A later version may allow wallet-native buyer sessions as a credential source when SPEC-040 defines a compatible local custody and refresh contract.

## 3. Contract profile

This section summarizes the contract shape for reviewability. R001-R008 remain the enforcing source of truth; if this summary and a detailed requirement appear to overlap, the more specific R001-R008 language controls.

Core product contract:

- `malibu-cli consume` starts a macOS loopback-only, plain HTTP/1.1 endpoint for local buyer tools.
- Local clients use the generated local token and loopback base URL; the upstream buyer credential stays in CLI custody.
- v0.1 supports `GET /v1/models`, `POST /v1/chat/completions`, and local `GET /v1/status`.
- Model access is allowlist-based, with an empty default allowlist until the operator opts in.
- Chargeable chat-completions requests require either a positive local run budget or explicit `--no-budget`, and may also use a per-request cap.
- Local budget admission is a conservative exposure control only; upstream MacProvider billing, settlement, gateway authentication, and quota authority remain with SPEC-005 and SPEC-006.
- Restart behavior is ledger-backed when a budget or explicit no-budget ledger is configured, with held-reservation recovery commands.
- Promotion beyond draft requires automated conformance coverage plus a signed real-gateway journey.

Safety invariants:

- The listener is loopback-only in the host network namespace and never binds public, LAN, wildcard, VPN, Unix-domain, or unresolved non-loopback inputs.
- Local bearer tokens are per-run secrets, authenticate only the loopback endpoint, and are never forwarded upstream.
- Local authentication, request-framing limits, and path normalization happen before body buffering or upstream forwarding.
- The server is not a general proxy: only the supported endpoint set is matched exactly after normalization.
- Upstream gateway configuration is an HTTPS origin only, rejects userinfo/path/query/fragment input, validates TLS normally, disables proxy/redirect bypasses, and sends credentials only to validated global addresses.
- Local request bodies, upstream metadata, and upstream responses are bounded; oversized, ambiguous, compressed, duplicated-key, or parser-exhausting inputs fail closed before admission or forwarding.
- Budget and ledger arithmetic uses integer micro-USD values, string-encoded in rows, with durable append-before-forwarding and closed state transitions.
- Logs, ledgers, status output, diagnostics, and cross-client error surfaces never persist or expose raw prompts, completions, bearer tokens, credential paths, raw receipts, full upstream bodies, local/private hostnames, usernames, or stable hardware identifiers. R006 separately allows the user-private active endpoint descriptor to contain the local token or same-security reference, and startup/status may show the bound loopback URL plus configured upstream origin. R007 separately allows the initiating local client to receive its own syntactically valid upstream error body.
- Pricing admission fails closed unless trusted signed pricing is fresh enough or an explicit unpriced override can reserve the full remaining budget without violating per-request caps.
- Upstream gateway errors are preserved to the initiating local client, but other diagnostics receive only redacted code/class/request-id material.

Release evidence checklist:

- R008 is the normative implementation evidence checklist and gates production promotion. It enumerates required automated coverage for the command, network boundaries, credential custody, request parsing, proxying, budget ledger, pricing trust, recovery, status, error mapping, resource limits, and real-gateway journey.
- R008 does not add a second product surface; it makes the proof obligations for R001-R007 explicit and mandatory.
- Implementation work is intentionally split into bounded BUILD_SPEC prompts under `specs/design/spec-045/`. Those prompts sequence implementation and review work; they do not create new normative authority beyond R001-R008.

## 4. Normative requirements

For SPEC-045, a request is chargeable if and only if local authentication under R003 succeeds and normalized endpoint matching under R002 identifies `POST /v1/chat/completions`. Chargeable classification does not require successful JSON body parsing, model admission, pricing admission, ledger reservation, upstream forwarding, or upstream success. The positive `--budget-usd` or explicit `--no-budget` configuration requirement, per-request cap requirement, warning-header rules, and local admission error mapping apply at runtime to every chargeable request; ledger reservation and budget mutation occur only after the request body can be parsed and estimated under R002/R004.

**SPEC-045-R001 - Loopback-only local command.** `macprovider-cli` MUST expose a local consumer endpoint command, with a stable spelling reserved for `consume`, that starts a plain HTTP/1.1 server bound to a loopback interface. The default bind address MUST be `127.0.0.1`; IPv6 loopback `::1` MAY be supported. The default port MUST be `11435`; port `0`, port collision, bind failure, or rejected bind input MUST fail startup with a nonzero exit and a redacted stderr error code `local_bind_rejected` rather than silently selecting a different port. Bind validation MUST be allowlist-based: after address parsing and name resolution, the only accepted listener addresses are IPv4 loopback addresses in `127.0.0.0/8` and IPv6 `::1`. If the implementation accepts the hostname `localhost` as a bind input, it MUST normalize it to an accepted loopback literal before binding, MUST prefer `127.0.0.1` when both IPv4 and IPv6 loopback records are available and IPv6 loopback was not explicitly requested, and MUST NOT reject it solely because IPv6 loopback is unsupported. The command MUST reject wildcard, LAN, VPN, public, Unix-domain, hostname-resolved non-loopback, or interface-scoped listener exposure unless a later spec defines an authenticated multi-user mode. The command MUST print the local base URL, upstream gateway origin, active model allowlist summary, budget mode, unpriced-request override state, and credential-source class on startup. Startup status information MUST be written to stderr; structured machine-readable output, when explicitly requested by a later flag or command, MUST be written to stdout. The model allowlist summary MUST print the total count and, when non-empty, a sample of up to five model ids; an empty allowlist MUST print an explicit empty-allowlist warning. It MUST NOT print the upstream bearer token, an expanded absolute credential path, a home-directory path, a username-bearing path, a secret-bearing path component, or any client prompt/completion content.

**SPEC-045-R002 - OpenAI-compatible endpoint subset.** The accepted local path set for v0.1 is `GET /v1/models`, `POST /v1/chat/completions`, and `GET /v1/status` as defined by R006; the local server MUST implement those paths before the mode can be promoted beyond draft. `GET /v1/status` is a local diagnostic carve-out, not the public SPEC-006 gateway status surface, and MUST NOT be proxied upstream. Before local authentication, the server MUST enforce bounded HTTP request-line bytes, bounded request-target bytes, bounded percent-decoding/parser work for the request target, bounded HTTP header bytes, bounded header count, a bounded header-read deadline, and a bounded cap on incomplete/pre-auth connections; violations MUST close or reject the request without body buffering or upstream forwarding. Requests with a non-empty local query string MUST fail locally as `local_invalid_request` and MUST NOT be forwarded, logged, or preserved as endpoint identity in status or diagnostics. After local auth succeeds under R003 and before endpoint matching for every local path, it MUST normalize the HTTP request path by resolving percent-encoding, MUST reject malformed encodings, encoded slash/backslash path separators, raw or encoded dot-segment components, and any path whose normalized form is not an exact supported path, and MUST NOT construct an upstream URL from an unnormalized local path. Requests with ambiguous framing, including duplicate `Content-Length`, conflicting `Content-Length`, any request containing both `Content-Length` and `Transfer-Encoding`, unsupported `Transfer-Encoding`, stacked transfer codings, non-final transfer codings, or any transfer coding other than a single final `chunked` coding when chunked is accepted, MUST fail locally as `local_invalid_request` before body buffering. Requests with `Content-Encoding` other than absent or `identity` MUST fail locally as `local_content_encoding_unsupported` and MUST NOT be forwarded upstream. Chunked local request transfer encoding MAY be accepted, but when accepted it MUST be decoded before body-size enforcement, duplicate-key detection, budget estimation, and upstream forwarding; the upstream-forwarded original body bytes are the decoded entity body bytes, not the local wire-framing bytes. Request bodies MUST be bounded before buffering or budget estimation to the smallest applicable limit among a local hard ceiling of 100 MiB, the trusted upstream/SPEC-006 request-body cap when known, and a default 1 MiB cap when no trusted upstream cap is available; larger bodies MUST fail locally as `local_request_too_large` and MUST NOT be forwarded upstream. `GET /v1/models` MUST return only gateway models that are currently visible through the upstream buyer model surface and allowed by the local model filter. If no explicit local model allowlist is supplied, the default allowlist MUST be empty: `/v1/models` MUST return an OpenAI-compatible empty model-list response and MAY include `X-MacProvider-Warning: empty_model_allowlist`, while `/v1/chat/completions` MUST reject chargeable requests as `local_model_not_allowed` until the operator supplies at least one allowed model. `POST /v1/chat/completions` MUST accept OpenAI-compatible JSON and streaming requests for allowed models, forward all standard SPEC-006/OpenAI chat-completions request fields verbatim unless this spec or a later SPEC-045 version explicitly restricts a field, and preserve streaming chunk order and termination semantics from the upstream gateway. Before admission or forwarding, the local server MUST parse the bounded JSON body with duplicate-object-key detection and MUST reject any duplicate JSON object key anywhere in the request body as `local_invalid_request`; the implementation MUST NOT rely on last-key-wins, first-key-wins, or parser-specific duplicate-key behavior for admission-relevant fields. The request body forwarded upstream MUST be the decoded entity body bytes as received after local transfer decoding; parsing for budget estimation MUST operate on a separate read of the same bounded buffer and MUST NOT cause JSON reserialization, field reordering, whitespace normalization, or semantic rewriting of the body sent upstream. Tool-calling fields such as `tools`, `tool_choice`, assistant `tool_calls`, and tool-result messages MUST NOT be dropped or rewritten by the local proxy; if the upstream gateway rejects them, the upstream error must be preserved under R007. Unsupported local paths or methods MUST fail with an OpenAI-shaped error envelope and MUST NOT be forwarded opportunistically, except unsupported `HEAD` requests MUST return `405` with no response body. `/v1/responses`, embeddings, image, audio, batch, fine-tune, or provider-control paths are out of scope until a later SPEC-045 version names their proxy and budget rules.

R002 JSON parsing MUST enforce bounded nesting depth and bounded parser work in addition to byte-size limits. Excessive nesting, parser recursion risk, or parser-work exhaustion MUST fail locally as `local_invalid_request` without upstream forwarding.

R002 upstream response handling MUST enforce resource bounds for every upstream-controlled response consumed by local endpoint mode, including `GET /v1/models`, `GET /v1/rate-card`, `GET /v1/rate-card.sig`, and proxied chat-completions responses. The implementation MUST bound upstream response-header byte length, header count, header-read deadline, decoded-body bytes, JSON nesting depth, JSON parser work, and signature/body work before trusting model, pricing, or error data. Streaming `text/event-stream` responses MUST enforce bounded event-line and event-frame sizes plus an idle-read deadline without buffering the whole stream. Non-streaming upstream responses MUST be buffered or spooled only up to the endpoint-specific decoded-body cap before any local body bytes are sent; exceeding any upstream response bound MUST fail as `local_upstream_unavailable` under R007 and MUST NOT leak partial unvalidated model or pricing data into admission.

R002 implementations MUST enforce bounded aggregate post-authentication resource limits before request-body buffering or upstream dispatch. The limits MUST cover at least authenticated active request count, total buffered request-body bytes, total non-streaming response spool bytes, open streaming responses, worker tasks, and process file descriptors or sockets consumed by local endpoint mode. A request that would exceed an aggregate limit MUST fail locally as `local_endpoint_busy` without upstream forwarding and without reading more request-body bytes than needed to make the admission decision. Aggregate limits MUST be independent from the per-request size cap: an individual body over the selected per-request cap fails as `local_request_too_large`, while a conforming individual request rejected only because current aggregate usage is saturated fails as `local_endpoint_busy`.

**SPEC-045-R003 - Upstream credential custody.** The command MUST obtain the upstream buyer credential from a bounded local source order: an explicit `--credential-file <path>` flag, `MACPROVIDER_HTTP2_API_KEY_FILE`, the default user-owned credential file `~/.config/macprovider/buyer-api-key`, `MACPROVIDER_HTTP2_API_KEY`, `MP_API_KEY`, then `BUYER_TOKEN`. The ordering is intentional: explicit credential-file sources, including `MACPROVIDER_HTTP2_API_KEY_FILE`, override the default durable user-owned MacProvider credential file; the default file takes precedence over raw-key environment variables. Credential-source class values MUST be the closed enum `explicit_file`, `default_config_file`, `environment`, or `missing`; `MACPROVIDER_HTTP2_API_KEY_FILE` uses class `explicit_file`, while `MACPROVIDER_HTTP2_API_KEY`, `MP_API_KEY`, and `BUYER_TOKEN` use class `environment`. Raw API keys MUST NOT be accepted as command-line flag values; a raw-key flag attempt MUST fail startup with a nonzero exit and redacted stderr error code `local_credential_flag_rejected`. The configured upstream gateway URL MUST default to the MacProvider production gateway origin, MUST use the `https` scheme, MUST pass normal platform TLS certificate and hostname verification, MUST reject expired certificates, untrusted roots, invalid chains, and hostname mismatches, MUST NOT contain a username or password component, path other than empty or `/`, query, or fragment, and MUST resolve only to globally routable addresses. Implementations MUST treat the configured upstream as an origin only (`scheme`, `host`, and optional `port`) for request construction and status output; any operator input with path, query, or fragment MUST fail startup as `local_upstream_url_rejected` rather than being preserved or joined with local paths. Startup and each new upstream connection MUST reject loopback, link-local, wildcard, multicast, private, carrier-grade NAT, documentation, reserved, IPv6 unique-local, IPv6 special-purpose, IPv4-mapped IPv6 addresses under `::ffff:0:0/96` whose embedded IPv4 address is non-global, and any other non-global address range; implementations MUST unwrap IPv4-mapped IPv6 addresses and apply all IPv4 block checks to the embedded IPv4 address before accepting the upstream address; rejected upstream URL input MUST fail startup with redacted stderr error code `local_upstream_url_rejected`, and a post-startup DNS validation failure MUST fail closed as `local_upstream_unavailable` without sending the buyer credential. The upstream transport MUST disable environment proxy, redirect, and connection-rewrite bypasses for gateway requests unless a later spec authorizes them, and MUST either connect to a previously validated global address or verify that the actual connected peer address remains in the validated global-address set before sending upstream `Authorization`. Credential files MUST be opened with user-only permissions or fail closed with a remediation message that names the credential-source class, observed permission class, and required permission class without printing the expanded path or token. File-based credential paths MUST be current-user-owned, MUST NOT resolve through parent directories writable by other users, MUST NOT be symlink-ambiguous when the R005 symlink-ambiguity rule is applied to the credential file path and credential parent directories, and MUST be revalidated before accepting a metadata-triggered reload. File credential initial load and reload MUST open the credential with no-follow semantics, then verify ownership, permissions, and file identity on the already-open file descriptor before accepting the bytes; a second path-only stat after opening is not sufficient. The local server MUST use the stored upstream credential for gateway authorization and MUST construct upstream request headers from implementation-owned metadata plus the decoded local request body bytes required by R002 rather than proxying arbitrary local client headers. Upstream redirects MUST NOT be followed automatically; syntactically valid upstream redirect responses MUST be returned to the initiating local client under R007 without sending the buyer credential to the redirect target, and `Location` MUST be stripped from those local responses because it is not in the R007 response-header allowlist. The implementation MUST generate upstream `Content-Type: application/json` for chat-completions requests, including streaming requests; it MUST NOT forward the local client's `Content-Type`. `Accept` MAY be forwarded only when its value is `application/json` or `text/event-stream`; any other local-client `Accept` value MUST be omitted or replaced by an implementation-owned value. All other upstream headers, including authorization, content length, user agent, gateway auth, tracing, and idempotency metadata, MUST be generated or omitted by the local implementation. The implementation MUST NOT forward local-client `Authorization`, `api-key`, `x-api-key`, cookie, `Proxy-Authorization`, `Proxy-Connection`, `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Port`, `X-Forwarded-Proto`, `X-Real-IP`, `Via`, `Connection`, `Transfer-Encoding`, `Keep-Alive`, `Upgrade`, `Trailer`, `Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-Dest`, `Sec-Fetch-User`, or `Sec-Purpose` headers upstream. At startup the server MUST generate a per-run local bearer token from at least 128 bits of CSPRNG input, MUST require that token on every local HTTP request through either `Authorization: Bearer <token>`, `api-key: <token>`, or `x-api-key: <token>`, and MUST reject absent or mismatched local credentials as `local_auth_required` before path normalization, body buffering, duplicate-key parsing, budget estimation, path-specific admission, or forwarding. The local bearer token MUST be written only to startup/setup output and the user-private active endpoint descriptor required by R006, MUST be redacted from logs, status, ledger rows, diagnostics, errors, and upstream requests, MUST be ignored for upstream identity, and MUST expire when the process exits. User-facing examples SHOULD use the generated local token as the OpenAI SDK `api_key` value rather than an empty string or the upstream buyer credential. Because local client authorization is not upstream identity, the server MUST keep browser-origin access default-deny: it MUST NOT emit permissive CORS headers, MUST reject CORS preflight requests, MUST unconditionally reject requests with `Origin: null`, MUST reject requests with any other `Origin` header value unless that value exactly equals the bound endpoint origin including scheme, the actual bound host literal, and port, for example `http://127.0.0.1:<bound-port>`, `http://127.0.0.2:<bound-port>` when explicitly bound to `127.0.0.2`, or `http://[::1]:<bound-port>`, MUST evaluate exact-origin comparison per listener when both IPv4 and IPv6 loopback listeners are enabled, MUST inspect browser fetch metadata before stripping it from any upstream-bound request, MUST reject browser fetch metadata that identifies a cross-site or cross-origin caller, and MUST NOT add a browser-access allowlist unless a later spec defines cross-origin delegation. When an upstream authentication failure indicates the stored buyer credential is invalid or expired, the server MUST keep running, mark local credential state as `invalid_or_expired` in status, return the upstream auth failure under R007, and re-read a file-based credential before the next request when file metadata shows an inode number, file size, ctime, mtime, or symlink target change. If a previously loaded file credential is deleted, becomes unreadable, or fails ownership, permission, file-identity, or symlink revalidation, the implementation MUST immediately zeroize and discard the cached upstream credential, status MUST report credential state `missing` before the next request, and chargeable requests MUST fail before upstream connection or forwarding as `local_credential_missing` until a conforming credential is loaded again.

R003 implementations MUST verify the per-run local bearer token through one timing-safe verifier shared by all accepted local authentication headers. The verifier MUST derive fixed-length comparison material from the presented token and the generated token using HMAC-SHA256 keyed by a per-run server-generated secret distinct from the bearer token, or a stronger keyed construction that does not expose raw-token length/content timing, and MUST compare only that fixed-length material with a constant-time primitive. It MUST reject malformed bearer syntax, multiple conflicting accepted auth headers, and token-length mismatches through the same redacted `local_auth_required` error path without leaking which condition failed.

When a metadata-triggered file credential reload accepts replacement credential bytes, new requests MUST use only the replacement credential after the atomic swap, and the implementation MUST zeroize superseded credential bytes and temporary read buffers. Superseded credential material captured by an already in-flight upstream request MAY remain only until that request completes or is canceled, then MUST be zeroized.

R003 browser-origin parsing MUST treat `Origin` as a single-valued header. A request carrying more than one `Origin` header field, or any `Origin` header value containing a comma, MUST fail locally as `local_invalid_request` before body buffering. Exact-origin comparison and unconditional `Origin: null` rejection MUST operate on one whole, unparsed header value with no comma.

**SPEC-045-R004 - Conservative model and exposure admission.** The command MUST support an explicit local model allowlist and a cumulative local estimated-exposure limit expressed in USD-equivalent units through `--budget-usd <amount>`. `--budget-usd` is a local admission cap and is not a buyer billing balance, settlement ledger, payment authorization, refund rule, or source of truth for gateway charges. `--budget-usd 0`, negative values, non-finite values, and unparsable values MUST fail startup with a nonzero exit and redacted stderr error code `local_budget_flag_rejected`; they MUST NOT be silently treated as an exhausted budget or as `--no-budget`. Before forwarding a chargeable request, the command MUST require either a positive `--budget-usd <amount>` or an explicit `--no-budget` risk acknowledgement for the process, MUST check that the requested model is allowed, that the model appears in trusted upstream/catalog metadata, and that the request can be admitted without exceeding the remaining local exposure cap under a conservative exposure estimate. Admission-relevant fields, including `model`, `messages`, `max_tokens`, output-bound fields, `stream`, tool-calling fields, and structured-output fields, MUST be read only from the duplicate-key-free parse required by R002; an explicit JSON `null` output bound MUST be treated as absent and estimated from the model's trusted maximum output limit. Trusted pricing metadata for v0.1 means either a SPEC-006 public `GET /v1/rate-card` body paired with `GET /v1/rate-card.sig` that verifies as Ed25519 against the SPEC-023 repo-trusted static catalog keyring and satisfies SPEC-023 detached-sidecar, policy-version, and `generated_at` freshness rules, or a gateway quote/estimate result only if that quote/estimate surface is defined by SPEC-006 or a later dependency. Missing or malformed sidecars, unknown or retired key ids, non-Ed25519 algorithms, invalid signatures, policy mismatch, projection-hash mismatch, future-dated bytes beyond the SPEC-023 tolerance, rate-card bytes older than the SPEC-023 maximum age, or a fetched rate card older than the baked trusted snapshot MUST fail closed as `local_pricing_unavailable` unless `--allow-unpriced` applies. A trusted rate card MUST use the catalog release shape validated by `scripts/catalog-release.py`: top-level `version`, `policy_version`, `generated_at`, `usd_per_million_credits`, and non-empty `rows` containing a `default` row, with each row carrying `prompt_rate_per_mtok`, `prompt_cache_hit_rate_per_mtok`, `completion_rate_per_mtok`, `provider_share_bps`, and `global_multiplier_ppm`; its `version` MUST equal the rate-card projection hash, and model-key lookup MUST follow SPEC-005 §5.5 exact, normalized, then default resolution. A gateway `/v1/models` result is trusted only for model visibility and model id presence, not for price or output-limit authority. If the trusted rate card or trusted quote surface cannot supply price fields for the requested model or default row, or if a request lacks an explicit output bound and no trusted maximum output bound is available, budgeted admission MUST fail as `local_pricing_unavailable` unless `--allow-unpriced` applies. Unsigned local files, client request fields, or ad hoc environment values are not trusted metadata. Trusted metadata MUST be fetched at startup or before first admission and MAY be refreshed only at bounded implementation-defined intervals; it MUST NOT run as an unbounded background refresh loop. Before every chargeable admission, cached trusted pricing metadata MUST be revalidated against the local clock and SPEC-023 freshness rules. If the cached metadata has crossed the SPEC-023 stale-warning boundary, status MUST surface `stale_pricing` in the pricing warning-code list required by R006 while admission MAY continue until the reject boundary. If it has crossed the SPEC-023 maximum-age or future-skew reject boundary, the pricing trust state MUST be atomically marked `unavailable`, new chargeable admission MUST fail as `local_pricing_unavailable` unless `--allow-unpriced` can produce a conforming conservative reservation under R004, and the implementation MUST NOT continue admitting from expired cached pricing. The admission check and reservation write MUST be atomic within the process so no two concurrent requests can both pass admission before either one reduces the remaining budget. The estimate MUST use trusted catalog/rate metadata and request bounds such as `max_tokens` when available; it MUST NOT trust client-supplied prices, client-supplied token counts, provider hints, or response metadata as the source of cost authority. The conservative admission estimate MUST be the gross buyer-side USD-equivalent exposure, never provider payout or provider-share exposure. Arithmetic MUST use fixed-point integer or exact rational math with overflow detection; overflow, precision loss, missing operands, non-finite values, or any under-reserving ambiguity MUST fail closed as `local_pricing_unavailable`. For v0.1, prompt cost MUST be estimated as `estimated_prompt_tokens * prompt_rate_per_mtok / 1_000_000` using the full `prompt_rate_per_mtok`; cached-token discounts from `prompt_cache_hit_rate_per_mtok` MUST NOT be applied unless a trusted gateway quote/estimate surface defined by SPEC-006 or a later dependency distinguishes trusted cache-hit token counts. Completion cost MUST be `bounded_completion_tokens * completion_rate_per_mtok / 1_000_000`. The sum MUST then apply `global_multiplier_ppm` multiplicatively as in SPEC-005 gross-credit math, converted through trusted `usd_per_million_credits` when credits-to-USD conversion is needed, and rounded upward to the smallest representable local ledger unit before reservation. `provider_share_bps` MUST NOT reduce the buyer exposure estimate. Prompt exposure MUST be estimated from the submitted request body using a trusted gateway estimate, a tokenizer bound to the requested model's trusted catalog identity, or a byte-to-token upper bound no less conservative than one UTF-8 byte equals one token. Completion exposure MUST use the request's explicit output bound when present; when no bound is present, it MUST use the model's trusted maximum output limit, and if that limit is unavailable budgeted mode MUST reject the request as `local_pricing_unavailable`. When trusted pricing is unavailable and a positive run budget is configured, the request MUST fail closed unless the operator supplied an explicit unpriced-request override for that run using `--allow-unpriced`. Under `--allow-unpriced` with a positive run budget, each unpriced chargeable request MUST reserve the entire remaining local budget before forwarding, ledger `admission estimate` MUST equal the pre-request remaining budget, status remaining budget MUST become zero until settlement/recovery changes it, concurrent unpriced chargeable admissions MUST fail as `local_budget_exceeded` while that reservation is active, and if trusted upstream usage/cost evidence remains unavailable at terminal settlement the reservation MUST settle to that full admission estimate. Any `--no-budget` or unpriced-request override MUST be shown at startup, included in local status, recorded in the ledger when a ledger is active, and surfaced as a warning before or with each affected chargeable request using response header `X-MacProvider-Warning` with value `no_budget` or `unpriced_override`; this warning header MUST NOT alter the OpenAI JSON or SSE body. If an upstream response already contains `X-MacProvider-Warning`, the local warning value MUST be appended as a distinct comma-separated token without deleting upstream warning values.

R004 implementations MUST also support an optional per-request estimated-exposure cap through `--max-request-usd <amount>`. The flag uses the same USD-equivalent parsing rules as `--budget-usd`: zero, negative, non-finite, or unparsable values MUST fail startup with `local_budget_flag_rejected`. For every chargeable request, the same conservative admission estimate used for cumulative budget reservation MUST be computed before forwarding and MUST be less than or equal to the configured per-request cap. A request whose estimate exceeds the per-request cap MUST fail locally as `local_request_cap_exceeded`, MUST NOT create a budget reservation, MUST NOT append a ledger request row, and MUST NOT be forwarded upstream. `--max-request-usd` MAY be used with `--budget-usd` or `--no-budget`; when used with `--no-budget`, it remains a per-request safety rail even though cumulative budget configured/used/held/remaining are null. Under `--allow-unpriced`, the per-request cap MUST still apply to the unpriced reservation amount; if the entire remaining local budget would be reserved and that amount exceeds `--max-request-usd`, the request MUST fail as `local_request_cap_exceeded`.

When `--no-budget` and `--max-request-usd` are both active, `--allow-unpriced` MUST NOT bypass the per-request cap. If trusted pricing is unavailable for a no-budget chargeable request with a per-request cap, the request MUST fail as `local_pricing_unavailable` before forwarding because there is no cumulative remaining-budget value from which to derive a conservative unpriced reservation. `--allow-unpriced` MUST NOT bypass the process-level admission stop after trusted actual cost exceeds a reservation and the status pricing trust state becomes `estimate_exceeded`.

R004 canonical local budget precision is micro-USD. All run budget, reservation, settlement, held, released, remaining, and per-request cap arithmetic MUST use signed integer counts of micro-USD (`1e-6` USD) as the canonical local ledger unit. Ledger rows MUST record amount fields as string-encoded integer micro-USD values, including `admission_estimate_micro_usd`, `settled_exposure_micro_usd`, and any budget delta fields, and MUST NOT use JSON floating-point numbers for monetary ledger state.

**SPEC-045-R005 - Restart-safe budget ledger.** When a cumulative run budget is configured, the command MUST persist a local exposure ledger under the default user-private state path `$HOME/Library/Application Support/macprovider/consume/ledgers/default.jsonl` on macOS unless the operator supplies an explicit ledger path, and it MUST hold an OS-enforced exclusive advisory file lock on a lock file named `<ledger-filename>.lock` adjacent to the ledger. The lock MUST use OS lock state, not lockfile presence; a stale lock file from a crashed process MUST NOT prevent a new process from acquiring the lock after the OS releases the prior lock on process termination. Ledger path class values MUST be the closed enum `default_user_state`, `explicit_absolute`, or `explicit_relative`; explicit relative ledger paths MUST resolve relative to the current working directory captured at process startup. The implementation MUST refuse any mode that creates a ledger, including budgeted mode and `--no-budget --ledger <path>`, when the state path is not user-private, is symlink-ambiguous, is not on a local filesystem with verified exclusive-lock semantics, or cannot be locked by exactly one active process. Implementations MUST verify local filesystem lock support using OS metadata such as `statfs`/`fstatfs` or a stronger platform-specific check, and MUST fail closed when the filesystem type or mount properties cannot be verified as local with real exclusive-lock semantics. A state path is symlink-ambiguous when the ledger path, lock path, or any parent directory resolves through a symlink that is not owned by the current OS user, or when the resolved target changes between validation and open/lock. Passing `--ledger <path>` without either `--budget-usd <amount>` or `--no-budget` MUST fail startup with `local_budget_flag_rejected` rather than creating an idle ledger whose admission mode is ambiguous. When `--no-budget` is combined with an explicit `--ledger <path>`, the ledger MUST be created, locked, and written with per-request no-budget records; the ledger path class is `explicit_absolute` or `explicit_relative` as appropriate. When `--no-budget` is used without an explicit `--ledger`, no ledger is created and per-request no-budget state is in-memory only. The ledger MUST record schema version `local_consumer_endpoint.ledger.v1`, immutable process launch id (`run_id`), a unique local `reservation_id` generated from at least 128 bits of CSPRNG input for every reservation, the same `run_id` and `reservation_id` copied onto every later state transition and audit row for that reservation, redacted request ids, model id, admission estimate or JSON null when `--no-budget` skips admission estimation, unpriced-override flag, no-budget flag when applicable, terminal local outcome, settled exposure amount when known, upstream request id when available, reservation state (`reserved`, `settled`, `held`, `released`, or `estimate_exceeded`), and created/updated timestamps; it MUST NOT record raw prompts, raw completions, bearer tokens, local bearer tokens, raw receipts, full upstream error bodies, hostnames, OS usernames, hardware serials, MAC addresses, or stable hardware UUIDs. A budgeted admission reservation MUST NOT be considered committed and MUST NOT be forwarded upstream until the ledger reservation append is durable; durable means the append bytes and required file metadata have been flushed with `fsync()` or a platform-equivalent durability primitive on the ledger file descriptor, and any newly created parent directory entry has been flushed with a platform-equivalent directory sync where supported. Every ledger state-transition append, including settlement, `estimate_exceeded`, held, released, and recovery audit entries, MUST satisfy the same durability rule before any local HTTP response, status output, recovery-command output, remaining-budget value, or restart-recovery decision relies on that transition. If a durable append fails, including fsync failure, the implementation MUST roll back any affected in-process reservation state when possible, mark ledger health unhealthy, return `local_budget_ledger_unavailable` for runtime chargeable paths, fail recovery commands nonzero without claiming success, and stop accepting chargeable requests until ledger health is restored. After a terminal upstream response, the ledger MUST settle a reservation to trusted upstream usage/cost evidence when such evidence is available, even when that evidence exceeds the admission estimate; if trusted usage/cost evidence is unavailable, it MUST settle to the admission estimate rather than inventing a lower cost. If trusted upstream usage/cost evidence exceeds the admission estimate, the ledger MUST record state `estimate_exceeded`, remaining budget MUST be allowed to reach zero or a negative value, status MUST surface the pricing-invariant breach, and the process MUST stop accepting new chargeable admission requests until restarted with corrected trusted pricing metadata or an explicit operator recovery path defined by a later spec; in-flight requests that already passed admission before `estimate_exceeded` was set MUST be allowed to complete. SPEC-005 billing and settlement remain authoritative. If the local client disconnects during streaming before trusted terminal usage/cost evidence is available, the implementation MUST cancel or close the upstream request when possible, wait no longer than one second for synchronous cancellation acknowledgement, and settle the reservation to the admission estimate unless the upstream returns trusted partial usage/cost evidence bound to the request. In-flight reservations MUST be treated conservatively on process restart: they become `held` and reduce remaining budget until a recovery command updates them. On graceful shutdown, including SIGTERM, the process MUST stop accepting new requests, drain in-flight requests for a bounded period no longer than five seconds, settle terminal requests, cancel or close remaining upstream requests, mark remaining in-flight reservations `held`, remove the active endpoint descriptor when possible, and then exit. Operators should expect long-running streaming requests that exceed the five-second drain bound to become held reservations requiring recovery-command handling; that operational cost is intentional in v0.1 because bounded shutdown takes precedence over waiting indefinitely. R005 conformance REQUIRES local recovery commands named `malibu-cli consume budget status` and `malibu-cli consume budget release-held`; `status` MUST show redacted held reservations, age, estimate, and ledger path class, while `release-held` MUST require a ledger selector `--ledger <path>` or `--ledger default`, a run selector `--run-id <process-launch-id>`, and `--confirm-release-held`, MUST fail rather than modify the ledger while another process holds the ledger lock, MUST only release held local reservations whose immutable `run_id` exactly matches that selected run, MUST append a redacted audit entry carrying the same `run_id` and each released `reservation_id`, MUST leave wrong-run and missing-reservation rows unchanged, and MUST NOT alter settled local exposure or upstream gateway records. `--ledger default` on recovery commands MUST resolve to the macOS default path computed at recovery-command invocation time from the invoking user's `$HOME`. Manual ledger deletion is not a conformant recovery path. If the ledger cannot be opened, locked, parsed, or written, budgeted mode MUST refuse to start or MUST stop accepting chargeable requests.

R005 ledger rows MUST be self-describing: every ledger row, including reservation, transition, settlement, held, released, `estimate_exceeded`, and audit rows, MUST include `schema_version: "local_consumer_endpoint.ledger.v1"`. There is no separate header row. Recovery commands MUST validate `schema_version` before acting on a row and MUST skip rows with unknown or missing schema versions while reporting a redacted warning code.

R005 reservation state transitions are closed for v0.1: `reserved` MAY transition only to `settled`, `held`, or `estimate_exceeded`; `held` MAY transition only to `released` through `release-held`, or to `settled` only if trusted upstream terminal evidence bound to that reservation arrives before shutdown completion; `settled`, `released`, and `estimate_exceeded` are terminal for that reservation and MUST NOT transition to any other state. A recovery command MUST fail nonzero rather than appending a transition that violates this table. The ledger reservation state `estimate_exceeded` is per-reservation, while the R006 pricing trust state `estimate_exceeded` is process-level. When a reservation in the current process durably transitions to ledger state `estimate_exceeded`, the process MUST set status pricing trust state to `estimate_exceeded` and stop new chargeable admissions under R005/R006.

R005 `release-held` MUST exit nonzero and emit redacted machine-readable code `local_no_held_reservations` when the selected ledger and `--run-id` produce zero eligible held reservations. A zero exit from `release-held` MUST mean at least one held reservation row was durably released and audited.

For non-streaming chat-completions settlement, trusted terminal usage/cost evidence means a complete upstream JSON response body that satisfies all R002/R007 response bounds, is not truncated or protocol-invalid, and contains a SPEC-006/OpenAI-compatible `usage` object or SPEC-006-defined cost metadata bound to that response. A partial, truncated, unparsable, protocol-invalid, or locally cap-rejected non-streaming response MUST NOT supply trusted settlement evidence.

For SSE streaming settlement, trusted terminal usage/cost evidence means either usage data in the final event frame or usage data from an earlier event frame that is confirmed by a subsequent `data: [DONE]` on the same upstream response. Usage data before `data: [DONE]` MAY be cached but MUST NOT finalize settlement by itself. If `data: [DONE]` arrives without trusted usage evidence, or the stream terminates before `data: [DONE]`, settlement MUST follow the conservative R005 admission-estimate rule.

**SPEC-045-R006 - Local status and diagnostics.** The local server MUST expose local status at `GET /v1/status` on the same loopback listener and MUST support `malibu-cli consume status` for CLI status output. On startup, the process MUST generate a process launch id as a lowercase RFC4122 UUID v4 from at least 128 bits of CSPRNG input, yielding 122 bits of effective UUID v4 randomness, MUST keep it stable only for that process lifetime, and MUST write a user-private instance descriptor to `$HOME/Library/Application Support/macprovider/consume/active-endpoint.json` on macOS containing only the bound loopback URL, process id, process launch id, started-at timestamp, ledger path class, and the per-run local bearer token or a same-security token reference so `consume status` can locate and authenticate to the active endpoint. Concurrent local endpoint instances are unsupported in v0.1: before acquiring or creating the descriptor or lock, the implementation MUST verify that `$HOME/Library/Application Support/macprovider/consume` and each relevant parent directory selected for active endpoint state are current-user-owned, not writable by other users, not symlink-ambiguous under the R005 symlink rule, and stable between validation, open, write, rename, and lock acquisition. Startup MUST acquire an OS-enforced exclusive advisory lock on `$HOME/Library/Application Support/macprovider/consume/active-endpoint.lock` before reading, validating, or writing the descriptor, MUST hold that lock until process exit, and MUST fail with redacted stderr error code `local_active_endpoint_exists` when another live process holds the lock or when an existing active descriptor points to a live process with a matching launch id. The descriptor lock MUST use OS lock state, not lockfile presence, so a stale lock file from a crashed process does not block startup after the OS releases the lock. The instance descriptor MUST be written atomically by creating a temporary file in the same directory with user-only read/write permissions before any bytes are written, then renaming it to `active-endpoint.json`; stale descriptors MUST be ignored when the process id or launch id no longer matches, because process launch id protects against process-id reuse. `malibu-cli consume status` MUST return a nonzero exit and redacted message code `local_endpoint_not_running` when no descriptor exists or all discovered descriptors are stale. Status MUST report schema version `local_consumer_endpoint.status.v1`, process launch id, bound loopback URL, upstream gateway origin, credential-source class, credential state (`missing`, `loaded`, or `invalid_or_expired`), model allowlist, pricing trust state (`trusted`, `unpriced_override`, `unavailable`, or `estimate_exceeded`), pricing warning codes as a closed bounded list including `stale_pricing` when the R004 stale-warning boundary is crossed, local-auth state (`required` or `rejected` only, never token material), unpriced-override state, no-budget acknowledgement state, budget configured/used/held/remaining, ledger path class, active request count, last successful upstream contact wall-clock time, and a redacted bounded error ring containing at least the last five and at most the last 100 local/upstream error code classes. **SPEC-045-R007 - Gateway error preservation and local error codes.** Upstream SPEC-006 errors and any syntactically valid upstream HTTP response, regardless of status code, MUST be proxied to the same local client under the preservation rule rather than being converted into local success or `local_upstream_unavailable`; `local_upstream_unavailable` applies only to transport failures and protocol-invalid responses. Startup failures MUST return process exit codes and stderr error codes, not HTTP envelopes. Once a streaming `text/event-stream` response has sent local response headers or body bytes, the implementation MUST NOT attempt to change the HTTP status to 502; on upstream reset, EOF, or protocol-invalid truncation after that point it MUST emit a terminal SSE error event carrying redacted `local_upstream_unavailable` code material when the local connection is still writable, then close the stream and settle the ledger conservatively under R005. `local_bind_rejected`, `local_credential_flag_rejected`, `local_budget_flag_rejected`, `local_upstream_url_rejected`, and `local_active_endpoint_exists` are reserved only for startup failure and MUST NOT be returned by a running HTTP server. Local errors MUST identify whether the request was forwarded upstream through `error.macprovider.forwarded_upstream`; local-only errors set it to `false`, and locally generated upstream-transport errors set it to `true` only after request bytes were sent upstream. The same `local_upstream_unavailable` code may appear with either `forwarded_upstream` value depending on whether the transport failure occurred before or after request bytes were sent upstream. The implementation MUST NOT retry non-idempotent chat completions after bytes have been sent upstream unless the gateway supplies an idempotency contract and the request is bound to it; before bytes are sent, it MAY perform at most one bounded connection attempt per upstream request before returning `local_upstream_unavailable`.

For a streaming upstream `text/event-stream` response, `Content-Encoding` other than absent or `identity` MUST fail as `local_upstream_unavailable` before local response headers or body bytes are sent; v0.1 implementations MUST NOT stream-decompress SSE responses. For a non-streaming upstream response, if local response headers have already been sent and upstream truncation occurs before the complete upstream body is received, the implementation MUST immediately close or reset the local connection and MUST NOT deliver the partial body as a complete HTTP success. When a non-streaming upstream response includes `Content-Encoding` other than absent or `identity`, the implementation MUST decompress the upstream body to enforce the R002 decoded-body cap. If the decoded size exceeds the cap, the response MUST fail as `local_upstream_unavailable`; if it is within the cap, the implementation MUST strip `Content-Encoding` or set it to `identity` and forward decoded body bytes. The verbatim upstream `Content-Encoding` forwarding rule applies only when forwarded body bytes remain encoded.

`local_request_cap_exceeded` MUST map to HTTP 402 and MUST be local-only with `error.macprovider.forwarded_upstream=false`. Upstream 3xx responses are intentionally returned without `Location` when preserved under R003/R007; this fail-closed protocol deviation prevents redirect-target credential exfiltration and implementations MUST NOT synthesize an alternate redirect target.

The handler buffers the bounded request body before upstream dispatch to support duplicate-key rejection and local estimation while still forwarding the original decoded entity bytes. It should share existing gateway client/auth helpers where possible instead of creating a second buyer protocol definition.
3. Implement a local exposure admission component with a durable, user-private, lockable ledger. 5. Add fake-gateway integration tests for non-streaming, streaming, upstream error, model list, and budget paths. Fake-gateway tests MUST use an injected transport or a test-only non-production override that is unavailable in release builds and cannot satisfy production-promotion journey evidence.

## 7. Evidence

Current implementation evidence is intentionally non-conformant:

- `phase5-gateway/README.md` documents direct OpenAI SDK usage against the public gateway base URL and buyer API key. SPEC-045 moves that client configuration to a loopback base URL while preserving gateway authority.
- `specs/SPEC-006-buyer-api.md` owns the public buyer `/v1` API and error contract. SPEC-045 consumes that contract but does not redefine public gateway behavior.
- `specs/SPEC-001-phase3-binary.md` owns the provider binary and local provider inference server. SPEC-045 is a buyer-side local proxy and not a provider inference server.

No requirement is conformant until the local command, proxy, budget ledger, tests, and signed journey evidence land.

## 8. Current contract notes

The local endpoint should feel like a development adapter, not a new account system. The local OpenAI SDK `api_key` value is the generated per-run local token because upstream identity comes from the CLI-managed buyer credential.

Budget enforcement is a local estimated-exposure safety rail, not a billing ledger. SPEC-006 remains authoritative for gateway quota and authentication, and SPEC-005 remains authoritative for billing and settlement; local budget state exists to limit accidental local exposure from tools and must fail closed when its conservative estimate is proven too low.

The first implementation should prefer failing closed over broad compatibility. Adding more `/v1` paths is allowed only when each path has explicit admission, redaction, and error behavior in a future SPEC-045 version.
