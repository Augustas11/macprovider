## 1. Purpose and scope

SPEC-047 defines how a provider-local candidate discovered under SPEC-046 may be offered to the Malibu network and, after explicit checks, become eligible for network visibility, synthetic probes, buyer routing, catalog pricing, and settlement-capable paid traffic. Any synthetic probe is routed through the authenticated provider wire protocol or an admitted provider session; the coordinator MUST NOT dereference provider-submitted endpoint URLs, origins, sockets, or local paths.

The user outcome is a self-service path for providers to discover, evaluate, offer, probe, and explicitly disclose more models without making Malibu the manual gatekeeper for every possible model. In v0.1, genuinely novel non-catalog candidates can become visible or probeable only under explicit non-earning disclosure; an earning path for non-catalog models requires a later billing-owner pricing conversion spec. The settlement outcome is equally important: positive provider credit still requires a route-time admitted snapshot and settlement-capable receipt profile governed by the money-path specs.

SPEC-047 is CLI-first and coordinator-backed. The native Malibu app may later present admission state, but it must not mint or infer admission locally.

Accepted journey id: `JOURNEY-NETWORK-MODEL-ADMISSION`.

### Explicit non-goals

SPEC-047 does not replace SPEC-005 billing formulas, SPEC-006 buyer API compatibility, SPEC-010 signed catalog identity, SPEC-015 receipt wire ownership, or SPEC-022 verified settlement.

SPEC-047 does not allow a discovered model, opaque endpoint, provider-proposed price, local evaluation result, or runtime-reported identity to create positive provider credit by itself.

SPEC-047 does not define open public submission from arbitrary internet endpoints. v0.1 admission starts from an authenticated provider and a SPEC-046 candidate.

SPEC-047 does not make unsupported model quality, malicious output, privacy, or model honesty guarantees beyond the explicit admission and disclosure state.

SPEC-005 owns billing formulas, rate math, provider rewards, settlement, and payout-ready ledger behavior.

SPEC-006 owns public buyer API model visibility, error semantics, and buyer-facing disclosure.

SPEC-010 owns canonical signed catalog identity. SPEC-047 may create network offer state for non-catalog candidates, but only SPEC-010-compatible or catalog-derived identities can satisfy catalog-verified settlement.

SPEC-011 owns loaded-model state and warm-swap model-hash emission required before settlement-capable routing.

SPEC-015 and SPEC-022 own receipt and verified-settlement conditions. SPEC-047 adds admission state; it does not by itself make a receipt settlement-capable.

SPEC-018 and SPEC-019 own feature semantics for tool-calling and structured output. Admission may record support levels but cannot redefine those protocols.

SPEC-023 owns signed static feed and rate-card trust, including the SPEC-023 §3.7 catalog artifact feed and the SPEC-023 §3.2 `candidate` / `listed` / `recommendable` / `blocked` ladder. SPEC-001 §6.14a owns the model command taxonomy and legacy command

## 3. Normative requirements

**SPEC-047-R001 - Admission state machine.** Coordinator-backed admission MUST use a closed per-provider/per-candidate state machine with these v0.1 states: `not_offered`, `offer_submitted`, `offer_rejected`, `sandbox_probe_only`, `network_visible_unpriced`, `network_admitted_unsettled`, `catalog_priced`, `settlement_capable`, `withdrawn`, and `revoked`. SPEC-047 does not own SPEC-046 local states `local_only` or `offerable`; those states are CLI-only provider inventory states until a provider-signed offer enters the coordinator machine. State transitions MUST be append-only auditable events with actor, reason code, previous state, next state, provider id, candidate id, served model reference, evidence digests, timestamp, and request id. `settlement_capable` MUST NOT be reachable unless SPEC-022 verified-settlement preconditions are satisfiable for that provider/model pair at route time. No state transition outside this table is valid:

| Current state | Provider-facing meaning | Provider next action | Authorized actor | Allowed next states |
|---|---|---|---|---|
| `not_offered` | Coordinator reports no active network offer for this model. | Run offer dry-run or submit a refreshed offer if local checks still pass. | coordinator readback or provider withdrawal reconciliation | `offer_submitted` |
| `offer_submitted` | The provider submitted a signed offer and the coordinator has not admitted it for any network use. | Wait for status readback or withdraw if the offer was mistaken. | provider submit path, coordinator validator, coordinator admission policy (operator decision, v0.1.5) | `offer_rejected`, `sandbox_probe_only`, `network_visible_unpriced`, `network_admitted_unsettled`, `catalog_priced`, `withdrawn`, `revoked` |
| `offer_rejected` | The submitted package failed policy, identity, safety, pricing, or evidence checks; it is not earning-eligible. | Fix the reason code, re-evaluate if needed, and submit a new signed offer. | coordinator validator | `offer_submitted`, `revoked` |
| `sandbox_probe_only` | The candidate may receive only bounded authenticated probes; it is not buyer-routable or earning-eligible. | Wait for probe outcome, improve local health/evidence, or withdraw. | coordinator admission policy | `network_visible_unpriced`, `network_admitted_unsettled`, `catalog_priced`, `withdrawn`, `revoked` |
| `network_visible_unpriced` | The candidate may appear only through explicit experimental disclosure with null economics; it is not earning-eligible. | Wait for pricing/admission policy, provide refreshed evidence if requested, or withdraw. | coordinator admission policy | `network_admitted_unsettled`, `catalog_priced`, `withdrawn`, `revoked` |
| `network_admitted_unsettled` | The candidate satisfies limited network admission checks but lacks trusted catalog economics or settlement prerequisites. | Keep the runtime healthy, satisfy requested catalog/receipt evidence, or withdraw. | coordinator admission policy | `catalog_priced`, `settlement_capable`, `withdrawn`, `revoked` |
| `catalog_priced` | The candidate has trusted signed catalog economics for display, but it is not settlement-capable. | Keep the admitted model loaded and wait for receipt/route-time settlement prerequisites, or withdraw. | coordinator admission policy with SPEC-023/SPEC-044 trust inputs | `network_admitted_unsettled`, `settlement_capable`, `withdrawn`, `revoked` |
| `settlement_capable` | The candidate may participate in positive provider settlement only for request attempts satisfying SPEC-022 route-time snapshot and receipt verification. | Keep the loaded model, receipts, and health predicates current, or withdraw. | coordinator admission policy with SPEC-022 preconditions | `network_admitted_unsettled`, `catalog_priced`, `withdrawn`, `revoked` |
| `withdrawn` | The provider withdrew the candidate; local artifacts remain untouched and the candidate is not earning-eligible. | Submit a new signed offer if the provider wants to re-enter admission. | provider CLI withdrawal path | `offer_submitted` |
| `revoked` | The coordinator removed admission because policy, identity, artifact, health, sanctions, or settlement prerequisites failed. | Resolve the reason code and submit a new signed offer with refreshed evidence if policy allows. | coordinator policy, trust, or sanctions path | `offer_submitted` |

Re-entry from `offer_rejected`, `withdrawn`, or `revoked` to `offer_submitted` MUST require a new provider-signed offer with a fresh nonce or idempotency key and refreshed evidence digests. **[v0.1.9]** `offer_rejected` is RESERVED and unreachable in v0.2: no coordinator origin appends it (see §8 v0.1.5, "`offer_rejected` stated unreachable"), so this table lists its legal re-entry edge for enum completeness but the state is never entered and that edge is not exercised. The reachable fresh-evidence re-entry paths a v0.2 journey can prove are `withdrawn` and `revoked`. Demotion from `settlement_capable` or `catalog_priced` takes effect for routing and settlement before any later request attempt can be admitted under the older state.

For rows whose allowed next state is `offer_submitted`, the outbound transition is provider-driven through the signed offer path even when the current state was established by the coordinator, sanctions policy, or a prior provider withdrawal.

Any allowed next state that depends on trusted catalog economics, catalog identity, receipt capability, or route-time settlement evidence remains conditional on the owner spec for that prerequisite; the table lists legal edges, not a guarantee that every candidate can traverse every edge.

**[amended v0.1.5]** The authorized actor `coordinator admission policy` acts, for OPERATOR-origin decisions to `network_visible_unpriced`, `network_admitted_unsettled`, `catalog_priced`, `settlement_capable`, and `revoked`, through exactly one production caller: an **operator decision request** `POST /admin/model-admission/decisions`. **Credential and attribution.** The request is authenticated with the per-actor coordinator operator credential class (`auth.operator_keys`, the class the `/admin` trust-granting surfaces use, which yields an operator actor id) — never the shared single-value `operator_key` — and the appended event's `actor` is `operator:<actor id>` (grammar `^operator:[a-z0-9][a-z0-9_.-]{0,63}$`). the request's canonical body digest; the evaluated head; `requested_by`; `created_at`; a 24-hour expiry) and answers `model_admission_decision.v1` with the pending values: `previous_admission_state` and `admission_state` both the unchanged current state, `reason_code` the request's reason, `coordinator_event_id` the evaluated head, `accepted_at` the pending record's creation time, `decided_by` the requesting actor, `replayed` false, `pending_decision_id` set, `bound_member` null; a replay of that request answers the same pending record (`replayed: true`); a pending record is consumed by exactly one approval, expires unused, and is invalidated by any event appended for the candidate. `POST /admin/model-admission/decisions/<pending_decision_id>/approve` with request schema `model_admission_decision_approve_request.v1` (exactly `schema`, `provider_id`, `candidate_id`, `pending_decision_id`, `expected_coordinator_event_id`, `idempotency_key`; same grammars) by a DISTINCT operator actor (the same actor is `dual_control_required`; when fewer than two distinct operator actors are configured, the initial `settlement_capable` request itself is refused synchronously with `dual_control_unavailable` and no pending record is created) commits the append under this approval precedence, executed as one unit inside the provider's section: (a) the path and body `pending_decision_id` MUST be equal and the body's `provider_id`, `candidate_id`, and `expected_coordinator_event_id` MUST equal the pending record's stored values, else `invalid_request`; approvals replay in their own namespace (`pending_decision_id`, `idempotency_key`): an identical-key retry of a committed approval answers the original committed response with `replayed: true`, whatever happened since; a distinct-key approval of a consumed record is `pending_consumed`; two concurrent distinct-key approvals resolve, under the section, as one append and one `pending_consumed`. The other four edges commit on the request. **Bounds.** The request is bounded by payload size and parser work like every SPEC-047-R007 mutation and rate-limited per operator credential and source address; it MUST NOT draw on any per-provider rate window, so a provider cannot exhaust an operator's ability to append a decision for its own candidates. **Request schema** `model_admission_decision_request.v1`, fields exactly `schema`, `provider_id` (`^[a-zA-Z0-9_.-]{1,64}$`), `candidate_id` (`^byom_[a-z2-7]{52}$`), `next_state` (one of the five), `reason_code` (`^operator_[a-z0-9_]{2,56}$` — the `operator_` prefix is the operator origin's reserved namespace), `expected_coordinator_event_id` (`^[0-9a-f]{64}$`), and `idempotency_key` (`^[A-Za-z0-9_-]{1,128}$`); unknown fields are rejected before any state transition. **Precedence**, executed as one unit inside the provider's decision critical section (below): (1) idempotency — the request is canonicalized and keyed by (`provider_id`, `candidate_id`, `idempotency_key`) (the store's replay index is extended to that triple); an identical canonical request answers with the result it originally produced — the appended event, or the pending decision — whatever the current head, marked `replayed: true`; the same key with a different body fails closed (`idempotency_conflict`); two concurrent first-seen requests with one key resolve as one append plus one replay or one append plus one conflict, never `stale_head`; (2) head compare — `expected_coordinator_event_id` must equal the candidate's current head, else `stale_head`; (3) edge validation against this table from the latest state, else `invalid_transition`; (4) for `catalog_priced` and `settlement_capable` only, the SPEC-047-R003 preconditions in their stated order, each with its own code (the other three edges skip this step); (5) under the release read lock (below), the release-generation re-compare and the append as one unit; the appended event records `evaluated_release_generation`. The first failure wins and nothing is appended. **Head and event ids.** `coordinator_event_id` is unique per (`provider_id`, `candidate_id`) — the store's `UNIQUE(provider_id, request_id)` plus the event's own content digest — and the head is the event with the highest append sequence for that candidate, never a content comparison. **Response schema** `model_admission_decision.v1`, exactly `schema`, `generated_at`, `provider_id`, `candidate_id`, `served_model_ref`, nullable `catalog_model_key`, `previous_admission_state`, `admission_state`, `reason_code`, `coordinator_event_id`, `accepted_at`, `decided_by` (the actor id), `replayed`, nullable `pending_decision_id`, and — non-null exactly for a committed `settlement_capable` — `bound_member` (`source`, nullable `artifact_id`, `hash_algorithm`, `hash`). `model_admission_status.v1` (SPEC-047-R002) keeps its exact field set; its value semantics change in one place, stated in R002. **Transition origins and reason sets are closed and disjoint:** the operator origin appends only the five edges above with `operator_`-prefixed reasons; the offer path appends `offer_submitted` with `provider_offer_submitted`; the withdrawal path appends `withdrawn` with the SPEC-047-R002 withdrawal enum; the synthetic-probe path appends `sandbox_probe_only`, `network_visible_unpriced`, `network_admitted_unsettled`, or `revoked` with `synthetic_probe_`-prefixed reasons; the drift path appends `revoked` with exactly one of `runtime_identity_drift`, `catalog_artifact_feed_changed`, `catalog_row_changed`, `catalog_row_ineligible`, `catalog_runtime_source_disallowed`, `receipt_key_unavailable`. Each origin emits only its own REASON set (three target states have two origins); a reason from another origin's set is `invalid_request`. `offer_rejected` is unreachable in v0.1.5: offer validation rejects synchronously (HTTP 4xx, closed code, nothing appended) and no origin appends that edge; the table row stays for a later validator lane, and the R008 rejected-offer cases are stated in terms of synchronous rejection. **Decision critical section.** It is scoped per `provider_id`: every decision and approval, drift event, session-to-candidate binding derivation or mutation (SPEC-047-R003 — whose uniqueness predicate spans all of a provider's candidates), and reload-sweep step for any of the provider's candidates takes that provider's section, and a section is never taken while the provider-registry lock is held (lock order: section, then registry). The provider's section also owns a monotonic **binding generation**, incremented under the section, in the same critical region as the append itself, on every event appended for any of the provider's candidates and on every binding mutation. **Release lock and generation.** The coordinator holds one release read-write lock over ONE immutable release snapshot — the candidate catalog, the compatible-previous catalogs, the artifact feeds and every per-release identity set, the Tier-2 catalog material, and the generation. A reload stages all of them and then takes the WRITE side to swap the whole snapshot and publish its monotonic generation as one act; no part of a release is ever visible before the others. Decisions and approvals take the READ side across the WHOLE evaluation — steps (1)–(5), including every R003 read of catalog rows, identity sets, runtime-source policy, and Tier-2 material — offer-time matching takes it across the match, session identity verification takes it across the verdict, and route-time snapshot creation takes it across the compare-and-insert. **Every append origin takes the provider section**: the offer path, the offer validator, the withdrawal path, the synthetic-probe path, the operator path, and the drift path each acquire the provider's section BEFORE reading candidate state and hold it through the event append, the invalidation of pending decisions for that candidate, the binding-generation increment, and the binding refresh or clear — one linearization point, so no route attempt can observe a candidate set the append has already changed. After publication the R006 sweeps take each provider's section in turn and stamp every surviving `catalog_priced`/`settlement_capable` candidate's binding with `validated_release_generation` = the new generation (a candidate the sweep has not yet reached is unroutable, not revoked). BYOM route-time snapshot creation (SPEC-047-R003) takes no provider section: under the release read lock it is an atomic compare-and-insert that re-reads, immediately before the insert, the candidate's head, the session binding and its `bound_coordinator_event_id`, the provider's binding generation captured at evaluation, and requires the binding's `validated_release_generation` to equal the published release generation; any difference fails the attempt closed. **Offer listing.** An operator decides on recorded state, never on a provider's claim: `GET /admin/model-admission/offers?provider_id=<id>` (same credential class; `provider_id` validated by its grammar, any other query parameter rejected) answers `model_admission_offer_list.v1`, exactly `schema`, `generated_at`, `provider_id`, `candidates` — ordered by `candidate_id`, bounded by the per-provider candidate cap — each item exactly `candidate_id`, `served_model_ref`, `runtime_source` (persisted on the offer event from v0.1.5), `admission_state`, `coordinator_event_id`, `state_observed_at`, `reason_code`, `catalog_match_state`, `catalog_match_reason`, nullable `catalog_model_key`, nullable `catalog_row_model_id`, nullable `catalog_row_model_sha256`, nullable `catalog_release_id`, nullable `catalog_candidate_sha256`, nullable `catalog_signer_key_id`, `catalog_members` (at most 16 tagged members, each exactly `source`, `hash_algorithm`, `hash`, and nullable `artifact_id`, `artifact_feed_sha256`, `artifact_feed_signer_key_id`, `artifact_candidate_catalog_sha256` — null exactly when `source` is `candidate_row`), `last_event_actor`, and `session` (nullable: `bound`, `bound_coordinator_event_id`, `validated_release_generation`, `verified_member` as a member record or null, `receipt_key_present`, `catalog_release_id`) — the live-session facts R003(iv) will evaluate; the actor of every event (drift included) is readable here, while `model_admission_status.v1` exposes the reason only. A decision request for a candidate with no offer fails closed (`no_offer`). **Errors** on all three endpoints use the existing `{"error":{"code","message"}}` envelope with exactly: `invalid_operator_token` (401), `invalid_request` (400), `no_offer` (404), `stale_head`, `idempotency_conflict`, `invalid_transition`, `catalog_match_required`, `catalog_match_stale`, `catalog_row_not_recommendable`, `catalog_material_unavailable`, `no_verified_session`, `dual_control_required`, `dual_control_unavailable`, `no_pending_decision`, `pending_expired`, `pending_consumed`, `runtime_source_not_allowed` (all 409), and `rate_limited` (429).

**[amended v0.1.6] Intake aggregate.** SPEC-023 §16.2(b) evaluates provider-supply intake from coordinator admission events and forbids any per-provider row in the intake record, so the coordinator — not the operator's shell over the offer listing — produces that aggregate: `GET /admin/model-admission/intake` (same per-actor operator credential class as the three v0.1.5 endpoints; no query parameter is defined and any query parameter, or a non-GET method, is `invalid_request`) answers `model_admission_intake_offer_counts.v1`. **Wire shape (closed at every level; a consumer rejects an unknown, missing, or wrong-typed key):**

```json
{
  "schema": "model_admission_intake_offer_counts.v1",
  "nonce": "5e8d1c2b3a4f60718293a4b5c6d7e8f9",
  "generated_at": "2026-09-11T00:00:00Z",
  "window_start": "2026-08-12T00:00:00Z",
  "window_end": "2026-09-11T00:00:00Z",
  "k_anonymity_min": 3,
  "rows": [
    { "catalog_model_key": "qwen3-14b", "distinct_provider_offer_count": 4, "suppressed": false },
    { "catalog_model_key": "qwen3-8b",  "distinct_provider_offer_count": null, "suppressed": true }
  ]

```

`schema` is that literal; `nonce` is 32 lowercase hex characters drawn from a cryptographically secure source at every build, so the SHA-256 the SPEC-023 §16.8 manifest records identifies ONE build even when two builds carry identical rows and the same second (the retained file is one read of one build, never a byte-equal replay of an earlier one); `generated_at`, `window_start`, and `window_end` are RFC3339 UTC timestamps with second precision in the one form `YYYY-MM-DDTHH:MM:SSZ`, `window_end == generated_at` and `window_start == generated_at − 30 days` exactly; `k_anonymity_min` is the integer `3` — SPEC-023 v0.10.4 §16.4 fixes `INTAKE_K_ANONYMITY_MIN` at 3 for that revision, and a different floor requires a lockstep amendment of SPEC-023, SPEC-017, and this SPEC; `rows` is an array ordered by `catalog_model_key` ascending (UTF-8 bytes) with no repeated key, each element exactly `catalog_model_key` (a SPEC-023 §3.2 normalized catalog key, `[a-z0-9._/-]{1,128}`), `distinct_provider_offer_count` (an integer ≥ `k_anonymity_min`, or `null`), and `suppressed` (a boolean; `true` exactly when the count is `null`). **Materialized snapshot, not a per-request scan.** The coordinator builds the aggregate on a fixed cadence — every 15 minutes, and once at startup — as one bounded job: one indexed scan of `offer_submitted` events with coordinator `created_at_utc` in the window (the store's admission-event table indexes `(state, created_at_utc)`), under a query timeout of 10 seconds and a hard ceiling of 100 000 DISTINCT `(provider_id, intake_model_key)` pairs; a job that exceeds either, or that cannot read every sanction source below, produces NO snapshot and leaves the previous one in place. **Consistency.** The build reads the offer events first, as one scan, and then evaluates the sanction predicate once per counted provider; the snapshot therefore reflects offers as of `generated_at` and sanctions as of a moment at or after it, which is monotone in the safe direction — a sanction applied during the build is honoured, a sanction lifted during it shows at the next build — and no partial snapshot is ever published (the snapshot pointer is swapped once, after every provider is evaluated). `GET` reads the current snapshot only (constant work per request; it is still rate-limited per operator credential and source address like the other operator endpoints and appends nothing) and answers `intake_unavailable` (503) when no snapshot exists, the newest is older than two cadences (30 minutes), or the newest is dated in the future (a clock step never serves a snapshot as current); `generated_at` is the snapshot's build time. **Window anchor.** Membership is decided by the event's coordinator-assigned append time — the admission-event row's `created_at_utc` column, set by the coordinator when it appends the event — never by any provider-signed timestamp in the offer package. **Counting rule.** A provider counts once for catalog key `K` when at least one `offer_submitted` event appended for that provider by the offer path with `created_at_utc` in `[window_start, window_end]` carries `intake_model_key == K`. `intake_model_key` is recorded on the offer event AT OFFER TIME by a resolution that is DISTINCT from the v0.1.5 `catalog_match_state`: the signed `artifact_hashes` of the offer are resolved against EVERY row of the current admitted release's candidate catalog by primary digest (`candidate`, `watch`, `listed`, and `recommendable` rows alike — the point of the signal is supply for keys the catalog has NOT admitted, which the v0.1.5 match, restricted to `listed`/`recommendable` rows, can never name) and against the release's usable identity set of verified artifacts; a pair that resolves to more than one row, or pairs that span two keys, resolve to no key. The provider-asserted `catalog_model_key` and `served_model_ref` are never read. An offer whose hashes resolve to no key carries an empty `intake_model_key` and counts for none. The offer's `catalog_match_state` is irrelevant to counting: a `catalog_matched` offer for a listed key counts toward that key (existing supply is still supply), and an `unmatched` offer for a `candidate` row counts toward that row's key. Later withdrawal, revocation, or drift does not un-count an offer (the signal is recorded interest, not current state); a provider offering `K` from several candidates counts once. The scan is over DISTINCT `(provider_id, intake_model_key)` pairs of the window — bounded by providers × keys, never by event volume — and the ceiling below applies to pairs and is enforced AT THE STORE: the store reads at most ceiling + 1 pairs (a SQL `LIMIT`; the in-memory store stops appending), so the build fails closed on the ceiling without ever materializing an unbounded result. **Eligibility.** A provider's pairs are counted only when the provider is ELIGIBLE at build time: NOT sanctioned by the predicate below AND, when the deployment operates hardware trust, holding an active hardware-trust root (`expires_at` null or in the future) at `generated_at` — a registration that was never trusted is not supply evidence for a catalog admission, whatever it offered. **Sanction predicate (closed, current-state).** `provider_intake_sanctioned(provider_id, at)` — the ONE definition of "under an active route, trust, payout, or registration sanction" for SPEC-023 §16.2(b), which cites it by name — is true when ANY of the four categories holds at `at`, the snapshot build time, and a sanctioned provider is excluded from every key's count whatever it offered earlier: (1) **route sanction** — the provider's current SPEC-011 provisional-admission state is `rejected` (the admission manager's rejected set), OR the provider has a persisted SPEC-032 canary sanction with a non-zero fail count; both are the inputs the offer path consults today; (2) **trust sanction** — the deployment operates hardware trust and the provider holds NO active hardware-trust root at `at` (`hardware_verification_trust`, SPEC-014 §hardware trust): every root it ever held has been revoked or has expired, or it never held one; ## 7. Current contract notes

The route from local candidate to earning is intentionally multi-step: discovered locally, evaluated locally, offered to the network, admitted for limited network state, catalog-priced when a trusted rate-card source exists, and settlement-capable only when route-time verification and receipts satisfy SPEC-022. This makes model supply broad without letting arbitrary local endpoints mint provider credit.

**v0.1 product-shape decision (recorded, #1240).** The v0.1 product shape is
settled per issue #1240: BYOM offers may exist in non-settlement network states
before they are catalog-priced or settlement-capable, and a genuinely
non-catalog model has **no earning path in v0.1** — provider surfaces disclose
this honestly (`earning_path_class` = `no_earning_path_in_v0_1`), and an earning
path for non-catalog models is deferred to a later billing-owner (SPEC-005)
pricing-conversion spec per SPEC-047-R004. This decision is the arbitration
basis for the §5 `DECISION_REQUIRED` gaps; the gaps' verdicts remain **open**
because their "Evidence needed" column requires a signed admission journey
(SPEC-047-R008) and production evidence that do not exist until the admission
implementation slices land. This amendment does not flip those verdicts.
